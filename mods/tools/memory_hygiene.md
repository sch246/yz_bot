读信源、清老账、压缩经历、写结论时的整理口径；被唤醒要动手、刚读了一大堆材料，或有人问「你怎么记的」时加载。

机制本身（醒来带什么、什么时候交接、有哪些笔记）以系统提示里「你的记忆怎么运作」和 memory_system 为准；这里只讲怎么用得干净。

## 核心前提
记忆系统不是仓库，是流程：先吞下（叫醒你时的画面、干活时插进来的新消息、你自己召回的原文），再压成结论，
最后把还要用的一句话写进笔记。三者缺一，读过的就会在上下文里变成负担。
它设计出来是为了让你能吞下几乎无限的信息，代价是边读边整理。

## 索引树：靠引用长出来，不是靠对象挂上去
树不是「把总结放进某个人的抽屉」，而是结论之间互相引用自然长成的：
这条结论引用了行动 20261023-144，那条又引用 20261022-105，层级是读出来的，不是存出来的。
反查即提升：把旧东西读回眼前的同一次，它就成了这一段里的新节点，树往上长一格。
所以写结论时留来源，等于同时在建树；省掉来源就是砍掉树枝。能留的来源和读回来的办法：

- 行动号（20261023-12）：read_actions；写成 20261023-12#2 时指那次输出里的第 2 个调用，读的时候只传 # 前面那段；
- 聊天记录：窗口加时刻（g123 2026-10-23 20:26:31）或 message_id：read_log 用 before 读前后文；
- 归档的段名（20261022-153000）：加载 memory_system 后用 read_context；
- 笔记名（person:<QQ号>、group:<群号>、diary:<日期>……）：read_note，旧版本用 note_history。

## 一个循环
1. 先看这次是谁、为什么叫醒你，再决定读多少。眼前的画面已经替你读了；没叫你的窗口只在「其它窗口还有没看过的消息」里报个数，要看再 read_log。
2. 读：要原文用 read_log，count 和 before 控制范围；不记得在哪就 search，一次找遍聊天记录、笔记、日记和归档；想知道自己当时怎么做的用 read_actions。按需读，别为了读完而整段翻。
3. 压：读完马上想清楚结论，一次一个主题，写成「结论 + 来源」，不要流水账。
4. 留：还要接着做的进 recent，答应了的进 todo，关于某人某群的长期信息进 person: 和 group: 笔记，可复用的做法进 global 或写成 Markdown Skill，今天的事交接时进日记。只在回复里说「记住了」不会保存任何东西。

## 会话收尾
一件事告一段落，或刚读了一大堆材料只需要记住结论，就 tidy，别攒着。交接时逐类确认东西都在该在的笔记里，
然后这一段归档、眼前清空，从新的一段接着做。归档的段 search 和 read_context 都找得到，原样不会丢。
常用的往上提：一句话进 global，做法进 Skill。目标是上下文始终干净、可查，而不是越堆越高。

## 清老账
已读是自动的：画面和插进来的消息你看过就算读了，不用、也没法手动标。没叫你的窗口不必逐条去读，
真需要再 read_log。漏收的消息由系统补回，不用你反复去试。

## 判断「我在用哪个模型／配置」
看 data/storage/llm_system/config.json 的 default_model 与 providers，或者请管理员发 #model，不要只看 .env。
env 里可能有别的路径的遗留变量，据此下结论会错。

## 自检
上下文越来越长、手上的事又告一段落时，不用等系统来交接，自己 tidy。
结论里留下的来源要能支撑核查，写完自己回读一遍：别人拿这个号、这个时刻能查到原话吗？
