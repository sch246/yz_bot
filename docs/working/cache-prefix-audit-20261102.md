## 排列问题与改动

完整请求在 view 前还有 self、身份与记忆说明、中心身份三条 head。只看 `read_context` 正文里“工具说明、笔记……”的顺序，会漏掉这部分。函数 schema 作为 API 独立字段发送；日志中的消息顺序不证明供应商内部如何排列 schema 和 system。

**工具说明。** 原来完整说明按模块名字排序，必需的 `meta` 会排在可选模块后面。最近 10 个可读完整行动首轮的 9 对相邻比较中，6 对首先在工具说明变化，前面三条 head 相同。将 `meta` 说明放到已激活模块的第一位，其余模块仍按名字排，工具目录、函数 schema、权限与增量状态不变。

**构造材料。** 时间线原本就排在 policy、目录、黑板、todo 之后。目录包含每份笔记的字数、行数、首行，改一份笔记就可能改变它；“目录固定不变”并不成立。调整为 policy → todo → 目录 → 黑板 → 最近事项 → 唤醒消息，只移动已有材料。todo 自身变化时也会提前截断前缀，这是一项按当前样本选择的权衡，并非适用于所有写入频率的最佳排列。

## Google 与 DeepSeek 的规则核对

现场 Google 配置使用官方 OpenAI 兼容端点。Google 当前文档给 Gemini 3.8 Flash 的隐式缓存门槛是 **4,096 token**，并非统一的 32,768；隐式缓存没有命中保证，建议复用较大的相同开头，并缩短相近请求的间隔。[Google 缓存文档](https://ai.google.dev/gemini-api/docs/generate-content/caching)

DeepSeek 当前文档描述请求边界、共同前缀检测和固定间隔的缓存持久化；前缀相同不保证当次已经可命中，还涉及写入时间与回收。“64 token 粒度所以固定前缀每次 100% 命中”不是现行文档的保证。[DeepSeek 缓存文档](https://api-docs.deepseek.com/guides/kv_cache/)
