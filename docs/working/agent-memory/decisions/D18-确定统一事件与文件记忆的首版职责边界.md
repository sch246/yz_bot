## 2026-10-20 第2问实际答案与首版职责结论

维护者实际选择：“主循环可主动修订，后台也可整理（推荐）”。结合第1问“保留 Python，补齐机制（推荐）”，本票的两项职责选择已回答：保留现有Python宿主；主循环在当前唤醒内可以主动提交记忆修订，后台也可以整理，二者走同一个校验和持久提交入口。不要求主循环只能提建议、等轮末图书管理员才写入；也不要求每醒必须写记忆或额外调用整理模型。

这是维护者对宿主和修订能力的选择，不是新一次生产切换、材料读取、凭据访问或付费指令。她已有自重启、.py、link能力继续保留；本轮没有执行这些能力。

### 实施所需的最小语义（由答案推导，尚未实现）

- **按已知材料确定截止，不按角色决定能否提交。** 主循环与后台都只能使用各自实际收到的材料、已持久提交的自身输出，以及截至所绑定时点已可确认的行动事实。后台可以取整轮终态后的完整材料，也可以对明确冻结的较早材料整理；“后台”不是必须等terminal的权限条件。未看到的新消息、随后才出现的结果不能补进旧候选。
- **允许记下自己的理解。** 自身已提交输出可以支持“当时这样想／提出了什么”，不自动证明外部主张为真。generated、待派发、尝试、失败、未知和完成分开；同批尚未执行的工具不能记为成功，未持久提交的流式片段不能冒充已提交经历。机械字段不能保证自然语言叙述正确，语义责任与后续反馈仍需验证。
- **共同提交规则。** 修订保留来源、产生过程、范围、原始bytes、父版本与理由；主／后台都须通过同一范围、来源截止、父版本和持久化校验。旧候选遇到新版本拒绝，不能换个新父版本就把旧截止伪装成新理解；不自动合并、重试模型或扩充费用。
- **可见性有明确时点。** 已冻结请求保留旧bytes。提交成功后，后续显式新读取可得到已提交新版；当前上下文不会被倒改。要让同醒后续模型请求真正消费新版，须接通读取或准确工具返回并验证实际wire，不能只证明磁盘更新。
- **既有载体边界保留。** 长期笔记、未完成事项hint、可复用Skill、原聊天／行动证据仍各有职责；本次不增加后台hint写者，不把笔记提交入口变成任意文件写权。删除／恢复／回退仍新增可追版本，不抹历史或撤回外界副作用。

## 第2问：主循环主动记忆与轮末整理的关系（待回答）

当运行中的她决定某个经历／理解值得以后记住时，是否允许主循环主动发起持久修订，经同一受控入口核对来源、父版本后生效；后台整理也走该入口？或仍由主循环只给建议，统一等轮末图书管理员提出写入？

推荐允许两类内部过程发起修订，提交机械规则统一，避免必须等待固定整理时机；这不是把中心模型认证当作主体性证明，也不开放任意生产文件操作。另一方案维持旧角色分工，减少写入发起者，但修改只能在整理时生效。等待维护者实际选择，不代答；选择若改旧分工，先标记直接受影响票再修订生效职责，保留旧答案。
