# 当前维护队列

本文记录已经确认的近期维护判断，帮助后续会话区分“现在要修的缺陷”“接受的现行约束”和“只有出现证据后才考虑的加固”。它不是运行契约；当前事实仍以[交互模型](../interaction-model.md)、[运行架构](../architecture.md)和各功能文档为准。

## 已确认要修

### 失败命令仍可被匹配

`cmds` 先按文件名建立 `commands`，导入失败时只记录到 `fails`，没有从候选表移除。之后同名点命令仍会匹配，并在 `modules[command]` 处触发 `KeyError`。

目标是让导入失败的插件不可调用，同时保留失败列表和重启反馈。这个修复不要求先建立 feature loader，也不顺带改变命令匹配语法。

### `^C` 没有终止 `.py input()`

当前取消只删除 catch，没有唤醒阻塞在 `Queue.get()` 的线程。目标是让 `^C` 真正结束这次等待并释放线程，同时保留 yield 交互现有的按用户线取消语义。实现前需要决定 `.py input()` 收到取消异常、哨兵值还是其它最小协议。

### 群聊 `.post` 映射被私聊键覆盖

`main.send()` 群发时会把 `user_id` 规范为 `None`，但 `connect.call_api()` 先选择群映射，随后又因参数中存在 `user_id` 键而查询 `uNone` 并覆盖端口。目标是群消息只采用群映射，私聊只采用用户映射，不改变 `.post` 的生产安全边界或测试用途。

### link action 异常仍可能走 `succ`

当前 action 内部捕获异常并发送 traceback，却不把失败返回给 `exec_link()`；节点仍按 cond 的真值进入 `succ`。目标是 action 异常不再继续成功后继。由于 action 抛错前可能已有部分副作用，异常后是否进入普通 `fail` 分支仍需在实现时明确。

## 接受的现行约束与取舍

### `.py` 是主路由硬依赖

`main.recv()` 在任何事件处理前取得 `cmds.modules['py']`，所以 `.py` 导入失败会影响全部消息。维护者把 `.py` 视为核心能力；这不是一次局部加载器修复能够解决的问题。只有未来明确要求 core 在 `.py` 失败时继续在线，才随纵向失败域重划解除这条依赖。

### `pyload.py` 名称需要一条消息刷新

冷启动后首条直接 `.py` 可能看不到 `pyload.py` 新名称，经过一次会刷新 `loc` 的消息后恢复。该短暂差异当前可接受，不列入近期修复。

### LLM 以可信聊天范围为主要边界

LLM 工具可以执行共享 `.py` 环境和读写用户 storage。维护者通过手动选择可信群控制启用范围，当前不要求逐工具确认或沙箱。私聊不受群白名单限制；若需要额外加固，候选方案是在所有 LLM 入口统一要求触发者为 op，但这尚未决定或实现。

无上限工具循环和 `assign_tasks` 递归/预算当前由 `.reboot` 作为极端恢复手段；完整 traceback 发送给可信模型供应商则是为故障分析保留的有意行为。只有出现实际事故证明这些机制不够时，再增加最小限制。
