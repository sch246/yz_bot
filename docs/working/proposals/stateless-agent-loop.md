# 无状态主循环：每次唤醒重建上下文

> 状态：提案，2026-10-19 由维护者提出方向，尚未实现。本文不描述当前运行行为；现行合同仍以[交互模型](../../interaction-model.md)、[运行架构](../../architecture.md)和[LLM 文档](../../llm.md)为准。
>
> 本文会推翻 [中心 reader 简化](reader-cleanup-and-split.md#21-上下文上限只决定从哪里开始读) 里 2026-09-26 的决定：固定起点、不滑窗、模型自己压缩。改向前须由维护者明确确认第 6 节的 D1。

## 1. 要解决的问题

维护者报告的两个实际问题：

- **token 消耗高**
- **记忆不好**：总是忘记刚刚发生了什么，把握不住时间顺序。

下面是从代码读出的机制。本文没有查看生产日志或用量数据，数字只是估计；第 7 节说明怎样测量。

| 现状机制 | 代码位置 | 后果 |
|---|---|---|
| 上下文是中心 agent 自己的**工作日志**：固定起点之后所有未覆盖的 O/R/input/通知按序重放 | `view.agent_rows`、`agent._run_agent` | 上下文随经历增长，直到模型 cover；每次调用都要重发整段 |
| 开局只给通知，正文要模型 `status`/`take` 拉取，下一次请求才正式读入 | `_base_prompt`、`agent._agent_provider` | 回一句话至少要两三次调用，每次都带完整历史 |
| 输出和行动返回不带时间，通知里是 unix 秒 | `view._output_projection`、`_result_projection`、`_activation_text` | 先后顺序只能靠位置推断 |
| 自己说的话以 `say(...)` 工具参数的形式出现，和群里的消息分在两处 | `view._output_projection` | "刚才那个群里发生了什么"要从散落的片段拼起来 |
| 压缩全靠模型自觉 cover | `cover_events`；回放实验见[离线回放](memory-replay-evaluation.md) | 默认提示只会形成深度 1 的线性摘要；不压缩就撑到上限 |

## 2. 参照

**QQ-agent**（[`src/prompt.js`](https://github.com/K0nd1us/QQ-agent/blob/main/src/prompt.js)，2026-10-19 读取 main，与[调查](qqbot-persistent-memory-research.md)核对的 `11577ba` 行数一致）文件开头写的就是"无状态 + 每次新开会话"。每次唤醒重建：

- 系统提示（静态）；
- 角色设定 → 引导说明 → 相关成员印象 → 该会话最近 80 条已读消息 → 未读消息 → 当前时间。

每条消息一行，形如 `[时间] 名字(QQ:号)：内容`；自己的发言标成"我"，和别人的话在同一条时间线里。本次运行内的工具调用和思考用完即弃，不进入下一次。段落按"越稳定越靠前"排列以命中前缀缓存，时间放最末。

**SLA**（[arXiv 2610.07625](https://arxiv.org/abs/2610.07625)，见[研究地图](memory-and-self-evolution-research.md#状态与上下文分离)）：

- 跨调用的状态归 harness，每次调用按角色重建上下文；
- 进展由产物携带（候选代码本身），而不是由对话携带；
- 它能这样做，是因为有外部评测器决定保留什么。

两者的共同点，以及群聊为什么能用：群聊里"该给模型看什么"有一条几乎白给的规则——这个窗口最近发生了什么。QQ-agent 就站在这条规则上。

**和柚子的差别**

- QQ-agent 一个窗口一个会话；柚子是一个主体跨所有窗口。
- QQ-agent 只聊天；柚子会执行代码、改文件，有跨唤醒的长任务。
- 柚子的 oplog 已经把"持久状态"和"一次调用看到的上下文"分开了，这是本提案的前提；缺的只是每次重建视图，而不是重放日志。

## 3. 目标形态

### 3.1 状态不变，只换上下文的构造方式

oplog、chatlog/`history`、全局待办、Skill 文件、cover 记录的写入权威都不变。输出和行动返回照旧写进 oplog，供 `recall_events` 和审计使用，只是**不再整段重放**。

### 3.2 每次唤醒的上下文

由一个纯函数构造，按"稳定 → 易变"排列：

1. **系统提示**：改写后的 `_base_prompt`，明确"你没有跨次运行的对话记忆；要记住的东西写进待办、Skill 或笔记"。
2. **长期部分**：图书管理员维护的笔记（3.4）、全局待办（`_agent_hint`）、已加载的 Skill。
3. **窗口画面**：本次涉及的每个窗口最近 N 条消息，取自 `history.getlog(window)`。
   - 带时间；自己的发言标"我"（`message_sent` 回声本来就记在窗口里）；
   - 分成"已读"和"未读"两段；
   - 每个窗口和全部窗口各有条数上限。
4. **其它窗口的未读摘要**：只给计数和提及，沿用 `_pending_hint` 的内容。
5. **当前时间**，放最末。

### 3.3 一次唤醒之内

单次 `_run_agent` 里的多轮工具调用照旧在 `session.messages` 中累积，结束就丢弃，和 QQ-agent 一样。`_drive_agent` 的续轮本来每次都会新建 `llm.Chat`，改造后每次续轮都重新构造 3.2。

保留的工具：

- `take` 和 `read_messages`：看画面之外的更早记录；
- `recall_events`：查自己过去的输出和行动。

### 3.4 图书管理员

- **时机**：聊天循环停下后（`_drive_agent` 的 `finally` 附近，或空闲一段时间后）跑一次独立的无状态调用。
- **执行线**：占用同一条 `AGENT_WINDOW` 执行线，不和主 agent 并发。
- **输入**：上次检查点之后的 oplog 事件，加上一版笔记。
- **输出**：新一版笔记，每条带来源正式号。
- **约束**：有大小上限；保留上一版，因为它同样没有评测器，写错了需要能回退。

它解决的是 QQ-agent 作者遇到的写入缺口：聊天模型几乎不主动写记忆。"刚刚发生的事"由窗口画面负责，图书管理员负责更长的时间尺度，两者分管。

离线回放的已有数据（[记录](memory-replay-evaluation.md)）：

- 提示写对时，短段整理能形成深度 3–8 的层级；
- 长跑会以长思考截断，父级整理也会被新输入饿死。

所以它的长期稳定性还要验证。

## 4. 删除与迁移

| 现有机制 | 去向 |
|---|---|
| `agent.history_start`、`#reset_start`、`#limit` 的起点语义 | 删除；上限改为窗口画面的条数／token 上限 |
| 压力提示 `_pressure_hint`、"达到上限先 cover" 的提示 | 删除，上下文不再增长 |
| `_TOLD_TOOLS_KEY` 差量通告（绑定 `history_start`） | 改为每次给出当前工具状态，或只在系统提示列出 |
| `_run_agent` 中"不滑窗"的 `WHY:` | 维护者确认 D1 后改写为新理由，不能静默删除 |
| `cover_events` | 主 agent 是否保留待定（D5）；图书管理员可以用它整理经历 |
| `_drain_legacy_results`、`_credit_recall` | 随重放一起失去用途，实施时逐个确认再删 |
| 通知只列唤醒、正文需拉取 | 改为直接推送画面；见 D3 |
| 正式文档 | `interaction-model.md`、`llm.md`、`commands.md` 中关于固定起点、压缩和拉取的段落随实现一起改 |

不保留新旧两套上下文模式的生产开关；对照用离线回放分别检出新旧代码来做。

## 5. 风险

- **写入缺口转移**：长任务的进展只能靠待办、Skill、文件和笔记携带。模型不写，跨唤醒的多步任务就会断。
- **笔记成为权威**：图书管理员写错后会持续影响后续行为；需要来源号和可回退的版本。
- **跨窗口连续性**：一个人在 A 群答应的事、在 B 群提起，画面里看不到；要靠笔记或 `recall_events`。
- **前缀缓存**：现状的追加式上下文缓存命中率高；重建后要靠稳定排序保住前缀。QQ-agent 的锚点机制等测出缓存确实是问题再考虑。

## 6. 需要维护者裁定

- **D1**：确认推翻 09-26 的决定。窗口画面只显示最近 N 条，相当于画面滑动；经历本身仍在 oplog，可以反查。
- **D2**：N 取多少；哪些窗口进画面（只有本次被唤醒的窗口，还是最近有活动的窗口）。
- **D3**：画面里展示的未读消息是否直接算作正式阅读（`read_via="screen"`，没有发起输出号），还是保留拉取。
- **D4**：思考内容一律丢弃（QQ-agent 的做法），还是保留上次唤醒的简短行动摘要作为桥接。
- **D5**：图书管理员的触发条件、使用的模型、笔记的组织方式（全局／按人／按窗口）、能否删改旧条目；主 agent 是否还保留 `cover_events`。
- **D6**：跨窗口的先后顺序怎么表示：画面按各窗口的实际时间排，主观阅读顺序只保留在 oplog 里，是否可以接受。参见[主观时间轴的论点](chat-client-for-an-agent.md)。

## 7. 验证

**离线回放对照**：在同一冻结快照上跑四组，并在至少两个累计 token 预算点上分别报告：

1. 现状；
2. 现状加时间戳和尾部近况；
3. 无状态重建；
4. 无状态重建加图书管理员。

**观察指标**

- 每次回复的调用次数，以及普通输入、缓存输入、输出 token 和实际费用；
- 人工标注的探针："刚才发生了什么、先后顺序"、承诺有没有兑现、跨窗口的事有没有接上；
- 图书管理员笔记后来有没有被用到、有没有用错。

**估计（未测）**：现状一次回复要两三次调用，每次带最多约 40k token 的历史。QQ-agent 式一次回复通常一次调用，系统提示加 80 行画面大约在 10k 以内。

**代码检查**：每次改动后运行 `run.py --check` 和 `--smoke`。

## 9. 评审问题对照

按[设计原则](../../design-principles.md#评审新方案时必须回答)逐条回答：

1. **解决什么已观察到的问题**：token 高、记不住刚刚发生的事和先后顺序（第 1 节）。
2. **现有机制为什么不够**：现有机制本身就是原因——重放日志加拉取阅读。
3. **新增概念**：一个上下文构造纯函数、一份笔记、一次整理调用。
4. **直接组合能力**：不削弱 `.py`、link 和命令；oplog 照旧可查。
5. **少见需求是否变成固定成本**：画面构造是每次唤醒的固定成本，但比重放整段日志小。
6. **写入权威**：不变（3.1）；笔记的写入权威是图书管理员，保留上一版。
7. **坏了从哪里修**：笔记是普通文件；构造函数可以在 `.py` 里直接调用查看输出。
8. **保留、迁移、删除**：见第 4 节。
9. **能否先做纵向切片**：S1 单独可验证。
10. **删除新抽象会失去什么**：失去笔记就只剩画面和待办，会退化成 QQ-agent 不带印象的形态。
