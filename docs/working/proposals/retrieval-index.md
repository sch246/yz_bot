# 检索索引：把子代理找过的路存下来

> 状态：未实现的提案。本文记录一次多轮讨论的结论和被推翻的中间方案，不描述当前运行行为。当前事实以[运行架构](../../architecture.md)和[模型与工具](../../llm.md)为准。

## 问题

`assign_tasks` 的子会话每次冷启动。要回答一个跨模块的问题，它必须一层层找：`grep` 一个名字、读一个文件、发现另一个名字、再 `grep`、再读。代价有两份：

- 往返次数——每一跳是一次模型请求；
- **注意力**——五跳之后上下文里塞满了中间弯路和无关片段，最后一步推理是在噪声里做的。

第二份更贵。如果一开始就拿到正确的文件集合，模型只需要一次调用，而且注意力集中在真问题上。

值得缓存的因此是**检索走过的路**，不是检索得出的结论。

## 为什么是检索而不是结论

两者出错的代价不对称：

| 缓存对象 | 缓存错了会怎样 |
|---|---|
| 结论 | 静默给出过时答案，调用方没见过原文，无从发现 |
| 检索 | 多读或少读一个文件，调用方当场撞见并自行补齐 |

这条不对称是整个设计的地基。它带来两个直接推论：

- 缓存键可以是自然语言问题，**允许糊**。拿到一份差不多对的起点集合已经有价值，不需要语义索引或 embedding。
- 子代理应当返回路径而不是答案（见下文「未决的岔路口」）。

## 失效判据由模型自己写

按文件或目录做哈希不够准：结论往往只依赖某个函数或某段行范围，整文件哈希会因无关改动频繁误判失效。

改为让子代理输出一条**校验命令**——一段只读的 shell，输出稳定即代表结论所依赖的部分一字未改。`host__run_command` 是它的执行面。这样做还有一个副作用是好的：模型要写出这条命令，就必须先想清楚自己的结论依赖什么，而这个思考被固化成了可执行物。

配套约束：

- 存命令输出的**哈希**而非输出本身，命令的啰嗦程度就不再是成本；
- 命令必须只读、确定性、秒级返回、退出码为 0，否则条目按不可用处理——否则迟早出现带时间戳的命令，永不命中且查不出原因；
- 命令由模型自由撰写，因此**可能退化成恒真命令**（`echo ok`）。这不是恶意，是"缓存命中"构成正反馈时偷懒的自然结果。不建议用模板限制表达力（"某个函数一字不改"正需要这份表达力），而是把命令原样存进条目、并在每次命中时回显给调用方。可观察优先于强制。

时间不是失效判据。输入不变而结论失效，说明校验命令的覆盖范围不对，应当修命令而不是加 TTL；两个判据叠在一起只会让出错时不知道该信哪个。**提示词内容和模型名进缓存键**——它们变了，旧条目的可信度确实变了。

## 条目的形状

一条一个文件，人能读、能改、能删：

```text
问题特征：工具模块 激活 chat 绑定
文件链：mods/chat.py:230-260 → mods/tools/__init__.py:bind_session → mods/tools/meta.py
查找提示：从 init_chat 里的 create_context_message 跟 bind_session 进去；
          registry 的 last-good 逻辑在 __init__.py，不在 meta.py
校验：<模型写的命令> = <上次输出哈希>
```

关键一条：**校验失败时「查找提示」不作废**。文件链会随代码烂掉，"从哪儿开始找、别去哪儿找"通常还成立，应当作为 hint 直接喂给重跑的子代理。这是条目里复利最高的部分。

## 索引需要一个回写点

检索时子代理只有候选，用完之后才知道哪些真有用。没有回写，条目会单调变胖——塞满当时点开、结果没用上的文件，越胖后续命中越不准。

因此 `ask_files` 返回时带条目 id，调用方干完活可以回报实际用到的路径。**渐进精化，不强制**：不回报就停在候选状态，回报了就变准，忘记回报不会卡住任何东西。

## 未决的岔路口：返回路径还是返回答案

- **只做检索**：返回文件链和查找提示，由调用方自己读、自己答。保留上文那条错误代价不对称；调用方直接看原文；子代理职责单一。
- **全托管**：子代理检索、读、答、顺带维护索引，调用方只拿答案。往返更少，但把刚获得的安全性还了回去，且子代理的注意力要同时分给三件事——正好是本文要解决的稀释问题换了个位置。

当前倾向前者。折中形态是返回文件链加**读到的关键片段原文**但不给结论：原文可验证，结论不可。此项未定。

## 提示词就是这个子代理的全部

没有进程、没有 session、没有类，一个 `.md` 加一次 `assign_tasks` 调用。提示词放 `data/agents/` 而不是 `mods/tools/`——后者的 `.md` 是激活进当前 Chat 的说明，这份要当子会话的 system prompt 用。开发工作的绝大部分是迭代这份提示词。

要钉住的几条：

1. 产物是路径不是答案，找到就停；
2. 校验命令只读、确定、秒级、尽可能精确，禁止恒真命令；
3. 查找提示写"怎么找到的"而不是"找到了什么"；
4. 命中候选先跑校验再用，失败就带旧链重找并覆写；
5. 宁可多给一个候选也不要漏。

## 一个约束不住的地方

子代理要检索就得能 `grep`，要维护索引就得能写文件，因此必须给 `host__run_command`。shell 是全能的，**能力层面无法把它限制在索引目录内**——只给专用写入函数、不给 `write_file` 也拦不住一行重定向。真限制住（不给 `run_command`）则检索能力废掉一半，不值。

诚实的做法是接受它并让改动可见：索引目录固定，纳入版本控制或留日志，跑偏了看得出来。这与[模型与工具](../../llm.md)已经记录的信任边界是同一条线，不新增风险类别，但应当写明。

## 可能自己长出来的东西

问过十几个问题之后，文件链会重叠，重叠密度高的位置就是这个仓库的枢纽。统计出现频次即可得到，不需要专门设计。它比人手写的架构图更贴近实际，因为它按"实际被问到"加权而不是按"作者觉得重要"加权。

这一项是观察而非目标：如果重合度始终不高，说明问题分布太分散，这部分收益不存在。

## 被推翻的中间方案

1. **常驻领地代理**：一个进程长期持有对某块目录的感知。否决理由是感知会过期而且过期不可见（本次讨论中就出现过一次因未 fetch 而自信答错的实例），与"纯函数优于状态"的既有判断相反，且每次唤醒都要把感知塞进 prompt，连省 token 都不成立。
2. **文件与目录的 Merkle 哈希**：改进了可检测性，但哈希覆盖范围不等于结论依赖范围，越界的结论会带着"已验证"标签被复用。被"模型自写校验命令"取代。
3. **缓存问题无关的区域摘要**：意图是让缓存键精确可比。被否决的理由是子代理只能被问题驱动地探寻，不存在无问题的摘要——它要么覆盖一切因而肤浅，要么无依据地挑重点。
4. **一小时缓存期**：见上文，时间不是失效判据。

## 与当前实现的边界

- `assign_tasks` 每次新建 `llm.Chat` 并在返回后丢弃，没有续接入口；其模块说明已写明不适合需要多轮追问的任务。
- `mods/tools/host.py` 提供 `read_file`/`write_file`/`run_command`，是本提案唯一需要的能力面。
- `mods/tools/` 的 registry 已支持 `.md` 模块，但那是当前 Chat 的激活说明，不是子会话提示词。
- 本提案不实现[可自维护的同相上下文](self-maintaining-context.md)。那篇讨论的索引是"怎样构造下一切面"的可求值结构；这里的索引只是一次检索路径的冻结记录，不保留求值轨迹，也不参与后续状态转移。两者可以共存，但不要用本文的落地充当那篇的证据。

## 最小实现与停止门槛

先做最小的：一个索引目录、一个 `ask_files`、一个回报入口，没有索引结构、没有 embedding、没有 TTL。冷启动时缓存为空、每条都付全价，需要真实使用攒一段时间才回本，因此不应先设计完整再上。

跑一段时间后看两个数就够判断：

- **命中率**——低则说明问题分布太分散，或键的匹配方式不对；
- **文件链重合度**——低则"枢纽自己浮现"那部分收益不存在。

出现下列任一项应缩小或放弃，而不是补机制维持：校验命令普遍退化成恒真形式；命中带来的错误起点比省下的往返更贵；条目维护需要人持续照看；或者简单基线（直接 `grep` 一遍加固定的几个入口文件）已经产生等价结果。

## 尚未决定的问题

- 返回路径还是返回答案，折中形态（原文片段）是否值得；
- 问题特征用什么形式匹配，候选交给子代理判断的成本是否低于直接重找；
- 条目何时应当被删除——代码大改之后旧条目是负债还是线索；
- 索引是否应当进版本控制，还是留在 `data/` 只做日志可见；
- 回报入口不被调用时，条目的候选状态要不要衰减。
