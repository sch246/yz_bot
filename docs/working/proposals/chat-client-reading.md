# 中心化聊天软件：通知、信源与顺序阅读

> **状态：中心 reader、启动补回及有名历史信源已在主线代码接线；真实停机空窗未验收。** 本页保留设计理由和后续待办，当前行为以[交互模型](../../interaction-model.md)及[运行架构](../../architecture.md)为准。旧 mail 方案见[历史论证](mail-and-activation.md)，压缩的现状／目标见[状态索引](chat-condense.md)。

## 草籽已决定的行为

群友召唤柚子时，她先看到全局窗口通知，而不是把上次到现在的所有消息直接塞入一次请求。她**可以**用 `peek` 看相关会话最近的一小段、继续预览再答，也可直接按顺序拉取或先回复。**预览不消耗未读。** 回复后仍从选定窗口的持久未读队列按该窗口的到达顺序、每次一小段地正式拉取，逐段积累印象；本次追读只负责其开始时已到达、且在可信旧边界之后的那段，后来新到消息另列通知，不能让终点无限移动。不能把整天记录一次性总结成一块。`peek` 也可按需查看任意有界旧档，逐段建立可反查的记忆。

第一阶段的认知与执行归一个中心 agent，窗口只是消息来源、通知范围、FIFO 消费位置和发送目标。agent 自己的待办 hint、主模型、基础 prompt 和上下文预算全局各一份；未读概况可在同一全局 hint 中按窗口列出。旧窗口覆盖配置保留原数据，不自动合并成全局值，也不让读到哪个窗口就切换主设置。主 agent 的模型调用及辅助调用费用归 Bot 全局，不再硬记给唤醒它的群友。`say` 必须明确给出目标窗口，不能靠最后读到的消息或线程局部的 `context.current()` 猜接收者。

NapCat 历史读取有两个用途：主动查看本地未保存的旧记录，以及发现并补齐 Bot 停机时漏掉的消息。它是阅读的另一种来源，不意味着补来的旧消息自动作为新召唤、重新执行命令或 link；真实接口的分页、身份和缺口能力须先核实，见[离线消息恢复](offline-message-backfill.md)。

**2026-09-25 的下一层抽象：**窗口 mail 不是所有世界输入必须挤进的唯一 FIFO。每个有名字的信源提供 `status`、`fetch`、`peek`、`pull`；全局 hint 汇总其未读和缺口。启动补回在首次正式 `pull` 前把停机期间消息接到原窗口 mail 的旧前缀之后、开机后实时尾部之前；这个 FIFO 已被 `pull` 后再向更早处 `fetch`，应另开信源，不倒插已读经历。`peek` 的正文是工具返回、不消游标；`pull` 的正文才是独立正式输入并取得统一号。异步工具回调可有自己的来源，不必伪装成某窗口聊天消息。主线代码仅把 NapCat 历史作为第一个独立信源，尚不是任意回调都可接入的通用接口。

## 被替换的旧路径及剩余边界

旧 `Mailbox.rebuild` 与 `_run_chat` 曾在开局和轮内整段排空本窗口 mail；只加读取工具不会改变那条吞入路径。当前主线已切为全局 `AGENT_WINDOW` reader：开局先给通知，结果优先，正式读取须明确选信源和数量。窗口 `Mailbox` 仍是来源 FIFO 与写入互斥，不再独自拥有主模型。

**未读正文目前已经持久化，不能在切换时丢掉。** 正常候选 QQ 事件在入 mail 前写 chatlog，并以包含原始事件和激活状态的 `arrival` 写入 oplog；工具返回只走后者。重启从未被正式读取的 `arrival` 重建 pending，不能用「chatlog 减已读号」代替：chatlog 不是完整原始事件，也不含全部工具返回和激活事实。中心化后仍须先持久接纳世界输入；`peek` 可另生一次已编号的阅读返回，但**不因此给 pending 原文提前分配正式号或把它从未读队列删除**，以后按顺序正式拉取时再次看到同一来源是新经历。现行 chatlog 与 oplog 是两次追加，不是跨文件原子事务；切换时要核验其中断夹缝，不再复制第三份正文权威。

本地 `chatlog.read_range(before=_log_origin)` 现可按窗口使用严格排他的稳定锚点；同秒记录也不靠减一秒定位。`read_origin` 可精确续读过大的单条记录。档案位置和 QQ `message_id` 仍只是来源／协议元数据，唯一可引用的经历号在模型实际读到新输入时分配。

正式拉取仍受所选窗口 mail 的 FIFO 约束；`peek` 是在此顺序外主动浏览有界片段，返回按实际阅读时刻进入全局经历，且不推动 mail 水位。后来 FIFO 再呈现被预览的来源，是又一次经历，不倒插或复用旧号；一次预览返回的正文按原聊天从旧到新展示。

总结和反查可让模型以一个统一事件号取前后若干**已读事件**，或以两个统一事件号指定一段已读经历，再用可指定的过滤函数从该段挑选行动、聊天输入或其它内容，不再逐项穷举。**当前实施推论是先定范围、后过滤；过滤只挑选，不重排。** 范围本身沿唯一的全局经历选取，不能因旧代码按窗口覆盖就默认只含当前窗口；需要专看某窗口时才显式过滤。半径按原信息流的事件条数算，不是编号数字差、过滤后的命中数或引用图跳数；执行时按当次已读快照展开为实际成员，覆盖节点冻结这些成员及强绑定闭包。反查即使选了区间，也必须分批返回，不能重演“一次吞入太多”。

**系统只有经历的顺序。** 假设柚子先读 B、起疑、再读 A、修正认识，然后发生 C；这些已读事件照实际阅读顺序留在原位。她后来回翻聊天时，工具按聊天原来的 A→B 顺序呈现正文。这次返回排在 C 后，是一段新的阅读经历，获得新的统一号；若分多页返回，各页依实际读到的顺序取得各自的号。A→B 只是重放内容内部的顺序，不是给统一事件流增加另一条可查询的排序轴。尚未读过的旧消息在这次才取得号；重读已读内容则保留原事件的号，同时让重放返回取得新号。单纯重建既有上下文不是再次重放，不应凭重启制造新经历。

**重放 + 节点改变的是当前可见的经历，不是旧事件的 ID。** 在「乱序探索 → C → 按 A→B 重放 → 写节点 N」之后，N 可以把前面那段已经完成、现在与重放重复的探索精确收起，并引用其中的原经历。当前视图于是保留按 A→B 读到的重放，再呈现 N 所记录的探索所得：对于这段材料，读起来就是「聊天先发生，然后柚子探索并形成认识」。这不是把 A 倒插回旧号，而是她真的又经历了一次按 A→B 展示的内容，并在此之后把先前的探索折成节点；展开 N 仍能追到当时先读 B、后来修正的经历。更长的回忆可以分段进行：重放到某处，就把已完成的整理和探索作为一个真实发生的节点写入，再继续重放后面的内容。这样节点在新经历中自然落在前后片段之间，而不是事后给旧事件排序或往旧位置插记录。N 须写下仍有用的认识与未解问题，不能只写「读过了」；覆盖只能点名那段探索的实际成员，不能因首尾号包围了无关行动就吞掉它。**草籽裁决：一次跨两个群的探索可以折成同一节点，跨窗口反查和同一事件被多个节点覆盖都允许。** 节点明确列出实际引用与覆盖的成员，并保留各自来源；跨窗口交错不是强制拆节点或默认同窗口过滤的理由。反查已读经历、翻阅聊天档案都通过新的返回继续这唯一的信息流，不必为聊天另建索引或给统一号查询添加排序函数。

## 第一阶段的最小闭环

1. **一条主体经历，一份全局状态。** 唯一主 reader 串行处理激活、模型输出和未完成追读；已读输入、输出、行动返回、引用与覆盖组成同一条可重建的主观轨迹。原始聊天仍按来源窗口保存在 chatlog，不复制到另一份可写正文权威。全局 hint、主设置与主 agent 的工具激活只写一处；后者随主体归属是实施推论，不把旧窗口名单无条件拼进来。窗口自身的通知偏好、档案位置及外部消息身份仍按窗口保留。私有 `.chat`、人类命令与代行不是第二个中心 agent，保留各自明确的调用身份。
2. **来源和目标显式，不造大 DTO。** 模型可见输入至少能分清来源窗口、作者、原消息身份、发生时间和实时／本地旧档／NapCat 补回的来源；缺失字段留为未知，不猜。实际阅读顺序就是正式事件号，本地档案位置已有 `origin`，到达先后由追加记录提供，不把这些事实再复制成新字段；远端历史锚点须按接口实测，不伪造本地 `origin`。自身输出没有群友作者，工具返回有来源行动而不伪装成群友新发言。行动有正式输出号及位置，发消息的 `say` 必填明确目标（群／私聊类型与稳定目标 id 是候选参数形状），返回及回声仍与其行动确认关联。需要按窗口行动的其它模型工具，要么显式给目标，要么在切换前证明不依赖隐式当前窗口；人类命令的现有 TLS 不必为此全库删除。跨窗口材料进入同一主体后，来源与接收目标不能在摘要和发送时消失，私聊内容不能因为读过就默认发到群里。
3. **通知、预览、正式拉取、回复分开。** 窗口有普通新消息就显示普通未读状态；有 `@` 或提到柚子的消息就把这个区别标出，由中心 agent 决定先看哪个窗口、是否回复和何时拉取。召唤可以使 agent 有工作，但不自动消费未读正文；给模型的开局内容应是通知概况而非偷偷把最新消息从队列拿走。模型可用 `peek` 查看任意有界段（包括最新段），也可通过显式目标的 `say` 先回复。其它窗口的新召唤可在任意两次行动之间进入，同一时刻不启动第二个主 reader；工具返回不得被历史回读饿死。通知被模型看到与消息被正式拉取不是同一件事：已递交的召唤不因其正文仍 pending 而每轮重复唤醒，后来新到的召唤也不能被旧通知一并确认。**实施推论：**通知递交事实随信息流持久留下，和 FIFO 消费位置分开；普通消息是否也要主动唤醒尚未由“显示未读”这件事决定。
   先回复不意味着本次按顺序拉取的工作结束；要让唯一 reader 在安全边界继续到本次目标，而不是靠尚未正式收取的同一条 `@` 反复唤醒。这里的未完成追读、已递交通知与 pending 正文是不同事实，不能彼此代替。
   **末尾 hint 的实施推论：**每次由持久 pending 动态列出有新消息的窗口、待按顺序拉取的数量及 `@`／提及标记；`peek` 之后这些待收取数不减，只有正式 FIFO 拉取才减少。这里“未读”是 mail 尚未正式收取，不等于模型从未预览。它只报告状态，不催模型做决定，不改写全局 `edit_hint` 待办文本；原有 token 占比提示可继续并列。任意旧档的可浏览内容不自动算作无限大的 pending。
4. **预览与 mail 进度分开。** `peek` 的返回作为新输入经历持久留下，包含所看内容的来源位置；它不改变 mail 的 FIFO 进度。模型选窗口后，正式拉取只取该窗口队首有上限的一段，进入模型时才推进该窗口的持久未读水位；跨窗口由模型选择拉取次序，于是实际阅读形成唯一的全局经历顺序。不另写“这一段完成”标记。中断后可从已持久读取事件和 pending 恢复，不因预览过末段就跨过此前的未读。主动探访远古历史不倒退 mail 水位。**首次没有可信旧边界时**，只以最近一个有界尾部建立一次性的日常追读起点；其前的旧聊天到达事实仍留档、可主动 `peek`，但不自动列为无限追读义务，也不假称它们已读。这个尾部里的消息仍待正式拉取，`peek` 不能替它完成消费。这个起点要持久可重建，不能靠每次重启再跳过一批；已有可信边界、未完成追读及工具返回不能套用首次豁免。正式号不能伪造档案位置。
5. **分段积累印象，但不把整理当收取确认。** 预览和正式拉取都是真实进入模型的经历，可以留下印象、写入 Skill／全局待办或用节点收起；只有后者减少 pending。若整理前中断，读取返回仍可重建和反查，不必因为没有“完成”动作而重复自动拉取。重复见到同一来源是两次真实经历，可在之后折成节点；没有新印象不必制造“无新信息”的节点。当前预算仍限制一次模型请求及累积印象；`count` 不是清空目标，不能变成连续 pull 直到把所有未读堆满上下文。此阶段不引入退休标记、H 或物理删除。

这些事实尽量用普通事件字典、现有追加信息流和可推导索引表达，不预建通用聊天软件 DTO、树对象或调度器。只有一个新的主执行路径：切换时替换窗口级主 reader，不能长期让两条主 agent 路径同时消费同一批消息。

## 历史实施顺序

1. 先用合成交错轨迹冻结最小事件来源、档案锚点、明确发送目标及全局计费语义；定向审计模型可达工具的隐式窗口和无界等待。用稳定档案位置做排他式、按记录数和 token 双上限的本地分段读取，不碰生产聊天。单条超大内容须有明确的可继续读取结果，不能静默算作已读。
2. 接通一条中心 reader：全局主体经历、hint、工具状态和显式 `say` 一起切换；开局与轮内两个整段排空入口改为通知概况、任意有界 `peek` 和有界 FIFO 拉取，不再默认把 pending 全投给模型。保留实时消息与档案写入的原子截面、尾缘召唤不丢、Bot 固定权限及窗口 `^C` 对关联工作的取消。窗口相关但尚未显式路由的模型工具不得在中心主会话中悄悄沿旧 TLS 发消息或读私人状态。
3. 接通回复后继续拉取、分段印象和跨重启进度。验证 A 窗口召唤→`peek` A 最近段→向 A 回复→B 召唤→向 B 回复→继续从 A 的 FIFO 队首有界拉取；`peek` 不减少 pending，同一来源后续正式拉取可再次出现。全过程仅一条主 reader，重建保留真正的阅读顺序，费用归 Bot，发言不串窗。再让主动远古阅读复用有界 `peek` 与记忆路径。
4. 只读验证当前 NapCat 历史接口的窗口范围、锚点、请求分批、稳定身份、中断和不可得情况；确认来源后才接入缺口恢复。补回记录不经实时路由重放副作用；本地一段读完与远端缺口已确认补齐是两件事。控制台展示日志仍只能作为有不确定性的观察，不能冒充 OneBot 原事件。

主线代码已接通第 1–4 项的中心 reader、通知、显式目标 `say`、全局设置及记账、重启后本地 pending 恢复，并把未读／外部历史读取面收敛为 `status/fetch/peek/pull` 四个动作；g/u 窗口和主动取得的历史 key 都是信源名，模型不再管理 NapCat 页号。部署中的进程只有在完整重启后才会使用对应版本。`event_span` 也已能按正式号中心半径或两个端点选至多 40 条已读经历，再按事件种类和来源窗口筛选；它仅返回实际编号，模型仍明确点名 `recall_events` 或 `cover_events`，尚未提供任意过滤函数或一次性自动覆盖。本机 NapCat 4.18.28 的群聊／私聊 `message_seq` 请求方向已脱敏核实；启动补回、sidecar 档案和持久信源已用合成轨迹验证读取顺序，但真实停机空窗尚未验收，也不把控制台近似日志当成原事件。

## 决策状态

**草籽 2026-09-25 裁决：`聊天开始／结束` 退为普通聊天内容。** 当前代码的中心 reader、`peek`、正式拉取与重建均不因此截断或清空全局经历；模型实际读到时按普通内容留下经历。此裁决不删除原有的唤醒或回复命令，只改变消息作为历史边界的效力。

在沿用现有唤醒规则、不扩大普通用户的设置权限、并保留此前“回复后继续分段阅读”目标的前提下，**当前没有仍需预先请草籽裁决的语义闸门**。若实施证据证明这些前提无法同时成立，再带具体冲突回来，而不是泛问工具参数。

其它暂按现有裁决落地，不再作为泛泛提问：普通消息先更新通知列表，`@`／提及沿现有唤醒规则；全局主设置优先取既有全局默认，旧窗口覆盖配置留存但不合并；新增全局设置入口不能让原本只改本窗口的普通用户顺手改所有窗口。若具体字段没有可用默认且存在冲突，再拿字段和影响到站询问。跨窗口拉取按**选定窗口内 FIFO**，全局经历顺序由实际拉取形成；单一全局 FIFO 反而会剥夺选窗口的能力。

**工程核验而非用户决策：**来源 `origin` 与 pending `arrival` 的映射、`peek`／正式拉取返回的细粒度可索引性、通知递交与重启恢复、按日事件文件的恢复顺序、上游请求游标和容量、跨窗口工具隐式目标、`say` 确认／回声绑定、共享请求中的窗口取消、NapCat 历史接口能力。内部批量上限、hint 数字和工具参数先取可调整默认，用临时合成轨迹与假接口验证；不读取生产聊天或向 `5701` 注入消息。退休、CQ 数组迁移和 LLF 均不是此阶段前置。
