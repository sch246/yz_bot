# 浏览器、计算机使用与远程操作：未来支线备忘

> **状态：未来支线，不是当前提案。** 当前实施方向是[中心化聊天软件阅读](chat-client-reading.md)；[压缩、遗忘与消息模型交接](condense-and-unify-handoff.md)保存旧路线。本文只保存方向、已有家底和以后进入这条支线前需要查清的事情；不据此安排实现顺序，也不预先决定接口或模块划分。

## 想获得的能力

这条支线包含三类相关但不同的能力：

1. **浏览器操作**：让模型在真实网页里观察、导航、点击、输入、提取内容，并利用现有图片阅读能力处理只靠 DOM 无法理解的页面。
2. **计算机使用**：让模型观察和操作浏览器以外的桌面应用，包括截图、可访问性信息、元素或像素输入。
3. **远程操作**：让柚子能够在另一台机器上调用命令、浏览器或桌面能力，并在断线、重连和自身重启后给出可理解的状态。

它们可以复用部分观察和输入机制，但现在没有证据说明它们应该共用一套通用框架。以后应从真实使用场景和最小纵向切片出发，再决定哪些职责值得提取。

## 柚子已经有的家底

当前浏览器能力不是空白。`mods.browser` 自管一份常驻 Chromium，以裸 CDP 提供页面导航、渲染后正文、链接、JavaScript、截图和真实输入；每个聊天窗口拥有自己的标签页，截图可以直接进入现有视觉链路。浏览器进程与一次工具调用解耦，启动时清理 Chrome 恢复的遗留标签页。顶层导航只校验 http/https 地址语法，本机、内网、公网和云元数据 HTTP 服务都可访问，页面后续请求不做地址拦截；这是宿主机信任域内的明确选择。现行事实见[运行架构](../../architecture.md#llm图片与可观察输出)，实施过程和已踩过的坑见[柚子迁移备忘](../kouzi-memo.md)。

这意味着以后首先要确认现有 CDP 能力缺少哪些可观察行为，不能因为出现了新的能力名称就重做浏览器底座。

## 值得调查的外部实现

DeepSeek Harness 目前把相关能力分成两条：

- `@deepseek-ai/dsh-browser-use`：通过 Playwright MCP、Chrome DevTools MCP 或 Stagehand provider 管理浏览器操作；浏览器由 live Session 持有，状态可以跨 turn，但 reload 或 fork 不恢复。
- `@deepseek-ai/dsh-computer-use`：通过 Cua Driver 的 MCP 或 native provider 提供桌面截图、可访问性树、元素或像素输入。

这份划分只作为调查入口。以后应重点读它们的实际观察表示、生命周期、失败语义、模型工具面和 provider 代价，而不是直接复制 package 边界。DSH 的 [Browser Use 文档](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45fbc/docs/subsystems/browser-use.zh.md)与 [Computer Use 文档](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45fbc/docs/subsystems/computer-use.zh.md)是当前入口。

## 以后必须先收集和验证的信息

进入实现前，按能否改变方案的程度依次查清：

1. 最先需要解决的真实任务是什么，以及它究竟需要网页、完整桌面还是远端宿主机。
2. 操作目标在哪里运行：柚子所在机器、受信局域网机器，还是公网节点；谁负责安装、升级和恢复远端执行端。
3. 哪些动作沿用当前 op 宿主机信任域，哪些动作还需要逐次确认、只读模式或目标限制。
4. 模型需要哪些互补观察：DOM、可访问性树、截图、窗口列表、终端输出；哪些是原始事实，哪些只是可重建投影。
5. 浏览器标签页、桌面窗口和远端连接分别归属于窗口、任务还是 Bot 实例；并发操作时谁能接管和打断。
6. 断线、超时、柚子重启和远端重启后，哪些状态可以重新探测，哪些动作绝不能自动重放。
7. 外部副作用如何留下可追踪事实，同时避免把当前 provider 的协议和中间状态固化成长期历史格式。
8. 现有裸 CDP 在真实任务上的缺口是什么；Stagehand、Playwright、DevTools MCP、Cua Driver 或更小的自写函数分别实际消除多少代码和失败模式。

## 与当前基础设施主线的关系

这条支线不要求等递归压缩和遗忘全部完成才开始，但外部操作会放大行动记录、观察回流、打断和重启连续性中的含糊处。重新进入时，应先核对当前主线是否已经明确：

- 模型发言与其它外部动作怎样记账；
- mail 缓冲、激活和插话怎样工作；
- 一轮结束、等待和取消分别是什么意思；
- 哪些工具事实进入 oplog，哪些环境事实进入 chatlog 或其它权威记录；
- 自身重启后怎样知道上一项外部操作做到哪里，而不猜测或重放。

只有与首个纵向切片直接相关的缺口才是前置条件。不要借这条支线提前建设通用会话、通用环境、统一驱动或兼容层。

## 进入这条支线时的第一步

先选一个真实任务，记录现有柚子能做到哪里、在哪里失败，再用 DSH 或其它实现完成同一任务作对照。证据至少包括模型实际看到的观察、发出的动作、用户如何介入、失败后的剩余状态，以及重启或断线后的行为。完成这次对照后，再写正式提案和实现依赖序。
