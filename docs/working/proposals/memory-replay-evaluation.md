# 长期记忆离线回放实验

> 状态：实施中  
> 最后更新：2026-09-25

相关论文与工程资料的核对结果见[记忆与自我演化研究地图](memory-and-self-evolution-research.md)。该文只提供外部证据和实验启发，不替本文决定当前实验协议。

> 2026-09-26：生产工具面已删除只列编号的 `event_span`，范围选择直接并入 `recall_events`；旧 `condense_ops`／`recall_ops` 也已由统一事件覆盖／反查取代。下文提到 `event_span` 的段落是当时实验记录，不代表当前可用工具。

## 要回答的问题

本实验现在明确分成两个问题，不能再用一组固定召回指标把它们混在一起：

1. **能力上限：**现有经历流、覆盖／反查、hint、工具模块、分叉与重放，是否足以让柚子产生一种新的做法，并让后续求值真实使用它；还是关键改进仍只能由维护者在系统外改 prompt 或代码？
2. **实践反馈：**若这条因果能力存在，怎样让柚子从真实失败中提出可逆改动，在不偷看后果的相同处境中重放，再根据实际新经历保留、修订或撤回，而不是追逐一套逐渐僵化的评分指标？

持续聊天中的自主阅读、整理、覆盖和反查，是验证这两个问题的主要材料：可见上下文不应随经历线性增长，事实、印象、话题关系和后来形成的经验仍应可恢复。但“召回某条标准答案”只是其中一种实践，不再被当作长期记忆的最终定义。

这不是摘要质量比赛。实验主要检查：

- 启动时只选一次初始上下文，之后不靠滑动窗口替模型遗忘；
- 新消息只能经 FIFO 分段读取，读到后才进入统一经历流并取得正式编号；
- `cover_events` 产生的结论保留可反查来源，同一事件允许进入多个索引；
- 模型能区分事实、他人原话、自己的解释与自己的情绪；
- 经历纠正或失败后，模型会在确有需要时修改工具模块或 hint，并在后来实际使用；
- 随经历增长，可见 token、检索成本、错误事实和无关记忆仍可控制。

## 已定实验口径

- **主体材料**：维护者指定的主群档案。群号只作为运行参数传入，不写进仓库。
- **模型**：显式固定为 `deepseek/deepseek-flash`，禁止失败后回退到其他模型。
- **基准提示**：当前生产默认提示词原样作为基准，不另写一个更容易通过实验的“简化基线”。
- **共同任务**：额外说明“当前正在离线回看已经发生的历史；把冻结 FIFO 分段正式读完并自行整理；不能影响或回复当时的参与者”。它只定义实验要完成的工作，不规定如何组织记忆；所有策略臂共享。
- **执行环境**：沿用生产的聊天投影、FIFO、统一事件编号、oplog、覆盖、反查、工具模块和 hint 语义；运行目录、存储和用量账本完全隔离。
- **发送边界**：不启动真实 Bot，不连接 QQ。`say` 即使被调用也只记入实验轨迹，不发送消息。
- **工具行为**：不人工编排工具测试。整理过程中自然产生的 `cover_events`、`recall_events`、工具模块加载／修改、hint 及其他行动就是被观察对象。
- **历史世界**：原聊天已经发生。实验 agent 的输出不会改写后续档案；它自己的阅读、整理和工具返回仍按真实顺序进入本次经历流。
- **人工参与**：不要求人工通读样本或逐条标注。样本选择、出题、证据核验、回放和评分应自动完成；人工只裁定实验目标及最终是否接受结果。

## 主样本

授权档案覆盖多年，普通日志可按日期、时间和文件内顺序稳定重放；当前没有补回 sidecar 需要合并。正文不会复制进仓库。

此前固定策略初筛选择了两个互不重叠的连续窗口；它们继续作为已冻结材料，不再承担选出永久“胜者”的职责：

| 用途 | 日期 | 消息量 | 原始体量 | 目的 |
|---|---|---:|---:|---|
| 策略初筛 | 2023-03-14 至 2023-03-16 | 约 8,490 条 | 约 1.32 MB | 至少三天高频聊天，暴露首次长期整理行为 |
| 保留验收 | 2023-03-01 至 2023-03-07 | 约 18,120 条 | 约 2.35 MB | 七天连续聊天；调提示时不得查看其评测结果 |

固定策略初筛阶段只准备把更长时间跨度给当时的胜出策略；这一顺序已被后文的实践反馈主线取代。文件体量不是调用预算；预算仍按 API 实际返回的普通输入、缓存输入和输出 token 分别累计。

## 已完成的固定策略初筛

所有策略使用相同模型、聊天、FIFO 页大小、工具、初始上下文和费用上限。

1. **生产基线**：当前默认提示词，仅增加离线回看事实。
2. **经历整理原则**：说明事实、解释、情绪、来源和多重索引的区别，但不规定固定模板。
3. **预测用途**：整理时考虑“未来在什么情况下会需要找回它”，比较是否减少无用流水账。
4. **主观记忆**：允许优先保留惊讶、情绪、关系变化、反例和独特经历，检查是否形成有个性的记忆而不把推测写成事实。
5. **压缩经济性**：要求每次覆盖考虑净 token 收益，允许琐碎内容被很短地归纳或不单独建索引。
6. **低频反思**：只在前述策略出现稳定失败后加入；一次只调整一个整理或检索习惯，并与未调整分叉比较。

这组候选记录了已经做过的初筛空间，不再规定下一阶段必须从中选两个策略跑完。后续先让模型从一次实际失败产生候选改动，避免继续由维护者枚举提示词并把费用花在措辞微调上。

## 观察、练习与反馈

冻结探针仍有价值，但它只用于定位失败、比较一次候选改动的实际影响，不是系统永久优化的单一目标。题目在记忆形成结束后才向被测 agent 揭示，不能反过来指导它整理。

### 实践反馈循环

一次有效练习必须让后续运行消费本次运行才产生的值。首版按下面的因果顺序执行：

1. 从真实轨迹中选择一个已经发生的摩擦，冻结失败前检查点、相同输入和可合法用于判断的后来证据；
2. 让柚子读取完整失败轨迹并修改隔离副本中的候选 Markdown 工具模块，或产生索引习惯等其它可加载载体，同时预先写下预期行为变化和否定条件；这个原案例因此是已见练习，不是盲测；
3. 从失败前检查点建立控制分支与候选分支；两边使用相同模型、输入、工具和预算，重放任务不再额外直给待检验结果，但候选载体允许携带上一步真正学到的规律；
4. 候选分支必须加载上一步实际生成的载体，不能由实验脚本重新口述成另一份 prompt；
5. 行动完成后再给出可合法比较的证据或独立反馈，保留两边完整轨迹；让柚子据此选择保留、修订或回退。旧回复之后的聊天只能评价旧回复，不能冒充参与者对候选新回复的反应；
6. 候选还要在未参与其诊断和形成的新情景中再次使用。原题重放只证明一次练习怎样改变行为，未见案例才提供迁移证据。

候选分支与当前启用版本分开保存：回退或暂未胜出的候选仍保留父版本、产生原因、预期、实际证据和结果，但不会因此自动进入生产或继续占用实验预算。任务层工具模块闭环走通以后，若真实摩擦显示“柚子不会产生或选择有效改动”，再单独比较不同的诊断、实验选择或候选生成方法；普通任务表现不冒充元修改能力。

控制器固定的是隔离、同初态、不在重放任务中额外泄漏待检验结果、实际加载、可回退和轨迹完整性。它分别记录“载体被消费”“行为改变”“实践结果改善”，不因一次随机消融就把三者合并成确定因果。什么值得记、为什么反查、怎样组织同一事件的多个入口，仍由柚子在实践中调整。

### 自动产生观察点

- 利用后续回复、引用、再次提及和明确纠正，生成关于较早事件的探针；
- 独立上下文中的 DeepSeek Flash 从完整档案生成“问题、答案、证据编号”；
- 第二个独立上下文只核验答案是否确由给定证据支持，不支持的探针自动丢弃；
- 对同一来源生成不同话题入口，检查多重索引是否真的能到达同一原文；
- 从相同检查点分叉进行探问，探问本身不写回后续记忆。

自动生成的答案是弱 oracle，不宣称等同于事实真理。因此最终结果同时报告结构性指标、证据支持和回答表现，不用单一 LLM judge 分数决定胜负。

### 诊断量，不是永久奖励

`calls` 和覆盖深度都不是单调目标。`calls` 多可能表示持续工作，也可能只是反复检查；深度增加说明总结确实能覆盖旧总结，也可能只是形成昂贵单链。下面各项只帮助柚子与维护者看清一次改动发生了什么，不合成为永久总分，也不预先规定“理想索引”的固定形状。

- **持续性**：未覆盖事件意外消失数；首次容量失败位置；处理到第几天；未读下降速度。
- **上下文健康**：每轮可见 token；峰值与增长斜率；每次覆盖的净 token 增减；重复失败的覆盖次数。
- **来源与事实**：回答正确率；证据编号支持率；错误自信；旧事实侵入；更正后的最新状态准确率。
- **检索**：找到正确证据所需的 `recall_events` 次数、返回事件数和 token；取回噪声比例。
- **多重索引**：同一来源能否由不同人物或话题入口找到；重复覆盖带来的 token 成本，不把重复成员虚算成额外召回。
- **主观记忆**：能否保留后来再次相关的惊讶、情绪和关系变化；是否把玩笑、猜测或自己的感受误写成客观事实。
- **经验积累**：一次错误后相似任务是否改善；移除新增工具模块改动或经验节点后改善是否消失；条件改变时能否停止套用旧经验。
- **费用**：每个策略的普通输入、缓存输入、输出、调用次数和实际价格；超出预设上限即停止该实验臂并记为失败。
- **派生观察**：可旁路记录结构路径与实际行走；若[记忆估值与索引演进](memory-valuation-and-index-evolution.md)的评分器校准通过，再记录指定基线下的压缩成本。这些量在首轮不向被测 agent 暴露，也不自动决定候选晋级。

文献中可迁移的比较包括整块重写与增量节点、gist-only 与 gist+lookup、单入口与多入口、任务层与元层改进分别验收。它们仍只是候选实验臂；只有出现对应失败并冻结同一初态、输入、预算和独立证据时才运行，不为覆盖论文清单而增加调用。

## 隔离与失败条件

- 不调用 `main.py`、`mods.boot()` 或真实消息发送路径；
- 不修改生产 `data/`、`chatlog/`、`log/`、配置和用量账本；
- 每个实验臂使用独立临时运行目录，固定输入快照并记录 manifest；
- 模型名、provider 或工具能力不符合 manifest 时立即失败，不静默降级；
- API 返回错误文本、上下文溢出、无法继续读取、悬空引用或未经覆盖的事件消失都必须显式计入结果；
- 不用自动滚窗把失败的策略救活后继续算成功。

## 尚未决定

- 每次练习、复盘与未见案例复验的实际计费上限；它按案例预估并作为硬停止条件，不按文件字节猜测，也不成为优化目标。
- Markdown 工具模块之后是否值得开放 Python 工具模块或其它代码修改；后两者需要更严格的权限、激活和回退边界。
- 需要真实参与者反应才能判断的候选新回复，怎样取得新的外部反馈；旧 chatlog 不能提供这种反事实结果。
- 模型拒绝整理并最终到达真实上下文上限时，生产系统应报错等待人工恢复，还是停止读取正文只保留通知；实验先记录故障，不替维护者决定。

## 运行记录

### 2026-09-25：三天基线校准

- 已冻结三天连续档案，共 8,716 个可重放事件；快照和正文只在仓库外的私有实验目录。
- 第一次校准限制为 6 次调用。API 报告输入 32,348 token，其中缓存 23,680；输出 5,320。模型反复调用 `pull_mail`，但没有正文取得正式号。由此发现生产 provider 只要还有工具结果就不兑现已安排 pull，`pull_mail` 自己的返回会让读取永久饥饿。
- 修复后用相同调用数上限重跑。模型正式读取第一批 8 条，并自主建立一个覆盖 4 个成员的节点；随后一次请求以 `finish_reason=length` 结束，fail-fast 正确停止。本轮用量文件含 4 次 API usage 与 1 次无 usage 的保守预留，合计输入 37,327、缓存输入 12,160、输出预算记账 8,000 token。
- 上述两次都只是校准，不评价记忆策略。它们证明了真实 DeepSeek 请求、FIFO、正式编号、自主 `cover_events`、用量记录和失败停止已经连通，也暴露了必须在正式长跑前解决的调度问题。
- 当时的生产 `pull_mail` 随后改为在同一请求边界依次交付有界工具结果、通知和一次 mail 读取；离线 scope 也取消了每轮后缀重选。当前模型接口又进一步收敛为 `pull(source, count)`，普通生产上下文仍保留事件与 token 上限。

### 2026-09-25：三天生产提示基线停止

- 基线分 8 段、共 171 次模型请求运行；断点续跑保持同一 oplog、Mailbox、hint 和隔离 storage，没有重投已经读过的档案。
- 模型累计正式读取 1,344 / 8,716 个事件，建立 143 个覆盖节点，覆盖成员 1,311 个。最后一次请求的 prompt 已达到 127,547 token。
- 后期几乎每轮都在“覆盖刚读的一页，再拉下一页”，但主要产生并列的叶子摘要，没有继续覆盖旧摘要形成更高层索引。于是原文虽被收起，摘要节点仍随阅读页数近似线性增长。
- 已记录约 11.74M 输入 token、至少 11.10M 缓存输入 token 与约 210.7k 输出 token；其中早期无 usage 的截断请求按预算上限保守记账。
- 这已经回答基线问题：默认提示会使用覆盖工具，却不会自行维持递归层级；继续跑完三天只会重复同一失效方式。下一轮应从同一冻结快照新建实验臂，比较明确讲解“摘要也要继续被整理”的提示策略，而不是延长本基线。
- 此基线结束后，生产 reader 已取消“确认通知后自动追完固定终点”，改为只有模型显式 `pull(count)` 才推进 FIFO，并恢复跨轮可见的模型输出正文。因此上述结果是旧读取策略的历史基线，不再代表当前默认提示；下一实验臂必须从冻结快照重新开始，不能接着该 checkpoint 冒充同一策略。

### 2026-09-25：当前 reader 的共同任务与结构初筛

- 只附“这是过去历史、不能回复”时，模型在 17 次调用里没有一次 `pull`：它反复 `status`、`peek`、整理自己的探索轨迹，正式历史输入始终为 0。这不是 FIFO 故障；生产提示明确允许未读保留。回放若要评价长期记忆，必须给所有实验臂共同的工作目标——把冻结 FIFO 分段正式读完——而不能靠旧 reader 自动追读偷偷完成。
- 加入共同任务后，默认提示在 12 次调用里读取 314 条，但 5 个覆盖根全是深度 1，最后 prompt 约 32.7k token；旧“叶子摘要线性累积”失败重新出现。
- 泛泛说明“递归整理”会让模型把单次 `pull` 扩到 120–200 条，很快以 `finish_reason=length` 失败。把批次限制为 16–24 条、禁止猜连续编号后，读取和叶覆盖稳定下来。
- 初筛暴露并修复了一个真实运行缺陷：完整输出在工具派发前已取得正式号，但它的纯文本投影要等整批工具结束才替换进当前 Chat；同批 `cover_events` 的可见性清理会误删这个尚未插入的对象映射，导致后续无法在同一 Chat 覆盖先前总结。当前实现只为 `active_action` 所属输出保留这一条暂存映射；纯内存复现、`run.py --check` 与隔离 smoke 均通过。
- 修复后，`grounded-hierarchy` 的干净 16-call 运行读入 120 条、7 次覆盖全成功，留下 2 个顶层根，最大深度 3；各请求 prompt 约 2.6k–7.5k。继续运行后仍会周期性产生没有行动的长思考并以 `length` 截断，因此“图能递归”与“执行能长期持续”必须分开评分。
- `grounded-loop` 用短决策循环减少全局重演：首段 16 calls 形成单根、深度 4、覆盖 116 条来源。长段到 480 条时又因同一输出同时 cover 和 pull，使父级整理被新输入持续饿死，顶层根重新累积到 17 个，随后截断。

### 2026-09-25：未折叠思考 A/B

思考不是永久特殊区。实验增加一个只在离线 scope 生效的变体：完整响应的 `reasoning_content` 与正文、行动同住一个 output 事件；该 output 尚未被覆盖时思考随统一投影保留，被上位节点覆盖后整段退出默认上下文。流式响应若以 `length` 截断，仍不登记半个输出或半段思考。

- 两臂使用同一个单步策略：每次输出只能做 cover、父级收拢或 pull 之一，禁止 cover 后立刻拉下一批。唯一变量是是否保留完整思考。
- 不保留思考：32 calls、260 条正式输入、17 个覆盖节点、2 个顶层根，最大深度 5；第 32 次调用以 6k 输出上限截断。累计 prompt 约 180k。
- 保留思考：42 calls、320 条正式输入、24 个覆盖节点、3 个顶层根，最大深度 8；第 42 次调用以同样的 6k 输出上限截断。累计 prompt 约 330k。共持久化约 44k 字符思考，其中约 7.3k 字符在停止时仍属未覆盖输出。
- 初步结果支持“已完成的思考可作为未折叠经历，帮助后续沿用决定”：它在本次单样本中多推进 10 calls、60 条输入并形成更深层级；代价是 prompt 明显增加，而且没有消灭周期性长思考。该结果只够保留为候选，不足以改生产默认；下一步应在冻结探针和至少一个独立运行上比较召回质量与费用。

### 2026-09-25：hint 执行状态

`hint` 与经历图不是同一种记忆：前者保存尚未兑现、忘掉后会重新推导的决定；后者保存长期事实、印象和来源关系。可查询的未读数、FIFO 游标、全部根或历史摘要不应复制进 hint。Markdown 工具模块（Skill）则留给跨任务复用的做法，三者不新增统一“记忆管理器”。

- 仅建议“必要时写 hint”的第一版没有产生任何 `edit_hint`，18 calls、140 条输入后便截断；它只证明软建议会被忽略，没有测到 hint 本身。
- 强制开局 checkpoint、只在下一步或阻碍改变时更新、限制约 200 字后，模型在 40 calls 内调用 `edit_hint` 21 次，长度通常 75–184 字、一次达到 234 字；正式读取 360 条，19 次覆盖成功、1 次失败，累计 prompt 约 293k，随后仍以 6k 输出上限截断。
- 与同口径对照相比：无 hint 在 32 calls／260 条停止；保留完整思考在 42 calls／320 条停止。checkpoint hint 几乎达到完整思考的持续调用数，却读得更多、累计 prompt 更少，因此目前是更经济的执行记忆候选。
- 但 checkpoint 臂停止时有 10 个顶层根，最大深度 4。它改善了“我下一步要做什么”，没有保证模型及时把叶摘要收拢为上位节点。下一轮若继续，不应继续增加模板字段，而应在冻结探针后比较：清空 hint 是否破坏任务接续、召回是否仍由经历图完成，以及独立重复运行能否复现单位输入成本优势。

### 2026-09-25：自动探针协议校准

本节只记录评测器校准，不把临时题库算作已经冻结的正式探针。所有正文、答案和模型控制台仍只存在于仓库外的私有实验目录；仓库只记录数量、费用和失效方式。

- 三条待比较 checkpoint 分别正式读入 260、320、360 条档案输入，共同已读来源为 260 条。探针只能从这个交集取证；否则较晚臂仅凭“多读了”就会得到额外题目，不是同题比较。
- 第一版让 DeepSeek Flash 从四个有界片段自由生成 JSON 候选。3k 输出上限在首段即以 `length` 停止；提高到 6k 后仍会截断，另一次完整输出还引用了当前片段之外的档案号。问题不是 JSON 解析，而是开放式出题本身触发了过长思考和越界联想。
- 尝试用强制函数调用只提交结构化候选时，provider 明确返回“thinking mode 不支持这种 `tool_choice`”。因此不能靠 schema 强制把同一模型变成廉价、确定的出题器；继续提高输出上限只会扩大费用和失败面。
- 第二版改为由档案里的显式 reply 边确定性地产生候选，模型只看题目和两条精确证据做独立核验。共同前缀最初得到 9 题，9 题全部通过；核验共用 1,683 prompt token、13,133 completion token，单题最高 4,272 completion token。这个结果说明核验链路可用，也说明“只判 true/false”仍会产生昂贵思考，不能把 judge 调用当作免费过滤器。
- 首批 9 题里出现了“同一作者回复自己”的措辞。独立核验器仍判为无歧义，但实际被测 agent 会停下来质疑题意，说明单一 LLM verifier 有稳定的假阳性。确定性生成随后排除了同作者回复和纯 CQ 内容，只剩 4 题；4 题再次全部通过，核验合计 722 prompt token、4,936 completion token，单题最高 2,077 completion token。
- 这 4 题的证据在三条经历图里都可达，但路径不同：无思考对照的两条证据约需 3–4 层，保留思考臂约需 4–7 层，checkpoint hint 臂约需 1–3 层。这使它们适合校准“实际能否沿图找到原文”，而不是只证明某条输入曾经读过。
- 首次只读实际探问从无思考对照的独立 checkpoint 副本开始，只开放 `event_span`、`event_links`、`recall_events`。模型在 8 次请求内产生 8 个输出、12 次只读检索行动（4 次 `event_span`、1 次 `event_links`、7 次 `recall_events`），但没有形成最终答案，按调用上限停止。它证明了模型会沿索引探索，也暴露出当前检索协议会让深层记忆触发“大穷举”；不能把“证据理论可达”当成“可经济召回”。
- 进一步把 12 次行动与正确证据的覆盖祖先链对照：只有 3 次点到了祖先路径，没有一次直接命中两条证据；其余 9 次在邻近范围或无关分支中探索。正确路径一共只有 5 个总结节点，每个上位节点约有 3 个子总结可选，但这 5 个结论里出现的正式号引用数均为 0。`cover_events` 参数只说明“这一批成员被覆盖”，没有说明结论中的哪一项由哪个子节点支撑；模型只能在每层分支中猜。这正是“有可达图却没有可用索引”的差别。

当前结论：正式题库不应继续依赖开放式 LLM 出题。首版应先冻结可机械核验的 reply 探针和少量明确更正探针；LLM 只用于最终答案语义评分。实际探问必须记录最短理论路径、真实工具次数、首次命中和噪声，且给每题独立分叉与调用预算。下一项研究不是再润色 hint 或增加调用上限，而是让每条保留结论把语义片段映射到**直接成员正式号**；父级总结引用子总结的输出号，叶级总结引用实际输入号。这样反查才能从主题命中明确的下一跳，而不是枚举整个覆盖集合。

### 2026-09-25：语义下一跳与实际反查

为验证上一节的根因，新增实验臂 `serial-loop-linked`。它与无思考单步策略共用模型、20 条读取批次和“每次只做一个核心动作”，唯一新增要求是：cover 结论中的每项保留语义都必须就地引用直接成员号，父级引用子总结输出号，叶级引用实际输入号。

- linked 臂在 20 calls 后以 `length` 停止：正式读入 140 条、10 次 cover、4 个顶层根、最大深度 3；10/10 个结论都出现正式号。累计 prompt 120,421、缓存输入 65,920、输出 31,247 token。
- 同取前 20 calls：无思考对照读 160 条、10 次 cover，引用号 0/10，prompt 94,238、输出 14,600；保留完整思考读 140 条、11 次 cover，引用号 2/11，prompt 129,812、输出 15,486；checkpoint hint 读 180 条、9 次 cover，引用号 0/9，prompt 105,563、输出 18,349。linked 成功改变了索引形状，但输出成本约为无思考对照的两倍，并更早触发长输出失败。
- 现有四题中有三题的全部证据已被 linked 臂正式读取。对第一题不附额外检索指导时，模型在第 8 次请求完成答案，共做 13 次只读行动；第 10 个行动才首次直达 gold。它引用 3 个正式号，其中两个正是两条 gold 证据。盲判认为语义答案 `correct`，但证据不支持全部具体展开，标记 `unsupported_specifics=true`。因此“最终引用了正确原文”不等于“回答中的每项内容都由原文支撑”。
- 在同一 checkpoint 的新分叉中，禁止 `event_span`，只要求沿问题相关条目旁的直接号逐层 `recall_events`。第一次运行的 5/5 个行动都在正确祖先链上，第 3 个行动已经直达 gold；原先无指导运行只有 4/13 个行动在正确路径上、第 10 个才命中。这证明语义下一跳确实可以把盲目探索变成定向遍历。
- 但第一次定向运行命中后仍继续核验，随后再次因 `length` 停止。再加“直接输入足以回答就立即停止”的单一规则后，模型用 4 calls、6 次 `recall_events` 完成，prompt 49,614、缓存输入 33,024、输出 2,399；仍精确引用两条 gold。代价是盲判从 `correct` 变为 `partial`，并继续报告证据外具体化。更快停止解决了路径和成本，没有解决回答如何忠实于短原话。
- 两次盲判自身分别消耗 4,031 和 1,117 completion token，而输入仅 352 和 363 token。DeepSeek Flash 的 judge 也不是廉价权威；正式统计应优先用“是否命中 gold、是否引用不存在编号、是否包含机械 oracle”等确定性指标，只把无法机械判断的语义差异交给盲判，并单列 judge 成本。
- 随后把三道 linked 已读题改成可机械评分的“只提交取回的回复原文”。仅靠正文 JSON 时，三题只有一题完成：它用 2 calls 命中两条 gold，但把 3 字 oracle 扩成 65 字；另两题分别耗尽 6 calls 和以 `length` 停止。自然语言里的“只填原文”没有形成可靠约束。
- 再给探问分支增加只用于评测的 `submit_answer(answer, evidence_ids, confidence)`，调用即结束，不进入生产工具或原经历图。三题中两题完成：一题用 6 calls、7 次工具行动，答案与 13 字 oracle 逐字相等并精确引用两条 gold（prompt 83,241、输出 8,096）；另一题用 2 calls、2 次工具行动并精确引用两条 gold（prompt 11,426、输出 547），却仍把 3 字 oracle 扩成 65 字；余下一题耗尽 6 calls。结构化提交能固定协议和终止边界，不能替模型保证语义忠实。

这一轮把问题拆成了两层：**索引形成**需要语义到直接号的映射，**回答形成**需要从直接证据中抽取而不把上层总结继续扩写进去。linked 提示支持第一层有效，却以更高形成成本换取；三题复测说明第二层仍不稳定。下一实验不应再堆答案措辞，而应把正式探针 harness 固化为“确定性 gold、每题 fresh fork、结构化提交、机械指标优先”；记忆形成侧再单独比较自由文本内联引用与更窄的 claim→direct-sources 参数形状，判断能否降低 linked 的形成成本。

### 2026-09-25：方向订正——从评分器到实践实验室

上一节最后一句把下一步收窄成了“固化探针 harness，再比较两种索引参数形状”。这仍把维护者当前想到的检索任务和指标放在了过高位置。探针校准、linked 对照和结构化提交的结果继续作为有效诊断证据保留，但不再决定实验的最高目标。

新的主线先问系统是否允许柚子改变自己的实际做法，再问这种改变能否经受实践。当前隔离回放已经有冻结档案、检查点、分叉、完整轨迹和发送阻断；缺的接缝是：让柚子根据失败生成一份受控、可版本化的候选载体，让后续分支精确加载这份载体，并在得到合法的新证据后决定保留或回退。没有这一步，更多 probe 只会更精确地评价维护者设计好的固定系统。

因此下一实验使用已经记录的“大范围反查”失败作为首个**已见练习**：先冻结失败前提交点和可机械核验的证据，让柚子阅读失败并修改隔离副本中的候选 Markdown 工具模块，同时预写预期差异与否定条件；再从同一提交点分出旧版和候选版，重放相同问题。候选可以携带从失败中学到的规律，因此这一步只观察载体消费与行为改变；是否真的改善、能否保留，还要结合证据表现与随后未见案例，而不是由原题单次成功或单一总分自动晋级。
