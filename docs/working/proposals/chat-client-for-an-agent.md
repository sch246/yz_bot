# 给 agent 做一个聊天软件：主观时间轴，以及它推翻的东西

> **2026-09-25 已转为实施方向，尚未落地。** 草籽决定第一阶段就采用中心 agent；召唤后先用不消费未读的 `peek` 浏览最近有界片段，可先回复，再按 FIFO 分批正式拉取积累印象。全局 agent hint、主模型／prompt／预算、明确 `say` 目标和按 Bot 记费也已确定。实施范围、现状阻碍与未决见[中心化聊天软件阅读计划](chat-client-reading.md)。本文仍保存论点与推论，不描述当前运行行为；自身经历如何遗忘仍无答案，暂不引入退休标记或删除。

> **这是一份论点与讨论记录，不是实施提案。** 机制落在 [mail 与激活](mail-and-activation.md)，
> 推进顺序落在[交接索引](condense-and-unify-handoff.md)，这里只记**论点本身**、它是怎么来的、
> 它推翻了什么，以及哪些结论有独立证据、哪些只靠这个隐喻站着。
>
> 体例照 [可自维护的同相上下文·讨论来源](self-maintaining-context-discussion.md)：保留原话与修正链。
> 日期 2026-09-20，对话双方是草籽与本仓库的助手。**推论**一律标出。

## 一句话

**柚子不是「每个窗口一个会话循环」，而是一个主体在用一个聊天软件。** 这一方向现在已由草籽选为第一阶段目标，不再只是隐喻；下文关于旧目标顺序和 mail 整段排空的推论，按[当前阅读计划](chat-client-reading.md)的有界 FIFO 拉取与不消费未读的 `peek` 理解。

推论链在下面，但先把最深的那条摆出来，因为它是唯一一条有**独立证据**的：

> 模型看到的内容顺序，和消息实际发生的顺序，**是两条不同的时间轴**。
> 客观时间记在 chatlog 里（这句话何时被说），主观时间**今天没有任何地方记着**
> （柚子何时知道的）。上下文必须按主观轴排，因为那是它自己的推理唯一说得通的顺序。

## 它是怎么来的

不是设计出来的，是**被一连串局部问题逼出来的**。按发生顺序：

| # | 在解决什么局部问题 | 得到什么 |
|---|---|---|
| 1 | 工具返回不该触发下一轮 | mail 是缓冲区，触发与工具返回解耦 |
| 2 | 缓冲区里有激活元素时怎么办 | 「下一次可用时**整个**放入上下文」 |
| 3 | 轮内是拉、轮外是推，两套机制 | **反转视角**：红点、阅读、「叫我一声」——推和拉合成一件事 |
| 4 | 攒了一星期的邮箱怎么读 | 按预算**分次阅读**，像自然人读未读 |
| 5 | 缓冲区里有多个不同权限的激活元素 | 权限不该因阅读消息而改变 |
| 6 | 模型怎么知道有什么没读 | hint 显示未读列表，**用工具手动拉取** |
| 7 | 未读列表要不要跨窗口 | **「我想我们本质上是在给 bot 制造一个聊天软件」** ← 就是这里 |

前六步各自都在解决一个具体麻烦，谁也没在设计一个架构。第 7 步只是**给已经走到的地方起了个名字**。

### 判据：隐喻开始自己产出答案

一个说法是不是真的抓住了结构，判据不是它听起来顺不顺，是**它能不能替你回答你还没问的问题**。
命名之后立刻落下来的几条，都不是再分析一遍得到的，是**从聊天软件这个形状直接读出来的**：

- 红点只管**叫不叫醒**，不管**能不能看见**——聊天软件里会话列表永远可见，提醒是另一回事；
- 提醒级别**由 Bot 自己配**（全部／只 at／免打扰）——这正好答了当时挂着的一个闸门；
- 执行应当**集中化**——一个人用一个客户端，不是 N 个人各用各的；
- 「从有史以来的历史重建以消除消息上限」**降级**——软件里你不需要把全部聊天记录同时摆在屏幕上；
- 「调 NapCat API 补拉离线消息」**变可选**——那只是「这个会话有一段我没拉过」。

**但同一个性质也是它的风险**：会自己产出答案的隐喻，也会自己产出错答案。见最后一节。

## 最深的那条：两条时间轴

草籽 2026-09-20：

> 因为这个架构下，模型看到的内容顺序实际上与消息的实际顺序解耦了……而且需要单独追踪，
> **应该以 ta 实际接收到这个消息的时间为准**，这恐怕是最本质最底层的变化。

和补充的：

> 一个好处是，如果 ta 的体验线性被记录下来，那么**上下文的稳定性就得到了保障**且不需要
> 从消息进行不稳定的重建——**之前其实一直存在这个问题**，消息按时间重建和模型当时收到的
> 实际上下文顺序存在差异。

| 轴 | 记在哪 | 回答的问题 |
|---|---|---|
| 客观时间 | chatlog 的 `time` | 这句话**什么时候被说的** |
| **主观时间** | 当前无完整权威记录；要连起自身输出片段与随后阅读的 mail 批次 | 柚子**什么时候知道的** |

两条都是事实，**谁也换不出谁**。一条昨天发的消息，柚子今天才读到：客观上它排在昨天，
主观上它排在今天。

**2026-09-23 订正：**旧版此表把「mail 的入列序号」直接写成主观时间，漏掉了模型自身输出。若 B 在模型生成片段 D 时入 mail，模型只有输出完 D 才在间隙读取 B（以及其后的同批输入），主观顺序为 D→B，而非按宿主到达时刻排 B→D。mail 入列序号维持**输入之间**的先后，不单独表达整条经历；持久记录如何表达输出片段和读取批次尚未决定。

### 这一条有独立证据，不靠隐喻

核过代码，**缺陷今天就在**，而且 `mods/chat.py` 自己招了：

1. 一轮**跑的时候**，插话走 `on_round`，按**到达顺序**追加，落在模型已经做过的那几次工具调用**之后**；
2. **下一轮**，`build_context` 从 chatlog 按 `time` 重排，外加「同一时刻聊天排在工具轮前面」的平手规则；
3. 那条消息于是被挪到它**时间戳**该在的位置——很可能排到那几次工具调用**之前**。

失败的样子：**模型读自己上一轮的记录时，会看到自己在「已经知道某件事」的情况下，
做了一串其实是在不知道时做的动作**；反过来也会出现它当时明明看见了的消息在记录里靠后。
它的推理链读起来不连贯，而它无从察觉。

`build_context` 的 WHY 原文：

> 顺序不保证与当时完全一致：一轮里几个并发调用完成时间不同，工具执行期间到达的消息
> 其真实先后也无法从一个时间点还原。**这是明知的近似。**

主观轴让这条 WHY 可以**删掉**——不是缓解，是消除：顺序不再需要从时间戳还原，它本来就被记着。
删除条件已经写回那段 WHY 旁边（`mods/chat.py`）。

### 它顺手把几个悬着的问题夯实了

- **前缀稳定**（闸门 K）要求重建**逐字可复现**。按客观轴做不到——同一秒的多条消息谁先谁后
  没有事实可依；按主观轴天然可复现，序号唯一。
- **mail 只记顺序、不记内容**（闸门 L）原先的论据是「状态最少」，那是**节约**论据，不够硬。
  换成本体论据：**mail 记的是 chatlog 根本没有的事实**，不是副本。
- **跨窗口**之后客观轴甚至不再可比——两个群各有各的时间线，混排只有主观轴说得通。

## 它推翻了什么

### 推翻了我（助手）的两条分析

1. **「op 门是结构性管制，挡得住注入」——不成立。** 门问的是「**谁触发了这一轮**」，
   不是「这一轮的上下文里有**谁的字**」。而插话早就会把任何人的正文放进 op 触发的轮里。
   所以今天一个非 op 的文字已经可以出现在握着 op 工具的轮里；门拦住的只是
   「非 op **直接**命令 op 工具」。草籽的原话：

   > 混合的消息触发机制下，这本来也防不住就是了，任何人实际上也可以插话进行注入……
   > 如果都防不住，我愿意选择更简单的方案。

2. **「邮箱太大就退化成重建」——被否。** 重建会**跳过**水位线中间那一段；
   按预算**分次阅读**一段都不跳。后者才配叫不漏消息。

### 推翻了「上下文是投影」这个隐含前提

这一条最容易被漏掉，因为它从来没被写下来过，只是一直成立。

**旧**：上下文每轮从权威（chatlog + oplog）重算。上下文是**投影**。
**新**：上下文是「我读过什么」的累积结果，是**路径依赖的历史**。

几乎所有旧结论都压在旧前提上：

- 「设置改了自动生效、坏掉的上下文自动痊愈」——那是重算的副产品，路径依赖之后没有了；
- 「消息永不删、工具调用按高度退休」两条线够用——**够用是因为投影不需要遗忘**；
- 「消息条数上限」是个问题——**上限来自预算自动选取**，而软件模型下没有自动选取。

## 因此变难的：遗忘

草籽：

> 它将拥有自己的记忆，而**遗忘机制似乎变得更难设计了**。

两条线变成三条：

| 线 | 内容 | 现有答案 |
|---|---|---|
| 客观记录 | chatlog 的消息 | 永不删（草籽定） |
| 自己的行动 | oplog 的工具调用 | 按高度退休 |
| **自己的经历** | **主观轴 + 读过什么** | **没有答案** |

第三条难在（**推论**）：

1. **要忘的和绝不能忘的长在同一批记录上**——顺序是重建的脊梁，绝不能删；
   而「我读过这些」恰恰最该被压缩。同一串条目的两个面。
2. **删除不再幂等。** 消息删了还在 chatlog 里，可以再读；
   「我曾经读过它」删了就真没了——再读会得到一个**新的**主观时刻，
   等于把历史改写成「我是现在才知道的」。
3. **未读语义被波及。** 未读从水位线算。「读过」可以被忘的话，水位线退不退？
   退了会重读，不退就出现「忘了、但也不会再看见」的洞。
4. **压缩节点坐在主观轴的哪个位置？** 盖住「上周读过的三十条」的那个节点，
   它的主观时刻是那三十条的开头、结尾，还是压缩发生的那一刻？三种选法会把同一段历史
   排到三个不同的地方。

**结论：别急着设计。** 第 1、2 条说明这不是把高度退休搬过来就行；第 4 条说明它与压缩树的
形状耦合。而树（待办 4c）还没落地，**在有一棵真树可以观察之前，第三条线只能是猜。**

## 哪些结论靠得住，哪些只靠隐喻站着

这一节是给以后的人的，也是给现在的自己的。**会自己产出答案的隐喻，也会产出错答案。**

| 结论 | 凭什么 | 落地时要重验吗 |
|---|---|---|
| 两条时间轴，上下文按主观轴排 | **代码里的缺陷已核实**，与隐喻无关 | 不用重验论点，要验实现 |
| 权限不随阅读改变 | 论据是「现有的门本来就挡不住」，也已核实 | 不用 |
| 分次阅读不跳段 | 逻辑：重建会跳、分次不跳 | 不用 |
| 红点只管叫醒、不管可见 | **只有隐喻**——聊天软件是这样的 | **要** |
| 通知级别由 Bot 自己配 | **只有隐喻** | **要** |
| 执行集中化 | 隐喻 ＋ 串行性诉求；**已知代价**：一个卡住的工具会堵住所有会话，而今天只堵一个窗口 | **要**，而且工具超时是它的前置 |
| 全量重建降级、补拉变可选 | 压在「上下文是 Bot 自己读的」这个**尚未落地的选择**上 | **要** |

最后一行要特别小心：它们不是被证伪了，是**软件路线的前提还没成真**。即使待办 3b 的既定部分落地，
把它们当成「已经不需要了」而删掉现有机制，是拿一个还没兑现的设计去换一个正在工作的东西。
[交接索引](condense-and-unify-handoff.md)第四点五节因此明写：**都别现在动手。**
