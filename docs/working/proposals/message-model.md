# 统一消息模型：窗口、正文与双向转换

> 状态：第 1-6 步已实施，第 7 步未实现。当前事实见[运行架构](../../architecture.md)，行格式的协议见[chatlog 记录格式](../../chatlog-format.md)，用户可见语义见[交互模型](../../interaction-model.md)。
> 本篇取代 [Storage 加载校验与历史恢复](storage-and-history.md#chatlog-双向恢复) 里那一节的概述；那篇继续负责 storage 的加载校验。

一句话：`chatlog` 已经是聊天历史的唯一写入点，但它写下去的东西还不足以再读回来。本篇定义读回来所需的**最小事实集**，并据此收掉一份重复的持久化。

## 先排除四种相邻方案

它们都不是本篇要做的事，写在前面以免被当成默认前提：

- **不引入 `Message` / `Event` class，也不建 `Source`/`Sink` 层级。** 事件继续是普通 dict。本篇新增的全部东西是：一个窗口键、一对 `format`/`parse` 纯函数、一个带范围参数的查询。
- **不把聊天历史并进 `mods.log` 的流。** [日志分流](log-streams.md)明确把 `chatlog` 列为「已经存在的独立流先例」而不是成员。形状像不代表该共用路由：合并会让终端订阅集获得对产品数据的影响力。
- **不建搜索索引。** 按窗口按日分文件，线性扫的量本来就小；索引会引入一个新的权威和一份要同步的派生状态。
- **不重写既有 `chatlog/` 文件，也不做一次性转换脚本。** 那是几年的生产数据，只读。转换在技术上也做不到位：**unescape 不可逆**，脚本能给私聊行补上 QQ 号，却无法把正文还原成原始串——重新转义会把 859843 条含 CQ 的正文里的真实码变成字面文本，不转义则等于给一份投影贴上 v1 的标签。半截转换的结果是保留了版本分支却毁掉了原始字节，把一个**已标注的缺口**换成一个**没有标注的谎**。

## 已经观察到的问题

### 1. `event["user_id"]` 在群聊和私聊里不是同一个东西

- 群聊：`mods/message.py:97` 把 Bot 自发消息的 `user_id` 设成 `sender.user_id`（即 Bot）；收到的消息 `user_id` 也是发送者。**`user_id` == 发送者**。
- 私聊：`mods/message.py:95` 把 Bot 自发消息的 `user_id` 设成对端 `user_id`。**`user_id` == 窗口对端**，发送者只在 `sender` 里。

后果可验证：`history.is_self`（`mods/history.py:82`）用 `candidate["user_id"]` 判断「同一个人」，因此**在私聊窗口里，Bot 自己发的消息会被算成对端发的**。`mods/op.py:45`、`mods/post.py:62` 的提醒节流和 `mods/cave.py:168` 的 `get_self_log` 都建在这个谓词上。而 `chat.msg2chat`（`mods/chat.py:122`）读的是 `sender.user_id`，是对的——同一个问题在仓库里已经有两套读法并存。

这是本篇的核心：需要的不是新抽象，而是把**窗口**和**发送者**当成两个显式的东西。

### 2. 私聊行没有发送者 id

`_private_str`（`mods/chatlog.py:87`）只写显示名；群聊行是 `【头衔】名字(user_id)`。而显示名可以被 `identity.setname` 随时改。于是同一份私聊日志里，Bot 说的话和对端说的话，只靠一个可变昵称区分。这是问题 1 在文件侧的同一处缺口，也是唯一需要新增的 key。

### 3. 正文是投影，且投影不可逆

`mods/chatlog.py:159` 写的是 `_unescape(message)`。两点已实测确认：

- `cq.unescape` 的替换顺序把 `&amp;#91;` 还原成 `[`（正确结果是 `&#91;`）。这是一个独立的现存缺陷，见[维护队列](../current-issues.md)。
- **即使顺序修好，歧义也不可约**：用户字面输入 `[CQ:at,qq=1]` 时，OneBot 传来 `&#91;CQ:at,qq=1&#93;`，unescape 之后与一个真实 at 码完全同形。在一个日常讨论 `.link` 动作和 CQ 码的聊天里，这不是边角情况。

同时 `chat.msg2chat`（`mods/chat.py:129`）把**原始**串直接喂给 LLM。也就是说日志看到的正文和模型看到的正文今天就不一致；改成存原始形式反而让两者对齐。

### 4. 「窗口」被编码了两次

`history` 用 `(kind, uid)`（`mods/history.py:71`），`chatlog` 用目录路径（`mods/chatlog.py:104`、`:110`）。同一个概念，两处拼写。

需要同时说清的反例：`context.interaction_key`（`mods/context.py:68`）返回 `(group_id, user_id)`，那是**交互线**——群内某个人的一条 yield 线，用来登记 continuation。它和窗口不是一回事，**不要合并**。三处编码里只有前两处是重复。

### 5. 近期消息有第二份持久化

`data/cache_msgs` 是每窗口至多 256 条事件的 `repr()`，靠 `ast.literal_eval` 读回（`mods/history.py:169`）。它保存的内容 `chatlog` 已经有了。这违反「一个事实一个写入权威，允许多个有意投影」：现在有两个写入权威。

## 版本切线

**v0 = 切换之前已经写下的所有行，只读、尽力解析、永不重写。** 它缺私聊发送者 id、正文经过不可逆 unescape、notice 只有中文散文，这些都不追认为契约，解析结果按下节的三级标注如实降级。

**v1 = 切换之后写下的行。** 相对 v0 只有两处变化：

1. 私聊行补上发送者 `user_id`（新增的唯一 key）；
2. 正文改写原始形式，`unescape` 移到显示侧。

行的整体形状、缩进规则、目录布局和文件名都不变。**不引入文件头版本号**：格式差异可由行本身判定（私聊行是否带 `(数字)`），再加一个存在 storage 里的切换时间戳作为兜底；给每个已存在的日志文件补写头部，等于改写历史数据。

## 最小 key 集合

原则：**只存不可推导的事实**。下面第一列是「记录里必须能读出的东西」，不是「每行要多写的字段」。

| 事实 | v1 由什么承载 | 是否新增 |
|---|---|---|
| 发生时间（秒） | 路径 `YYYY-MM/DD.log` + 行内 `HH:MM:SS` | 否，已有 |
| `message_id` | 行尾 ` \| {id}` | 否，已有 |
| **发送者 `user_id`** | 行内 `名字(user_id)`，私聊补齐 | **是，唯一新增** |
| 正文 `message` | 缩进块，改为原始形式 | 否，语义修正 |

推导，不存：

| 字段 | 推导来源 |
|---|---|
| `group_id` / `message_type` | 路径 |
| `post_type`（`message` / `message_sent`） | 发送者是否 `identity.bot_id()` |
| `self_id` | `identity.bot_id()`；全仓库只出现在 `mods/msgs.py:12` 的键名清单里，无行为消费者 |
| `raw_message`、`font` | 同 `message` / 常量垃圾；同样只出现在 `mods/msgs.py:13` |
| `sub_type`（消息的 `friend`/`normal`/`anonymous`） | `msgs.is_friend`、`msgs.is_anonymous` 在 `mods/` 内无调用者，不予恢复 |
| `reply` / `reply_cq` | 正文里的 `[CQ:reply,id=...]`。`mods/bot.py:150` 的 `chatlog.write` 发生在 `_strip_reply` 之前，回复关系原样留在正文里 |
| `sender.nickname` / `card` / `title` | 行内渲染的 `【头衔】名字`（写入当时的历史值），或 `identity` 的当前值 |

`sender` 在重建结果里必须存在且带 `user_id`——`chat.msg2chat` 只认这一处。其余 `sender` 字段按上表填入并标为推导值。

行内那个 `【头衔】名字` 不算冗余：它承载的是**写入当时**的显示名，而 `identity` 只保留当前值，重建时没有别的地方能拿到它。但它不是身份权威，解析时只能作为推导值填进 `sender`，不能反查 id。

## 三级标注

`parse` 的每个字段属于三类之一，结果里必须能区分：

- **事实**：直接读自行内容（时间、`message_id`、发送者 id、正文）。
- **推导**：由路径、`identity.bot_id()` 或正文算出，规则确定（`group_id`、`post_type`、`reply`）。
- **缺省**：v0 里根本没写下的东西（私聊发送者 id、`sender.role`）。

重建出的事件另外带一个显式来源标记（如 `_source: "chatlog"`）。今天 `history.getlog` 的每个消费者读的都是原始 OneBot 字段；没有这个标记，字段缺失就是静默降级而不是明确失败，与「失败后仍有清晰的观察入口」冲突。

## 明确不恢复的东西

按「允许真实的不对称」，下列内容 v1 也不做结构化往返，并写明理由：

- **notice 默认保持中文散文，但戳一戳和撤回是例外。** 通用的反解仍然不做：`group_ban` 的 `{d}天{h}时{m}分{s}秒`、`group_card` 的带引号名片、`group_decrease` 靠措辞区分踢与退，反解这些会在任何一次措辞调整后静默失效，而且没有消费者。notice 的默认定义因此仍是「带时间戳的不透明事件文本」。

  但**有消费者的那两类要恢复，而且恢复得起**——这正是上面预留的「按那一类单独决定」，第 6 步把它触发了：

  | 家族 | 消费者 | 需要的字段 | 从哪读 |
  |---|---|---|---|
  | 戳一戳 | `chat._is_context_poke` | `user_id`、`target_id` | 行内 `名字(id)戳了戳名字(id)` |
  | 撤回 | 启动重建（不能把撤回的消息放回内存） | 被撤回的 `message_id` | 行尾 `一条消息(id)` |

  关键在于**这两类都以 id 结尾，而那个 id 是本文件自己写下去的**，所以读的是最右侧的锚点而不是句子的含义。戳一戳更强一层：`chat.get_msgs` 拿到事件之后又交回 `format_poke` 渲染，所以往返是「本文件的格式化函数 ↔ 本文件的解析函数」，用的还是当前 identity——**重建出来的戳一戳和实时事件逐字相同，不是降级品**。不匹配的行原样留作不透明文本，所以措辞变化让它**消失**而不是**出错**，与版本自判同一个方向。

  格式修正随之而来。**私聊的通知行以前只有名字没有 id**，于是无法判断是谁——这与问题 2「私聊行没有发送者 id」是同一个缺陷在 notice 家族的重现，一共三处：戳一戳、私聊撤回、私聊文件上传。现在一律 `{名字}({QQ号})`，两种窗口同形。因为 v1 尚未上线，这些随 v1 一起落地，不产生第二条版本线。

  **`format_poke` 同时修掉两个迁移引入的回归。** 迁移前（`4ae8d5f^` 的 `_code/bot/chatlog.py:210`）群聊取群名片、私聊取账号昵称，都不碰自定义名；迁移后改成了 `identity.getname`，它比原来多做两件事：叠加 `.setname` 的自定义名，以及在没给 `group_id` 时去读 `context.current()` 的窗口。前者让一个显示偏好改写「发生过什么」的记录，后者让同一个事件在重建路径或别的窗口里渲染出不同结果——格式化函数必须只是它的事件的函数。现在与 `chatlog` 其余部分一致：群名片 / 账号昵称，不碰自定义名。

  由此定下一条通则，写进[格式协议](../../chatlog-format.md)：**`chatlog` 里的名字一律取 QQ 侧的真实身份，`.setname` 只影响柚子说话时的称呼，不进日志。**

  但模型看到的名字是另一回事，那正是 `format_poke` 当初改用 `getname` 想要的东西。`msg2chat`（`mods/chat.py:137`）本来就用 `identity.getname` 渲染消息作者，所以戳一戳若不这样渲染，模型就会对同一个人看到两个名字。**两条路因此分开**：`chatlog.format_poke` 是日志的协议渲染器（QQ 侧身份），`chat._poke_text` 是模型侧的渲染器（自定义名），后者与 `msg2chat` 一致。

  这也让第 6 步「戳一戳往返在 `format_poke` 闭合」那句证据形式变了：现在模型侧另有渲染器，闭合的是「重建出的事件带齐 `user_id`/`target_id`」这一点——那本来就是两个渲染器各自唯一需要的东西，所以重建的保真度没有变，变的只是论证方式。

### 第 6 步之后：v0 私聊发送者的补齐

真实数据（270 万条群聊行，3.77 万条 v0 私聊行）：**柚子的当前账号在整份存档里只用过一个显示名，且没有任何别人用过它**；全局同名不同号的昵称 22 个，与柚子无关。按整份群聊语料判，18248 条判为对端、14002 条判为柚子、5399 条判不了、58 条「两边都像」。

那 58 条有个确定的解释而不是巧合：既然没有别人用过柚子的名字，「两边都像」在数学上只可能发生在**对端就是柚子自己**的窗口里——QQ 允许给自己发消息，也允许在自聊窗口里戳自己。所以那 58 条不是歧义，是自聊。

**排除法本身没问题，缺的是「柚子用过哪些名字」的完整清单**——换号之前用旧账号名字写下的行在当前身份里匹配不上任何东西，排除法会把它们悄悄记到对端头上。所以规则按那份清单是否**被声明完整**分成两支，而声明不是第二个开关：配置 `chatlog/format.bot_names` 这个动作本身就是声明。声明了就用排除法（覆盖全部行），没声明就两侧都要正面证据（柚子侧查那张表，对端侧查当前昵称，都对不上就留空）。

同一份数据还量了第三种判据：**一个显示名出现在几个私聊窗口里**。前提成立（柚子当前昵称出现在 21 个窗口，对端天然只出现在自己那一个），但它不能当运行时规则用——阈值在做太多工作。全部 37727 行只有 32 个不同显示名，其中 27 个只出现在一个窗口；而出现在 **2** 个窗口的名字里有一个占了 14041 行，那显然是某个高频对端而不是柚子。阈值取 ≥2 会把 96.8% 的行判给柚子，取 ≥3 得到 18799/18928 的对半分——一条正确性悬在 2 和 3 之间、且边界紧挨着反例的规则，不该进解析器。

它作为**发现工具**很有用：≥3 那档只剩两个名字，一个是柚子当前昵称（21 个窗口 / 14072 行），另一个是 5 个窗口 / 4727 行的候选。把它确认下来填进 `bot_names`，排除法就有了它需要的完整清单。

同一个事实还修掉一处更早的问题：`post_type` 原本按 `sender_id == bot_id` 推导，换号之前的**群聊**行会因此被读成「收到的」而不是「发出的」。现在按历史账号集合判定。

补出来的身份进 `_guessed`，与 `_derived` 分开。它只服务于检索——启动重建只收 v1 记录，所以猜出来的发送者永远进不了内存或模型上下文。
- **`sender.role`（群主/管理员的历史值）。** 无消费者。
- **匿名消息的 `anonymous` 块。** `msgs.is_anonymous` 无调用者。
- **末尾换行与空白。** 正文末尾的换行和空白被清掉——这是**有意行为**，QQ 客户端本身也清。聊天消息末尾的空白几乎不存在有价值的情况，因此它不算保真缺口，而是格式的既定规则。正文内部的空行仍写作 4 个空格，保留。v0 只执行了半条规则，这是 22663 条正文不一致的全部来源，见上节。

## 解析规则

- 记录头在第 0 列，正文缩进 4 个空格；一条真正的空行表示空正文（`_addtab("")` 返回空串），正文内部的空行是 `"    "`。因此**正文里伪造的记录头也是缩进的**，不会被误读成新记录。
- 显示名可由用户自设（`identity.setname`），一个精心构造的名字能在头部里造出假的分隔符。因此**从右往左解析**：先取最右的 ` | `，再取它左边最右的 `(数字) HH:MM:SS`，剩下的整体是名字。这不需要新增 key。
- 时间推导假定写入与解析使用同一本地时区。设备换时区会平移历史时间戳；把完整 epoch 写进每一行正是本篇要避免的冗余，因此把这条记为**已知的推导假设**，而不是用一个字段消灭它。
- `group_upload` / `offline_file` 走的是 `_group_str` / `_private_str`（`mods/chatlog.py:199`、`:201`）但 `message_id` 为空——解析为「消息形状的 notice」，正文是文件描述，不是消息正文。
- `chatlog/bot/` 的兜底行（`mods/chatlog.py:278`）正文就是 `repr(dict)`，本身几乎无损。不必为它另设 sidecar。

## 正文改原始形式的连带影响

`unescape` 从写入侧移到显示侧，落点是三处，都是既有代码：

1. **`.search` 输出**：`mods/search.py:27` 已经在 `cq.escape` 之后发送，改成先 unescape 再 escape。
2. **终端回显**：`mods/bot.py:150` 与 `mods/message.py:58` 打印的是 `chatlog.write` 的返回值，改为打印显示投影。
3. **LLM 上下文**：不变。`msg2chat` 今天就吃原始串。

命令侧不受影响：`.py`、`.link`、`.hs` 等 13 处 `cq.unescape(body)` 读的是活事件而不是日志。

但**转义本身有一个必须先修的缺陷**：`cq.unescape`（`mods/cq.py:30`）按 `_inside` 的字典序替换，`&amp;` 排在最前，于是 `&amp;#91;` 先变成 `&#91;` 再被当成实体变成 `[`。`&amp;` 必须最后替换。`escape` 方向的顺序是对的（先 `&`），不用动。这个缺陷独立于本篇，但本篇依赖它修好——否则「原始形式」的解析侧仍然是坏的。

## 对 history 与 cache 的影响

`chatlog` 可解析之后，`data/cache_msgs` 就从**第二个写入权威**降级为**纯优化**：冷启动可以改由 chatlog 重建近期窗口，缓存文件保留或删除都只影响启动耗时。权威关系变成：chatlog 是事实，内存是投影。

范围查询用**同一个函数、显式的范围参数**，而不是「无感路由」：

- `getlog()` 无参 = 今天的行为，一次 dict 查找。`op.py`、`post.py`、`link` 和 `.py` 都在热路径上调它；让这个名字背后可能发生文件 IO 和 `OSError`，就是「常见功能不被罕见需求增加固定成本」的反面。
- `getlog(window, since=..., until=...)` = 跨进文件。签名让代价可见，不需要第二个概念。
- **别名语义要显式决定**：`getlog` 现在返回的是 `msgs[kind][uid]` 那个活列表本身（`mods/history.py:71`），`remove_message` 直接 pop 它，而 `mods/py.py:262` 把它暴露给了 `.py` 共享环境——现场代码可能持有引用。深范围查询只能返回新列表；浅路径是否也改成拷贝，要单独决定，不能顺手改。

范围查询是给 LLM 开只读工具的前提，但工具本身不在本篇范围内。

## search

`chatlog.search_current`（`mods/chatlog.py:22`）按行扫 `*.log`，纯 stdlib、无 shell，返回 `path:line:text`。实现不换，但它有一个**现存缺陷会被 parser 顺手修掉**：按行匹配时，命中正文行拿不到上面的发送者头，命中头行又拿不到正文。改成按记录搜索之后，结果与范围查询同形。search 是 parser 的消费者，不是第四件要统一的东西。

## 里程碑

1. ~~**修 `cq.unescape` 的替换顺序。**~~（已实施）`mods/text.py` 的 `replace_by_dic2` 改为倒序遍历——这正是「撤销 `replace_by_dic`」的定义，`&amp;` 因此最后还原。`escape` 方向不变。实测 `unescape(escape(x)) == x` 对字面文本全部成立，包括先前会塌成 `[` 的 `&#91;`。
2. **纵向切片：`format_message` 与 `parse_log` 两个纯函数**（已实施；差分已跑过一轮，分类待复跑）。`mods/chatlog.py` 末尾新增，`write()` 一行未动，因此运行行为不变。合成往返 68/68 精确，覆盖伪造记录头的正文、字面 CQ 文本、`&amp;#91;`、内部空行、空正文、相邻空正文记录和末尾空行；v0 行可读且如实标注缺口。真实数据的结果见下节。
3. ~~**切到 v1 写入**~~（已实施）：`_message` 改为唯一走 `format_message`，私聊行补 id，正文存原始形式；`chatlog.display()` 承担显示投影，终端回显与 `.search` 都经过它，`.search` 因此仍按用户看到的文本匹配。`on_load` 把切换时刻记进 `storage` 的 `chatlog/format`——只有这一刻知道分界线在哪，事后无法恢复。差分：群聊终端回显 8/8 与切换前逐字相同（末尾空白除外，那正是规则）；文件字节只在正文含 `&`/`[`/`]` 时改变。
4. ~~**窗口键**~~（已实施）：`history.window(event)` 成为窗口的唯一推导，`getlog`、`remove_message` 和 `chatlog._message` 都用它，顺带修掉 `group_id` 存在但为 `None` 时旧的 `"group_id" in msg` 会崩的边角。`context.interaction_key` 的 docstring 补上与它的对照，两者不合并。

   同一步把 `is_self` 改名 `same_author` 并改按 `sender` 判定作者：`user_id` 在私聊里是窗口对端而不是发送者，Bot 自己的消息也带对端 id，因此私聊窗口里两者无法区分。**用户可见的变化只有一处**：私聊里 `.cave addn -<n>` 之前会把柚子的回复合并进回声洞、并漏掉最早的一条，现在只收发起者自己的消息；群聊逐字不变。

   这个缺陷不是迁移引入的。迁移前 `_code/main.py` 的发送路径（私聊 `self_msg['user_id'] = user_id`）、`_code/bot/cache.py` 的 `IsSelf`（`m['user_id'] == msg['user_id']`）和 `_code/bot/cmds/cave.py` 的 `addn` 与现在逐字同构，所以私聊的 `.cave addn -<n>` 一直是坏的；`.cave add` 与 `.cave addn <正数>` 不走这条路径，始终正常。
5. ~~**范围查询**~~（已实施）：`getlog(msg, since=..., until=...)` 加两个仅关键字参数，两者都为 `None` 时逐字保持今天的行为（一次 dict 查找，返回活列表）；给了任一边界就转由 `chatlog.read_range` 读文件，返回**新列表**，每条带 `_source`/`_derived`/`_missing`。第一个参数现在也接受 `window()` 的键。

   **不做合并，因为不需要合并**：`chatlog` 的三个 `_write` 都是先 `_append` 再 `history.add_msg`，所以进过内存的事件必然已经落盘，文件是内存的超集。这正是提案里那句「chatlog 是事实，内存是投影」的可执行形式——范围查询只读文件，没有边界秒、没有去重、没有两种保真度混在一张表里。

   由此产生两处与 `getlog()` 的固有差异，写进 docstring 而不是抹平：被撤回的消息仍在结果里（目录只追加，撤回是另一条 notice 行），notice 仍是中文散文。

   顺序是**追加顺序的倒序，而不是按 `time` 排序**：日志的含义是「这条写在那条之后」，而没有时间戳的遗留行在排序里没有位置、在倒序里有。设了任一边界时这些无时间的记录会被丢掉——时间范围回答不了它们；两边都不设时则不施加任何过滤，它们保留。

   版本提示按**整个日文件**给：该日完全在切换点之后为 v1，完全之前为 v0，跨越切换点的那一天不给提示。跨越日里私聊行仍自报，群聊行按 v0 读——少认保真度，且只影响切换发生的那一天。

   **浅路径的别名语义没有动**：`getlog()` 仍返回 `msgs[kind][uid]` 本身，`remove_message` 仍 pop 它，`.py` 仍拿到它。深路径天然是新列表，所以这一步没有被迫做出选择；是否把浅路径也改成拷贝仍未决，见下。
6. ~~**`cache_msgs` 删除**~~（已实施）。实测判据：从 chatlog 倒着读日文件重建 68 个窗口共 7066 条要 **0.35s**（单窗口 p50 1.1ms / p95 12.8ms / max 22ms，读了 594 个日文件），而 `literal_eval` 那个 3.0MB 的 `cache_msgs` 要 **1015ms** 且只覆盖 20 个窗口。重建比它保留还快，所以「留作纯优化」这个选项没有立足点，直接删。

   `history` 因此变回纯内存：`on_load`/`on_exit`、`CACHE_FILE`、`_valid` 全部移除，第二个写入权威消失。重建放在 `chatlog.on_load`（它在 `history` 和 `identity` 之后加载，那时 `bot_id()` 才可用），`history` 只多导出一个 `lock()` 上下文管理器供它直接写 `msgs`。

   **只重建 v1 的消息记录**，这是这一步唯一需要品味的地方。三类东西被挡在内存之外，因为它们进去就是静默的错误内容：

   | 挡掉 | 进内存会怎样 |
   |---|---|
   | v0 私聊记录 | 没有 `sender`，`chat.msg2chat` 会把柚子自己过去说的话当成对方说的 |
   | v0 正文 | 是 unescape 过的投影而不是原始串，喂给 LLM 与实时消息不同形 |
   | 已被撤回的消息 | 撤回的意思就是它不该再被看见 |
   | 除戳一戳外的 notice | 重建不成事件，没有消费者能读 |

   代价是**刚上线时重建不出东西**，随 v1 的天数累积自然长满——降级是渐进的、自愈的，而且启动日志会打出「重建 N 个窗口 M 条」，不是静默的。切换时刻同时用来收敛遍历：倒着走到第一个完全早于切换点的日文件就停，不会走进几年的存档。

   **撤回的消息不会回到内存。** 倒着走意味着撤回通知总在它撤掉的那条消息之前被读到，一趟就够。这只作用于重建：`read_range` 仍然返回它们，因为档案对「发生过什么」的回答本就包含后来被收回的东西。

   **戳一戳也重建**，它没有 v0/v1 的缺口，因此不受切换点约束——理由见上面「明确不恢复的东西」那节。

   `data/cache_msgs` 本身不由代码删除，留给维护者手动清理。
7. **search 改为按记录返回**，随后才谈是否给 LLM 开只读工具。

第 2 步的差分结果可能推翻第 3 步的具体形状；在拿到那份数据之前不要写第 3 步。

## 真实数据（第 2 步差分，270 万条记录）

| 指标 | 值 | 读法 |
|---|---|---|
| 文件 | 8408（群 6551 / 私聊 1367 / bot 490） | |
| 记录 | 2763699（消息 2711286 / notice 50576 / bot 1754 / 未解析 83） | 未解析占 0.003% |
| 正文往返 | 2682877 / 2711286 | 不一致 28409，占 1.05%，成因见下 |
| `missing: sender` | 37669 | 就是历史上全部私聊消息，占 1.4% |
| `missing: message_id` | 2460 | 借用消息形状的文件上传通知，占 0.09% |
| 含 CQ 码的正文 | 859843 | 占 31.7%，v0 全部无法判定真伪 |

三条结论：

- **格式的假设站得住。** 270 万条里只有 83 行解析不出来，缩进规则对真实内容成立。
- **v0 的缺口有确切大小。** 不可恢复的发送者身份是 1.4% 的记录（全部私聊），不是一个模糊的「有些」。
- **正文歧义是三分之一而不是边角。** 31.7% 的历史消息含 CQ 码，v0 无法区分真码与字面文本；其中 15204 条含有解析不成合法 CQ 码的片段，也就是确凿的字面文本。这条独自证明 v1 存原始形式是对的。

### 22663 条不一致的成因

不是解析错误，是 `_addtab` 不是单射：它把 `"a"` 和 `"a\n"` 渲染成同一个 `"    a"`，又把正文末尾的空行渲染成一个 `"    "` 行——而按末尾空白的规则，那一行本就不该存在。v0 因此只执行了半条规则：丢掉最后一个换行，却把更早的末尾空行留成了 4 个空格。

修法是把规则执行完整：`format_message` 写入前 `rstrip()`，`_deltab` 解析后 `rstrip()`。两者因此严格互逆，而一条末尾带空行的 v0 正文会解析成 v1 本该存下的同一条消息——按规则那就是同一条消息。合成用例已覆盖。

分类复跑之后（`_deltab` 补上 `rstrip` 使总数升到 28409）：

| 成因 | 条数 | 判断 |
|---|---|---|
| 正文末尾是空行 | 22619 | 规则。v0 把它写成了一个 `"    "` 行 |
| 正文末尾是空格或制表符 | 5685 | 规则。v0 原样保留了它们 |
| 正文内部有真正的空行（`""` 而非 `"    "`） | 105 | 遗留格式；解析结果仍是正确的消息，只是字节无法重现 |

前两类合计 99.6%，是规则本身而不是解析错误——已用逐形状的复现确认哪种正文落进哪个桶。**第 3 步的格式因此不用改。**

另外三项：

- **私聊误判 id 为 0。** 历史上没有任何私聊显示名以 `(数字)` 结尾，私聊行的版本自判在真实数据上没有假阳性；`version` 提示是冗余保险而不是必需品。
- **83 条未解析行全部没有时间戳**（49 条短于 40 字符，3 条带 `【`）。占 0.003%，形状上不像被截断的正常记录，更像更早期格式的遗留。按遗留处理，不为它们改 parser。
- **`missing: sender` 是 37669，而私聊消息是 37667**：多出来的 2 条是没有发送者 id 的**群聊**行。同属遗留异常，与上面的 105 和 83 合计 190 条（0.007%）。
- **15204 条正文里含有解析不成合法 CQ 码的 `[CQ:...]` 片段**，因此必定是字面文本。这是历史上确实存在字面 CQ 文本的硬证据，把 v1 存原始形式从推理变成了事实。

落地时定下的两处细节，提案原文没有写：

- **版本不能从群聊行判断**。私聊行会自报（只有 v1 带发送者 id），群聊行两版同形。因此 `parse_log` 收一个 `version` 提示，没有提示时按 v0 处理——那是正文只算投影的那一版，少认保真度是安全的方向。提示同时消掉私聊唯一的误判：v0 显示名恰好以 `(12345)` 结尾。
- **`【头衔】名字` 按最右的 `】` 切分**，与整体的从右往左一致。头衔和名字都只是推导值（填进 `sender`，不作身份权威），切错不影响结构。

## 未决

- **窗口键的具体拼写**（`("group", id)` 元组，还是一个 `str` 前缀）。等第 4 步实际动手时再定，先定形状没有收益。
- ~~**重建事件是否进入 `history.msgs` 内存**~~：第 5 步定为否，只作为查询结果返回。写入内存会让 `getlog()` 的返回值混入非事实字段，而那个列表正被现场代码持有引用。
- **浅路径 `getlog()` 是否也改成返回拷贝。** 第 5 步没有顺手改：`remove_message` 依赖 pop 那个活列表，`mods/py.py:262` 把它交给 `.py` 共享环境，现场代码可能已经持有引用。改成拷贝会让 `.py` 里既有的原地写法静默失效，收益只是防御性的，因此单独决定。
- **`chatlog/bot/` 的定位**：它现在混着好友请求、`friend_add` 和兜底 `repr`。它是不是第四种窗口，还是「没有窗口的事件」的堆放处，本篇不决定。
- **第 3 步之后终端回显的确切样子**：显示投影和文件内容首次不同，需要维护者看过真实输出再确认。
- **切换前的私聊戳一戳能否恢复方向。** v0 私聊发送者补齐的通知侧。旧行只有名字，可以对着两个候选各渲染一次再比对——不是解析句子，是**重新渲染后比对**，不匹配就跳过。没做，因为重建有切换点作下限，走不到那些日子。
- **notice 的其余家族是否结构化**。答案仍是「现在不做，且不预留接口」。禁言时长、名片、进退群靠措辞区分，反解会静默失效，而且没有消费者——有消费者的两类已经在第 6 步单独处理了。

## 边界

- `chatlog/` 是设备本地的真实聊天记录。差分脚本、解析样本和失败行都不得复制进文档、提交或对外回复。
- 本篇不改变任何用户可见的命令语法。`.search` 的输出在第 7 步之前逐字不变。
