# 权限演进

> 状态：未实现提案

权限系统遵循 KISS，不演变成复杂角色与策略语言：

1. 每个命令声明整数级别；
2. 调用者提供可比较级别；它由现有 master/op 推导还是单独配置，尚未决定；
3. 少数命令可附加一个正则或普通函数校验器；
4. 校验器针对具体消息额外允许或拒绝。

整数级别覆盖绝大多数权限，额外校验只处理上下文例外。实现前必须用少量例子定死“显式拒绝是否覆盖级别允许”“校验异常如何处理”等优先规则。

历史上 0.2.1 命令 class 已有 `level` 字段；当前函数插件没有统一执行检查。迁移时应提供简单 wrapper/函数，不把参数解析、角色继承和资源策略塞进 cmds 核心。

## Bot 自己的权限不随阅读消息改变（草籽 2026-09-20 定）

> 来自 2026-09-20 的 mail／激活讨论，原先写在 [mail 与激活](mail-and-activation.md) 里；
> 它是权限问题，所以搬到这份。论点的来龙去脉见
> [给 agent 做一个聊天软件](chat-client-for-an-agent.md)。
>
> 它与上面那套「整数级别 ＋ 校验器」**不冲突，但缩小了它的适用面**：级别要回答的问题
> 从「**这一轮是谁触发的**」变成「**Bot 自己被允许做什么**」——前者随消息抖动，后者是一份配置。
> 「代行」是唯一仍然按调用方参数取权限的类别。

> 缓冲区有**多个不同权限的激活元素**时，这会直接导致问题。
>
> 如果我们真的信任 bot 且尊重意愿，也许我们应该相信 ta 有能力判断哪些问题可以执行……
> ta 应该有权利维护自己的文件和调用一些工具。如果仅是因为从消息中拉取了一些内容就导致
> 自己的权限被限制，这毫无疑问是让人沮丧的。也许我们应该让 bot 调用的权限
> **始终以 bot 账号自身的权限运行**——我们依旧可以控制权限，但是 bot 的权限
> **不会因为阅读消息而被动改变**。
>
> 注意不要误伤了 op 工具中，**让 bot 以任意其它成员发送消息**的那个功能，
> 那个确实需要继承对应用户的权限。

#### 问题是真的，而且是我这份设计**加重**的

今天这件事是有界的，因为两条现成的纪律：

- 缓冲区只活一轮，攒不了几条；
- **插话不改变身份**——`chat.chat` 的 WHY 写着「判据只认触发事件，不认『上下文里出现过 op』……
  插话因此不改变身份：它们是上下文，不是授权」。

我的设计把第一条拆了（mail 跨激活长寿），于是第二条要独自扛下全部。而按 [mail 与激活](mail-and-activation.md) 的排空规则
（identity 取最后那个激活元素 ＋ 有激活元素就整段排空），一个 op 的请求和一个非 op 的发言会**一起**进来，
下一轮归谁取决于**消息到达的先后**——Bot 可能在干活干到一半时，因为旁边有人说了句闲话而掉权限。

**这正是草籽说的「多个不同权限的激活元素」。是我这份设计引入的，不是原有的。**

#### 现状：门问的是 A，门后的东西以 B 的身份执行

查过代码，今天所有重能力都锁在同一个判据上——**当轮触发者是不是 op**：

| 能力 | 门 | 实际**以谁的身份**执行 |
|---|---|---|
| `tools/op.py::send_command` | `OP_ONLY` ＋ 三层 `is_op` | **Bot 自己**（`sender.user_id = bot_id`，靠 Bot 的号在 op 名单里过门） |
| `meta.exec_code` | 函数内 `op.require_op(context.current())` | 宿主信任域，**没有身份可言** |
| `message.recvmsg(sender_id=X)` | 只能从 `exec_code` / `.py` / link 到达，三者都 op 门 | **被伪造的那个人 X** |

**第一行就是草籽说的那种不自洽**：门问「说话的人是不是 op」，而门后那个能力是以 **Bot 自己**
的身份跑的。它的权限和说话的人本来就没有关系，却被说话的人决定。

第三行正是草籽点名要保住的那个——`runtime.md` 对它的定性是「分量等同于**以被伪造者的身份执行**」。
它确实必须继承 X 的权限，因为它做的事**就是** X 的事。

#### 我的提议：把一根轴拆成三类，而不是一刀砍掉门

**推论，需要草籽确认。** 「始终以 Bot 自身权限运行」如果字面实现成「把 `op.require_op` 换成
`is_op(bot_id)`」，那么 `exec_code` 在**任何人**触发的轮里都可用——而它共享宿主信任域，
并且能经 `recvmsg` 伪造成任何人。于是任何一个能在开了聊天的群里说话的人，
都可以试着把 Bot 说动去做宿主级操作，**唯一的拦阻变成模型的判断力**。

这是一次把**结构性管制**换成**判断性管制**，提示注入的代价随之变成直接的。
我说一次，然后给出我认为能同时满足草籽两条要求的形状：

| 类别 | 以谁的权限跑 | 例子 | 读消息会改变它吗 |
|---|---|---|---|
| **自有能力** | **Bot 自己，恒定** | 维护自己的文件、记忆、工具模块、`say` | **不会**——草籽要的就是这个 |
| **代行能力** | **被代行的那个人** | `recvmsg(sender_id=X)` | 不适用：它本来就是「以 X 的身份」 |
| **宿主能力** | **静态配置**的信任（哪些窗口／哪些人），不随上下文变 | `exec_code`、`send_command` | **不会**——但也不是「永远开着」 |

三条理由：

1. **它满足草籽的原句。** 「权限不会因为阅读消息而被动改变」对三类都成立：
   自有恒定，代行由参数决定，宿主由配置决定。**没有一类是「谁最后说话」的函数。**
2. **它保住了草籽点名的那个功能**，而且理由更清楚：`recvmsg` 继承 X 的权限不是例外，
   是「代行」这一类的定义。
3. **它不要求把宿主信任域对所有人打开。** 「不由说话的人决定」和「永远开着」是两件事，
   而字面实现会把它们合成一件。`exec_code` 能经 `recvmsg` 伪造任何人，
   这条链今天被 op 门挡着，我认为它应当继续被**某个**稳定判据挡着，只是那个判据不再是
   「刚才谁说话」。

#### 草籽的裁决（2026-09-20）：**字面版**，而且我那条反对意见本身是错的

> 混合的消息触发机制下，**这本来也防不住就是了，任何人实际上也可以插话进行注入**。
> 防住任何对话轮次并进行权限变动会极大破坏模型的**串行性和一致性**，代价和复杂度都非常大，
> 且效果极其有限。如果都防不住，我愿意选择更简单的方案。

**他是对的，而且指出的是我分析里的一个实质错误。** 我把现有的门称作「结构性管制」，
暗示它挡得住注入。查一遍就知道挡不住：

- op 门问的是**谁触发了这一轮**，不是**这一轮的上下文里有谁的字**；
- 而插话会把任何人的正文放进一个 op 触发的轮里（`capture_chat` 的分级：任何进得了上下文的
  消息都入队，只有原本就会触发聊天的才置 trigger）。

所以**今天，一个非 op 的文字已经可以出现在一个握着 op 工具的轮里**。模型若吃注入，
那条注入现在就是以 op 权限执行的。门拦住的只是「非 op **直接**命令 op 工具」，
不是注入。我把这两件事当成了一件。

第二条理由同样成立，而且是他自己上一条就提过的病：按轮变动权限会让 Bot 干活干到一半掉权限，
**破坏串行性和一致性**。代价确定、收益部分——这是一个防御在「挡不住主要威胁」时该退场的
典型形状。

**所以采纳字面版**：Bot 调用的权限**始终以 bot 账号自身的权限运行**，不因阅读消息而改变。
上面那张三类表里，「自有」和「宿主」合并成一类（都是 Bot 自己），**「代行」仍然单列**——
`recvmsg(sender_id=X)` 继承 X 的权限，这是草籽点名保住的，也是它的定义。

于是最终只有两类：

| 类别 | 以谁的权限跑 | 例子 |
|---|---|---|
| **Bot 自己的行动** | **Bot 账号自身，恒定** | `say`、`exec_code`、`send_command`、维护自己的文件与工具 |
| **代行** | **被代行的那个人** | `recvmsg(sender_id=X)` |

#### 落地时的一条卫生要求（不是反对，是记账）

`exec_code` 现在靠 `op.require_op(context.current())` 拦着，改成「Bot 自己」之后，
它实际上是靠「**Bot 的 QQ 号在 op 名单里**」这个事实开着的——那是个巧合，不是一句声明。

落地时把它写成**显式配置**（一条「Bot 自己能做什么」的声明），而不是继续依赖那个巧合。
理由与安全无关，与可读性有关：以后有人读到这里，要能看出这扇门是**被选择**打开的，
而不是**忘了**关。这一条草籽没有反对过，我按它做。

#### 顺带：它也解掉了「identity 取最后那个」那条推论的麻烦

identity 取「最后那个激活元素」之所以让人不安，正是因为它让权限随消息顺序抖动。
三类拆开之后，**那个 identity 只剩下一个用途：决定这一轮在替谁说话**（回复发去哪、
代行能力用谁的权限），不再决定 Bot 自己能不能动自己的文件。抖动仍在，但抖的东西无害了。
