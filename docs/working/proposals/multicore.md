# 多项目共存设计

> 状态：独立设计提案，尚未实现

这里的“核”不是同一项目里的模块、进程角色或微服务，而是一个完整、独立的 Bot 实现。第二核可以是另一个仓库、另一种语言对现有能力的重写，也可以采用完全不同的架构和功能哲学；它与当前 Python 项目没有共享内部接口的义务。NapCat 天然允许多个 Bot 后端同时接入同一 QQ 账号，因此它们只在用户可见的日志、响应和宿主机维护层面需要避免相互妨碍。

## 设计目标与边界

- 任一项目退出不影响另一个项目继续通过 NapCat 接收事件和调用 OneBot API。
- 两边都可以记录同一聊天，不强制只有一个日志拥有者。
- 显式命令不会因前缀重叠而重复执行。
- 自然语言和主动反应只有实际功能重叠时才需要协调。
- 管理员可以按聊天独立开关某个 Bot 项目的日志和响应。
- 两个项目可以在人工命令下修改、停止和重新启动对方，不引入自动健康检查、选主或故障转移协议。
- 两个项目都失败时仍需进入宿主机维护；多核不承诺消除最后一个故障边界。

## 独立进程，不共享运行时

Python 与 TypeScript 只是例子；两个实现应是独立项目和独立进程，分别拥有：

- 代码目录和依赖环境；
- OneBot 入站端口；
- 自己选择的内部架构、领域模型、内存状态和发送策略；
- application log；
- 自己的数据格式和持久化文件。

NapCat 直接把事件提供给多个 Bot 后端，两边也分别调用 NapCat API；不增加 fan-out、事件代理或共享消息总线。任何一边都不是另一边的协议入口，因此重写版可以自由改变内部消息模型，只需在 OneBot 边界正确处理同一外部数据。

不同项目之间不共享可变内存，也不应同时覆盖同一 storage JSON。每个项目自行保存日志/响应开关和功能配置；对方的工作目录、启动命令、PID/锁位置等只是本机维护配置，不构成跨项目 API。

## 日志和响应是两个独立开关

每个项目、每个聊天窗口分别保存：

```text
log_enabled: bool
respond_enabled: bool
```

这里两个布尔值比四项模式枚举更直接，因为四种组合都合法，而且管理员经常只想改变其中一个维度：

- 关闭日志不应顺带使核心沉默；
- 关闭响应不应妨碍它继续积累自己的聊天上下文；
- 两者都开启时正常参与；
- 两者都关闭时完全忽略普通事件。

`log_enabled` 只控制该项目自己的 chatlog，不关闭 application warning/error；`respond_enabled` 只控制该项目的普通命令、自然反应和主动回复。用于查询状态、重新开启响应、重启另一项目等最小管理命令属于 control plane，即使当前窗口 `respond_enabled=false` 也必须能处理并给 op 回执，否则关闭后无法从聊天恢复。

新加入的第二核心应默认 `log_enabled=true`、`respond_enabled=false`：先观察真实事件和日志，再由 op 在测试窗口显式开启响应。Python 现有 `-l` 大致表达全局“记录但不响应”；`nolog_groups` 试图表达“响应但不记录”，只是当前实现错误地比较整个消息 dict 与群号列表。多核开关应把这两个方向提升成明确的窗口级设置。

两个项目都记录同一事件本身没有语义冲突，它们自然写入各自项目的 chatlog 即可。需要查看完整历史时由搜索工具同时读取；以后若需要单一视图，可按 OneBot `message_id` 派生合并结果，而不是要求两个不同架构共同实现一次 append 协议。

## 响应冲突按实际功能解决

不必先回答“这个窗口归哪个核心”。真正会冲突的是具体响应能力：

1. **显式命令**：两个项目使用不相交前缀，各自只识别自己的命令。管理前缀必须始终保留。
2. **自然语言/link/notice**：若两边功能不同，可以同时开启响应；没有重叠就没有仲裁问题。
3. **重叠功能**：例如两边都提供 LLM 聊天或相同骰子反应，优先在其中一个项目里关闭该窗口对应的反应；若某个项目没有细粒度开关，再关闭它在该窗口的整体响应。

因此，项目级 `respond_enabled` 是总开关；更细的功能开关完全由各项目按自己的架构实现。当前 Python 项目可以按纵向 feature/link 反应族控制，TypeScript 或其它重写不需要模仿这套模型。两边不建立共享的 feature 名表、handler 注册表、响应投票或中央 arbiter。

如果以后确实出现无法靠前缀和 feature 开关消除的冲突，再用实际案例决定是否需要更细的 reaction ID。不要预先要求两个项目为每条消息协商“谁可以说话”；那会让任一项目依赖另一项目在线。

如果某种 NapCat 配置会把 Bot 自身发出的事件再次投递给后端，各项目都应在自己的边界识别 `self_id`，避免把另一实现的回复当作新的用户触发；chatlog 仍可按各自设置记录。

## 相互修改与重启

多核最独特的恢复能力来自交叉维护，而不是自动拉起：

- Python 项目保留修改另一项目代码、查看其错误和执行其启动/停止命令的管理员入口；
- 另一项目对 Python 提供对称能力，不要求使用同一种语言或命令实现；
- 操作只由 op 显式触发，不自动检测故障后反复重启；
- 每个项目继续保留自己的 `.reboot`/等价命令。

交叉重启不要求一个项目成为另一个项目的父进程。每个部署只需给出对方的工作目录、启动命令和进程身份。目标项目使用 PID 文件、OS 文件锁、独占控制端口或等价的单实例机制，防止两边同时执行启动命令产生重复进程。优先请求目标优雅退出；目标已经失联时，op 才显式选择强制停止后重新启动。

两个项目处于同一 master/op 信任域，能够修改对方代码等价于能够控制宿主机。这不新增权限等级，但跨项目命令必须沿用各自严格的 op 校验，并在 application log 中记录操作者、目标项目和结果，不复制聊天正文。

这种设计把恢复决策留给在线的人：Python 坏了时从另一个实现修改并重启，另一实现坏了时反过来。它没有崩溃计数、自动回滚、leader election 或相互 watchdog，因此比复杂自启动更容易理解；代价是两个项目同时损坏时不能自救，这是明确接受的边界。

## 最小控制面

具体前缀尚未决定，但每个项目至少需要下列等价能力：

```text
<core-prefix> status
<core-prefix> log on|off|status
<core-prefix> respond on|off|status
<core-prefix> feature <name> on|off|status  # 若该项目支持细粒度功能开关
<core-prefix> peer status|start|stop|reboot
```

控制命令修改的是“当前聊天窗口”，除非 op 显式指定其它群/用户。`status` 至少显示项目/实现 ID、版本或启动时间、日志与响应开关、最近 incident，以及另一项目是否可见；内部 feature 状态只在该项目本身存在这个概念时显示。

## 推荐引入顺序

1. 修复 Python 当前的 `nolog_groups` 判断，并把 log/respond 变成真正独立的窗口设置；
2. 给 Python 项目增加始终可用的管理前缀和状态命令；
3. 启动第二核心，但默认只记录、不响应；
4. 验证 NapCat 多后端投递、自身消息循环和两个独立 chatlog；
5. 开启第二核心的一个独有显式命令；
6. 再逐项启用自然反应，并为真实重叠 feature 选择一边关闭；
7. 最后加入人工触发的交叉查看、编辑和重启能力。

最低验收场景是：两个独立项目收到同一事件并分别记日志；关闭任一项目响应不影响另一个；关闭响应后仍能用管理命令重新开启；不同前缀只得到一个回复；一个项目退出后，另一个仍能查看其 incident、修改文件并显式重启，而且单实例约束阻止重复进程。
