# 聊天消息递归压缩：历史方案与演进记录

> **历史归档，非现行规范或实施顺序。** 本文原样保留早期 `condense_ops` 方案、当时的取舍、后续订正和已失效的 `WHY` 清单；文中的「已拍定」「落地顺序」仅表示写作当时，不得直接据此实施。当前压缩状态与目标从[压缩与反查状态索引](chat-condense.md)进入，运行行为以[模型与工具](../../llm.md)为准。
> 当前事实以[运行架构](../../architecture.md)、[交互模型](../../interaction-model.md)和[模型与工具](../../llm.md)为准。
> 北极星语义见[可自维护的同相上下文](self-maintaining-context.md)；那篇不选具体机制，本篇是其中一条具体机制，两者不互相断言。
> 标注「草籽定」的条目是设计者本人的判断，不是从代码推出来的。

## 一句话

`condense_ops` / `recall_ops` 今天让模型把得出结论的工具调用移出上下文、按 cid 取回。本篇把同一套延伸到聊天消息上：模型点名一组消息和自己的发言，附一段结论，这组东西离开上下文，留下一个**节点**；节点自己是一次工具调用，因此可以被再次压缩，层级由此长出来。

## 先排除四种相邻方案

这里保留原方案的取舍来历，不得当成统一 id／同一信息流已经接受的存储前提。

- **不用时间区间做嵌套轴**（草籽否决）。要嵌套的从来不是集合，是节点——节点自带 cid，于是它规约进现有的工具压缩链。随之作废的还有「索引对每一个时刻都有覆盖、没有洞」这条不变量。
- **旧方案不建独立的覆盖 overlay 存储。** 当时打算把覆盖关系放在 oplog 节点的 `arguments` 里；不制造重复可写权威是应保留的理由，具体落点并未由新方向拍定。
- **旧方案不给 chatlog 加 id 列、不动行格式。** 当时依据[统一消息模型](message-model.md)的 V0/V1 迁移代价作此选择；统一 id 方向不能再以这条旧存储选择为前提。
- **不做按大小自动压缩。** 理由与 `llm.Chat.chat` 里那条一字不差：按大小砍会在结论产出之前砍掉前提。当前 hint 只报告占比，何时及如何总结由模型决定。

## 问题：两条线，别混

这是提出此篇时按现有来源区分的上下文／磁盘寿命模型。聊天档案不删等已定承诺仍在；但统一 id 与输出／输入同一信息流之后，不能直接按现有文件或 API 角色决定新记录怎么分、怎么退休：

| | 上下文 | 磁盘 |
|---|---|---|
| **聊天消息** | 可约（被节点替掉） | **永不删，无界增长，且是刻意的** |
| **工具调用** | 可约（同上） | 按高度退休（见第 3 条） |

- **上下文压力不在考虑范围内**，相信压缩能保持住它。所以「上下文会不会被占满」不是本篇要解决的问题。
- **要解决的是磁盘**，而索引本身解决不了磁盘——解决它的是高度限制，而高度只有在有了树之后才定义得出来。**索引让上下文可约；高度限制让磁盘可约；后者靠前者提供的度量。**
- **压缩 ≠ 遗忘。** 早期的原文被一个节点替掉，那是压缩，是基础原语，发生在上下文那一列。遗忘是磁盘概念，只对工具调用生效。这两件事在早先几版里被混为一谈过。

上下文那一侧的收益仍然真实，只是不构成「问题」：滑窗满了之后每来一条新消息就挤掉最老一条，前缀从第 0 个 token 起全变，所以压缩真正换到的是**把「每条一次全量失效」摊成「每段一次失效」**。判据是回本轮数而不是压缩率——不压缩的那份也命中缓存，折价倍数（`deepseek-flash` 是 `prompt_price: 2` 比 `prompt_cached_price: 0.04`）只在收缩当轮起作用，所以**压缩要稀少且大块**。

## 已拍定

### 1. 单位是节点，不是区间

第一层：一次工具调用压普通消息，产出一个节点。第二层及以上：`condense_ops` 把节点当普通工具调用压，机制原样复用。同一条消息被压进两个节点**不打算防**（草籽定）——在「显式枚举」的表示下那只是两个固定集合有交集，无害。

**2026-09-23 重新审视中：**这里否决的是「拿时间区间当嵌套轴／覆盖的长期权威」，不必然否决「用 A 到 B 作为一次操作的选择入口」。若选择范围入口，执行时必须按一次确定的上下文快照解析并保存成员；范围端点本身不能取代每个可反查成员的身份。范围是否作为入口、如何处理范围外的强绑定成员，均尚未裁决。

**2026-09-24 新方向：**草籽希望总结和反查能围绕一个统一事件号取前后若干已读事件，或按两个统一事件号选已读区间，以免模型逐项穷举；还可在选定范围内指定过滤函数，分别查询自身行动、聊天输入等。过滤不重排信息流，当前实施推论是先按原流确定边界，再过滤。选择入口不改变节点形状：一次有效覆盖仍冻结实际成员和 `say`／回声等强绑定闭包，不能让区间随之后的新事件漂移。半径按原流事件条数而非正式号的数值差；大段反查仍须分页。原始聊天的档案位置只用于翻阅来源记录，不是与统一事件号并列的第二套记忆身份；旧消息直到模型读到才获正式号。**系统只有经历的顺序：重放 A→B 是排在当前事件之后的新阅读返回，正文内部按 A→B 呈现，各次返回按实际读到的顺序取得新号；旧事件不改号。** 随后用节点精确覆盖先前乱序且与重放重复的探索，留下重放的内容和对先前探索的可反查节点引用，当前视图自然呈现「聊天先发生，柚子再探索」。更长的回忆可分段重放，在适当片段之间把整理、探索本身写成节点，再接着读；这仍是新的经历顺序，不是给旧事件插队。不必为聊天另建索引，也不必给统一号查询排序；恢复已有上下文不重新编号，主动重读才有新输入。具体工具参数仍待实施切片确定；完整例子见[中心化聊天软件阅读计划](chat-client-reading.md)。

**2026-09-25 草籽裁决：**全局半径和区间不默认按窗口过滤；按窗口查看只是可选过滤。跨两个群的同一次探索可以折为一个节点，反查可以跨窗口，同一事件也允许多次覆盖。当前 `cover_events`、`recall_events` 与文本引用索引仍按单窗口校验，这是现行逐窗口执行路径的限制，不是中心化主体要继承的规则；跨窗口节点仍须显式冻结实际成员、保留各成员来源，不得吞掉区间中无关的行动。

### 2. 覆盖的表示

原设想中，一层节点的 `arguments` 是 `{cids: [...], message_ids: [...], conclusion: "..."}`——字面上就是一条 `condense_ops` 加一个字段；统一 id 方向**不再以这组字段或两套来源分类为前提**。

- `message_ids`：模型可见且有有效 `message_id` 的 QQ 消息，模型从 `<metadata>` 里点名，零新增渲染成本；旧档案可能缺号，不能猜一个号代替。**原提案只写「用户消息」，但阶段 2b 已把 Bot 回声也投影成带 `message_id` 的 `user` 消息。**注入的合成消息用 `-time.time_ns()`，id 可能为负，任何处理不得假设为正。非 `say` 的 Bot 回声是否一并允许点名，见 B+H 闸门。
- `cids`：工具调用，其中 Bot 自己通过 `say` 发言的动作有 cid。**单收 `say` 的 cid 并不会让那条消息的窗口回声离开上下文**：回声是独立的 QQ 消息，也必须被同一次有效覆盖收掉。原方案让模型同时点名回声的 `message_id`，但这不足以系统保证强绑定，见下方新约束。

**2026-09-23 新约束、方案待定：**草籽要求可进入模型历史的内容都应有可总结、可反查的身份，不接受「戳一戳及缺号记录只好被预算滑窗遗忘」作为最终方案。原来的 `{cids, message_ids}` 枚举不足以给无号事件寻址；QQ 的 `message_id`、本地可持久的记录身份与跨类型的范围端点是三个不同问题，不应给戳伪造 QQ 消息号。`say` 与**已确认的**对应回声在压缩语义上必须强绑定；当前模型自行同时点两个号码的方案无法系统保证这点。两者可继续分别存动作与窗口事实，但需要可靠关联、选取闭包和重建后不漂移；未确认发送不能靠相邻时间或相同正文猜配。

**草籽进一步明确（2026-09-23）：**对所有进入上下文且可能无限增长的内容，必须选择「轮间丢弃」或「可索引」，不能因为缺 id 就悄悄随滑窗遗忘。此前暂定轮间只留必要的交互痕迹、丢弃思考和自言自语；但纯文本调用也可能是 assistant 正文，不能再用 API 字段或是否发往 QQ 判定是否丢弃。值得保留的输出与输入应共用**本地、按天递增的记录 id**，形如 `20260923-234`，不是工具沿旧 cid、消息另外补号；QQ `message_id` 另用于回复／撤回。无论先压晚段还是后压早段，不能引入「最后总结到哪」的高水位或改写已有 id。若用「从 A 到 B」点名，应在当轮看到的确定快照里展开成员、连同 `say` 的强绑定一起闭包，再把成员冻结在节点里；是否增加范围入口仍待选择。

**落地前的事实边界：**现有 chatlog 按事件的本地日期分窗口追加，通知没有消息号；mail 的序号只存在进程内。全局还是窗口内自增、用事件日还是写入日、重启及写入失败时怎样避免重号、旧档如何提供稳定引用，都尚未拍定。仅把内存计数器存入异步刷盘的 storage 不能证明重启后不重复；不先改线上日志格式，也不猜一个万能的时间轴。

**草籽对编号语义的纠正（2026-09-23）：**新号拟标识值得留存的交互痕迹，不按外部事件发生时间；旧 `opN` 可以退役，不需要替它预设永久别名。派发行动前执行器须知道其输出的 id，后来的输入按需要引用；不能沿用现在「结果完成才分配 cid」的登记时点。旧 `opN` 若退出可见记录，所指的旧摘要链必须明确一并退出或迁移，不留下假可反查引用；这不意味着获准删除档案。**认知顺序已明确：**模型当前输出片段 D 结束后，才在间隙按 mail FIFO 阅读已入队的 B、C，所以是 D→B→C；mail 入队与认知时点不能继续混写。如何在这个顺序下分配稳定号和记录阅读批次仍待验证，不能拿现有 `_add.seq` 假定全部解决。

相关内容必须在**一次有效覆盖**里收掉；关联的 `say` 与回声不能由模型分两次自由拆开。否则问题被收起来了、回答还在，或动作离开上下文却留下孤立的窗口原文。模型传什么参数、系统如何补齐闭包仍待定。

**旧方案当时的理由：**`_referenced_cids` 原样认得 `cids` 字段（按写法认不按名字认），不必再定节点／叶子的分类规则；统一 id 方向不承诺保留这一字段或分类。

**原方案因显式枚举而不需要求值「两个端点之间的一切」。** 现在范围是否仅作为操作入口、如何展开冻结可见成员仍待判断；不能再声称冻结与求值的问题已被旧字段形状永久消除。

### 3. 退休按深度，对整棵树统一（草籽定）

**2026-09-24 最新裁决：退休暂不实施。** 目前不知道 H 应取多少，也没有已证实的存储压力；先保留所有原文，不删除，甚至不写退休标记。现有反查继续按原号取回仍在的内容；不为尚未发生的退休引入状态或高水位。等存储压力确实出现，再做不改动记录的候选 H 报告，依据实际效果决定是否需要退休。

**若将来启用退休，退休指物理删除原文。** 保留下来的节点即使仍写着已退休记录的 id，反查也只能明确返回「已退休」，不能为了让每条旧引用永远可解而保留已退休文件。必须与「从未存在」区分；删掉载荷后用何种最小分配痕迹判别这两种情况（如持久高水位或墓碑）尚未选定。当前 `_next` 从现存事件日志重建，不能假设删除最后一个号后仍记得它分配过。

**2026-09-24 草籽补充：保留到 H 层，再给这些节点直接点名的记录多保留一跳。** 从选定的根按引用广搜，深度 ≤ H 的节点保留，并保留它们直接引用的原文；深度 H+1 的记录只作为末端载荷，不从它继续展开。若这个末端本身是总结，它参数里更深的号可以退休，届时反查那个号返回「已退休」。这就是下文旧提案所谓「H 层内的节点 + 它们引用的原文」的精确定义；不是无限深可达性遍历。

**本节下方旧的「只换根、遍历不变」「任何被引用原文都不删」推导退为历史，不是可直接实施的退休算法。** 若日后重启退休设计，根的选取、允许任意挑选压缩时能否收敛，以及删除集合与持久编号的具体实现，都须先做 report-only 核验；选择 H 不授权真删。

**以高度 ≤ H 的节点为根做可达性标记，标不到的物理删除。** 节点和工具叶子同一条规则，不分类。

早先这条写作「超过高度限制 H 的**整个子树**物理删除」，2026-09-20 草籽改掉了：**删除的优先级必然低于保存的优先级**——层级提升靠的是反查，而直接删整棵子树必然误伤还有人引用的东西。所以「子树」是常见情形，不是规则；判据是**高度超限且无人引用**，两个条件的合取。

为什么它自足（草籽的论证）：**召回会提升深层内容**——模型反查任何东西都会把它提上来；而长期不被提升的内容随着树的增长自然下沉，越过 H 就删。树是始终增长的，所以不存在「永远不会超高度」的内容。

**因此遗忘时间是多余的，不需要第二个时钟。** 早先几版里提过的「工具叶子拿最近 N 轮 / 最近 T 小时」作废——它是在用时间去回答一个结构已经回答了的问题。真要有「时钟」，它的单位也是总结次数（树又长了一层），而那就是高度本身。

这条自足性**原先假设淘汰总吃最老的一段**。若模型可以任意挑着压，一个老节点能停在深度 1 上不动，它和它的整棵子树就都不退休。2026-09-24 已决定当前 hint 只报告 token 占比、不代选旧段，因此这个前提**尚未满足**；高度退休前必须重新核对收敛性，不能把旧推论当成现成保证。

**H 是指数敏感的旋钮。** 活着的集合大致是 `b^H` 量级（`b` 是压缩比），所以 H 加一不是「多留一点」，是多留一个数量级。它不该按「感觉留多久合适」来调。

**同一个删除有两重含义，别当成一件事：**

| 被删（标不到）的东西 | 后果 |
|---|---|
| 工具调用原文 | **彻底销毁**——`record` 存全量不截断，没有第二份 |
| 它覆盖的聊天消息 | 原文仍在 chatlog（永不删），但**失去了索引路径**，变成索引不可达 |

这就是草籽说的「遗忘的两个层级」：磁盘删除，和上下文内索引不可达。后者是前者的**后果**，不是另一套机制。

顺带一个一致性检查：「遗忘只对工具调用生效」是**字面成立**的，而且恰恰因为节点就是工具调用——被删的永远是工具调用记录，其中一部分记录的内容是关于聊天的摘要。消息本身一条都没删。

**于是退休就是旧 `sweep` 的语义，换一个根。** 这条早先写反了（写作「被引用就保活整个作废，按深度退休不需要可达性遍历」），草籽那条判断把它翻回来：

| | 根是什么 | 遍历 |
|---|---|---|
| 旧 `sweep`（已于 `1948d56` 拆掉） | 窗口内的轮，按**聊天时间** | 顺 `cids` 递归标记，标不到的删 |
| 按高度退休 | 高度 ≤ H 的节点，按**深度** | **一个字不用改** |

所以 `mods/oplog.py` 里留下的 `_referenced_cids` 不是「留着等接管者复用的零件」，**它就是接管者本身**。

早先反对可达性的理由是「方向反了——用节点→叶子的引用去保活体积最大、最易腐的那一类」。换根之后这个顾虑是**有界**的：旧根是聊天窗口，一个节点只要还在窗口里就把它引用的全部原文拽着，而窗口很长；新根是 H 层内的节点，自己沉过 H 就不再是根、也就不再保活任何东西。保活集合因此收敛到「H 层内的节点 + 它们引用的原文」，正是 `b^H` 那个量级。

「工具调用原文彻底销毁」仍然成立，只是**时机推后**：原文要等它的所有引用者都沉过 H 才删。这正是旧 `sweep` 那条 WHY 描述的形状——一串「收缩的收缩」把整条证据链一直拽着，直到最新那次也失去根，那一刻整条链一起没有根，一次全清。

**召回提升层级在可达性下自动成立**，不需要额外机制：`recall_ops` 把老节点拉回上下文，它就有了新的引用者，于是标得到。

现状：`recall_ops` 对不存在的号还没有「已退休／从未存在」两种返回；实现物理退休之前，必须先补上上述判别依据和明确返回，不能把缺号一概当成退休。

### 4. 两个压缩工具的可逆性不对称，而且必须写给模型看

它们背后是两个存储，所以承诺不同。这是模型判断「能多大胆地压」的唯一依据，抹平成一句统一承诺等于让它对两类东西用同一个胆量，而其中一类会真的丢。

- 压聊天：**无条件可逆，永远**（chatlog 没有删除代码；最坏情况是索引路径断了，原文还在）。可以毫不犹豫地压。
- 压工具调用：可逆到它退休为止，而退休由「被盖到多深」决定。多想一秒。

`mods/tools/meta.py` 里那句「收缩不必犹豫，它不销毁任何东西」要按这条改写。

### 5. `keep_since` 整条消失，不是被修好

`build_context` 今天用 `_selected_events(...)[-1]`（**过滤后**列表的末尾）当 `oplog.sweep` 的 `keep_since`。压缩会把老消息从这个列表里滤掉，于是门槛前移、那段时间的操作记录被**真删除**——而索引本身就住在那个存储里。这是一个自毁循环：压得越多，索引删得越快。

早先几版在这里推过一条修法（「门槛取未过滤切片的末尾，禁令变构造」）。**那条作废了**：删除门槛换成高度（第 3 条）之后，`oplog.sweep` 不再从聊天取任何门槛，`keep_since` 连同那条修法一起没有消费者。留在这里只是为了让读到旧版本的人知道它去哪了。

**已落地（2026-09-19）**，而且是被一次真实事故推着落的：一条「聊天开始」让 `keep_since` 抬到当下，下一轮装配上下文时物理删除了 515 轮操作记录（op1598→op2112），而发它的人和模型都以为那只是「不再往前看」。现在 `oplog.sweep` **整个删掉**，`build_context` 不再回收任何东西，边界只管可见性。代价是接管者（第 3 条）落位之前操作记录只增不减——这是刻意选的过渡态，理由见第 3 条那张「一次删除的两个含义」表：不可逆删除挂在每轮都会发生的读操作上，比无界增长糟得多。同一笔里把可见性过滤下推给 `build_rounds(window, since=floor)`，否则每轮装配会随记录数线性变慢。

连带：`max_msg` 数原始条数还是数可见条数，从此只影响「看得多远」，不影响「删不删」，可以放开选（见第 10 条）。

### 6. 总结沿用工具的载入规则，索引另算

**到站订正（2026-09-23，草籽）：**总结本身也是工具调用。短期继续按现行 `build_rounds(window, since=floor)` 载入：无论普通工具还是顶层结论，早于本轮所选聊天消息的 `floor` 就不自动进入上下文；「聊天开始／结束」边界也照现行规则起作用。这里的「预算裁剪」是聊天预算让 `floor` 前移后**间接截掉工具轮**，不是给每条工具轮另算 token 预算。原先提出“节点不受 `floor` 管”是把**自动可见**误当成了**索引可达**，现已否决，不加例外。

被上层成功收缩的节点本来就不再自动显示，但它和被引用的工具调用一样，仍能沿直接或间接引用找到，直至后续退休规则真正删除它。取覆盖关系必须看全量记录（含 `condensed`），不拿当前上下文的切片代替索引。仅有 `arguments.cids` 引用不代表调用已经被收缩：`recall_ops` 也引用 cid，是否自动显示仍由实际收缩标记与现行载入范围决定。未来若确实取消有界的自动选取，再重评 `floor` 的职责；它不是当前 4a 的前置。

### 7. 覆盖是事实，不是渲染

覆盖关系要靠扫 oplog 的节点 `arguments` 得到，而 `entries()` 默认 `include_condensed=False`。用默认值扫的话，二层压缩吞掉一层节点之后，**它覆盖的那批聊天消息下一轮原样复活**。

`entries()` 的默认可见性是为渲染设计的（收缩过的不渲染）。两个问题共用一个函数，默认值服务前者，所以**取覆盖必须显式 `include_condensed=True`**：覆盖一旦声明就永久，与节点自己还在不在上下文里无关。

### 8. 压缩只改渲染，不改 `history`

`history.remove_message` 已经存在（撤回用的），实现者伸手就够得着，而「把被覆盖的消息从 history 里摘掉」是最自然的写法。

**不能这么做，理由现在只剩一条，但够了：`history` 是这一轮之外还要用的东西。** 摘掉之后，`#ops`、`.chattop`、link 条件、`.py` 里所有读 `getlog` 的地方看到的都是一份被上下文层裁剪过的历史，而它们要的是「这个窗口发生过什么」。压缩是**模型这一侧**怎么看的问题，不该改变别人看到的事实。

（早先这条还有第二个理由——「会污染 `keep_since` 那个删除门槛」。那个门槛已经没有了，见第 5 条，所以别再引它。）

所以过滤是**渲染层**的独立函数，作用在 `_selected_events` 的返回值之后；`_selected_events` 的职责保持「这个窗口能回溯到多早」，**它不知道节点存在**。

### 9. 「聊天开始 / 结束」边界与 `#ops clear` 一起撤掉

草籽定：索引出来之后边界检测是多余的——边界当初存在是为了表达「重开一段」，而索引本身就是分段；`clear` 原本就不在初始设计里，「没有也罢」。

于是 `chat.py` 里那条 `break`、`#ops clear` 子命令、`oplog.clear` 一起删。撤掉之后 `_selected_events` 里只剩三个跳过式裁剪（非消息非戳的通知、`#` 开头的消息、私聊里不是戳 Bot 的戳），**没有 `break`**。

**但边界还有第二个作用，撤它之前必须先有替代（草籽 2026-09-19 指出，这里原先漏了）：它是前缀缓存的锚。** `_within_budget` 从新往老走、`used > token_limit` 就 `break`，所以当 `max_msg` 撑得比 `max_token` 更远时（草籽那个窗口就是 16.4k 条 / 200k token），每轮都以 token 为界断，`picked` 的**老端每轮向后滑一格**。前缀缓存从 token 0 起匹配，老端一动整段失效——按 `deepseek-flash` 的 50× 折扣算，这是每轮全价。而「聊天开始」让候选集合从边界起算，边界之后的若干轮里候选还没涨满预算，于是老端**钉死在边界**不动，缓存能复用，直到重新涨满。

**这颗钉子本身也是有条件的（2026-09-20 合成实测，见 [mail 与激活](mail-and-activation.md) §4）：**边界之后那段一旦超出 `max_token`，或者 `max_msg` 比那段还短，预算先绑定，边界就不再钉住任何东西——实测那两种情形下公共前缀同样是 **0 条**。同一组测量还给出一条量化事实：任一上限绑定时前缀不是「少几条」而是 **0 条**，因为 `_within_budget` 用 `insert(0, ...)` 组装，老端移动一条，整个列表整体平移。

所以这条要拆成两半看：**索引能替代边界的「可见性」作用，不自动替代它的「钉子」作用。** 撤边界的前提因此是两条而不是一条——压缩落位，**且**缓存锚点有替代（第 10 条的 `max_msg` 语义直接影响它：如果 `max_msg` 改成数可见条数，老端滑动的频率就变了）。这条没解决之前，第 9 条不能落。

**但那个替代可能就是树本身（草籽 2026-09-20 的全量重建设想，见 [mail 与激活](mail-and-activation.md) 第八节）。** 如果树始终装得下预算，预算就从不绑定，上下文是「若干节点 + 未覆盖的尾巴」，新消息追加在尾巴上而节点一个字不动——**前缀天然稳定，不需要任何钉子**。前缀失效只发生在压缩真的触发的那一刻，而那是模型得出结论时的偶发动作，不是每轮都有。

那么「缓存锚点有替代」这一条就不必单独设计，它是压缩落位的副产品。代价转移到别处：重建必须读树而不是读原始历史（给第 12 条的覆盖索引加了性能要求），以及压缩跟不上时树装不下，预算重新绑定、老端重新滑动，**而且是静默的**。

### 10. `max_msg` 的语义必须严肃选一个

**到站裁决（2026-09-23，草籽）：短期改成「可见聊天消息条数目标」**，覆盖的消息不占这个名额，向更早的同窗口历史继续找，直到达到目标、碰到现行聊天边界或触及 token 限制。总结节点仍按工具轮随选出的最老聊天消息的 `floor` 截断，不另给预算豁免。「可见条数」不意味着即刻取消 `max_msg`；全量无界重建留到后续研究。缓存方面**暂保留「聊天开始／结束」边界**，但它仅在边界后的段尚未用尽条数及 token 预算时才钉住前缀；未来要撤边界，仍需有经过验证的替代锚。

**2026-09-24 草籽订正及当前接线：上段以聊天消息确定回溯下界的选择已失效。** 统一 id 之后，输入、模型输出和世界返回同属一条已读信息流；`say` 早已是工具行动，不能再让工具与摘要依附于「最老聊天消息」。当前工作树已让它们共同接受 `max_events` 可见事件条数及 token 预算，旧 `max_msg` 只作读取回退，无聊天锚时摘要也可选取。“聊天开始／结束”边界仍在；有稳定来源位置的旧 chatlog 记录仅在主模型读取时补号。v0／缺 QQ 消息号的旧消息保守跳过，缺来源定位的旧正式输入日志有重复补号风险，部署前须核实。

`events = history.getlog(current)[:message_limit]` 是**硬上界**：能回溯多远先被条数卡死，然后才轮到 token 预算，而压缩只放松预算那一侧。推论是反直觉的：**在 `max_msg` 不动的前提下，压缩根本不会让上下文看得更远**——压掉 20 条里的 15 条得到的是「5 条原文 + 1 个节点」，省出来的空间不会自动去装更老的消息。

所以要么退役 `max_msg`，要么把它从「切片长度」改成「可见条数目标」（实现上是从最老那头继续往前找，直到凑够或碰到硬上限）。「压缩换深度」只在后者下自动发生。

**历史倾向（2026-09-20，不是本次短期裁决）：退役。** 全量重建的设想里，「此时消息条数就不再有限制意义了」——树装得下的时候，回溯多远由树决定，不由条数决定。那是后期设想，不能覆盖上面的短期决定。

### 11. 面向模型的正文只有一条投影

`chat.py` 里「插话与 `get_msgs` 必须走同一条转换」那条纪律，这里升级成：**面向模型的正文消费端一共三个——`get_msgs`、插话、反查——它们走同一条投影。** 注意只升级到「面向模型」；link 条件、入口判定那些消费端各自还原各自的，那是现状，统一它们是[消息表示](message-representation.md)§4.A 后半的事，不由本篇带过。

投影要做的是**过滤**：`read_range` 会返回模型当年没看到的东西——`#` 开头的调试输出，以及已撤回的消息（内存那份不含，文件那份含）。不滤就是让模型「回忆」起从未进入过它上下文的内容。

**投影不做转义还原，这是有意的，别去「修」它。** chatlog 存转义形态，`display()` 与 `format_message` 两处 docstring 都说还原属于显示；但那条规矩是对**人**说的，模型不在它的范围内，理由是往返：

- 入站：字面 `[` 是 `&#91;`，CQ 码是 `[CQ:...]`，本来就分得开。
- 出站：`say` → `message.sendmsg` → `call_api("send_msg", …)` **全程不转义**，所以模型写出的 `&#91;` 被 NapCat 还原成 `[`，写出的 `[CQ:at,qq=…]` 被解析成真 at。（阶段 2 之前这条路是 `get_handler` → `sendmsg`；`31d13d6` 把发送换成 `say` 工具，不转义这一条原样保留，见 `mods/tools/meta.py` 里 `say` 的 WHY。）

也就是说模型是一个 **CQ 原生参与者：入站 raw、出站 raw，往返闭合且无歧义**。只给入站还原会单方面破掉往返，还会制造一个今天不存在的碰撞——用户手打的 `[CQ:at,qq=…]` 还原后与真 at 逐字相同，而模型会照抄，抄出去就是真的 at。代价只有一条：模型得知道这套转义约定，那是系统提示里的一句话，不是一次文本变换。

（`display()` 的边界今天就是对的：它的三个消费端——`bot._route` 与 `message._chatlog_write` 的终端回显、`search_current`——全是给人看的，它从没碰过模型这条路。`read_range` 走 `parse_log` → `_message_record`，那里是 `"message": body` 直接赋值。）

**一处保真度残留，不是形态分叉：** v0 记录的正文在**写入时**就被还原过，是展示投影而不是 OneBot 发来的字节（`_message_record` 老实地把 `message` 记进 `_derived`），而 `read_range` 不按版本过滤。它不造成「当场看」与「反查看」不一致——v0 记录只可能经 `read_range` 进上下文（开机重建只收 V1），两条路是同一个函数。但反查跨过 `v1_since` 时拿到的东西保真度更低，应当尊重 `_derived`。

**旧节点方案不存正文。** 下述 `message_ids` + `cids` 是提出此方案时的引用形状，**不是统一 id 的待兼容契约**；新的输出／输入痕迹是否留存、怎样引用和收缩由第一层树到站时决定。旧方案里正文的权威始终是 chatlog，所以「给模型看 CQ 串还是 parts」落在投影层，压缩不引入第二个正文形态，`read_range` 与 `getlog` 不需要返回同一形态；这些理由不自动证明新结构必须继续拆两种 id。

反查**不解除覆盖**：取回只是把原文放进本轮上下文，与 `recall_ops` 一致。

## 落地顺序

早先这里写过的前三步是在「`keep_since` 是唯一删除门槛」的前提下排的，其中两步随那个门槛一起作废。现在是：

0. ~~**拆掉 `oplog.sweep`**（第 5 条）。~~ **已落地 2026-09-19。** 它不在早先那份顺序里——被事故推着提前落的。它让后面每一步都不再有「改错了就物理删数据」的风险，也是第 5 步的前置：接管者要接管的是一个已经没有旧回收的模块。
0b. **前提：消息发送工具化**（见上）。在它之前，一层压缩只能收 `message_ids`，Bot 自己的话压不掉。
1. **第 6 条（节点沿用工具载入规则）与第 7 条（`include_condensed`）。** 节点和普通工具同受当前 `floor` 裁剪，索引则独立于自动可见范围；计算覆盖时必须读取已收缩记录，否则二层压缩藏起一层节点后，原先被覆盖的聊天消息会重新出现。当前还没有写入成功覆盖的生产者，不先落一个无人消费的索引空壳。
2. **第 10 条（`max_msg` 语义）已选短期可见条数。** 第 9 条（边界与 `clear` 撤除）**排在它之后、而且要等缓存锚点有替代**；选取实现需读真实覆盖，和下一步一层节点接通，而非先写一套空算法。
3. **一层压缩工具与反查工具，同时接通覆盖索引和已选定的选取算法。** 当前工作树已完成有正式号、主窗口可见且保留聊天锚点的受限切片；旧历史寻址、非 `say` 回声与无锚覆盖仍挡住全量完成。树从这里开始长。
4. **压力信号**已有只读 token 占比提示；不点名、不自动总结。先观察模型是否会据此持续总结，再决定是否需要更强机制；第 5 步的高度退休不能借用旧的最老段保证。
5. **高度限制与按深度退休**（第 3 条、未定 1）。它是唯一一步会**物理删除**的，所以放在最后：前面几步都只改上下文，错了重来一轮就好；这一步错了是不可逆的。`keep_since` 与那个按聊天时间取根的 `sweep` 已经在第 0 步拆掉，但**可达性遍历本身要在这一步原样回来**，只换根（第 3 条）——`_referenced_cids` 连同它记下的两条约束（被引用的原文不能删、收缩不释放磁盘）留在 `mods/oplog.py` 里，它是这一步的核心而不是可选零件。

第 1、2 步不引入新工具，是给现有机制补上被压缩暴露出来的洞；第 3 步起才是新能力。
