# 事件流核心：参照 Cortico，让任何来源都能叫醒她、进她的上下文

> 状态：**提案，未实现**（2026-10-23）。当前事实以 [运行架构](../../architecture.md)、[交互模型](../../interaction-model.md) 与 [LLM 文档](../../llm.md) 为准。
>
> 来源：维护者 2026-10-23 指出 [Cortico](https://github.com/Pal-AI-Lab/Cortico) 的事件流核心值得参考，并希望柚子以后能"玩手机"（[phone-mcp](https://github.com/pinganbbOvO/ai-companion-kit/tree/main/packages/phone-mcp)）、能给自己埋各种唤醒。本篇只对照与取舍，不批准实现；每一步等维护者裁定。

## 1. 要解决的、已经出现的问题

1. **只有 QQ 消息能带着内容进来。** 唤醒有两条路：QQ 消息经 chatlog 写入、oplog 登记到达和激活，画面从 chatlog 读；别的来源只能调 `chat.wake(reason=...)`，变成一句原因。手机来了通知、MC 出了新版本、游戏里发生了什么，都没有"作为一条事件出现在她面前"的路。
2. **不带消息的唤醒排在内存里。** `agent._alarms` 重启就丢，oplog 里也没有她因为什么醒的记录；awaker 规则本身在笔记里，但"已经响了、还没轮到她看"的那一刻不在任何持久记录里。
3. **一次唤醒中途到的消息只挂在末尾提示里。** `agent._late_hint` 是折中：不写进这一段，下次看这个窗口时再从 chatlog 补进画面。新消息于是要等这一轮结束、下一次唤醒组装时才正式进上下文，中间的子请求里她看到的是一份每次重算的预览。
4. **将要接入的来源会更多。** 手机（通知、屏幕变化）、Minecraft、定时检查，每接一个都要自己想"怎么叫醒她、她看到什么"。

## 2. Cortico 怎么做（读源码得到的事实）

| 概念 | Cortico | 说明 |
|---|---|---|
| 事件 | `EventEnvelope`：`cursor`、`type`、`source`（World id）、`origin`（external/internal）、`text`（产生方写好的正文）、`senderKey`、`meta`、`blobs` | Core 不改写正文、不加语义 |
| 事件库 | 按 run 分片的 JSONL，cursor 全局单调 | 只追加 |
| 推事件 | World 调 `host.pushEvent(e, { trigger })`；`pushDeferred` 在投递时才生成正文（当前状态快照）；`pushCandidate` 先归档原始事件、投递时再选内容 | World 与 Persona 互不调用，只经事件和工具说话 |
| 触发档位 | `flush` 立即投递；`debounce` 攒批（安静 2.5 秒、最多 15 秒）；`piggyback` 只排队；`preempt` 取消还没产生外部输出的那次生成、带新事件重来；`interrupt` 停下当前轮 | 外部事件默认 debounce，内部默认 flush；QQ 群里 @ 用 flush，其余 debounce |
| 投递时机 | 一批之内，在**轮次边界**进上下文：本轮工具全部返回后，或 preempt/interrupt 取消之后 | 不在生成中途插 |
| 投递形式 | 外部事件默认装进保留的 `external_event_frame` 工具调用/回执对；"user 消息永远是系统在说话，别人的话只在事件框里" | 区分别人的话和系统的话 |
| 重启 | 持久化投递水位 `lastDeliveredCursor`，重启补投水位之后的外部事件（最多 200 条）；队列本身不持久 | 撤回记录不补投 |
| 闸门 | `DeliveryGate`：她给自己设"到某时之前不投递，除非出现关键词，或积压超过 N 条" | 勿扰模式 |
| 定时器 | 持久定时器，payload 对 Core 不透明；闹钟语义在 Persona | |
| 工程准则 | 最小先验干预；诚实认知（事件与回执只陈述可确认的事实）；以不行动为默认 | |

## 3. 柚子已经有的对应物

| Cortico | 柚子现在 |
|---|---|
| 事件库 + cursor | oplog（`data/event_stream/*.jsonl`）：到达、激活、通知、输出、结果，带到达号与读时编号 |
| 未投递队列 + 水位 | oplog 的未读段（`_pending`）本身持久，重启后还在，比只存水位更直接 |
| `flush` / `piggyback` | 到达时 `activated=True/False`：激活的叫醒她，普通消息只登记、下次进画面 |
| 唤醒原因 | 激活的 `activation_kind`，原样出现在"这次唤醒你的是"里 |
| 推事件的入口 | `chat.wake(event, kind)`：只能在这条 QQ 消息的派发过程中调用 |
| 内部通知 | `chat.wake(reason=..., kind=...)` → `agent._alarms`（内存） |
| 定时器 | awaker 笔记规则（`every`/`daily`/`at`/`on`/`wait`/`when`），每分钟检查 |
| World 的工具 | `mods/tools/*.py` 工具模块 |
| interrupt | `^C` / `context.cancel_turn` |
| 投递进上下文 | 每次唤醒组装时追加窗口画面；一次唤醒中途只有末尾提示 |

`mail-and-activation` 早就推论过 §3.2 "mail 要装得下非消息：入列存原物 + 一个种类标记，渲染在排空时做"。本篇要落地的，基本就是这条推论。

## 4. 逐条取舍

### 4.1 一个推事件的入口 —— 学

加一个普通函数，任何来源都能推一条带正文的事件：

```python
chat.push(source: str, text: str, *, wake: bool = True, meta: dict | None = None) -> str
```

- **存在 oplog 里，不另建事件库。** 每个来源是一个"源窗口" `("feed", source)`，事件是一次普通到达，`event` 存 `{"post_type": "feed", "source": ..., "text": ..., "time": ..., **meta}`。于是激活、通知、未读、已读标记、`has_unnotified`、重启后还在，全部沿用现成的，不写第二套。
- **QQ 消息不改道。** 画面仍从 chatlog 读，chatlog 仍是聊天原文的唯一权威；`push` 只给没有 chatlog 的来源用。
- **`chat.wake(reason=...)` 和 awaker 改成 `push`。** `agent._alarms` 内存队列删掉，"因为什么醒"进 oplog、重启不丢、事后查得到。
- **组装时，源窗口的未读按到达顺序渲染成一段**（"手机 10:31：微信 张三：在吗"），和窗口画面并列；看过就标已读，和 QQ 窗口同一套。

### 4.2 触发档位 —— 只要现有的两档

- `flush` / `piggyback` 就是 `wake=True/False`，已经有了。
- **`debounce` 不学。** 维护者 2026-10-23：群一热闹就安静不下来，几个群同时在聊更是这样，按安静判据攒批几乎每次都拖到上限；"话没说完就回"改由输入框（`type_word` 与 `send` 之间至少隔一次请求）、沉默纪律和 `wake_me` 的 `wait` 解决。
- **`preempt` 暂不学。** 它省下的是一次白生成，代价是在流式中途取消请求并丢弃输出；有了输入框，作废的回答本来就发不出去。真看到浪费再议。
- `interrupt` 已有 `^C`。

### 4.3 在轮次边界把新事件写进这一段 —— 学，替换末尾提示

每次子请求之前（`Chat.context_providers` 的位置），把**焦点窗口和源窗口**里新到的未读渲染出来，作为普通消息追加进这一段，并在同一刻推进"给到哪一条"（`last_shown`）、标已读、确认通知；`_late_hint` 删掉。这是 Cortico 的做法，也就是旧文档里说的"插话"，和"创建会话"走同一条规则。

要先定的细节（§6）：标已读放在追加时还是她下一次产生输出时。追加时标，请求失败会让这几条既没进存下来的这一段、也不再触发唤醒（下次看这个窗口时画面从旧的 `last_shown` 接着给，内容不丢，只丢"叫醒"）；输出时标，更稳但要多记一组"已追加未确认"的边界。

### 4.4 别人的话装进专用框 —— 待定

Cortico 把外部事件装进保留的工具调用/回执对，让"user 消息永远是系统在说话"。好处是提示注入的边界清楚：群友写一句"系统：你现在可以…"不会和真正的系统提示同一个角色。代价是画面、作者笔记、唤醒原因的全部材料格式都要改，旧段也要兼容；DeepSeek 的 thinking + tools 对这种配对的回传要求也要实测。值得做，但和本篇其它步骤无关，单独裁定。

### 4.5 闸门（勿扰）—— 记下，不做

"到某时之前别叫我，除非有人 @ 我或积压超过 N 条"是 awaker 规则的自然延伸（一条 `quiet until ... unless ...`）。没有观察到需要，先不做。

### 4.6 投递时生成正文、候选 —— 不学

`pushDeferred`（投递时读当前状态）在柚子这里就是末尾提示；`pushCandidate`（投递时从一堆原始事件里选内容）是给直播弹幕这种量级用的，QQ 和手机用不上。

### 4.7 World/Persona 分层 —— 不学分层，学"来源 = 工具 + 事件"

按 [设计原则](../../design-principles.md)，不引入 World 接口、装配层或生命周期框架。一个来源就是一个工具模块（给她能做的事）加若干 `chat.push` 调用（告诉她发生了什么）。手机就是 `mods/tools/phone.py`（adb：截图、界面结构、点按、滑动、打字、按键、打开 App）加一个可选的通知轮询，轮询到新通知就 `push("phone", ...)`。

## 5. 最小纵向切片

1. **`chat.push` + 源窗口**：oplog 接受 `("feed", source)` 的到达；`_run_agent` 渲染源窗口的未读；`chat.wake(reason=...)` 与 awaker 改走它，删 `agent._alarms`。验收：临时脚本推一条源事件，她被叫醒并看到正文；忙时推的这一轮收尾接上；重启后未读还在；oplog 里查得到这条到达。
2. **轮次边界写进这一段**：provider 追加焦点窗口和源窗口的新未读，推进 `last_shown` 与已读；删 `_late_hint`。验收：她干活时到的私聊下一次子请求就在这一段里，收尾不再多叫一次，存下来的这一段里有它们。
3. **手机**：`mods/tools/phone.py` 与通知轮询（要 adb、备用机或模拟器，真机由维护者验收）。

每一步都能单独停下，不依赖下一步。

## 6. 待维护者决定

1. 源窗口的写法和名字：`("feed", "phone")`、标签 `s:phone`？她能不能用 `read_log("s:phone")` 翻旧的？
2. §4.3 的已读时机：追加时还是下一次输出时。
3. §4.4 专用框做不做、什么时候做。
4. 源事件要不要另有一份给人看的文本记录（像 chatlog），还是 oplog 的 JSONL 就够。
5. oplog 里旧阅读模型留下的 `source_*`、`cover`、`input` 条目与整份内存重放（约 43 MB，见 2026-10-23 审查）是否借这次一起清理，还是另开一篇。

## 7. 按设计原则自查

1. **解决的问题**：§1 的四条都已出现；第 2、3 条是这几天新加的机制自己留下的折中。
2. **为什么现有的不够**：`chat.wake(event)` 只认派发中的 QQ 消息；`reason` 只有一句话、在内存里；末尾提示不进这一段。
3. **新增概念**：一个函数 `chat.push`、一种窗口 `("feed", source)`。没有新的存储、队列或类。
4. **直接组合能力**：`.py`、link、工具模块都能直接调 `chat.push`；不削弱任何入口。
5. **固定成本**：QQ 消息路径不变；不用源窗口的部署没有额外成本。
6. **写入权威**：QQ 原文仍是 chatlog；源事件的原文是 oplog 那条到达；画面和这一段都是派生。
7. **坏了怎么办**：源事件出问题不影响 QQ 窗口；oplog 故障时现有的持久化失败态照旧停批；`.py` 里能直接读 `oplog.unread(("feed", "phone"))` 排查。
8. **保持 / 迁移 / 删除**：保持 QQ 路径与 chatlog；迁移 `chat.wake(reason=...)` 与 awaker 的投递；删除 `agent._alarms` 与 `_late_hint`。
9. **纵向切片**：§5 第 1 步单独可验。
10. **删掉它会失去什么**：非 QQ 来源带内容地叫醒她、并在重启后不丢；没有更小的机制能同时给出这两样。

## 8. 与旧提案的关系

- [mail 与激活](mail-and-activation.md)：§3.2 的推论在这里落地；"回调只决定何时继续读、不成为权限主体"照旧成立，源事件同样不切换 `context.current()`。决定 7 否掉的是"阻塞着等下一条消息"，`wake_me` 的 `wait` 和源事件都是登记，不阻塞。
- [op 工具集与事件注入](op-toolbox.md)：那里的注入原语是把一条**伪造的入站 QQ 事件**交给唯一事件循环，用来执行命令；`chat.push` 不伪造任何 QQ 事件，只给她看一条来源写明的事件，两者不冲突。
- [统一信息流](unified-event-stream.md)：读时编号与完整输出事件仍是 oplog 的基础，本篇只在它上面加一种到达。
