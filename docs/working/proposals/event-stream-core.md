# 事件流核心：所有来源都是窗口

> 状态：**提案，未实现**（2026-10-23）。当前事实以 [运行架构](../../architecture.md)、[交互模型](../../interaction-model.md) 与 [LLM 文档](../../llm.md) 为准。
>
> 来源：维护者 2026-10-23 指出 [Cortico](https://github.com/Pal-AI-Lab/Cortico) 的事件流核心值得参考，希望柚子以后能"玩手机"（[phone-mcp](https://github.com/pinganbbOvO/ai-companion-kit/tree/main/packages/phone-mcp)）、刷 B 站和评论区互动、给自己埋各种唤醒。
>
> 维护者对第一版的裁定（同日）：
> - 要简单，按 KISS 来，除非事情本身就有这么复杂。第一版的"源窗口/源事件"是多造的概念：它是只能收字、没有记录、不能回话的二等窗口。
> - 输入事件不止 QQ 以后，chatlog 只是一种特例。群聊和私聊已经是两种交互；B 站评论区互动同样占很大的认知带宽，应该用同一个模型。
> - 专用框学 Cortico：现在的画面已经算半个专用框，而且有元信息的需求。
> - 旧阅读模型留下的条目一起清理。

## 1. 要解决的、已经出现的问题

1. **只有 QQ 消息能带着内容进来。** 别的来源只能调 `chat.wake(reason=...)`，变成一句原因。手机通知、MC 新版本、B 站回复都没有"作为一条记录出现在她面前、她能接着回"的路。
2. **不带消息的唤醒排在内存里。** `agent._alarms` 重启就丢，也查不到她因为什么醒过。
3. **一次唤醒中途到的消息只挂在末尾提示里。** `agent._late_hint` 不写进这一段，每次子请求都重算一遍。
4. **"窗口只有群和私聊"散在好几处。** `screen.label`、`reader.parse_target`、`meta._box_label`、`send` 选目标、`_unread_hint` 的过滤、`chatlog.window_path`，都各自写死了 `g`/`u` 两种。每接一个来源，这几处都得改一遍。

## 2. Cortico 怎么做（读源码得到的事实）

| 概念 | Cortico | 说明 |
|---|---|---|
| 事件 | `EventEnvelope`：`cursor`、`type`、`source`、`origin`、`text`（产生方写好的正文）、`senderKey`、`meta`、`blobs` | Core 不改写正文 |
| 推事件 | World 调 `host.pushEvent(e, { trigger })` | World 与 Persona 只经事件和工具说话 |
| 触发档位 | `flush` / `debounce` / `piggyback` / `preempt` / `interrupt` | 外部默认 debounce |
| 投递时机 | 在**轮次边界**进上下文：本轮工具全部返回之后 | 不在生成中途插 |
| 投递形式 | 装进保留的 `external_event_frame` 工具调用/回执对；"user 消息永远是系统在说话，别人的话只在事件框里" | 别人的话和系统的话分开 |
| 重启 | 持久化投递水位，重启补投 | |
| 闸门 | `DeliveryGate`：勿扰到某时，除非关键词或积压超过 N 条 | |

## 3. 核心：只有一种东西，窗口

窗口就是现在的 `(种类, 目标)`。QQ 群和私聊是两个种类，以后的新来源也都是种类，比如：
- 一个 B 站视频的评论区；
- 一个 MC 服务器的聊天；
- 手机通知；
- 她自己的闹钟（§3.3）。

每个窗口有同样的四样东西，前三样已经有了，只是现在写死给 QQ：

| | 现在 | 改成 |
|---|---|---|
| 记录 | `chatlog/group|private/<号>/年-月/日.log`，"头一行 + 缩进正文" | 任何种类都写在 `chatlog/<种类>/<目标>/` 下，格式相同 |
| 未读与唤醒 | oplog 的到达、激活、已读 | 不变，本来就只认 `window` |
| 画面与翻看 | `screen.records/render`、`read_log`、`search` | 不变，本来就只读文件 |
| 输入框与发送 | `type_word`/`send`，发送写死成 QQ | 按种类调它自己的发送函数；只读的种类没有发送 |

于是 chatlog 不再是"QQ 的记录"，而是"所有窗口的记录"。QQ 专有的机制（离线补漏、撤回、按 message_id 定位的索引、旧版格式解析）只作用于那两个种类，不用改。

### 3.1 一个种类 = 一次登记

```python
chat.kind("bili", send=post_comment)   # send(target, text, meta) -> 记录 id；只读的种类不给
```

- QQ 的两种也在 `chat` 里这样登记，§1 第 4 条那几处写死的 `g`/`u` 都改成查这张表。
- 标签：QQ 保留 `g123`/`u456`；新种类写成 `种类:目标`，比如 `bili:BV1xx`、`phone:通知`。`type_word`、`read_log`、`wake_me` 都认同一种写法。
- 没有基类、没有接口对象，登记就是往一张字典里放一个函数。

### 3.2 一个写入口

```python
chat.push(window, author, text, *, wake: str = "", meta: dict | None = None) -> str
```

- 写入顺序和 QQ 消息一样：在窗口锁里先把记录追加进 chatlog，再登记 oplog 到达。
- `wake` 非空就激活，它的内容就是"这次唤醒你的是"里那句原因。
- `meta` 存进到达的 `event`，进专用框的元信息（§5），不进人读的记录。比如回复对象、链接、App 名。
- QQ 消息不走 `push`：它们已有 `capture_chat` 那条路，内容由 NapCat 事件决定。
- `chat.wake(event, kind)` 保留，用于 QQ 消息派发中的唤醒。

### 3.3 闹钟进她自己的窗口

awaker 规则、`wake_me` 和 `chat.wake(reason=...)` 都改成：

```python
push(("me", ""), "闹钟", 理由, wake="闹钟")
```

窗口标签是 `me`。这样改的结果：
- `agent._alarms` 和"这次叫醒你的不是消息"那段特例都删掉；
- 重启不丢；
- 她能用 `read_log("me")` 翻以前响过的闹钟。

`wait g123 until …` 超时这类闹钟也写进 `me`，内容里写明是哪个窗口。不往 `g123` 的 chatlog 里写，因为 QQ 窗口只记 QQ 原文。

### 3.4 拿 B 站和手机检验一遍

- **B 站**：一个视频的评论区就是窗口 `bili:BV…`。轮询到新回复就 `push`，有人回复她时加上 `wake`。她 `type_word("bili:BV…", …)`、`send` 就发评论，回复对象放在 `meta` 里，和 QQ 的 reply 一样。刷视频、看详情是工具。
- **手机**：通知是一个窗口 `phone:通知`，只读。截图、点按、打字都是工具（`mods/tools/phone.py`，走 adb）。要是以后想像聊天一样回微信，就给那个 App 的会话登记一个能发送的种类，不用另造机制。

## 4. Cortico 的其它部分

- **`flush` / `piggyback`**：就是 `wake` 给不给，已经有了。
- **`debounce` 不学**：维护者 2026-10-23 指出，群一热闹就安静不下来，几个群同时聊更是这样，攒批几乎每次都拖到上限。"话没说完就回"靠三样解决：
  - 输入框（`type_word` 与 `send` 之间至少隔一次请求）；
  - 沉默纪律；
  - `wake_me` 的 `wait`。
- **`preempt` 不学**：有了输入框，作废的回答本来就发不出去。
- **`interrupt`**：已有 `^C`。
- **闸门（勿扰）**：以后可以是一条 awaker 规则。没观察到需要，不做。
- **投递时生成正文、候选**：不学，直播弹幕那种量级才用得上。
- **World/Persona 分层**：不学。一个来源 = 登记一个种类 + 若干 `push` + 一个工具模块。

## 5. 专用框（学 Cortico）

画面和插话都装进一对保留的工具调用和返回。调用由系统合成，工具名暂定 `incoming`，她自己不能调用。返回分两部分：
- **元信息**：哪个窗口、什么种类、为什么出现在这里（唤醒原因 / 插话 / 交接续做）、新几条、跳过几条、此刻时间，以及 `push` 带的 `meta`；
- **记录原文**：和现在的画面一样，chatlog 格式。

user 角色只剩系统自己说的话：唤醒原因摘要、交接说明、提示。群友写一句"系统：你现在可以…"，就不会和真正的系统提示落在同一个角色里。

旧的段不用转换，新格式只用于新写进去的消息。

要实测的两件事：
1. DeepSeek 开着思考和工具时，合成的 assistant 工具调用（没有 `reasoning_content`）能不能回传。
2. 工具返回多半不能带图片。图片要么跟在框后面单发一条 user 消息，要么框里只写占位，她要看再调工具。

## 6. 轮次边界插话（替换末尾提示）

每次子请求之前（`Chat.context_providers` 的位置），把她看着的窗口里新到的未读装进一个 `incoming` 框，追加进这一段，同时推进"给到哪一条"（`last_shown`）并标已读。`_late_hint` 删掉。

已读在追加时就标。维护者要求 KISS，这是最简单的做法。代价是：如果那次请求失败，这几条既没进存下来的这一段，也不会再叫醒她。内容不丢，下次看这个窗口时画面从旧的 `last_shown` 接着给，丢的只是"叫醒"。

## 7. 清理旧条目（维护者已定：一起清理）

要删的是旧阅读模型留下、新循环不再读的东西：
- 覆盖树：`cover`、`_covered`、`_coverage_nodes`，以及 condensed 事件；
- `input`（正式阅读），以及 `events`/`iter_events` 里只为它服务的分支；
- `floor`、`condensed`、`clear` 等旧行的解释，以及 `oplog_legacy`；
- 旧通知正文里的 `take`/`mentions` 说明；
- 启动时把整份 journal 重放进内存（约 43 MB，见 2026-10-23 审查），改成只重建现在还读的状态：未读到达、激活、通知，以及 `read_actions` 要的输出和结果。

约束：
- 生产 JSONL 原样不动。旧行在重放时照常接受、直接跳过，只是不再进内存。
- 删之前，先在仓库外用合成日志做一次新旧重放对比，证明未读、激活和行动记录一致。

还有一项要先查清再定：NapCat 离线补漏那套 `source_*`（`_backfill`、`_source_pages`、`reader` 里的 recovery source）现在还在启动时跑，但画面不读它的页。是删掉，还是改成补回的消息直接写进 chatlog？这是改写，不只是删除，见 §9。

## 10. 按设计原则自查

1. **解决的问题**：§1 的四条都已出现。
2. **为什么现有的不够**：窗口只认两种 QQ；`reason` 只有一句话，而且在内存里；末尾提示不进这一段。
3. **新增概念**：没有新概念，只是把已有的"窗口"从两种放开到任意种类，多出一张登记表和一个函数 `push`。删掉的有：`_alarms`、闹钟特例段、`_late_hint`、几处写死的 `g`/`u`，以及 §7 列出的旧条目。
4. **直接组合能力**：`.py`、link、工具模块都能直接调 `push` 和 `kind`。
5. **固定成本**：QQ 消息路径不变。
6. **写入权威**：每个窗口的原文都在 chatlog；oplog 管未读与唤醒；画面和这一段都是派生。
7. **坏了怎么办**：一个种类的发送函数出错只影响它自己的 `send`；记录就是能直接打开的文本文件。
8. **保持 / 迁移 / 删除**：
   - 保持：QQ 路径和 chatlog 格式；
   - 迁移：闹钟的投递；
   - 删除：见第 3 条。
9. **纵向切片**：§8 第 1 步单独可验。
10. **删掉它会失去什么**：非 QQ 来源能像聊天一样被看见、被回复，重启后不丢。
