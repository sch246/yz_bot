# 重启后的离线消息补拉

> **状态：未实现提案。** 当前只有从本地 chatlog 重建近期 history，以及 Bot 自己发起 `.reboot` 后在原窗口续话；没有向 NapCat 补拉停机空窗消息的启动步骤。本文先保存问题、证据顺序和实施依赖，不把尚未验证的 NapCat 接口写成现行能力。

## 要解决的缺口

消息现在只在 NapCat 实时推送到 `mods.connect` 后进入路由，再由 `chatlog.write` 写入 chatlog 和近期 history。进程停止、监听器尚未启动或入站连接失效期间发生的消息没有经过这条路，因此本地记录会留下空窗；启动时的 chatlog 重建只能恢复已经写在本地的消息，不能补回空窗里的消息。

这里的目标是：Bot 恢复接收后，从上游消息历史中找出本地缺失的连续区间，按原有时间顺序补进同一份 chatlog 权威，并让随后建立的模型上下文能看到它们。

它不同于两项已有能力：

- **本地历史重建**把已落盘的近期记录放回内存，不访问上游；
- **重启后续话**决定启动后是否在原窗口再开一轮，不发现缺失消息，也不修补记录。

## 第一版不顺带解决什么

- 不把 QQ 全量漫游记录复制成本地第二份档案；只修补可以从本地锚点确认的停机空窗。
- 不默认重放命令、link、自然唤醒或其它入站副作用。补拉首先是记账恢复，是否以及怎样响应是后续明确选择。
- 不为上游接口提前设计通用同步框架、事件总线或兼容层。
- 不另建一份与 chatlog 平行的消息数据库。只有在实测证明无法从现有记录确定安全锚点时，才讨论最小水位状态。
- 不承诺补回 NapCat 自身离线时也没有保存、或其历史接口不再提供的消息。

## 当前已确认的事实

1. `mods.connect` 只有实时 HTTP 入站队列和通用 `call_api`；当前代码没有调用消息历史接口。
2. chatlog 是消息的持久写入权威，`history` 是从它恢复的近期内存投影。
3. 实时事件以 NapCat 推来的原始消息字典进入记录；补拉接口返回的字段是否与实时事件等价，目前没有验证。
4. Bot 自己发送的消息也依赖 `message_sent` 回声记账。若回声落在停机空窗里，补拉还可能承担这类缺账的恢复。
5. Bot 自己发起的 `.reboot` 会在启动完成后立即续话。将来如果补拉晚于续话，模型仍会先在缺消息的上下文中行动，因此二者需要明确的启动顺序。

## 需要按阶段收集的证据

### 阶段 0：验证上游能力，不改运行行为

先在当前 NapCat 版本和当前 OneBot 配置上验证，而不是从接口名称推断：

- 私聊与群聊分别有哪些历史查询 action，是否覆盖 Bot 离线期间；
- 请求的锚点、方向、页大小与终止条件；返回是否会包含锚点本身；
- `message_id` 能否作为同一窗口内稳定锚点，是否有可比较的序号，时间戳精度是否足够；
- 返回消息与实时事件在 `post_type`、窗口字段、发送者、CQ 正文、回复、合并转发和 Bot 自发消息上的差异；
- 撤回、戳一戳等 notice 能否通过同一历史能力恢复；
- 第一次见到的新窗口是否可以被发现，还是只能对本地已知窗口补拉；
- 分页中途失败、历史已过期、无权限和限流分别怎样表现。

证据应来自只读 API 查询和脱敏后的字段结构对照；不要把真实聊天正文、账号或群号写进提案。若需要脚本，先用仓库外的临时脚本，不因此建立永久测试套件。

**退出条件：** 能针对至少一个私聊和一个群聊，从本地已有消息出发向后取到一段可判定边界的历史，并写下真实返回字段与失败语义。若上游不能稳定定位本地锚点，本提案在此停止，不能靠时间戳猜一个“多数时候可用”的同步器。

### 阶段 1：确定恢复语义

只有阶段 0 的证据齐备后，再依次确认这些选择：

1. **窗口范围。** 只补本地已知窗口，还是还要发现停机期间首次出现的新私聊或群聊；后者取决于上游是否提供可靠的会话列表。
2. **补拉后的行为。** 建议第一版只记录、不派发；如果维护者希望 Bot 对离线消息作答，再单独定义哪些消息能激活、多个窗口如何排队、过旧消息何时不应回复。
3. **启动可用性。** 补拉完成前是否阻止聊天模块进入可用状态，还是先接收实时事件、后台修补后再开放模型响应。这个选择必须结合阶段 0 的实际耗时和失败率。
4. **续话顺序。** Bot 自己发起重启后的 `resume_chat` 是等待本窗口完成补拉、超时后降级，还是完全不等待；不能让两条路径自行竞速。
5. **可见反馈。** 正常补齐是否静默；补拉失败、存在无法闭合的缺口或积压过大时，哪些信息进日志，哪些需要向 op 报告。

这些问题在阶段 1 按顺序询问，不在开始实现前一次性要求维护者回答全部分支。

**退出条件：** 写出一条可观察的不变量，明确“哪些缺失消息会进入哪个权威记录、会不会触发行为、什么时候启动算完成”，并能据此判断所有验收场景。

### 阶段 2：设计最小补拉机制

实现设计至少要闭合以下关系：

- **锚点来源：** 优先从每个窗口最后一条可验证的本地记录取得；只有无法表达可靠锚点时才增加独立水位，而且水位不能早于 chatlog 成功写入而前进。
- **重叠去重：** 实时回声、停机前已落盘消息和补拉页可能重叠。去重依据必须来自阶段 0 验证过的稳定身份，不能只拿正文和秒级时间猜。
- **顺序：** 查询通常从新到旧，chatlog 必须按旧到新补写。只有与本地锚点连成连续区间的批次才能提交；部分分页失败不能把洞两侧写成看似完整。
- **实时竞态：** 补拉期间新推送仍可能到达。需要先接住实时事件，再把补拉结果与已接收事件去重、排序，最后才开放会产生副作用的派发；不能用“先拉完再开监听”制造新的空窗。
- **记录路径：** 补拉记录应复用 chatlog 对窗口和消息格式的唯一解释，但不能为了复用而把历史消息重新投入正常路由，触发命令或 LLM。
- **失败恢复：** 上游不可用时保留原锚点并清楚报错，下一次可以重试；不得为了让启动显得成功而把不连续区间标成已经同步。

这一阶段再决定代码落点。候选职责是一个只负责“查询并产出原始历史消息”的 NapCat 适配器，以及一个由 chatlog 拥有的“验证连续区间后记录”入口；是否值得成为独立 Module 由实际代码量与生命周期决定。

### 阶段 3：按风险递增实现

1. 先实现私聊或群聊中证据更完整的一种，只提供显式、只记录的补拉入口。
2. 用仓库外临时假 API 验证分页、重叠、倒序返回、中途失败和重复执行；同一批执行两次不得多写。
3. 接入另一种窗口，消除经证据确认的字段差异，不用虚构的统一对象遮住差异。
4. 加入启动协调：实时入站缓冲、补拉、释放派发之间只有一条明确顺序。
5. 最后接入 `.reboot` 续话等待，并根据阶段 1 的决定处理超时与用户可见反馈。
6. 更新 `docs/architecture.md`、`docs/runtime.md` 与交互文档；提案只保留取舍和未决边界。

每个实现切片都先跑 `uv run --frozen python run.py --check`，再与改动前同机的 `--smoke` 结果比较。涉及真实 NapCat 的验收只做授权过的只读查询和受控重启，不向运行实例注入合成消息。

## 最低验收场景

- 正常退出与异常中断各产生一段停机空窗，恢复后本地只新增真正缺失的消息；
- 私聊、群聊、他人消息和 Bot 自发消息的窗口、作者、正文与时间顺序正确；
- 本地最后一条消息与上游第一页重叠，重复启动或重复补拉不产生重复记录；
- 补拉期间同一窗口收到实时新消息，最终顺序正确且没有漏记或重放副作用；
- 多页历史在中途失败时不会留下被误认成完整的水位，重试后能够闭合；
- 上游不支持、无权限或历史已过期时，Bot 的降级行为符合阶段 1 的决定并留下可定位原因；
- Bot 自己发起 `.reboot` 时，续话看到的是该窗口补拉后的上下文，或明确走了已决定的超时降级；
- 补拉得到命令前缀、link 文本或唤醒词时，第一版只记录、不执行。

## 与其它计划的关系

- 它建立在现有[消息模型](message-model.md)与[自发消息回流](self-message-echo.md)之上：前者决定记录事实，后者决定实时发送如何记账。
- 它与[聊天压缩](chat-condense.md)正交。补拉先恢复原始消息事实，压缩再决定模型窗口如何投影；不能用压缩节点代替缺失原文。
- 它不阻塞当前[压缩、遗忘与消息模型交接](condense-and-unify-handoff.md)主线，也不应被塞进该主线的阶段编号。
- 它会影响未来的远程操作连续性，但不依赖[浏览器、计算机使用与远程操作](browser-computer-remote.md)支线。
