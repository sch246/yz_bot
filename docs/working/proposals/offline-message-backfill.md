# 重启后的离线消息恢复

> **状态：代码已接入自动补回与有名信源；真实停机空窗未验收。** 启动只覆盖已有本地档案的窗口，缺口须如实显示。草籽明确指出控制台展示日志不足以作权威补回，使用 NapCat 历史 API，而不把只读预览误写成已补档。

下文的阶段是实施时的历史清单，不再代表待办；当前代码行为以[交互模型](../../interaction-model.md)和[运行架构](../../architecture.md)为准。尚待验收的是实际停机空窗、上游缺页和长时间运行时的容量与失败恢复。

**新用途（草籽 2026-09-24）：**[中心化聊天软件阅读](chat-client-reading.md)可主动翻看很久以前的记录；NapCat 历史接口既可能提供本地没有的旧页，也可帮助辨认并补齐 Bot 停机期间的缺口。控制台展示日志只能作有不确定性的观察，不作为自动补档来源。历史 API 的当前分页与字段已初步实测；是否覆盖具体离线缺口仍需逐段核实。

2026-09-25 对本机 NapCat 4.18.28 做了少量只读、脱敏的群聊与私聊查询：两类响应均有 `message_id`、`message_seq`、时间、作者、原始 CQ 文本和消息列表；`message_seq` 可在本地已有消息号上作为锚点。`reverse_order=true` 给出更旧的消息，返回含锚点自身，结果按旧到新排列；`message_id` 参数不会产生同样的锚定行为。私聊历史没有 `target_id`，读取投影须由查询窗口明确补上。以一段本地近期记录为锚，群聊和私聊都可向后读取且看见锚点；某个私聊样本的本地六条与上游响应仅重合四条，因此不能仅凭请求成功就宣称“连续无缺”。查询正文未写入仓库或报告，且尚未构造实际停机空窗验证。早期直接预览 NapCat 的工具已退役；当前先 `fetch` 固化为 FIFO，未读提及用 `mentions` 查，聊天正文用独立 `read_messages` 按档案查。

**2026-09-26 修正：**末尾 hint 如手机通知栏，列出各个有名字的可分段读取来源。同一窗口可以有多个 FIFO；FIFO 提供 `status`、`mentions`、`fetch`、`pull`、`mark_read`。`pull` 从队首正式读一段，正文进入唯一经历流并取得正式号；`mark_read` 把调用时已有的水位推到底而不伪造 input。聊天档案不是 FIFO 动作；`read_messages` 在指定窗口内按 `message_id` 或 `origin` 查前后文，已读后仍可使用。不同来源可交错阅读，各自消费位置互不推进；异步工具回调不必伪装成聊天窗口 FIFO 的消息。来源名字是展示与选择入口，不是第二种经历号。

**启动恢复仍进原窗口 mail：**启动时固定原有 chatlog 锚点，从 NapCat 最新响应反复向旧请求；没有可靠锚点的首次窗口只接纳最近一批，旧档留待主动 `fetch`。停机期间世界发来而柚子尚未读的消息，最终排在本次开机后实时到达的消息前面；这只是调整尚未正式拉取的 FIFO，不倒插已读经历。恢复未收束时该窗口首次 `pull(g/u, count)` 立即返回“补回中”，收束后可重试；实时入站仍可接收，不能因此丢消息。未接上的缺口作为自然的 `status`／hint 内容留下，让柚子不必频繁手工探查。之后再向更早历史 `fetch`，若该 FIFO 已被正式读取，就创建新 FIFO，不改写已消费前缀。这是对上一版“NapCat 永远单独一队”的修正。

**已定的分页事实与终点：**对每个窗口先固定 chatlog 中最近一条有可靠消息身份的记录作为本次锚点；首请求取 NapCat 最新页，再以每页最旧记录的 `message_seq` 反复向旧翻，排除接口重复返回的锚点，直到遇到固定的本地锚点或上游确实没有更旧记录。**一次成功的 API 请求、一页不足额、或当前 chatlog 后来出现了新消息，都不是停止理由。** 请求失败、响应畸形或游标停滞是未完成，不冒充“拉不到了”。

补拉取得的真实消息和未接上的事实都应保留。命中锚点只说明请求链抵达本地边界，不保证上游没有漏消息。远端倒序取回时，**单次响应内旧→新不等于多次响应整体旧→新**：启动恢复须先追到旧端，再把补回批次按旧→新接在尚未读取的实时尾部之前；如果中途失败，已取得部分也须标明缺口，不能假称连续。代码已接入自动循环补拉、可前插的 FIFO 和统一 `fetch` 入口；请求分批是内部实现，不是模型的阅读单位。

**档案查询与 `pull` 刻意不同：**`mentions` 和 `read_messages` 的正文是工具返回，和查看行动一起留在轨迹中；它们不推进 FIFO，也不给返回的消息逐条分配正式输入号。`pull` 的正文才作为独立输入正式入流，按实际读到的顺序编号。重复查阅和正式拉取是两次真实经历，可用原 QQ 身份关联，不复用正式号。若不再需要按 FIFO 重放，`mark_read` 会明确推进水位；档案正文仍保留。

**chatlog 回填方式已定方向：**草籽同意在 chatlog 下使用独立回填文件，再由读取层合并视图。现有 `_log_origin` 是相对路径加行号，`read_origin` 与 `read_range(before=...)` 都依赖它；向已有日文件插行会使旧定位指错记录，简单把旧消息追加到文件尾又会让当前倒序分页把它看成最新。实现不得原位改写既有日文件，回填文件也须有稳定定位；归档和 mail 接纳的中断夹缝由实现幂等修复，不能因一边成功就漏掉另一边。

## 2026-09-24 的日志观察（不作补回源）

只读抽样 `/var/log/napcat.log`：展示行的月份从 2 月延续到 9 月，文件创建与修改时间均在 2026 年（行内没有年份）；约有 26 万条“接收”、1.7 万条“发送”的展示行。实际消息正文出现在其中，当时因此猜测它可覆盖不少停机期间的可读内容；这只是历史观察，**已被草籽否定为自动补回来源**，不据此推断完整性。

它不是原始 OneBot 事件：接收展示行没有 `message_id`、`post_type` 等字段，行时间只有月日与秒；回复、图片、转发等被渲染为展示文本，部分长行出现省略号。因而它不能直接伪装成实时事件交给 `chatlog.write`，也不能凭相似正文与秒级时间安全去重、恢复 QQ 回复／撤回身份或重放入站路由。读时统一事件号可以索引一条经确认的**日志观察**，但不能冒充缺失的 QQ `message_id`。

这条日志分支不继续推进，也不将展示文本当作“近似补回”。后续须用真实停机空窗核验 NapCat 历史 API 与本地锚点；真实正文、账号或群号不写进文档。

## 要解决的缺口

原先消息只在 NapCat 实时推送到 `mods.connect` 后进入路由，再由 `chatlog.write` 写入 chatlog 和近期 history。进程停止、监听器尚未启动或入站连接失效期间发生的消息没有经过这条路，因此本地记录会留下空窗；单靠 chatlog 重建只能恢复已经写在本地的消息，不能补回空窗里的消息。

这里的目标是：以 NapCat 历史 API 的真实消息身份逐页找回可取得的消息，在持久 mail 中留下尚待正式阅读的输入，并如实保留接上本地锚点或未接上的结果。不用展示日志或猜测内容填充缺口；chatlog 通过独立回填文件保存原文，并提供可稳定分页的聊天顺序视图。

它不同于两项已有能力：

- **本地历史重建**把已落盘的近期记录放回内存，不访问上游；
- **重启后续话**决定启动后是否在原窗口再开一轮，不发现缺失消息，也不修补记录。

## 第一版不顺带解决什么

- 不把 QQ 全量漫游记录复制成本地第二份长期档案；没有本地锚点的启动恢复只取最近一页，更早内容由显式 `fetch` 探索，这也不等于宣称历史完整。
- 不默认重放命令、link、自然唤醒或其它入站副作用。补拉只接纳事实；正式读取后是否回复由 agent 决定。
- 不为上游接口提前设计通用同步框架、事件总线或兼容层。
- 不另建一份与 chatlog 平行的消息写入权威；读取层可维护由 chatlog 派生、可重建的索引。
- 不承诺补回 NapCat 自身离线时也没有保存、或其历史接口不再提供的消息。

## 当前已确认的事实

1. `mods.connect` 有实时 HTTP 入站队列和通用 `call_api`；主线代码通过它自动补回或由 `fetch` 建立历史信源，早期直接暴露的 `peek_napcat` 已退役。
2. chatlog 是消息的持久写入权威，`history` 是从它恢复的近期内存投影。
3. 实时事件以 NapCat 推来的原始消息字典进入记录；历史接口的分页字段已核实，但返回字典与实时事件在所有消息类型上是否等价，尚未完整验证。
4. Bot 自己发送的消息也依赖 `message_sent` 回声记账。若回声落在停机空窗里，补拉还可能承担这类缺账的恢复。
5. Bot 自己发起的 `.reboot` 会在启动完成后续话。补回在监听新事件前准备，在后台翻页；窗口恢复未收束时正式拉取会返回“补回中”，不能把空窗当成已读完。

## 历史实施清单：历史 API 精确补拉

以下阶段要求可核验的消息身份与分页前进；只读预览不等于补拉成功。旧的“必须连成连续区间才可接纳”门槛已被上面的裁决替换。

### 阶段 0：验证上游能力，不改运行行为

先在当前 NapCat 版本和当前 OneBot 配置上验证，而不是从接口名称推断：

- 私聊与群聊分别有哪些历史查询 action，是否覆盖 Bot 离线期间；
- 请求的锚点、方向、页大小与终止条件；返回是否会包含锚点本身；
- `message_id` 能否作为同一窗口内稳定锚点，是否有可比较的序号，时间戳精度是否足够；
- 返回消息与实时事件在 `post_type`、窗口字段、发送者、CQ 正文、回复、合并转发和 Bot 自发消息上的差异；
- 撤回、戳一戳等 notice 能否通过同一历史能力恢复；
- 第一次见到的新窗口是否可以被发现，还是只能对本地已知窗口补拉；
- 分页中途失败、历史已过期、无权限和限流分别怎样表现。

证据应来自只读 API 查询和脱敏后的字段结构对照；不要把真实聊天正文、账号或群号写进提案。若需要脚本，先用仓库外的临时脚本，不因此建立永久测试套件。

不能只凭接口存在就宣布离线缺口一定能补：NapCat 官方仓库曾记录 [`get_group_msg_history` 未返回离线期间消息](https://github.com/NapNeko/NapCatQQ/issues/1838)，也记录过带锚点时翻页方向与预期相反的[问题](https://github.com/NapNeko/NapCatQQ/issues/441)。这只是上游风险证据，不代替当前设备版本的只读实测；即使分页抵达本地锚点，也不宣称上游逐条无缺。

**当前进度：** 群聊和私聊均已从一条本地消息号锚定并向后读取；字段和分页方向已核实。还缺真实停机空窗、分页失败与上游尽头的样本；这些不确定性要保留在结果中，而非靠时间戳猜连续性。

### 阶段 1：确定恢复语义

群聊和私聊的锚点参数、方向已核实。信源四动作与启动补回次序已经裁定；下面是范围边界与实现核验，不是新的启动前决策闸门：

1. **窗口范围。** 首版自动恢复本地已知窗口；停机期间首次出现、仅 NapCat 知道的新窗口需要可靠会话发现能力，是可另行扩展的产品范围，不阻挡已知窗口。
2. **首次边界。** 冻结启动前的本地锚点与既有未读前缀，补回内容插在旧前缀之后、新实时尾部之前；本窗口首次正式 `pull` 须等恢复结束，不阻断实时接收和别的信源。
3. **可见反馈。** 本次是否抵达固定锚点、上游耗尽、停滞或失败，应当可区分；未闭合范围不能被下一次成功查询自动抹平。缺口进入该信源的 `status`，再自然出现在全局 hint。

尚无本地锚点的窗口只把最近一页留为待读；这是一条明确的首次边界，不代表上游尽头，也不证明全部旧消息都存在。更早内容通过显式 `fetch` 形成可独立读取的信源；首次 floor 与恢复边界必须一致，不能静默吞掉已经接纳的最近页。

**退出条件：** “取得的消息持久入列但不提前编号；首次 pull 前可向前扩展，之后 fetch 新建 FIFO；缺口可见；正式 pull 才推进唯一经历”，并能据此判断下列验收场景。

### 阶段 2：设计最小补拉机制

实现设计至少要闭合以下关系：

- **锚点来源：** 每次开始时冻结对应窗口 chatlog 最近的可靠消息身份；本次期间新增的实时消息不能移动这一锚点。有可靠锚点就翻到命中、上游耗尽或分页失败，不能悄悄改成页数／时间阈值；没有锚点的启动恢复只取最近一页，更早内容由显式 `fetch` 继续。
- **重叠去重：** 实时回声、已接纳的历史页、停机前已落盘消息可能重叠。以窗口与可用的完整 QQ 消息身份从现有持久记录推导，不以正文或秒级时间猜，也不另建可写的同步表；NapCat sidecar 的身份包含 `message_seq`，缺少该字段的普通日档不与它强行归一，歧义时允许保留重复而不隐藏事实。chatlog 已写但 arrival 未写的停机夹缝，要单独修复待读事实。
- **顺序：** 从最新页开始逐页向旧，直到固定本地锚点或真正无旧页；用临时页文件避免查询阶段无限积累正文，再按旧到新接纳。部分分页失败保留已取得的真实消息及未闭合事实，不能把它们写成完整区间。
- **实时竞态：** 补拉期间实时推送仍正常接收并持久暂列，但本窗口首次 `pull` 等恢复收束；补回批次排在这批实时消息前，而原有待读前缀不被反转。并发 fetch 与首次 pull 须在同一个窗口提交边界决定是前插还是新 FIFO。相同 QQ 消息不能因两条路径同时到达而在同一 FIFO 排队两次；补回记录不进入实时路由，不重新触发命令或自然唤醒。
- **记录路径：** 补回原文写入 chatlog sidecar，信源页与消费位置持久保存在事件流；正式 input 只在 agent 拉取时写入。读取层合并日文件与 sidecar 的聊天顺序视图，不向既有日文件插行。
- **失败恢复：** 区分无更旧页、仅返回重复锚点而游标停滞、接口失败和命中本地锚点；保留原锚点及已接纳消息，下次可以重试，但未闭合尝试不能被误报成已同步。

代码落点复用现有 NapCat API、窗口 Mailbox 和 oplog 事件流；查询过程暂存页，读完后按旧到新接纳，chatlog 独立回填文件是档案而非另一份可写同步状态。信源持久保住名字／身份、来源窗口、队列次序、消费位置、缺口、远端查询边界和已取得正文；不能重启后只存游标、再向可能变化的 NapCat 重新要正文。长期容量仍须在真实数据规模下核验，不得把“请求分页”误称为“内存有界”。

### 阶段 3：按风险递增实现

1. 共用已核实的群聊／私聊分页规则，从最新页逐页翻到固定锚点或上游尽头；任何中途失败都不能误判为尽头。
2. 用仓库外临时假 API 验证三页含锚点、短页继续、游标停滞、中途失败和重复执行；同一消息不能重复入 mail。
3. 接入启动已知窗口，保留实时入站；补回只进入持久 mail，正式读取仍由中心 reader 的有界 FIFO 控制。
4. 处理首次 pull 屏障、持久缺口与 `status`／hint；已 pull 后的显式远端 fetch 创建新信源，再处理 chatlog 的安全回填视图。
5. 更新 `docs/architecture.md`、`docs/runtime.md` 与交互文档；提案只保留取舍和未决边界。

每个实现切片都先跑 `uv run --frozen python run.py --check`，再与改动前同机的 `--smoke` 结果比较。涉及真实 NapCat 的验收只做授权过的只读查询和受控重启，不向运行实例注入合成消息。

## 历史 API 分支的最低验收场景

- 正常退出与异常中断各产生一段停机空窗，恢复后持久 mail 只接纳尚未接纳的真实消息；
- 私聊、群聊、他人消息和 Bot 自发消息的窗口、作者、正文与时间顺序正确；
- 本地最后一条消息与上游第一页重叠，重复启动或重复补拉不产生重复记录；
- 补拉期间同一窗口收到实时新消息，补回批次在其前、原有待读前缀仍在最前，且没有漏记或重放副作用；
- 多页历史在中途失败时不会留下被误认成完整的水位，重试后能够闭合；
- 上游不支持、无权限或历史已过期时，Bot 的降级行为符合阶段 1 的决定并留下可定位原因；
- Bot 自己发起 `.reboot` 时，续话不会暗中把补回正文一次性塞入上下文；
- 补拉得到命令前缀、link 文本或唤醒词时，第一版只记录、不执行。

## 与其它计划的关系

- 它建立在现有[消息模型](message-model.md)与[自发消息回流](self-message-echo.md)之上：前者决定记录事实，后者决定实时发送如何记账。
- 它与[聊天压缩](chat-condense.md)正交。补拉先恢复原始消息事实，压缩再决定模型窗口如何投影；不能用压缩节点代替缺失原文。
- 自动补拉不阻塞当前[中心化聊天软件阅读](chat-client-reading.md)的第一阶段；主动旧档阅读与缺口辨认仍是该方向的目标，不应被塞进旧[交接阶段表](condense-and-unify-handoff.md)。
- 它会影响未来的远程操作连续性，但不依赖[浏览器、计算机使用与远程操作](browser-computer-remote.md)支线。
