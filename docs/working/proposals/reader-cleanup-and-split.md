# 中心 reader 简化与大文件拆分

> **状态：计划，未实施。** 本文不是现行合同；当前行为以[交互模型](../../interaction-model.md)、
> [运行架构](../../architecture.md)、[LLM 文档](../../llm.md)和代码为准。
> 它合并并取代了此前的两份计划（《中心 reader 与事件流的低熵收束》、《大文件拆分：先搬家，再简化》），
> 两者的讨论过程见 git 历史。

## 1. 要解决的问题

1. **文件太大，难找。** `chat.py` 2800 行，`oplog.py` 1308 行，`tools/meta.py` 824 行。
   09-20 时它们分别是 1350、346、377 行，增长主要来自 09-25 起的中心 reader。
2. **“读消息”散在四个文件里，难改。** 不算仓库起点那次整体导入，改过 `meta.py` 的 15 次提交里，
   14 次同时改了 `chat.py`，12 次连 `oplog.py` 一起改；09-24 以来改 `context.py` 的 8 次提交，
   每次都同时改了 `chat.py` 和 `oplog.py`。
3. **token 上限的作用和维护者的本意不一样。** 见第 2 节，这一条是维护者 2026-09-26 指出的。

## 2. 已经拍板的决定（2026-09-26，维护者）

### 2.1 上下文上限只决定“从哪里开始读”

维护者设的 `max_token`（默认 40000，而模型实际上下文远大于它）和 `max_events`（默认 500）是给 agent
看的压缩信号，不是裁剪工具。

**现在：** 每次叫醒 agent，都从磁盘重新装一遍历史，只留最近 40000 token。超过的旧内容每次醒来自动掉出去，
agent 不压缩也会“自动忘”。离线回放实验里反而已经不滑窗，`_run_agent` 那条 `WHY:` 写着“生产路径继续使用两个上限”。

**改成：**

- 第一次加载时，照现在的办法按两个上限选出起点，把起点（一个事件号）记进全局 agent 设置。
- 之后每次加载都从这个起点读到最新，不再按 token 或条数裁剪；重启也沿用同一个起点。
  被 `cover_events` 覆盖的事件照旧只显示结论，所以上下文靠 agent 自己压缩变小。
- 只有两种情况会重新选起点：第一次加载（包括这次改动上线后的第一次），以及管理员用一条 `#agent`
  子命令手动重置（名字实施时定）。
- 占用超过 `pressure_percent`（默认 75%）时，末尾提示照旧显示“上下文占用 x/40000 token”；
  **达到 `max_token` 时，提示改为明确要求先用 `cover_events` 压缩，再做别的事。**
  这只是要求，不拦截工具调用。模型真不压缩也不做自动处理；万一撑到供应商拒绝请求，恢复入口是上面那条手动重置命令。

独立 `.chat` 本来就不重建历史，不受影响；给 `.py`／link 用的窗口级辅助查询 `get_msgs`、`build_context` 也不在本次范围。

### 2.2 删掉“读消息”的 token 预算

代码里写死的 `MAIL_PULL_TOKENS = 4000`（09-25 加入）不是维护者设的，删掉。`take`、`mentions`、`pull`、
`read_messages` 选中了几条，下一次请求前就完整读入几条。条数上限 500 保留。随之删除：

- 单条过长时截成片段（三条读取路径各有一份）；
- 一次读不完、拆到后面几次请求去读；
- 来源桥太长就报错、停止这次阅读计划，并报告“读了一部分”。

09-26 的两次修补提交（“Keep provenance through budget fallbacks…”、“Clarify partial read progress…”）
处理的正是这几条分支。

`status` 的输出、通知和未读概况提示是系统自己生成的状态列表，不含消息正文，继续保留长度上限
（`status` 现在借用 `MAIL_PULL_TOKENS`，改用自己的常量）。

### 2.3 长消息不再截断

由 2.1、2.2 自然解决：消息读进来就是全文，事件号永远对应全文。旧数据里已经截成片段的输入不改写，照原样显示；
来源桥里也显示当时存下的内容，不再按“正式读取片段”“补回消息过长，先读片段”这类中文字样去识别片段、重建全文。

### 2.4 其它

- **provenance（`read_by`／`read_via`）不改磁盘格式。** 旧日志不重写，又能被来源桥和 `recall_events`
  引用到任意久远，改新格式只会让代码多认一种格式。2.2 删掉降级分支后剩下的重复，用一个普通函数合并。
- **只留这一份计划。**
- 独立 `.chat`、`pull`、来源桥、原生 O/R、`mark_read`、`cond`／`call` 等现有产品行为全部保留。

## 3. 做法的几条规矩

1. **每一步拆成两个提交：先纯搬家，再改逻辑，两个一起上线。** 纯搬家可以用脚本证明没改行为，
   改逻辑的 diff 就只剩真正的改动；但不单独上线一个只换了位置的版本。
2. **不新建公开模块。** 公开模块会进入 `.py`／link 的共享环境成为新名字，还有自己的加载阶段和失败隔离；
   “reader 加载失败、chat 加载成功”没有意义。所以默认用文件夹：`mods/chat/`、`mods/oplog/`。
   执行者看了实际依赖后若有更好的放法，可以换，但要说明理由。
3. **会被重新赋值的全局量只住一处。** `chat` 的 `settings`、`prompts`、`chat_groups`、`description_cache`、
   `llm_config` 在 `on_load` 里重新赋值，`experiments/memory_replay.py` 还直接改写它们和 `chatlog.rootfile`
   来隔离回放。子文件若用 `from mods.chat import prompts` 绑到自己名下，回放时拿到的就是真实提示词和配置，
   隔离悄悄失效。所以它们留在 `chat/__init__.py`，子文件在调用时写 `chat.prompts`。
4. **公开名字先全部保留。** 今天能写 `chat.X`（X 不以下划线开头）的，搬完仍能写。之后哪些可以删，
   由 GPT 在设备上查 link、`data/pyload.py`、`#hint` 代码里实际用了哪些再定。
5. `WHY:` 跟着代码走；不改 import 顺序、`LOAD_AFTER`、`PHASE`；`chat/__init__.py` 里原来那行
   `from mods import ...` 原样保留。
6. 不改磁盘上的任何数据格式（2.1 新增的起点是 agent 设置里多一个键，不是格式变化）。

## 4. 步骤

### 第 1 步：oplog 写入安全

- **搬家：** `oplog.py` 改成 `mods/oplog/`，把重放规则搬进 `replay.py`（`_apply`、`_validate_*`、
  `_reference_candidates`、`_message_identity` 等，约 330 行）。它们本来就是纯函数，所有索引都作参数传入。
- **改逻辑：** 现在写一条记录是先检查、写盘、fsync，再调 `_apply` 改内存；检查写了两遍而且不一样，
  例如 `source_reopen` 的状态检查只在 `_apply` 里，也就是写盘之后。改成：
  - 所有会拒绝记录的检查收进一个函数，写盘前调它，启动重放时也调它；
  - 写盘、fsync，或写盘后改内存，任何一步出错都停止后续写入（现在改内存出错时不会停），等重启时检查磁盘。
- 目前我只确认了已读到的调用方都事先挡住了这些情况，没有查生产日志，不能说从没触发过。

### 第 2 步：chat 拆成文件夹，同时改上下文和读取规则

- **搬家：** 先 `git mv mods/chat.py mods/chat/__init__.py`，再拆成五个文件：

  | 文件 | 回答什么问题 | 约行数 |
  |---|---|---:|
  | `__init__.py` | 什么时候叫醒 agent；设置存在哪；`.chat` 单句怎么跑 | 650 |
  | `view.py` | 消息、输出、工具结果、通知在模型眼里长什么样；从起点重建历史 | 570 |
  | `reader.py` | 有哪些未读；`take` 等怎样把消息正式读进来；补回信源 | 750 |
  | `agent.py` | 中心 agent 的一次激活怎么跑 | 490 |
  | `subcommands.py` | 群里的 `#model`、`#limit`、`#hint` 等设置命令 | 470 |

  行数取自 2026-09-26 的一次仓库外试拆（见第 6 节），改逻辑后 `reader.py` 会明显变短。
- **改逻辑：** 2.1 的起点与压缩提示、2.2 删读取预算、2.3 桥显示存下的内容，并把三条读取路径
  （补回、实时、档案）里剩下的“投影 → 加 provenance → 加来源桥 → 登记”合成一个函数。
  同一提交改写 `_run_agent` 那条关于滑窗的 `WHY:`。

### 第 3 步：`meta.py` 只留工具外壳

现在 `meta.py` 的 `_take` 自己遍历未读、按来源顺序排序、亲手拼请求 dict；`status` 自己汇总状态；
`cover_events` 调 chat 的私有函数删会话里的消息。改成：

- 这些逻辑挪进 `chat/reader.py`、`chat/agent.py`，成为有名字的普通函数；
- 请求 dict 只由 `reader.py` 创建和消费；
- `meta.py` 的每个阅读工具只剩签名、给模型看的说明、“只有中心 reader 可以……”那条检查和一次调用。

工具名、参数、返回文字都不变，模型看到的一样。

### 第 4 步：删掉 Mailbox，未读只记在 oplog

**现在：** 未读记了两份：oplog（磁盘，重启以它为准）和 `context.Mailbox`（内存）。每种读法都要先写 oplog
再同步 Mailbox，同步方法有三种（`absorb`、`pull`、`commit_recovered`）。上面那 8 次同时改 `context.py`
的提交，有 6 次在增改这些同步方法。Mailbox 比 oplog 的持久未读先出现，后来就成了镜像；
维护者在 [mail 与激活](mail-and-activation.md) 里裁决过同类问题：“内存本身是不稳定的”。

**改成：** Mailbox 真正提供、oplog 不提供的只有两样，用小东西保留：

1. 每个窗口一把锁，保证“写 chatlog + 登记到达”对读取方是一步：一个“窗口 → 锁”的字典；
2. 让 `capture_chat` 找到路由刚登记的事件对应哪个到达号（路由不许往事件 dict 里塞键）：
   一个有上限的“事件对象 → 到达号”对照表。

其余未读查询全部问 oplog。一次切换所有使用者，不留两份并存的中间版本。
`context.py` 回到“当前事件、等待输入、轮”三件事，删掉约 230 行。

### 第 5 步：收尾

- 旧版 `_stream_results` 到达的恢复桥，确认生产里已没有这类未处理记录后删除（部署和查看生产数据前另行确认授权）；
- 给离线回放一个明确入口，实验不再直接改 chat 的全局变量、调私有函数；
- 更新现行文档：`llm.md`“上下文如何组装”一节和第 5 条“超限时截断更早的内容”、交互模型里关于输入预算和
  “报告已兑现前缀”的描述、架构文档里的 Mailbox。

### 不在本计划里

- `chatlog.py`（1566 行）拆出档案查询：两半互相调用比 chat 乱，收益也最小，另议。
- `browser.py`、`tools/__init__.py`、`llm/__init__.py`：大但单一，没有观察到因此出错；
  其中 `tools/__init__.py` 需要的是“这层机制解决了什么问题”的讨论，不是拆文件。

## 5. 怎样验证

全部用仓库外的一次性脚本和临时运行目录，不新增测试，不碰真实数据、端口和账号。

- **每个提交：** `run.py --check` 通过，公开模块数仍是 84；`run.py --smoke` 与同机改前一致
  （本机基线 82/84，可选失败只有 `mcf`、`minecraft`）。
- **搬家提交：** 旧文件每个顶层定义在新文件里恰好出现一次，AST 相同，唯一允许的差异是 `chat.` 前缀；
  旧的公开名字都还在；仓库里所有 `chat.xxx` 引用都能解析；`WHY:` 条数不变。
- **第 1 步：** 各种非法记录在写盘前被拒，日志文件字节和内存都不变；人为让写盘后的改内存出错，确认后续写入被停止。
- **第 2 步：** 合成一段超过 40000 token 的经历：首次加载选出起点；模拟重启后起点不变；新事件继续累加而不裁剪；
  75% 出提醒、100% 出强制要求；`cover_events` 后占用下降；手动重置后重新选起点。
  另测：一条很长的消息完整读入；`take` 很多条、来源桥很长都不报错；条数上限仍生效。
- **第 3 步：** 同一串工具调用在改前改后返回的文字和写出的 oplog 一致。
- **第 4 步：** 同一串合成事件（普通消息、@、补回与实时重合、`mark_read` 后再到达、取消）分别喂给改前和改后的代码，
  比对 oplog 写出的行和模型收到的消息。

## 6. 已有的证据：chat 试拆

2026-09-26 在仓库外按第 3 节规矩用脚本自动拆了一遍 `chat.py`（只搬家），并改了 `meta.py`、
`tools/agents.py`、`experiments/memory_replay.py` 的私有引用：

- `--check` 通过，公开模块仍是 84；`--smoke` 与改前相同，82/84；
- 163 个顶层定义 AST 全部相同，其中 26 个函数只多了 `chat.` 前缀；`WHY:` 64 条不变；93 个公开名字都在；
- 五个子文件之间没有环。但子文件运行时要回读 `chat/__init__.py` 里的设置，而 `__init__` 又导入子文件，
  所以包这一层仍是双向的：`__init__` 要负责“设置放哪”和“对外名字清单”两件事。

这只证明搬得动、没搬坏，不代替正式提交时重跑第 5 节。

## 7. 完成的标志

1. token 和条数上限只在首次加载与手动重置时决定起点；读消息不再因 token 截断、分批或报错。
2. 未读只记在 oplog 一处。
3. `meta.py` 不知道未读成员怎么排、请求长什么样、会话消息怎么删，只调用 chat 提供的普通函数。
4. oplog 不会先写盘再拒绝可预见的错误；写盘后出任何错都停止后续写入。
5. `chat` 拆成文件夹，每个文件都能一口气读完。
6. 第 2.4 节列的现有产品行为都还在。
