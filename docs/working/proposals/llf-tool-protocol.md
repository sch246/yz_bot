# LLF 纯文本工具调用迁移

> **可选长期格式方向，尚未实施，不是统一信息流的必要条件。** 维护者先前所说的「放弃 JSON，使用 LLF」是**模型与 Bot 之间的工具调用／结果以纯文本承载**，不是只把 LLF 放入供应商原生 `tool_calls` 的 JSON 参数中；2026-09-23 明确裁定「LLF 不是必要的，工具协议是可绕过的」。当前仍用原生工具调用协议，见[模型与工具现状](../../llm.md)；[统一信息流计划](unified-event-stream.md)不等待 LLF，压缩／索引进度见[交接索引](condense-and-unify-handoff.md)。LLF 是独立格式草案，不在本仓库内定义其语法或版本。

## 从交互轨迹出发

第一性的是智能体与世界的交互：它的输出与世界的输入都可能留下需要再读、引用或总结的痕迹，属于**同一条信息流**。所谓「工具调用」不是要另造一种独立存在的对象类型；一次发出的行动和随后收到的结果，是流中各自可能留下的事实。若需要说明因果关系，后者引用前者的记录 id，不要求二者相邻，也不要求每个输入都有来源。此前定为仅在轮内使用的思考和自言自语可以丢弃；需要跨轮理解、引用或总结的交互痕迹则应可索引。**不能按 API 字段或是否发往 QQ 决定**：纯文本调用也可能是 assistant 正文。

LLF 用行结构界定多行字面值，避免文本靠层层转义维持边界，并允许逐行解析。它使调用与结果都可以在普通文本信息流里表达，不必为供应商原生 `assistant(tool_calls)` → `tool` 的人为配对校验改变 mail 的阅读次序。**格式校验是执行器识别边界所需的机制，不是决定信息是否存在、是否值得留痕的本体规则**；LLF 也不决定何时执行、谁能执行或新消息何时进入下一次模型请求。

## 迁移前必须闭合的边界

1. **不能因历史重放或阅读引用再次执行旧输出。** 本次新生成、处在调用帧内并通过调用 schema 校验，是一种候选的执行边界；它不决定输出和拒绝执行的反馈是否值得留痕。截断或非法帧也不能产生未承诺的外部副作用。
2. 派发行动前，执行器须已为对应输出取得并登记可引用的统一 id；模型生成时不需预知正式 id。其余输入输出要不要留存、怎样划分记录，依据需要保留的信息，不按「同步结果／异步回调」等标签预设。`say` 的已确认回声必须能可靠关联；其它来源关系仅在确实需要时保留，不能靠邻近时间或正文猜测。
3. 模型完成当前输出片段后，才在下一阅读间隙接入 mail 中排队的输入；这一批输入内部按 mail 接收顺序阅读。B 在生成 D 时已入队，也应是 **D→B**，不能误写成模型生成 D 时已知 B。**机制推论：**自身刚产生的输出无需再作为未读 mail 投递，但不重复投递不等于从可读历史删除。统一信息流**不预设唯一物理日志或新对象层级**；留痕、恢复和总结覆盖的最小记录形状仍待身份／压缩主线验证。
4. 在隔离的合成流中对比现有协议：多调用并发、返回倒序、回声早于结果、异步跨轮、帧截断、历史重放、执行后崩溃。证实语义和停止条件后才安排生产切换，不同时保留两套可执行调用权威。

**尚未决定：**具体帧／结果的文本外形、逐帧提交与更早流式执行的边界、失败恢复、旧记录如何收束或淘汰，以及供应商对纯文本格式的实际表现。旧 `opN` 等半成品形态不享有迁移兼容承诺；不应为了适配它们制造长期双轨。不能从「无转义」直接推出无风险可执行或自动实现跨轮异步关联。
