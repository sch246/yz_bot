# 可编程经历数据：让 Python 组合查询，而不是继续增加专用工具

> 状态：P0、P1 已完成，下一步是 P2 的一次模型自审闭环。隔离回放不读取生产聊天、不替换现有查询工具，也不改写持久事实。后面的工具退役和全量恢复迁移只是进入条件，不是已排期实现。
>
> 现行行为仍以[运行架构](../../architecture.md)、[交互模型](../../interaction-model.md)和[LLM 文档](../../llm.md)为准。长期记忆的价值与实践反馈分别见[记忆估值与索引演进](memory-valuation-and-index-evolution.md)和[长期记忆离线回放实验](memory-replay-evaluation.md)。

## 这次修正了什么

现有方向容易把每一种模型需求都翻译成一个新工具：按范围反查、查引用、查未读提及、查档案附近消息、查状态。这样可以完成已想到的问题，却会把未来查询限制在维护者预先写好的参数和对象上；模型若想临时换一种筛选、对照或图遍历，往往又要扩充 schema。

本计划改成：

1. 已有 `exec_code` 继续作为唯一通用 Python 入口，不新增 Python 工作台、查询语言或 agent 状态管理器；
2. 消息、经历和引用尽量以普通 `dict`、`list` 或惰性迭代器出现；
3. 筛选、分组、统计、路径检查和临时图由模型用普通 Python 组合；
4. 只有改变外部世界或持久事实的动作保留明确提交边界；
5. 是否删除专用查询工具由实际使用证明，不以“工具越少越好”先验决定。

这不是把 class 机械换成 dict。若同一事实仍有多份可写镜像、同步顺序仍隐藏在调用者脑中，普通容器只会把复杂度藏起来。目标是减少模型必须学习的概念，同时保持一个事实一个写入权威。

## 不新增的东西

- 不新增 `World`、`Snapshot`、`AgentState`、Memory Manager 或第二棵可写记忆树；
- 不把 `ctx` 改造成当前上下文或主体自我模型；
- 不把 event log、chatlog 和终端日志复制进统一数据库；
- 不监听任意 dict 原地修改并猜测它是否应该持久化；
- 不为所有未来查询预先设计通用事务、操作语言或筛选 DSL；
- 不因有 Python 就让普通聊天模型绕过 Bot 自身权限；
- 不在第一阶段重写 oplog 恢复、FIFO、覆盖、发送或工具 registry。

`ctx` 继续只是共享 Python 环境中的“模块名 → 已加载模块对象”字典。它负责让模型找到能力，不承担认知状态。

## 三种记录保持分开

| 记录 | 回答的问题 | 权威与用途 |
|---|---|---|
| 结构化 event log / oplog | 柚子实际读到、输出、行动和覆盖过什么 | 主体经历与稳定引用的事实来源；支持重建和记忆关系 |
| chatlog | 某个聊天窗口实际发生过什么 | 世界档案；包含尚未正式进入主体经历的消息 |
| 终端运行日志 | 代码这次怎样执行、哪里报错或重试 | 运维与排障材料；不能证明模型确实读到某条输入，也不是记忆权威 |

三者可以通过正式号、窗口、消息号、档案位置或交互标识关联，但不因此合并为一个对象。

## 模型如何认识自己

只保留三个小入口，不建立“自我认知系统”：

1. **短 Skill 说明行为区别。** 写清 `ctx` 是模块表、经历与聊天档案的区别、直接正文不等于 `say`、Python 扫描不等于模型逐条读过、需要长期留下的改变应写到哪里。只给名字和短例子，不复制整份源码说明书。
2. **源码回答机制问题。** 模型需要知道某函数到底如何工作时，精确读取对应函数，而不是开局加载全部实现。
3. **本轮结果和运行痕迹回答实际发生。** 工具返回、状态和必要的日志说明这一次是否发送、是否失败、是否已经提交；源码只能说明可能如何运行。

## 长历史的最小数据形状

目标不是把几百 MB 历史变成一个常驻 Python list，而是让磁盘记录表现为普通可迭代数据源：

```python
for event in iter_events(start=..., stop=...):
    ...
```

实现要求：

- 按现有日期分片逐文件、逐条或小批解析，调用者用完即可释放；
- 产出与运行中权威脱离的普通记录，不能把 `_events`、嵌套消息、Mailbox 条目或其它活对象直接交给模型修改；
- 第一阶段只依赖已有日期和正式号缩小范围，不预建新索引；
- 查询慢与内存大是两个问题：惰性迭代只解决后者；出现可重复的慢查询证据后，再增加可重建索引；
- 迭代器返回四类正式经历和独立 `cover` 关系；正文引用在每条正式经历上派生且保留断号。source/FIFO 水位等技术记录不混进这条经历迭代器。

当前 `oplog._restore()` 仍会把全部日志重放进内存。新增迭代入口不会改变这一事实，也不得宣称已经实现无界历史。全量恢复只有在实际消费者逐一迁出后才能删除。

## Python 扫描不等于主体读完

Python 可以扫描十万条磁盘记录，只把十条匹配和统计结果返回模型。主体经历的是这次行动及其返回，不是那十万条原文逐条进入上下文。

因此：

- 仅被 Python 扫描的旧记录不重新编号，也不自动推进 FIFO 水位；
- 返回模型的选中结果作为现有同步行动返回进入统一经历流；
- 若模型据此建立总结，必须把最终采用的具体正式号或稳定来源冻结进新节点；
- 不能只保存变量名、查询代码或“当时满足某条件的集合”，因为以后重跑可能得到不同成员；
- 自我审查必须能回到原文，不能只检查自己先前写下的摘要和派生图。

## 保留的提交边界

普通 Python 负责“看、选、算和检查”。下列行为仍须经过能持久恢复的窄入口，具体以后是否继续表现为独立 JSON 工具另行决定：

- `say`：向 QQ 产生真实外部输出，并处理发送成功、失败、未确认和收轮；
- `pull`：让 FIFO 内容正式成为主体输入并推进持久水位；
- `mark_read`：不伪造经历，只推进调用时已经存在的未读水位；
- `cover`：把明确成员和结论追加为可重建的记忆关系；
- `fetch`：从 NapCat 向本地档案和有名信源补充世界记录；
- Skill、hint 或代码的持久修改：明确写入相应载体，不能靠修改一次 Python 临时变量冒充已经学会。

这些入口保护的是事实含义、并发提交、失败恢复和外部副作用，不是为了限制模型能提出什么查询。

## 第一条纵切

只验证一件事：**柚子能否通过现有 `exec_code`，从磁盘按需读取一段自己的结构化经历，自行检查重复行动和断裂引用。**

### P0：确定记录单位

- [x] 列出当前正式经历、cover 关系、引用关系和 source/FIFO 技术记录分别住在哪些 journal 行；
- [x] 迭代四类正式经历及独立 `cover` 关系；文本引用逐条派生但不先过滤断号，多父关系由调用者从 cover 行计算；
- [x] `start` 含、`stop` 不含，均使用正式号中的日期和当日序号；cover 按物理 journal 位置自然出现。

### P1：只读磁盘迭代

- [x] 在 oplog 增加普通 Python `iter_events`；不注册新的模型工具；
- [x] 逐分片、逐行读取并返回由 JSON 解码得到的脱离内部权威的 dict；
- [x] 不调用现有全量 `_restore()`；隔离合成日志从 500 条增至 5 万条时，扫描峰值分别为 19,640 与 19,648 字节；
- [x] 旧运行路径和现有查询工具保持不变；隔离样本已通过真实 `exec_code` → `ctx["oplog"].iter_events()` 路径找出断裂引用，未把接口实验和全量恢复迁移绑在一起。

### P2：模型自审实验

- [ ] 在回放实验目录使用隔离历史，不读取生产数据；
- [ ] 样本包含一次重复行动、一条错误或断裂引用，以及至少一种现有工具 schema 没有预设的临时筛选条件；
- [ ] 模型通过现有 `exec_code` 自行编写筛选、分组或图检查；
- [ ] 允许它在观察结果后改变查询条件，不修改工具 schema；
- [ ] 要求最终说明依据的具体 ID，并回查至少一处原文，而非只验证自己的摘要。

## P2 之后的未排期方向

### 根据使用删工具

只有 P2 成立后，才逐个比较：

- `event_links` 是否已被普通 Python 图计算完全替代；
- `recall_events`、`read_messages`、`mentions`、`status` 哪些仍是高频且低认知成本的快捷入口；
- 复杂范围参数是否可以退回为 Python 选择 + 明确 ID 提交；
- 现有 `exec_code` 提示中“优先找现成工具、重复能力应做成工具”的方向是否应改为“先组合已有普通数据，稳定且高频后再沉淀”。

不追求一次删到只剩一个工具。工具调用更少不是成功条件；模型能改变查询而无需维护者扩 schema，才是这条方向的主要证据。

### 全量恢复迁移

只有磁盘迭代被实际使用并稳定后：

- [ ] 盘点 `_events`、`_by_id`、`_mentioned_by`、coverage、pending 和 source 状态的全部消费者；
- [ ] 区分必须常驻的当前尾部／未读水位，与可按需从磁盘重建的旧经历；
- [ ] 每迁出一类消费者就删除对应全量缓存责任，不保留新旧双权威；
- [ ] 只有重复扫描成本已经被观察到，才为具体查询建立可删除、可重建的派生索引。

## 成立与停止条件

第一条纵切成立需要同时满足：

- 没有新增总览对象、可写镜像状态或第二棵记忆图；
- 读取范围增长时，迭代本身不把整个历史常驻内存；
- 模型能临时改变筛选方式而不用改工具代码或 schema；
- 能定位样本里的重复行动或断引用，并给出可回查的具体依据；
- 需要保留的总结冻结实际成员 ID，重跑查询不会悄悄改变旧节点含义。

若模型为简单查询反复写错 Python、输出难以理解或始终不回查原文，先判断是入口不清楚、Skill 不足，还是模型本身没有形成有效检查方法。只有前两者直接支持改接口；第三者不能靠继续增加对象解决。
