# 压缩与反查：现状、目标与历史

> **状态：中心 reader、跨窗口覆盖与反查已在主线代码实现；持续自动总结和退休仍未实现。** 部署中的进程只有完整重启后才会使用对应版本。当前用户可见行为以[模型与工具](../../llm.md)为准；旧阶段方案在[历史归档](chat-condense-history.md)，不能把其中的聊天 `floor` 或旧退休算法当成今天的实现计划。执行路径见[阅读计划](chat-client-reading.md)。

## 当前代码

- 已有按模型实际阅读分配的统一事件号：一次完整模型输出共用一个号，行动以号内位置区分；入列但未读的 `arrival` 先持久保存，尚无正式经历号。信息流已按日分文件追加。
- 主聊天由唯一中心 agent 运行。`cover_events` 以一次行动的位置作节点，允许跨窗口点名已读或明确反查的成员，冻结实际覆盖成员及行动／返回／确认回声的绑定；同一事件可被多个节点覆盖。覆盖只隐藏默认投影，原文与节点仍可反查。
- `recall_events`、`event_links` 与文本引用索引可沿中心已读流跨窗口使用；`condense_ops` 只处理私有 `.chat` 的原生工具历史，**不是**中心聊天覆盖节点的生成方式。`status/fetch/peek/pull`、`event_span` 和中心 agent 已接线；NapCat 补回与独立历史信源见[离线恢复](offline-message-backfill.md)。
- 不做退休标记、不按 H 删除，也没有持续自动总结。模型末尾只在超过阈值时报告上下文占用比例；其它现行限制见[模型与工具](../../llm.md)。

## 已定且接线的阅读语义

- **只有经历的顺序。** 有界 `peek` 可以查看任意聊天片段，包括最新段；返回是新的可反查经历，但不消费持久未读。正式内容只按 mail FIFO 小段拉取，因此同一来源后来再次出现是第二次真实经历，不是要去重的错误。原消息来源位置不是第二套记忆 ID。
- 全局中心 agent 从按窗口列出的通知概况选择行动；普通新消息显示普通状态，`@`／提及明确标出。通知递交、未读正文与未完成的追读不能混成一条水位。全局 hint、主设置及费用归 Bot，`say` 必须明确目标。
- 全局已读事件可用统一号加半径或两号区间选择，再按需要过滤；过滤不重排，也不默认限当前窗口。一次跨窗口探索可折成一个节点，跨窗口反查、多重覆盖均允许；节点精确冻结所选成员与必要的强绑定，不吞掉夹在区间里的无关行动。
- 重放旧内容是在当前又经历一次。分段重放到合适位置时，可以把先前混乱的整理／探索收成可展开的节点，再继续阅读；旧事件不改号，节点保留反查路径，当前视图不必长期铺开重复原文。具体例子见[阅读计划](chat-client-reading.md)。

## 暂缓或待实现

- **退休暂缓。** 不知道合适的 H，且未证实存储压力；现阶段既不标记也不删除。若未来重开，应先报告不同 H 的实际影响；历史文档里「只换根、遍历原样回来」已被否定，不能复用。
- **持续整理尚未自动化。** 模型可按明确数量分段阅读、写 Skill／待办和显式 `cover_events`，但系统不替模型决定何时总结。NapCat 上游历史是否覆盖真实停机空窗尚待运行验收；首次构建大型归档索引的写入等待时间也尚待观察。不要把这些未验收项当成当前机制不存在。
