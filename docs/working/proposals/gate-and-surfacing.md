## 0. 来由

2026-11-07 这一天从“成本涨了，看不出效果有没有变好”开始，经过一次离线检索对照，又读了几个 DSH 记忆插件和 DeepSeek 的 super-agent 原型，讨论落到下面这几句维护者原话上：

> 整理经验的问题更大的是怎么确保需要的时候能触发……这说到底都是需要穷尽性的保证的，不如说长期记忆的问题就是穷尽可信的问题

> 只要占据注意力，那么提醒本身就是偏向。。异常检测可以很多，但是是否显出来要看是否需要……我想象的是水面下的小岛，注意力就像吹风机把部分地方的水位给吹低，但是只要一移开又淹没

> 原子应该有生命周期……数据结构应该是静态的吗？可以学习和进化吗？……许多长期记忆插件构造了复杂的结构，增加了更多的上下文，往往导致最后结构本身的维护成为了负担

> 目的可派生吗？什么是目的？它理解为势差是否更合适？熵导致情绪（同时解释预测偏差和学习率），情绪好像也是一种势差？

> 一条线是一件事，线往往是相互交叠和分叉的，这个判定肯定不能程序化，但是这就引入 agent 判断了，对于人来说这个就是情景/临时记忆切换……因为 agent 判断是昂贵的，所以程序化整理是有必要的，包括我们提到的信号计数，或者可以做一个读空气的数据统计这种，都是同一类东西

## 1. 视角：岛、水位和门卫

这一节是讨论里形成的工作假设，用来给第 3 节的未决项定位，不是实现合同。

**四层。**

1. **常驻的廉价信号（门卫）。** 不调模型，一直在算：面包屑、相近笔记、引用回复、信号计数、读空气统计。它们只产出“高度”，不直接进上下文。
2. **目的决定水位。** 正在做的那件事，把和它有关的地方水位压低。和它有硬连接的（回复了她刚说的话、同一个人接着说）降得最多，只有软关联的（用词相近）要高出更多才露头。
3. **露出来的交给模型判断。** 判断贵，所以只看露出来的几样。
4. **判断的结果回头校准门卫。** 露出来以后她用没用、她自己翻开了什么而门卫没点到，都记下来；慢路径做过的决定，变成快路径下次的规则（第 18 节“慢路径的决定变成快路径的规则”）。

**穷尽靠结构，不靠排序。** 排序给不了穷尽：前 N 名之外总可能漏，而且不知道漏了什么。能穷尽的只有每次把所有条件都检查一遍、而每个条件又足够便宜的情况，面包屑就是这样，所以点到的一定可信。代价是条件得有人写。能保证“需要时一定被想起”的，只有自己声明了触发条件的原子：承诺、带时间的 todo、awaker 规则、笔记的名字和别名。普通经验只能尽力排序。

**结构靠使用顺带维护。** 伸展树（Sleator & Tarjan, 1985）每次访问把节点转到根，数据库裂解（Idreos 等, 2007）让索引只长在被查过的地方。两者的维护都是访问的副产品，没有单独的整理步骤。别名随漏网补、目录按使用的激活度挑（ACT-R 基础激活，Anderson & Schooler, 1991），都是这个方向；以后加的门卫信号也应当这样，不另起一套整理流程。

**目的作为势差。** 外部势差（消息到了、被点名）、存着的势差（todo、承诺、黑板上悬着的事）、预测落空，都是“期望和现状之间的差”。构造问的“现在该干什么”是挑最陡的梯度；一条线服务于一个集中的目的，势差抹平，线就结束。情绪在这个框架里可以读作势差的变化率：Joffily & Coricelli（2013，PLoS Comput Biol）把效价定义为自由能变化率的负值；Behrens 等（2007，Nature Neuroscience）显示学习率跟着环境波动性变。这两条只是可以对照的文献，还没有落到任何设计上。

**super-agent 的对照。** DeepSeek 的原型（[dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)，研究原型）同样拒绝按语义分派：Thread 由来源的结构定义（同一个 PR、同一个话题、同一串回复），“话题相近本身不够”，关联（Correlation）只补上下文、从不分派。它的门卫只认谁发的、在哪发的，读内容的判断交给模型。线的交叠和分叉，就被拆成程序能确定的硬连接（分派）和语义上的软关联（材料）两层。

## 3. 未决项

每项写明：要决定什么、现在有什么证据、建议、哪份记录能回答。

### 3.1 门卫信号用一份记录还是各记各的

**问题。** 信号计数、读空气统计、引用链、相近笔记、漏网，都是门卫层的“高度”。如果各自记账、各定露头规则，就又回到“激活、存储、链接各管各的”。

**建议。** 一份记录。现有的 `data/usage/recall/` 已经按 `event` 区分行的种类（`wake`、`open`），新信号加新的 `event`，共用时间、窗口、ctx 这几个字段。等种类多了再考虑改名（例如 `gate/`）；现在改名没有好处。

**要维护者定的。** 同意一份记录；新信号是否一律先只记录、不影响行为（建议是）。

### 3.2 露头规则

**问题。** 水位由当前目的决定，但目的在代码里落在哪？可选的落点有构造交的 `focus`、规格负责的窗口、黑板上悬着的事。

**选项。**

- (a) 每种信号一个固定门槛。最简单，不看目的。
- (b) 硬连接总是露头，软关联要过门槛。硬连接指引用了她的话、在她负责的窗口里接着说，软关联指用词相近、别的窗口提到同一个词。
- (c) 不推送，让构造需要时去拉：信号只放在一个可读的地方，构造用工具查。
- (d) 先 (b)，等记录够了再讨论更细的规则。

**建议。** 先不定，等 3.1 的记录积累两周。到时候拿真实记录对比 (b) 和 (c)：同样的唤醒，哪种露出来的东西她更常用。

**要维护者定的。** 记录多久再来定（建议两周）。

### 3.3 QQ 引用回复作为第一个硬连接

**问题。** QQ 消息里的引用回复 `[CQ:reply,id=…]` 已经在聊天记录里，`mods/msgs.py` 能解析，但画面和注意力层都没有用它串线。它是 super-agent 唯一信任的那类连接：结构上确定，不需要理解内容。

**建议。** 第一个接入门卫的新信号就是它，只记录：被引用的消息是不是她的、是不是她当前负责窗口里的、离她那条过了多久。先不改变叫醒、防抖和画面。

**要维护者定的。** 同意先做这一项；“引用了她的话”以后是否允许绕过防抖立即叫醒，留到有记录再说。

### 3.4 读空气统计

**问题。** 哪些量值得统计。下面全部是结构或计数，不需要理解内容：

- 接话结构：她上一条发出后，多久有人回，谁回的。
- 节奏：窗口里的消息速率；是不是两三个人在快速往来；她插话后节奏有没有变。
- 指向：有没有点她的名字或别名；有没有问号紧跟在她的话后面。
- 连续性：新消息和她上一条的用词重合度（现成的 BM25 就能算）。

**建议。** 单个都不可靠，但都便宜。先挑两个只记录：她发言后的回应延迟，以及新消息和她上一条的重合度。看它们能不能预测“她接了这条线”。能预测的再谈露头。

**要维护者定的。** 先做哪两个；以及“她接了这条线”在记录里怎么认（建议：下一次行动负责这个窗口并发了言）。

### 3.5 线的归属与续接（第 18.3 节的续篇）

**问题。** super-agent 让 Worker 订阅它负责的 Thread，后续消息由程序直接送达，不经过 Router；Worker 判断超出范围时交还一次，并写明理由。这和 18.3 撤回的快路径不同：被撤回的是“跳过构造、从零判断”；Worker 是“沿一条早先串好的线求值”，也就是 18.3 认可的那种快路径。它判断要不要交还只需要对照这件事的范围，不需要完整的知识。18.3 留的方向“同一段对话接着聊时，构造沿用上次给这个窗口的规格”，是它的弱化版本。

**代价。** 据 DeepSeek 文章的转述，多会话方案读缓存的 token 是单会话的 2 到近 4 倍，换来的是速度和连续性。线一直活着不是免费的。

**没解决的。**

- 聊天里一件事的“范围”是什么、由谁写：构造的 `focus`？她自己？
- 线什么时候结束。势差抹平的判据在代码里落在哪？超时？她说“这件事完了”？
- 线的交叠：同一窗口里两件事并行，一条消息该给哪条线。按 3.3 的结论，只有硬连接能分派。
- 和“说话一律经过构造”的关系：续接时这一步算不算经过构造？

**建议的第一步。** 先不改运行方式，做离线回放。构造已经有重放功能（`construct.replay`）。挑同一窗口里相邻两次唤醒的历史记录，让构造在第二次唤醒时看到上一次给这个窗口的规格，量两件事：它会不会选择沿用；沿用时的输出长度和缓存命中。这一步能回答“组合缓存”能省多少，再决定要不要往“线一直活着”走。

**要维护者定的。** 是否做这次回放；“范围”和“结束”有没有倾向。

### 3.6 每次运行记下依据的版本

**问题。** 删掉 `assess_change` 以后，“证据要晚于改动”只靠说明（见 `mods/tools/memory_system.py` 末尾的 WHY）。super-agent 在每个决定里都记下当时的 Policy 版本，提示的每次修改都留成一个不可变的版本，每个会话记着自己用过哪些版本。

**建议。** 每次运行在视图的 `stats` 里记下 `policy/construct`、`policy/settle`、`global`、`self` 当时的摘要。评估 `changes.md` 时，程序就能直接筛出“改动之后的运行”，夜里交给她，不靠她自觉。改动小，不加新工具，只多几个字段。

**要维护者定的。** 记哪几份文件（建议上面四份，`recent` 变得太频繁，不记）。

### 3.7 相近笔记什么时候挂出来

**问题。** 现在照算不显示（`construct.SHOW_SIMILAR = False`）。召回日志记着：面包屑没点到、她自己翻开的笔记，在候选里排第几。

**建议的判据。** 部署后累计至少两周、至少 50 次“面包屑没点到的翻开”。其中排在候选前 8 名的比例：

- 达到四成以上：挂出来，再记一段时间，看翻开率是否只是因为它摆在眼前。
- 低于一成半：删掉这项功能（`notes.similar` 的 WHY 已写明“别加权重去救”）。
- 介于两者之间：维持影子模式。

**要维护者定的。** 这两个数字。

### 3.8 激活度用在哪

**问题。** 现在只用来挑目录里列哪 80 份，眼下影响很小。它同样可以用来给相近候选排序、在面包屑命中太多时取舍、决定黑板上 `@引用` 的折叠顺序。

**建议。** 等 3.7 有结论再说。在激活度证明有用之前，不把它用到更多地方。

### 3.9 “效果”怎么算

**问题。** 这一切的起点是“成本涨了，看不出效果有没有变好”。现在成本可以按请求逐条拆开（请求组成记录 + usage），效果还没有定义。

**可用的代理量**（都能从已有记录派生，不需要新的写入）：

- 每次唤醒的 token 和缓存命中，按运行种类分开。
- 面包屑命中率、漏网次数。
- 构造被退回的坏引用次数、兜底次数。
- 行动里补读笔记的次数：构造漏带了材料，行动才要补读。

**要维护者定的。** 哪几个算“效果”，或者效果本来就只能由你看聊天来判断，这些量只算诊断。建议是后者：这些量只用来诊断，不当作目标去优化。

### 3.10 构造检查清单的结构化判断（暂缓）

super-agent 的 Router 要对每条规则都给结论（不匹配的也写），并附上原话作为证据；意图不明确时安静忽略，不去打扰人确认。柚子的 `policy/construct` 是一段文字，没人知道每一条有没有被考虑到。这样做会增加构造的输出和成本，等 3.9 有了结论再看值不值。

### 3.11 待查：LLMClient 配置的自引用清空

2026-11-07 提交的那批本地改动（`19b0cfd`）删掉了 `LLMClient.__init__` 里一条 WHY。它记的是 2026-09-17 的崩溃：用配置自身去更新自身，导致配置被清空。现在客户端经 `_LLMConfig` 代理两份字典，这个坑还在不在没有查过。需要有人读一遍代理的 `clear`/`update` 路径，再决定把 WHY 改写后放回去，还是确认它已经不适用。

## 4. 不做的

| 不做 | 理由 |
| --- | --- |
| super-agent 的 Eval/Mandate/准入表/授权强度 | 为多人团队、多账号的权限设计；柚子的信任模型是固定的一份 Bot 权限（见[运行架构](../../architecture.md#单实例权限与退出)） |
| 按语义把消息分派到线 | super-agent 同样拒绝；只有结构上的硬连接分派，语义关联只当材料 |
| 向量检索 | 离线对照里没有比 BM25 好；需要再测时，脚本可以复用 |
| 先存后做的副作用队列、Watchdog | 没有观察到要解决的问题；循环已经有“没事做就逐次延长间隔” |
| 门卫信号直接影响行为 | 一律先只记录，按 3.7 那样的判据再放开 |
