# Storage 加载校验与历史恢复

> 状态：部分未实现提案；热同步已实施

## 已实施的文件热同步

内存权威、十分钟滚动扫描、文件事件、baseline CAS、原子写、空文件恢复、`DELETE` 业务删除和失败日志已经成为当前行为，见[运行架构](../../architecture.md#storage-与设备状态)。本文件不再保留旧的 manifest 和多写入间隔方案，避免把已放弃的第二套同步模型误当成未来兼容要求。

## 加载校验

检查器保持为普通函数：`check(value) -> None`，失败抛带路径和原因的 `ValueError`。`storage.get(..., check=...)` 在功能第一次认领数据时验证，并记住函数供热加载复用；不引入 schema DSL、校验 class、自动迁移或自动修复。

- 文件不存在：调用方可显式使用 default；
- 文件存在但 JSON 无法解析：报错，不当作不存在；
- checker 不通过：报错，不安装进内存；
- 冷启动没有有效内存：必要数据使其 feature 启动失败，可选功能可明确禁用自身；
- 热加载失败：保留当前有效内存并等待修复；
- checker 自身异常：保留 traceback，不能退回默认值。

Storage 已收集启动解析错误到 `load_errors`，并在功能通过 `get()` 认领坏文件时拒绝退回默认值。这里剩余的提案是让功能提供 `check(value)`，并在初次认领和热加载时复用同一校验函数。

## Chatlog 双向恢复

这一节已经展开成独立提案，见[统一消息模型：窗口、正文与双向转换](message-model.md)。那里定义了最小事实集、v0/v1 的版本切线、明确不恢复的内容和实施顺序；本文件不再第二次断言 chatlog 的格式要求。

仍然成立的只有原则本身：chatlog 以实时追加的人类可读文本为主，不保存冗余的全量 OneBot JSON；恢复结果必须标明哪些字段是原始事实、缺省值或推导值。

## 剩余提案的最小验收

- 被功能认领的值在启动和热加载时经过同一个 checker；
- checker 失败保留最后有效内存和完整错误原因；
- chatlog 的验收条件移交[统一消息模型](message-model.md)，不在本文件重复。
