# 日志分流：流的身份与出口

> 状态：第 1 步（行原子）已实施，其余未实现。

本篇与[异常、日志与 link 报错节流](errors-and-logging.md)正交：那篇分的是**严重程度**（ERROR/WARNING/INFO/DEBUG 与 incident），本篇分的是**流的身份**（哪个子系统、属于哪次交互）。两条轴互不替代，混用其中一条去描述另一条正是当前问题的来源。

## 已经观察到的问题

1. 一次 LLM 调用会把整条请求消息栈打进终端。轮内重复已经消除（每轮只打新增，通常为零），但**每次聊天仍有约 68 行**，其中 62% 是整场对话都不变的工具 system 提示。
2. ~~至少三个线程同时写同一个 stdout，其中两个写半行~~（第 1 步已修）：`mods/llm/console.py` 的流式 delta（`end=""`）、`mods/bot.py` 收到消息时的时间戳前缀（`end=""`）、`mods/tools/agents.py` 最多 5 个子任务线程。**一条消息在模型吐字中途到达，就会插进模型那句话中间。** 这不是观感问题，减少输出量也修不掉。
3. 三个模块已经各自发明了标签：`[storage]`、`线程 N:`、`[时间]【收到消息】`。同一条轴被重复发明三次，说明它确实缺一个统一表达，而不是需要有人多加几个前缀。

## 现在有什么

- `mods/log.py` 已经建立了两个出口：`app.log`（INFO 以上、保留完整 traceback）和终端（WARNING 以上、剥掉 traceback）。它的注释已经写明意图：文件是证据，终端是状态面。
- 但这条轴只按严重程度分。请求栈不是 warning 也不是 error，它是某个子系统的批量轨迹，于是 `mods/llm/console.py` 和另外 42 处 `print` 全部绕开 logger 直写 stdout。
- `_ConsoleFilter` 已经在按 `record.name` 做路由（屏蔽 `mods.storage`）。**按名字分流的机制已经在用了，只是没有被承认成一条设计轴。**
- `chatlog` 是已经存在的独立流先例：自己的目录、自己的格式、自己的消费方式。
- `context` 已经持有交互身份：`current()` 是线程绑定的当前事件，`interaction_key()` 给出 `(group_id, user_id)`。

## 提案

一条记录携带两件事：**出口**（它属于哪条流）和**归属**（它属于哪次交互）。消费者是可插拔的 handler。

### 出口 = logger 名

`yz.llm.request`、`yz.llm.message`、`yz.msg`、`yz.storage`、`yz.mc`、`yz.link`…… 产出者只负责选一个名字，不关心谁在看。

不自建消息总线：stdlib `logging` 已经提供名字层级、多 handler、filter、写入锁和按日轮转，而且这个仓库已经在用它按名字过滤。自建一套只会多一个概念、少一份成熟度。

### 归属 = 一个 filter 注入，调用点不改

一个 `logging.Filter` 从 `context` 读当前事件，把 `(group_id, user_id)` 挂到 record 上。**所有现有和未来的日志调用都自动带上归属，没有一个调用点需要传参**——这是这套方案可扩展性的关键，也是它比"每个 print 自己加前缀"强的地方。

### 消费者 = handler

| 消费者 | 形态 | 何时加 |
|---|---|---|
| 终端 | 订阅集可改，见下节 | 第一步 |
| 每流一个文件 | `log/llm.log` 等，tmux 开窗口 `tail -f` | 第一步 |
| WebUI | 内存环形缓冲 + 订阅队列 → SSE/WebSocket | 真要做 WebUI 时 |

加一个消费者 = 加一个 handler；加一个产出者 = 选一个名字。两者互不影响，这是选择这套方案而不是"直接把 print 改成写文件"的唯一理由。

## 终端订阅集

终端不预先规定留哪些流，而是订阅一组流名前缀，订阅集存在 storage 里可以随时改：

```text
.log                     列出已知流、各自是否被订阅
.log on yz.llm           订阅一条流（前缀匹配，含 yz.llm.request 等子流）
.log off yz.storage      退订
.log only yz.msg yz.link 一次替换整个订阅集
```

- **前缀匹配来自 logger 名的层级**，不需要另写匹配规则：订阅 `yz.llm` 自动包含它下面所有子流，订阅 `yz` 就是全订，空集就几乎不打印。
- **默认订阅集覆盖当前所有 stdout 产出者**，所以迁移完成时终端行为与现在接近；操作者是主动往下减，而不是被动发现少了东西。
- **改动立即生效，不需要重启**：filter 每条记录读一次 storage 里的当前列表，而 storage 是内存权威，这就是一次 dict 查找。
- **属于 Bot 实例级配置**，不是聊天窗口级：终端只有一个，`.chat image` 那种按窗口存的做法在这里不适用。命令需要 op。
- **已知流不需要注册表**：filter 记下启动以来出现过的 logger 名，`.log` 同时列出"已订阅"和"出现过但未订阅"。新增产出者零登记即可被发现。

### 不可退订的恢复底线

订阅集只控制 INFO 级的流量。**WARNING 以上无论是否订阅都进终端**，退订不能让故障静音。终端的实际内容是：

> （已订阅流的 INFO 及以上） ∪ （所有流的 WARNING 及以上）

这条底线不是保守，而是本仓库的既定优先级：动态能力可以损坏，恢复入口必须还在。同理，进程启动与退出摘要由 `main.py` 直接打印，不走流，也就不受订阅集影响。

与[link 报错开关](errors-and-logging.md#聊天提醒节流)的一个有意不对称：那个开关重启后恢复开启，因为它静音的是用户可见的聊天提醒；终端订阅集则持久保存、重启不重置，因为它静音的只是终端的 INFO 流量，证据仍在每条流各自的文件里，而且底线保证错误照常可见。

退订永远不丢证据：订阅集只过滤终端 handler，文件 handler 不受影响。这正是可以放心大幅退订的原因。

## 流式粒度

LLM 输出是逐字 delta，而日志记录是整条形状的。两者不该硬塞进一个粒度：

- **v1**：只路由整条消息（请求栈、完整回复、工具结果）。终端的流式打字效果保持现在的直写 stdout——它是终端的交互效果，不是日志。
- **v2（真做 WebUI 时）**：delta 也成为记录，但标成"易失"：只有内存订阅者收，文件 handler 过滤掉。写进轮转文件的逐字 delta 既巨大又不可读。

"易失"是一个 record 属性加一个 filter，由 delta 与整条消息的真实差别支撑，不是预留扩展点。v1 完全不需要它。

## 代价与边界

- 42 处 `print` 按模块增量迁移，新旧可以并存，不需要一次切换。
- **`mods/py.py` 的 `chat_print` 不是日志**：它把 `.py` 的 `print` 输出发到 QQ 聊天。扫 `print(` 时必须排除，否则会把用户可见输出误伤成日志。
- 终端将失去完整请求栈，改成一行摘要 + `llm.log`。这与"每次聊天打一次完整栈、往上翻就好"的先前结论相反，需要显式确认后再改。
- `llm` 流会包含聊天正文、提示词和工具参数。它必须与 `chatlog` 同等对待：设备本地、进 `.gitignore`、按日轮转限期保留，且不得复制进文档、提交或对外回复。
- 新增 `log/` 目录需要进 `.gitignore`（现有规则只覆盖 `app.log*`）。

## 里程碑

1. **行原子**（已实施）：`mods/log.py` 包装 `sys.stdout`，让持有半行的线程独占终端并继续直写，其余线程的完整行排队等它结束。**缓冲的是打断者而不是写作者**，所以逐字打字效果完整保留——这是终端唯一值得实时看的东西，不能为了整齐牺牲它。代价是后台的行可能稍晚出现；一行被持有超过 `HOLD_LIMIT` 会断行让路，避免无限等待。所有调用点不变，因此没有出口命名的必要前提——命名必须和终端订阅集一起落地，否则改名之后 INFO 级输出会直接从终端消失。
2. **出口命名 + 终端订阅集**：产出者改用带名字的 logger，同时加入订阅集与 `.log` 命令，默认值保持当前行为。两者必须同一步完成。
3. **归属注入**：加 filter，从 `context` 补 `(group_id, user_id)`。
4. **每流一个文件**：各流落盘，用 tmux + `tail -f` 看。
5. **订阅 handler**：真要做 WebUI 时再加，此前不写任何为它准备的接口。

## 未决

- **归属粒度**：`(group_id, user_id)` 标识的是一条交互线，不是一次活动。WebUI 若要"展开这一次 `.chat` 调用"，需要在 `context` 里再加一个每次活动的自增 id。这是本提案唯一需要新增状态的地方，做 WebUI 之前不必决定。
- **默认订阅集的具体内容**：迁移完成时应逐条对照当前 stdout 产出者确定，使默认行为与现在一致，而不是先拍一个集合再补差异。
- **是否需要命名预设**（例如在"日常"和"调 LLM"之间整组切换）：订阅集是 storage 里的普通列表，预设可以后续单独决定，第一版不做。
- **LLM 流式打字是否算流**：它是终端的交互效果而非记录（见上节流式粒度），第 1 步已确认它必须保留。若它也纳入订阅集，需要先解决 delta 记录与文件 handler 的关系，以及退订它之后终端还剩什么。
