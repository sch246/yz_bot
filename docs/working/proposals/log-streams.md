# 日志分流：流的身份与出口

> 状态：第 1-4 步已实施（行原子、出口命名与终端订阅集、归属注入、每流一个文件）。只剩第 5 步的订阅 handler，等真要做 WebUI 时再说。

本篇与[异常、日志与 link 报错节流](errors-and-logging.md)正交：那篇分的是**严重程度**（ERROR/WARNING/INFO/DEBUG 与 incident），本篇分的是**流的身份**（哪个子系统、属于哪次交互）。两条轴互不替代，混用其中一条去描述另一条正是当前问题的来源。

## 提案

一条记录携带两件事：**出口**（它属于哪条流）和**归属**（它属于哪次交互）。消费者是可插拔的 handler。

### 出口 = logger 名

`yz.llm.request`、`yz.llm.message`、`yz.msg`、`yz.storage`、`yz.mc`、`yz.link`…… 产出者只负责选一个名字，不关心谁在看。

不自建消息总线：stdlib `logging` 已经提供名字层级、多 handler、filter、写入锁和按日轮转，而且这个仓库已经在用它按名字过滤。自建一套只会多一个概念、少一份成熟度。

### 归属 = 一个 filter 注入，调用点不改

一个 `logging.Filter` 从 `context` 读当前事件，把 `(group_id, user_id)` 挂到 record 上。**所有现有和未来的日志调用都自动带上归属，没有一个调用点需要传参**——这是这套方案可扩展性的关键，也是它比"每个 print 自己加前缀"强的地方。

已实施：群聊渲染成 `[g<群号> u<QQ>]`、私聊 `[u<QQ>]`（沿用 `.post` 已有的 `g`/`u` 记法），没有当前事件就是空串，所以后台记录的行形状和以前一样。只有落盘出口带归属，终端不带——终端是状态面，保持产出者自己选的形状；归属属于事后追查，而追查看的是文件。

### 消费者 = handler

| 消费者 | 形态 | 状态 |
|---|---|---|
| 终端 | 订阅集可改，见下节 | 已实施 |
| 每流一个文件 | `log/<流>.log`，tmux 开窗口 `tail -f` | 已实施 |
| `app.log` | 只记严重程度：全部 WARNING 以上 + 非流 logger 的 INFO 以上 | 已有 |
| WebUI | 内存环形缓冲 + 订阅队列 → SSE/WebSocket | 真要做 WebUI 时 |

**文件按顶层流名分**：`yz.llm.request` 和 `yz.llm` 同写 `log/llm.log`。子流是订阅粒度，不是文件粒度——分开订阅有意义（只要请求栈不要别的），分开 tail 没有，而且 `tail -f log/llm.log` 看整个子系统正是想要的；完整 logger 名在每行上，要挑子流用 grep。文件在该流第一次产出时才建，与"已知流不需要注册表"是同一件事的两面。

加一个消费者 = 加一个 handler；加一个产出者 = 选一个名字。两者互不影响，这是选择这套方案而不是"直接把 print 改成写文件"的唯一理由。

## 终端订阅集

终端不预先规定留哪些流，而是订阅一组流名前缀，订阅集存在 storage 里可以随时改：

```text
.log                     列出已知流、各自是否被订阅
.log on yz.llm           订阅一条流（前缀匹配，含 yz.llm.request 等子流）
.log off yz.storage      退订
.log only yz.msg yz.link 一次替换整个订阅集
```

- **前缀匹配来自 logger 名的层级**，不需要另写匹配规则：订阅 `yz.llm` 自动包含它下面所有子流，订阅 `yz` 就是全订，空集就几乎不打印。
- **退订要能从更宽的订阅里挖除**，否则默认全订之下第一个动作就失效：订阅集里以 `-` 开头的条目表示挖除，**最长前缀胜出**，于是 `["yz", "-yz.storage"]` 读作「除 storage 外全看」。这一条不是预留的表达力，而是默认值直接逼出来的。
- **默认订阅集就是流的根 `["yz"]`**：所有原先直写 stdout 的产出者都迁进了这个根，于是「默认 = 当前行为」由构造保证，而不是靠一份会漂移的枚举维护；以后新增产出者同样默认可见，与今天新写一个 `print` 一致。操作者是主动往下减，而不是被动发现少了东西。
- **改动立即生效，不需要重启**：filter 每条记录读一次 storage 里的当前列表，而 storage 是内存权威，这就是一次 dict 查找。
- **属于 Bot 实例级配置**，不是聊天窗口级：终端只有一个，`.chat image` 那种按窗口存的做法在这里不适用。命令需要 op。
- **已知流不需要注册表**：filter 记下启动以来出现过的 logger 名，`.log` 同时列出"已订阅"和"出现过但未订阅"。新增产出者零登记即可被发现。记的是所有 logger 名而不只是 `yz.*`，所以 `mods.chat` 这类模块 logger 也能被订阅进终端，无需为此另开机制。

### 不可退订的恢复底线

订阅集只控制 INFO 级的流量。**WARNING 以上无论是否订阅都进终端**，退订不能让故障静音。终端的实际内容是：

> （已订阅流的 INFO 及以上） ∪ （所有流的 WARNING 及以上）

这条底线不是保守，而是本仓库的既定优先级：动态能力可以损坏，恢复入口必须还在。同理，进程启动与退出摘要由 `main.py` 直接打印，不走流，也就不受订阅集影响。

与[link 报错开关](errors-and-logging.md#聊天提醒节流)的一个有意不对称：那个开关重启后恢复开启，因为它静音的是用户可见的聊天提醒；终端订阅集则持久保存、重启不重置，因为它静音的只是终端的 INFO 流量，证据仍在每条流各自的文件里，而且底线保证错误照常可见。

退订永远不丢证据：订阅集只过滤终端 handler，文件 handler 不受影响。这正是可以放心大幅退订的原因。

## 流式粒度

LLM 输出是逐字 delta，而日志记录是整条形状的。两者不该硬塞进一个粒度：

- **v1**：只路由整条消息（请求栈、完整回复、工具结果）。终端的流式打字效果保持现在的直写 stdout——它是终端的交互效果，不是日志。
- **v2（真做 WebUI 时）**：delta 也成为记录，但标成"易失"：只有内存订阅者收，文件 handler 过滤掉。写进轮转文件的逐字 delta 既巨大又不可读。

"易失"是一个 record 属性加一个 filter，由 delta 与整条消息的真实差别支撑，不是预留扩展点。v1 完全不需要它。

## 代价与边界

- ~~42 处 `print` 按模块增量迁移~~：实际一次迁完了 28 处。留下 `print` 的只有三类，都是有意的：`main.py` 的启动/退出摘要、`identity` 的首次配置验证码（恢复入口不可被订阅集关掉），以及 LLM 的逐字 delta（终端交互效果，见上节）。`run.py` 是外层启动器，不在 Bot 进程内。
- **`mods/py.py` 的 `chat_print` 不是日志**：它把 `.py` 的 `print` 输出发到 QQ 聊天。扫 `print(` 时必须排除，否则会把用户可见输出误伤成日志。
- 终端**没有**被改成一行摘要：默认仍然打完整请求栈，与"每次聊天打一次完整栈、往上翻就好"的结论一致；要精简的人自己 `.log off yz.llm.request`。
- `log/llm.log` 会包含聊天正文、提示词和工具参数，而且第 3 步之后每条流文件都带交互归属。`log/` 与 `app.log*` 都已在 `.gitignore` 内并按日轮转保留 7 天，但必须与 `chatlog` 同等对待：设备本地，不得复制进文档、提交或对外回复。
- ~~新增 `log/` 目录需要进 `.gitignore`~~：已加，`AGENTS.md` 的运行时状态清单也同步列上了它。

## 里程碑

1. **行原子**（已实施）：`mods/log.py` 包装 `sys.stdout`，让持有半行的线程独占终端并继续直写，其余线程的完整行排队等它结束。**缓冲的是打断者而不是写作者**，所以逐字打字效果完整保留——这是终端唯一值得实时看的东西，不能为了整齐牺牲它。代价是后台的行可能稍晚出现；持有是一份写入续租的租约：还在写就一直保住整行，卡住或线程已死才让路，避免无限等待。所有调用点不变，因此没有出口命名的必要前提——命名必须和终端订阅集一起落地，否则改名之后 INFO 级输出会直接从终端消失。
2. **出口命名 + 终端订阅集**（已实施）：产出者改用带名字的 logger，同时加入订阅集与 `.log` 命令，默认值保持当前行为。两者同一步完成。终端字节与迁移前逐字相同（差分验证），`app.log` 因此多收了原先只在终端出现的内容——每流一个文件（第 4 步）之前，这是「退订不丢证据」的代价。console handler 也从 stderr 改为写包装后的 stdout，否则警告会绕过行原子插进正在逐字打印的回复里。
3. **归属注入**（已实施）：加 filter，从 `context` 补 `(group_id, user_id)`。装在两个文件 handler 上，所以以后加的消费者只要挂同一个 filter 就有归属。
4. **每流一个文件**（已实施）：各流落盘 `log/<流>.log`，午夜轮转保留 7 天，用 tmux + `tail -f` 看。同一步把流的 INFO 从 `app.log` 撤出——第 2 步为了"退订不丢证据"暂借 `app.log` 装请求栈，现在证据回到各自的流文件，`app.log` 也回到只记严重程度。
5. **订阅 handler**：真要做 WebUI 时再加，此前不写任何为它准备的接口。

## 未决

- **归属粒度**：`(group_id, user_id)` 标识的是一条交互线，不是一次活动。WebUI 若要"展开这一次 `.chat` 调用"，需要在 `context` 里再加一个每次活动的自增 id。这是本提案唯一需要新增状态的地方，做 WebUI 之前不必决定。第 3 步照原样只补交互线，没有预先加这个 id。
- ~~**默认订阅集的具体内容**~~（已定）：默认是流的根 `["yz"]`，靠「所有产出者都在根下」而不是靠枚举来保证与迁移前一致。
- **是否需要命名预设**（例如在"日常"和"调 LLM"之间整组切换）：订阅集是 storage 里的普通列表，预设可以后续单独决定，第一版不做。
- **严重程度没有重新分类**：第 2 步只换了传输，没有改级别。`console.error` 的红色提示（图片处理失败、工具调用失败等）仍是 INFO，因为调用方都已经降级恢复；哪些该升成 WARNING 属于[另一条轴](errors-and-logging.md)，混进来会让「默认行为不变」无法验证。
- **LLM 流式打字是否算流**：它是终端的交互效果而非记录（见上节流式粒度），第 1 步已确认它必须保留。若它也纳入订阅集，需要先解决 delta 记录与文件 handler 的关系，以及退订它之后终端还剩什么。
