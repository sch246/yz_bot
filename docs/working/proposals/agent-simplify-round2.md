## 1. 已经拍板的决定

1. **独立 `.chat` 删除。** 维护者完全不用它。它的整套窗口级设置并入全局设置。
2. **工具状态的 ui 模式删除。**
3. **上下文开头不再有会自动变化的工具消息。** 工具状态像普通事件一样进入经历流：
   起点之后发送一次完整状态，之后有变化只追加变化部分；模型随时可以调用工具取回完整的最新状态。
   目的是让缓存一直命中，直到 agent 主动压缩。
4. **自动卸载保留，也改成追加事件。** 请求里的函数定义不因卸载而拿掉，由一条事件告诉模型不要再调用。
   推广开来，整个消息模型以“发送变更”为主：已经发给模型的内容不再被整体替换或回头修改。
   撤回本来就是一个事件，直接作为事件追加，原消息不从历史里拿掉；`say` 的回声不再标“已确认”，
   也不回头改工具结果，只在回声消息的元数据里写明是哪个行动发的；压缩不再把 say 和回声绑在一起。
5. **通知只写“谁在哪里、什么时候叫了一声”。** 未读概况交给末尾提示。
6. **离线补回和旧兼容分支由实施者检查后报告。** 旧兼容分支原则上不留：
   要么转换旧数据，要么删除旧数据，要么做成与主代码隔离的适配层。

## 2. 删掉独立 `.chat`，设置全部改为全局

**现在：** `.chat <内容>` 是一次不带历史的单句请求。为了它，存在一整套按群／私聊存的设置：
`#model`、`#use_model`、`#image`、`#reasoning`、`#tools`、`#prompt`、`#add_prompt`、`#setting`、`#use_setting`、
`#set_setting`、`#del_setting` 在群里改的都是这个群的 `.chat` 设置，对中心 agent 不起作用。
中心 agent 要用 `#agent ...` 来改，而 `#limit` 又直接是全局的。

**改成：**

- 删除 `.chat` 命令，以及只为它存在的分支：`_activate_chat(read_mail=False)` 那一支、`init_chat` 里按群／私聊
  写的状态消息、`getchatstorage()`／`window_setting()`／`limit(event)` 的窗口分支、`_usage_entry` 按作者记账的分支
  （费用一律记在 Bot 账上）。
- 上面那些 `#` 子命令改为直接读写全局设置，不再需要 `#agent` 前缀；`#agent` 里独有的功能（如 `ops`、
  `reset_start`）改成普通子命令名，`#agent` 这个前缀去掉。**修改全局设置一律要求 op**：以前改窗口设置不用 op，
  改成全局后若不加，任何群友都能换掉 Bot 的模型和提示词。只查看的子命令保持现在的权限。
- `#add_prompt` 的“追加最近几句聊天”依赖窗口视图，改成只接受显式列表，或改读中心已读流，由实施者定。
- 旧的窗口设置值（群／私聊 storage 里的 `model`、`image`、`reasoning`、`tools`、`max_events`／`max_msg`、`max_token`、
  `pressure_percent`、`prompt`、`active_tools`、`agent_hint`）不并进全局（全局已有自己的值），按第 7 节的原则处理：
  一次性脚本删掉，运行代码不再读它们。`#hint` 的窗口配置不属于 `.chat`，本轮不动。
- **四个工具模块会失去入口。** 中心 agent 现在对自己隐藏了下面四个模块，因为它们依赖“当前窗口”或“当前发消息的人”，
  而中心 agent 两者都没有；现在只有 `.chat` 能用它们，删掉 `.chat` 后就没人能调用。默认都改好后对中心 agent 开放，
  改不了或不值得的删掉，结果列给维护者确认：
  - `image`：识别图片；按文字或参考图生成图片，生成的图现在直接发到当前聊天。→ **（已定）生成的图存成文件，
    把文件路径返回给模型，由模型自己发送**（`say` 的正文不转义 CQ 码，可以写 `[CQ:image,file=file:///路径]`）。
    这样模型能先确认生成成功再决定发给谁。注意 `sendfile.send_file` 要求 op：Bot 没有 op 时，要保证 `say`
    这条路能发出这些图。识别本来就不需要窗口。
  - `later`：定时任务（到点发提醒或执行一段代码），任务属于当前聊天，到点发回那里。→ 加显式目标参数，任务属于目标窗口。
  - `amap`：高德地图查询（附近搜索、评分、人均、营业时间、路线）。API Key 按当前发消息的人存。
    → Key 改成 Bot 自己的一份，或由调用参数指定是谁的，实施者给建议。
  - `agents`（`assign_tasks`）：把一批互不相关的子任务并发交给另一个模型，一次取回全部结果。
    子代理现在从当前窗口派生，经历也记到那个窗口。→ 子代理的结果本来就作为工具返回交给中心 agent，不需要窗口；
    给子代理的模块若会发消息，同样走显式目标。
- 窗口级视图 `get_msgs`、`build_context`、`_chat_msgs` 读的是中心 reader 之前的旧窗口经历，只剩 `#add_prompt` 和
  `context_usage` 的兜底在用。若设备上的 link、`data/pyload.py`、`#hint` 代码也没用到，就一起删掉；
  指向“见 get_msgs 的说明”的注释改指 `_model_event`（`#` 开头的消息不进模型上下文，规则在那里）。

## 3. 删掉 ui 模式

删除 `TOOLS_MODES`、`#tools`、全局设置里的 `tools` 项，`create_context_message`／`SessionBinding`／`bind_session`
的 `ui_mode` 参数，`_UI_POINTER`、`_state_hint`，以及 `tools/__init__.py` 里所有 `if self.ui_mode` 分支。
存储里残留的 `tools` 值不再被读取。它要付的代价是：`meta` 的说明书始终处于加载状态，估算约 8000 token，
ui 模式下每次请求都要在末尾重发一遍、而且不命中缓存。

## 4. 工具状态进入经历流

**现在：** 上下文开头有一条系统消息，写着工具目录和所有已加载模块的说明书（含 `meta`，约 8000 token）。
每次唤醒都按当前已加载集合重新生成这条消息。一次唤醒里加载或重载模块，会在末尾追加一条“工具变了”的通告，
但通告只活在这一次唤醒里，不进经历流。已加载模块闲置 1 小时会被自动收回，它的函数定义也随之从请求里拿掉。
函数定义的顺序也不稳定：一次唤醒中途加载的模块排在最后，下次唤醒装回时却按名字重新排序。

历史起点固定以后，开头只要一变，整段历史都得按未命中缓存的价格重新计费。而每次唤醒之间，开头唯一会变的
就是这条工具消息：中途加载过模块，或某个模块被自动收回，都会让它变。函数定义如果也在供应商的缓存前缀里，
它的增减和重排同样会让整段缓存失效。

**改成：**

1. 上下文开头只留不会自动变化的内容：基础提示、人设提示、“你是唯一的中心 agent”。工具状态不再放在开头。
2. 起点之后、第一次请求之前，在经历流里追加一条**完整工具状态**：目录、每个已加载模块的说明书（含 `meta`）。
   手动重置起点后同样补发一条。
   **表示方式：复用现有的 input 事件，内容来源标成 `tools`，不新增事件种类。** `tools` 写在普通事件或冻结投影里，
   不占用 oplog 顶层 `source` 信源字段，也不产生未读 arrival。这样它天然有正式号，
   重放、`recall_events`、`cover_events`、事件号引用都现成支持；磁盘格式不变，回退到旧版本也照样能读。
3. 之后工具状态的**任何变化**都只追加变化部分，而且要写进经历流，不能再像现在的通告那样只活在一次唤醒里。
   变化包括：模型调用 `load_tools`／`reload_tools`；自动卸载；改了代码后重启；Bot 权限变化导致某模块不可用。
   **只在一个地方、一个时机追加：** 每次向模型发请求之前（上一批工具结果已经登记之后）对一次账——
   拿当前实际的工具状态和“已经告诉模型的状态”比，不同就追加一条差异事件，再更新“已告知”。
   - **不在工具执行途中写事件。** 否则事件会插在一次输出和它的工具结果之间；重建历史时只有紧挨着的输出和结果才能按原样
     配对还原，被隔开就只能改用文字重现，前面的缓存随之失效。`load_tools` 的返回只写简短结果，说明书正文由紧随其后的差异事件给出。
   - “已告知”记在全局 agent 设置里。追加事件之后、更新“已告知”之前如果崩溃，下次对账会把同样的差异再发一遍，
     最坏只是重复告知一次，不需要两处写入保持原子。
   - 原有的激活名单照旧管运行（实际加载了什么），不搬进经历流。工具状态事件被 `cover_events` 隐藏，
     不影响实际加载了什么，也不触发重新全量告知。
4. **自动卸载保留**（闲置 1 小时），同样由上面的对账追加一条：“X 已卸载，不要再调用它的函数；需要时重新 `load_tools`”。
5. **函数定义只增不减、顺序固定。** 请求里的函数列表在一个起点周期内按模块首次加载的先后往后加；
   卸载不把定义拿掉，也不按名字重新排序。调用已卸载模块的函数时，不执行，直接返回“该模块已卸载，先 `load_tools`”。
   这份列表（包含哪些模块、先后顺序）要持久化，重启后原样恢复；手动重置起点时按当前已加载集合重建。
   **函数定义始终按当前代码生成，不保存旧定义快照。** 代码改了（`reload_tools`，或改完文件后重启），定义跟着变，
   对账时追加差异事件说明；代码里删掉的函数或模块从列表中去掉，同样追加事件说明。改代码是显式的维护操作，
   接受那一次缓存失效。差异判断要看完整的函数定义（名字、参数、说明文字），不只看模块正文。
6. 模型随时可以调工具拿到**完整的最新工具状态**（目录、已加载模块的说明书、磁盘差异、最近失败）：
   扩展现有 `list_tools`，或新增一个，由实施者定。
7. 末尾那条“磁盘上的模块与已加载版本不一致”的提示保留。它在末尾，不影响缓存。
8. 子代理（`tools/agents.py`）的会话是一次性的，可以继续在开头放一份工具状态，不必写进经历流。

**需要实测的一点：** 供应商很可能把函数定义放在提示最前面。果真如此，模型加载一个从没加载过的模块时，
即使只是在列表末尾追加，缓存仍会整体失效一次。请用 usage 里的缓存命中数实测一次，结果写进文档。
按第 5 条做之后，函数列表只在两种情况下变：模型主动加载新模块、代码改了；自动卸载、单纯重启、重复加载都不再让它变。

## 5. 消息模型：发变更，不整体替换

规矩：发给模型的内容 = 固定的开头 + 只往后追加的经历流 + 末尾每次重算的提示。在同一套配置和代码下，
已经发给模型的内容（末尾提示除外）在以后的每次请求里逐字节不变；状态有变化就追加一条说明，不回头改旧内容。

明确的例外，发生时缓存失效一次是预期的：agent 主动压缩（`cover_events`）、手动重置起点、换模型或切换 reasoning 模式、
改人设提示或图片模式、改了代码（`reload_tools` 或改完重启）、`attach_image` 的一次性附图（见下文第 6 条）。
缓存实际命中多少由供应商决定，部署后看 usage 验证，不是本地代码能保证的硬承诺。

目前查到的违反之处，实施者请再全面查一遍：

1. 开头的工具消息：见第 4 节。
2. 函数定义列表的增减和重排：见第 4 节第 5 条。
3. **撤回的消息会从历史里消失。** 已读的消息后来被发送者撤回，下次重建时这条 input 直接被跳过，历史中间就变了。
   **（已定）** 撤回本来就是一个 QQ 事件，像其它事件一样作为未读追加、被正式读取；原 input 不动。
   注意现在撤回根本不进未读：路由收到撤回只处理近期窗口就结束，能进未读的也只有消息和戳一戳。要把入站和投影接通；
   chatlog 和近期窗口对撤回的其它处理不变。
4. **`say` 的回声确认会回头改工具结果。** 在文字投影下，工具结果 R 读到回声之后，下次重建时会补上“(已确认回声 X)”；
   回声那条 input 上也会加“（已确认由 O#n say 发出）”，而且这句是每次重建时现算的，不在存下的内容里。
   **（已定）**
   - 工具结果不改，也不再有“已确认”字样。
   - 读入回声的那一刻，在它的 `<metadata>` 里写一行发出它的行动号，例如 `<sent_by>20260927-12#1</sent_by>`，
     随这条 input 一起冻结。用的是本系统的行动号，不是供应商的原生工具 ID，后者只用于供应商配对，不是稳定的记忆号。
   - 匹配在**写入之前**做：现在是先存下投影、渲染时再动态补关系，要改成在存下之前就把这一行写进去。
     只匹配真实的自发回声（`message_sent`）、同一目标窗口、且恰好对应一个已登记的 say 返回；不凭文字猜。
     中心 agent 的 say 返回总是在回声被正式读取之前登记，所以这时能确定。
   - 找不到唯一对应就不写，以后也不回填：say 超时没拿到 message_id、同账号别的客户端发的、子代理发的
     （子代理的行动不在中心经历流里，没有行动号，不能拿父级 `assign_tasks` 的号顶替）。
     用 `read_messages` 从档案重读的消息不算回声，不写。旧记录不补写。
   - oplog 本来就会扫描 input 文字里出现的事件号建立引用关系，所以这一行写进去后，`event_links` 自然能从回声找到 say。
   - `cover_events` 不再把 say 和它的回声绑在一起覆盖：两者可以分别压缩，写了行动号的回声靠这条引用始终能找回 say。
     随之可以删掉 `oplog.say_links`、渲染时的 `_echo_relation`，以及覆盖时“自发回声尚无唯一已读 say 返回”
     这类检查。
   - **只删 say 和回声之间的绑定。** “一次输出和它的全部工具结果要一起覆盖”这条保留：它保证不会给供应商发出
     没有配对的工具消息。可见性检查、未完成行动不能覆盖、本次输出不能覆盖自己，这些规则也都保留。
5. **换模型或切换 reasoning 模式时，整段历史换一种渲染方式**（原生配对或文字投影）。
   这是管理员的显式操作，可以接受，文档写明“会让缓存整体失效一次”即可。
6. **图片在请求时才转换。** 每次请求都重新把图片变成模型能用的形式，而图片缓存和描述缓存都会过期、
   失败记录只在一次唤醒内有效、本地文件可能被改，所以同一张图前后可能渲染得不一样。按图片档位分别处理：
   - **关闭（默认）：** 图片始终换成固定文字，本来就稳定，不用改。
   - **描述模式（模型看视觉模型写的文字描述）：** 读入那一刻就把描述文字写进这条 input 存下的内容；即使转换失败，
     也冻结当次失败占位文字，之后不再重新转换该 input。
   - **看图模式（模型直接看图片）：** 接受图片缓存过期时缓存失效一次，不为此建附件管理或永久保存原图。
   - `attach_image` 在不支持“工具结果带图”的模型上，会把图作为附加消息保留在本轮会话中，但不进入 oplog，
     下一次激活不会重建。这是模型主动调用、很少发生的情况，列为例外，不做持久化。

## 6. 通知只写“谁叫了一声”

**现在：** 每条通知事件除了“这次谁叫了我”，还存着一份当时全部窗口的未读概况，外加一大段怎么读消息的操作说明。
概况会过时，末尾提示每次都会重算当前概况；操作说明在基础提示和 `meta` 说明书里已经有了。
之前旧通知缺 `ordinal` 导致重建失败的事故，就出在这份快照上（`814cb2f`）。

**改成：** 新通知只记**上一条通知之后新来的**唤醒：窗口、作者、时间、类型（@、名字开头、戳一戳），一次唤醒一行。
现在每条通知都重列“当时全部未读唤醒”（`053e579` 加的），这属于概况，改由末尾提示给出——末尾提示已经按窗口列出
当前未读唤醒的作者、时间和未读序号。操作说明只放在基础提示或 `meta` 说明书里，它们在开头或流里，能命中缓存。

不变的规则：没确认的通知会重投；通知被看到不等于消息已读；红点不会反复唤醒。
切换时**同一个提交里保留读取旧通知的能力**（带概况快照、缺 `ordinal` 的都要能重建），不等第 7 节的清单；
之后按第 7 节选定的方式统一处理。

## 7. 旧兼容分支和离线补回：先检查、后决定

### 7.1 旧兼容分支

原则：**主代码只认当前格式。** 每个旧兼容分支三选一：

- **转换：** 一次性脚本把旧数据改写成当前格式，之后主代码不再有旧格式判断；
- **删除：** 旧数据没有保留价值，删掉；
- **适配层：** 读入时集中在一个地方转成当前格式，主代码只看到当前格式。

对 oplog，我倾向用适配层：在重放前把旧记录转成当前形状，不重写日志文件。经历流里的正式号会被文字引用，
重写日志容易误改原号；这只是建议，由实施者评估后给出结论。

已有文档明确裁决过的不在此列：chatlog 的旧格式记录只读、不重写（见[记录格式](../../chatlog-format.md)），
`parse_log` 本身就是它的适配层，只需检查主代码里是否还有散落的旧格式判断。

实施者先出一张清单，每项写明：在代码哪里、保护哪种旧数据、建议三选一中的哪个、理由。
静态只读调查及待维护者确认的建议见[第二轮旧兼容与离线补回调查](../round2-legacy-and-backfill-audit.md)；
它不表示已查看或处理生产数据。
已知的起点（不完整，请补全）：

- oplog 重放里的 `condensed`、`clear`、`floor` 三种旧记录；
- 没有 `ordinal`、带未读快照的旧通知；
- 没有 `read_by`／`read_via` 的旧 input，没有发起号的旧 `mark_read`（显示成 `skipped_by=unknown`）；
- 旧 `_stream_results` 到达的恢复桥（`reader._drain_legacy_results`）；
- 中心 reader 之前按窗口分开的旧经历号，以及读它们的窗口视图；
- `active_tools` 的旧列表格式、窗口设置里的旧键 `max_msg`，以及第 2 节删 `.chat` 后留下的窗口设置；
- `chat.cond()`／`chat.call()` 这类公开兼容名（要先在设备上查 link、`data/pyload.py`、`#hint` 有没有在用）。

清单交维护者确认后再动。转换或删除生产数据前必须有维护者的明确授权，先备份、能回滚；
转换后检查 oplog 能完整重放、正式号和引用关系不变。

### 7.3 调查之后的决定（2026-09-27，维护者）

1. **允许只读统计生产数据。** 范围只限计数：oplog 里各种旧记录形状的条数、群／私聊 storage 里的旧窗口设置键、
   `active_tools` 的格式、设备上 link／`data/pyload.py`／`#hint` 代码对 `chat.cond`／`chat.call` 等公开名字的引用、
   旧 `_stream_results` 恢复桥是否还有残留，以及每个窗口 chatlog 的规模（月份数、天数、行数、文件大小，含补回文件）。
   不导出消息正文、账号、群号或密钥。统计结果写回
   [调查报告](../round2-legacy-and-backfill-audit.md)。转换或删除任何生产数据仍需另行授权。
2. **旧格式的翻译层做成适配器，不绑定主代码，是可选的。**
   - 主代码只认它自己的内部表示，里面不出现任何旧格式判断（包括现在散在 `replay.py`、`view.py`、`reader.py`、`oplog`
     里的那些分支）。例外：chatlog 的 `parse_log` 读旧格式行，是 7.1 已裁决的适配层，不在清除范围内。
   - **“内部表示”指主代码能处理的状态，不是“补齐成今天的写盘格式”。** 它可以表达“来源未知”“只有文字、没有原生配对”
     “这些事件被隐藏了”这类通用状态，但适配器不能编造当时没有的东西：不编行动号、不编通知内容、不编供应商的工具调用 ID。
   - **适配器不是逐条的纯字段翻译。** 有的旧记录要结合它之前的重放状态才能解释：旧 `source_mark_read` 要用当时的未读前缀
     恢复坐标；`condensed` 改变的是已有事件及其结果的可见性，不能冒充需要行动节点的 `cover`。所以接入点的形式是：
     一个普通函数，收到一条旧记录和“到这一条为止的重放状态”（只读），交回主代码能接受的内部表示。
     先拿这三个难例（旧 `source_mark_read`、`condensed`、旧 output／旧通知）做原型。如果做下来需要把整个重放器复制一份，
     或者要引入通用的转换框架，就停下来交回维护者复核，不能把“旧判断挪进一个文件”当成简化完成。
   - **接线：** 适配器是一个公开模块，在**被 import 时**就把自己注册到接入点上（和 `@command`、`@capture` 一样在顶层登记）。
     loader 先 import 全部模块、再执行任何 `on_load`，所以它一定先于第一次读 oplog——注意第一次读 oplog 不是在
     `chat.on_load`，而是 `connect.on_load` 里调用的补回准备。主代码不 import 适配器；删掉适配器文件，重启后就不再注册。
   - **没有适配器、又遇到不认识的旧记录时：** 这次读 oplog 整体失败，不留下读了一半的状态，不追加日志，
     中心 agent 不启动、不派发任何模型行动。普通命令、`.py`、`.reboot` 等维护入口照常可用，便于修复。
     主代码要对每条记录的种类和形状做明确检查，不认识的一律拒绝，不能让它落进普通事件的处理里被错误解读。
   - 适配器不改写磁盘上的日志，也不重新编号。部署后旧记录的显示文字若因此变化，属于第 5 节“改了代码”的例外。
   - 旧 `_stream_results` 恢复桥**不放进适配器**：它会登记新的工具结果，不是只读的格式翻译。它按原来的条件单独退休：
     部署新代码、旧进程停止后，再确认没有残留；有残留就保留这条恢复路径。
   - 存储里的小项（`active_tools` 旧列表格式、旧窗口设置键）按统计结果直接转换或删除，不走适配器；`#hint` 相关数据保留。
3. **离线补回保留，维持现在“并入原窗口未读顺序”的设计**，不改成独立信源；调查报告里“是否改成独立信源”的待决项就此关闭。
   下一步是按调查报告的方案做一次真实停机验收，时间由维护者安排。内部实现可以精简，但不改变这个行为。

### 7.4 去掉三处 SQLite 索引（2026-09-27，维护者）

`19b65ec`（2026-09-25）引入了三处 SQLite。三处都是派生索引，日志文件才是权威，替换它们不需要迁移数据。
当初的理由是避免重复解析、控制内存，没有记录说观察到过变慢。

**总要求：替换索引不改变任何读取结果。** 下面这些现有规则必须原样保留，并列入差分验证：

- 补回去重只认补回文件里 `message_id + 时间 + message_seq` 完全相同的记录；普通日志没有 `message_seq`，
  **不能**用来判断“这条补回已经有了”（`_backfill_archive.append_messages` 的现行约定）。
- 同一天的合并顺序：普通日志保持文件里的追加顺序；补回记录按时间、序号插进去，同一秒的补回记录排在普通记录之前。
  不是把所有记录重新整体排序。
- 按 message_id 查找：同一窗口里 id 不保证唯一，要查完全部候选范围，命中多条就报告歧义，让调用方用精确到秒的时间
  或 `origin` 消歧；不能命中第一条就返回。
- 按 `origin` 定位普通日志时，要读出**整条记录**（记录头加缩进的多行正文）以及它所在日期的格式版本，不能只取那一个物理行。
- 还有：来源内重复记录的可见性、被隐藏副本仍能按 `origin` 定位、`before`／`after` 跨日期、没有时间的旧记录、
  撤回通知不能充当原消息。实施者对照 `chatlog.py` 现有逻辑逐条保留。

三处的做法：

1. **补回时的临时去重库**（`_backfill.py`，临时目录里的 `members.sqlite3`）：换成 Python 集合，可以最先做。
   它汇集的是**所有**更早的同窗口启动补回收过的消息，数量随历史累计增长；现在是几千条级别，基准里测一下峰值内存。
2. **补回去重索引**（`_backfill_archive.py` 的 `.backfill-index.sqlite3`）：写补回页时只扫这一页涉及日期的**补回文件**。
   稀疏窗口的一页补回可能跨很多天，基准里要覆盖这种情况。
3. **档案阅读索引**（`chatlog.py` 的 `.archive-reader.sqlite3`）：改成直接读日志文件，加一点轻量结构。
   - 按位置（origin）定位、按时间范围读：直接读对应日期的文件。
   - 按 message_id 找：带了时间就直接定位到那一天；只有 id 时（比如引用回复 `[CQ:reply,id=…]`）要查所有月份。
     维护者提出**每个窗口的每个月份目录放一个布隆过滤器**，记下这个月所有 message_id（普通日志和补回文件都算），
     先排除“肯定不在这个月”的月份，只扫候选月份的日文件。
   - 布隆过滤器“误判只是多扫一个月，不会找错”只在过滤器**完整且新鲜**时成立。所以：缺失、损坏、过期、
     或者构建期间目录里的文件又变了，都要重建或退回直接扫描，**绝不能凭一个可能过期的过滤器回答“不存在”**。
     判断是否过期时，记下的是构建**开始前**各文件的大小和修改时间，建完再核对一次；新增、删除日文件，
     补回往旧日期写入，文件被替换，都算过期；过滤器文件自己不参与判断。当前月份可以不落盘，只在内存里维护。
   - 基准里同时量“直接扫描”和“扫描加布隆过滤器”两种，报告两者的耗时和布隆过滤器带来的额外代码量，
     再由维护者确认要不要保留持久的布隆过滤器。

**基准测试。** 按 7.3 统计出的真实规模（最大的单窗口、单月、单日）生成模拟日志，含新旧格式混合和多行消息。
测这些查找：按 `origin`、按时间范围、带时间的 id、只有 id（近期、久远、不存在、有歧义）；冷启动第一次查和之后再查；
当前月份持续追加、旧月份被补回写入之后再查；启动时读补回锚点、连续多页补回，以及查找持锁期间实时消息被阻塞多久。
同一台机器上和现有 SQLite 比较，记录耗时分布、最慢值、扫描量和峰值内存。

预算（维护者可改）：交互类查找一般 < 0.2 秒、最慢 < 1 秒；启动额外耗时 < 2 秒；额外峰值内存 < 100 MB；
实时消息因查找持锁被阻塞 < 0.1 秒。超出预算先报告是哪一项、超多少，不要自行继续叠加结构。

**上线与回退。**

- 新代码上线时**不删**旧的 `.sqlite3` 文件，原样留着：想回到旧代码，重启就行。新代码稳定运行、验收之后，
  经维护者授权、确认没有旧进程在用，再删；删了也能由旧代码重建。
- 存储转换和删键、旧记录退役：只有做了备份、写明恢复步骤，才算可回退；而且恢复备份会丢掉这之后新产生的状态。
- chatlog、oplog、补回页的原文和定位，本轮都不转换、不删除。
- 已经发出去的消息、执行过的动作、付过费的模型调用，恢复磁盘也撤销不了；不能笼统承诺“整轮都能回滚”。
