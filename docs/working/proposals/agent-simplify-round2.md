# 中心 agent 第二轮简化

> **状态：计划，未实施。** 本文不是现行合同；当前行为以[交互模型](../../interaction-model.md)、
> [运行架构](../../architecture.md)、[LLM 文档](../../llm.md)和代码为准。
> 上一轮见[中心 reader 简化与大文件拆分](reader-cleanup-and-split.md)（代码已实现）。
> 第 1 节的决定由维护者在 2026-09-27 拍板，实施时不再重新讨论。

## 1. 已经拍板的决定

1. **独立 `.chat` 删除。** 维护者完全不用它。它的整套窗口级设置并入全局设置。
2. **工具状态的 ui 模式删除。**
3. **上下文开头不再有会自动变化的工具消息。** 工具状态像普通事件一样进入经历流：
   起点之后发送一次完整状态，之后有变化只追加变化部分；模型随时可以调用工具取回完整的最新状态。
   目的是让缓存一直命中，直到 agent 主动压缩。
4. **自动卸载保留，也改成追加事件。** 请求里的函数定义不因卸载而拿掉，由一条事件告诉模型不要再调用。
   推广开来，整个消息模型以“发送变更”为主：已经发给模型的内容不再被整体替换或回头修改。
   撤回本来就是一个事件，直接作为事件追加，原消息不从历史里拿掉；`say` 的回声不再标“已确认”，
   也不回头改工具结果，只在回声消息的元数据里写明是哪个行动发的；压缩不再把 say 和回声绑在一起。
5. **通知只写“谁在哪里、什么时候叫了一声”。** 未读概况交给末尾提示。
6. **离线补回和旧兼容分支由实施者检查后报告。** 旧兼容分支原则上不留：
   要么转换旧数据，要么删除旧数据，要么做成与主代码隔离的适配层。

## 2. 删掉独立 `.chat`，设置全部改为全局

**现在：** `.chat <内容>` 是一次不带历史的单句请求。为了它，存在一整套按群／私聊存的设置：
`#model`、`#use_model`、`#image`、`#reasoning`、`#tools`、`#prompt`、`#add_prompt`、`#setting`、`#use_setting`、
`#set_setting`、`#del_setting` 在群里改的都是这个群的 `.chat` 设置，对中心 agent 不起作用。
中心 agent 要用 `#agent ...` 来改，而 `#limit` 又直接是全局的。

**改成：**

- 删除 `.chat` 命令，以及只为它存在的分支：`_activate_chat(read_mail=False)` 那一支、`init_chat` 里按群／私聊
  写的状态消息、`getchatstorage()`／`window_setting()`／`limit(event)` 的窗口分支、`_usage_entry` 按作者记账的分支
  （费用一律记在 Bot 账上）。
- 上面那些 `#` 子命令改为直接读写全局设置，不再需要 `#agent` 前缀；`#agent` 里独有的功能（如 `ops`、
  `reset_start`）改成普通子命令名，`#agent` 这个前缀去掉。**修改全局设置一律要求 op**：以前改窗口设置不用 op，
  改成全局后若不加，任何群友都能换掉 Bot 的模型和提示词。只查看的子命令保持现在的权限。
- `#add_prompt` 的“追加最近几句聊天”依赖窗口视图，改成只接受显式列表，或改读中心已读流，由实施者定。
- 旧的窗口设置值（群／私聊 storage 里的 `model`、`image`、`reasoning`、`tools`、`max_events`／`max_msg`、`max_token`、
  `pressure_percent`、`prompt`、`active_tools`、`agent_hint`）不并进全局（全局已有自己的值），按第 7 节的原则处理：
  一次性脚本删掉，运行代码不再读它们。`#hint` 的窗口配置不属于 `.chat`，本轮不动。
- **四个工具模块会失去入口。** 中心 agent 现在对自己隐藏了下面四个模块，因为它们依赖“当前窗口”或“当前发消息的人”，
  而中心 agent 两者都没有；现在只有 `.chat` 能用它们，删掉 `.chat` 后就没人能调用。默认都改好后对中心 agent 开放，
  改不了或不值得的删掉，结果列给维护者确认：
  - `image`：识别图片；按文字或参考图生成图片，生成的图现在直接发到当前聊天。→ **（已定）生成的图存成文件，
    把文件路径返回给模型，由模型自己发送**（`say` 的正文不转义 CQ 码，可以写 `[CQ:image,file=file:///路径]`）。
    这样模型能先确认生成成功再决定发给谁。注意 `sendfile.send_file` 要求 op：Bot 没有 op 时，要保证 `say`
    这条路能发出这些图。识别本来就不需要窗口。
  - `later`：定时任务（到点发提醒或执行一段代码），任务属于当前聊天，到点发回那里。→ 加显式目标参数，任务属于目标窗口。
  - `amap`：高德地图查询（附近搜索、评分、人均、营业时间、路线）。API Key 按当前发消息的人存。
    → Key 改成 Bot 自己的一份，或由调用参数指定是谁的，实施者给建议。
  - `agents`（`assign_tasks`）：把一批互不相关的子任务并发交给另一个模型，一次取回全部结果。
    子代理现在从当前窗口派生，经历也记到那个窗口。→ 子代理的结果本来就作为工具返回交给中心 agent，不需要窗口；
    给子代理的模块若会发消息，同样走显式目标。
- 窗口级视图 `get_msgs`、`build_context`、`_chat_msgs` 读的是中心 reader 之前的旧窗口经历，只剩 `#add_prompt` 和
  `context_usage` 的兜底在用。若设备上的 link、`data/pyload.py`、`#hint` 代码也没用到，就一起删掉；
  指向“见 get_msgs 的说明”的注释改指 `_model_event`（`#` 开头的消息不进模型上下文，规则在那里）。

## 3. 删掉 ui 模式

删除 `TOOLS_MODES`、`#tools`、全局设置里的 `tools` 项，`create_context_message`／`SessionBinding`／`bind_session`
的 `ui_mode` 参数，`_UI_POINTER`、`_state_hint`，以及 `tools/__init__.py` 里所有 `if self.ui_mode` 分支。
存储里残留的 `tools` 值不再被读取。它要付的代价是：`meta` 的说明书始终处于加载状态，估算约 8000 token，
ui 模式下每次请求都要在末尾重发一遍、而且不命中缓存。

## 4. 工具状态进入经历流

**现在：** 上下文开头有一条系统消息，写着工具目录和所有已加载模块的说明书（含 `meta`，约 8000 token）。
每次唤醒都按当前已加载集合重新生成这条消息。一次唤醒里加载或重载模块，会在末尾追加一条“工具变了”的通告，
但通告只活在这一次唤醒里，不进经历流。已加载模块闲置 1 小时会被自动收回，它的函数定义也随之从请求里拿掉。
函数定义的顺序也不稳定：一次唤醒中途加载的模块排在最后，下次唤醒装回时却按名字重新排序。

历史起点固定以后，开头只要一变，整段历史都得按未命中缓存的价格重新计费。而每次唤醒之间，开头唯一会变的
就是这条工具消息：中途加载过模块，或某个模块被自动收回，都会让它变。函数定义如果也在供应商的缓存前缀里，
它的增减和重排同样会让整段缓存失效。

**改成：**

1. 上下文开头只留不会自动变化的内容：基础提示、人设提示、“你是唯一的中心 agent”。工具状态不再放在开头。
2. 起点之后、第一次请求之前，在经历流里追加一条**完整工具状态**：目录、每个已加载模块的说明书（含 `meta`）。
   它和其它事件一样有正式号、写进 oplog、重建时原样出现在原位置，也一样可以被 `cover_events` 压缩。
   手动重置起点后同样补发一条。
3. 之后工具状态的**任何变化**都只追加变化部分，而且要写进经历流，不能再像现在的通告那样只活在一次唤醒里。
   变化包括：模型调用 `load_tools`／`reload_tools`；自动卸载；重启后磁盘上的模块版本变了；Bot 权限变化导致某模块不可用。
   判断“有没有变”要拿经历流里已记录的状态来比，不拿内存。
4. **自动卸载保留**（闲置 1 小时）。卸载时追加一条事件：“X 已卸载，不要再调用它的函数；需要时重新 `load_tools`”。
5. **函数定义只增不减、顺序固定。** 请求里的函数列表在一个起点周期内按模块首次加载的先后往后加；
   卸载不把定义拿掉，也不按名字重新排序。调用已卸载模块的函数时，不执行，直接返回“该模块已卸载，先 `load_tools`”。
   这份列表（包含哪些模块、先后顺序）要持久化，重启后原样恢复。
   只有两种情况会改动列表前面的部分：模型 `reload_tools` 了一个签名变了的函数（定义只能替换，同时追加事件说明）；
   手动重置起点（按当前已加载集合重建）。
6. 模型随时可以调工具拿到**完整的最新工具状态**（目录、已加载模块的说明书、磁盘差异、最近失败）：
   扩展现有 `list_tools`，或新增一个，由实施者定。
7. 末尾那条“磁盘上的模块与已加载版本不一致”的提示保留。它在末尾，不影响缓存。
8. 子代理（`tools/agents.py`）的会话是一次性的，可以继续在开头放一份工具状态，不必写进经历流。

**需要实测的一点：** 供应商很可能把函数定义放在提示最前面。果真如此，模型加载一个从没加载过的模块时，
即使只是在列表末尾追加，缓存仍会整体失效一次。请用 usage 里的缓存命中数实测一次，结果写进文档。
按第 5 条做之后，最坏情况也只是“模型主动加载新模块”时失效；卸载、重启、重复加载都不再引起失效。

## 5. 消息模型：发变更，不整体替换

规矩：发给模型的内容 = 固定的开头 + 只往后追加的经历流 + 末尾每次重算的提示。除了 agent 主动压缩（`cover_events`）
和手动重置起点，已经发给模型的内容在以后的每次请求里都必须逐字节不变；状态有变化就追加一条说明，不回头改旧内容。

目前查到的违反之处，实施者请再全面查一遍：

1. 开头的工具消息：见第 4 节。
2. 函数定义列表的增减和重排：见第 4 节第 5 条。
3. **撤回的消息会从历史里消失。** 已读的消息后来被发送者撤回，下次重建时这条 input 直接被跳过，历史中间就变了。
   **（已定）** 撤回本来就是一个 QQ 事件，像其它事件一样作为未读追加、被正式读取；原 input 不动。
4. **`say` 的回声确认会回头改工具结果。** 在文字投影下，工具结果 R 读到回声之后，下次重建时会补上“(已确认回声 X)”；
   回声那条 input 上也会加“（已确认由 O#n say 发出）”，而且这句是每次重建时现算的，不在存下的内容里。
   **（已定）**
   - 工具结果不改，也不再有“已确认”字样。
   - 读入回声的那一刻，在它的 `<metadata>` 里写一行发出它的行动号，例如 `<sent_by>20260927-12#1</sent_by>`，
     随这条 input 一起冻结。读入回声时 say 的结果已经登记，所以这时就能确定；找不到唯一对应的 say
     （超时没拿到 message_id、同账号别的客户端发的）就不写。用的是本系统的行动号，不是供应商的原生工具 ID，
     后者只用于供应商配对，不是稳定的记忆号。
   - oplog 本来就会扫描 input 文字里出现的事件号建立引用关系，所以这一行写进去后，`event_links` 自然能从回声找到 say。
   - `cover_events` 不再把 say 和它的回声绑在一起覆盖：两者可以分别压缩，靠这条引用始终能找回对方。
     随之可以删掉 `oplog.say_links`、渲染时的 `_echo_relation`，以及覆盖时“自发回声尚无唯一已读 say 返回”
     这类检查。
5. **换模型或切换 reasoning 模式时，整段历史换一种渲染方式**（原生配对或文字投影）。
   这是管理员的显式操作，可以接受，文档写明“会让缓存整体失效一次”即可。
6. **图片在请求时才转换。** 同一张图这次下载成功、下次失败（或反过来），渲染就不同。
   实施者检查图片缓存能否保证同一张图每次渲染一致。

## 6. 通知只写“谁叫了一声”

**现在：** 每条通知事件除了“这次谁叫了我”，还存着一份当时全部窗口的未读概况，外加一大段怎么读消息的操作说明。
概况会过时，末尾提示每次都会重算当前概况；操作说明在基础提示和 `meta` 说明书里已经有了。
之前旧通知缺 `ordinal` 导致重建失败的事故，就出在这份快照上（`814cb2f`）。

**改成：** 新通知只记**上一条通知之后新来的**唤醒：窗口、作者、时间、类型（@、名字开头、戳一戳），一次唤醒一行。
现在每条通知都重列“当时全部未读唤醒”（`053e579` 加的），这属于概况，改由末尾提示给出——末尾提示已经按窗口列出
当前未读唤醒的作者、时间和未读序号。操作说明只放在基础提示或 `meta` 说明书里，它们在开头或流里，能命中缓存。
旧通知按第 7 节处理。

## 7. 旧兼容分支和离线补回：先检查、后决定

### 7.1 旧兼容分支

原则：**主代码只认当前格式。** 每个旧兼容分支三选一：

- **转换：** 一次性脚本把旧数据改写成当前格式，之后主代码不再有旧格式判断；
- **删除：** 旧数据没有保留价值，删掉；
- **适配层：** 读入时集中在一个地方转成当前格式，主代码只看到当前格式。

对 oplog，我倾向用适配层：在重放前把旧记录转成当前形状，不重写日志文件。经历流里的正式号会被文字引用，
重写日志容易误改原号；这只是建议，由实施者评估后给出结论。

已有文档明确裁决过的不在此列：chatlog 的旧格式记录只读、不重写（见[记录格式](../../chatlog-format.md)），
`parse_log` 本身就是它的适配层，只需检查主代码里是否还有散落的旧格式判断。

实施者先出一张清单，每项写明：在代码哪里、保护哪种旧数据、建议三选一中的哪个、理由。
已知的起点（不完整，请补全）：

- oplog 重放里的 `condensed`、`clear`、`floor` 三种旧记录；
- 没有 `ordinal`、带未读快照的旧通知；
- 没有 `read_by`／`read_via` 的旧 input，没有发起号的旧 `mark_read`（显示成 `skipped_by=unknown`）；
- 旧 `_stream_results` 到达的恢复桥（`reader._drain_legacy_results`）；
- 中心 reader 之前按窗口分开的旧经历号，以及读它们的窗口视图；
- `active_tools` 的旧列表格式、窗口设置里的旧键 `max_msg`，以及第 2 节删 `.chat` 后留下的窗口设置；
- `chat.cond()`／`chat.call()` 这类公开兼容名（要先在设备上查 link、`data/pyload.py`、`#hint` 有没有在用）。

清单交维护者确认后再动。转换或删除生产数据前必须有维护者的明确授权，先备份、能回滚；
转换后检查 oplog 能完整重放、正式号和引用关系不变。

### 7.2 离线补回

这部分约 950 行辅助代码（`_backfill*`、`_source_pages`、`_napcat_history`），加上 reader 里“补回段和实时消息谁先谁后”的边界计算。
文档写着“真实停机空窗尚未验收”；把补回并入原窗口的未读顺序是专门改过的决定（见[离线补回](offline-message-backfill.md)）。

本轮只检查、不改行为。实施者报告：

- 现在有哪些规则，每条保护什么情况；
- 哪些可以简化，比如启动补回是否可以像 `fetch` 一样做成单独的信源，从而去掉边界计算；各自的代价；
- 怎样做一次真实停机验收（需要维护者配合和授权）。

## 8. 步骤

1. 删除 `.chat`，设置改为全局（第 2 节）。
2. 删除 ui 模式（第 3 节）。
3. 工具状态进入经历流，并按第 5 节改掉“回头改旧内容”的地方（第 4、5 节）。依赖第 1、2 步：`.chat` 和 ui 模式删掉后，只剩中心 agent 和子代理两种会话、一种工具呈现方式。
4. 通知精简（第 6 节）。可与第 3 步并行。
5. 旧兼容分支清单和离线补回报告（第 7 节），随时可以开始；只读代码和文档，不碰生产数据。

需要搬家的地方照上一轮的做法：机械搬迁和逻辑修改分成两个提交，一起上线。

## 9. 怎样验证

全部用仓库外的一次性脚本和临时运行目录，不新增测试，不碰真实数据、端口和账号。

- **每个提交：** `run.py --check` 和 `run.py --smoke` 与同机改前一致。
- **第 1 步：** `.chat` 不在 `.help` 里；`#model` 等在群里改的是全局设置，非 op 改不了；
  代码里没有地方再读群／私聊 storage 里的聊天设置；四个工具模块按确认的结果改好或删掉。
- **第 3 步：** 模拟多次唤醒和一次重启，期间加载、重载、自动卸载模块，并穿插撤回和 `say` 回声：
  每次请求里，上一次请求已发出的部分（末尾提示除外）逐字节不变；回声的元数据里有发出它的行动号，
  `event_links` 能从回声找到 say，say 和回声可以分别被覆盖；函数列表只在末尾增加、从不减少或重排；
  工具状态事件和卸载事件按顺序出现在经历流里，重启后原样重建；调用已卸载模块的函数得到提示且不执行；
  取完整状态的工具返回最新状态。
- **第 4 步：** 新通知只有一行一次唤醒；旧通知仍能重建（按第 7 节选定的方式）。
- **缓存：** 部署后看 usage 里的缓存命中数，确认唤醒之间命中稳定；函数定义变化的影响按第 4 节写进文档。
- **文档：** 同步更新 `llm.md`、`interaction-model.md`、`architecture.md`、`commands.md` 中关于 `.chat`、窗口设置、
  工具状态两种模式、空闲收回和通知的描述。

- 部署、重启、查看或改写生产数据，都要先得到维护者授权。
- 其余实施细节（新子命令名、取完整状态的工具叫什么、工具状态事件怎么存）由实施者决定。
