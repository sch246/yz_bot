# 设计原则与重写判断

本文记录维护者评估架构方案时使用的判断方式。它不是当前模块说明、目标目录树或某次重构提案；当前事实见[运行架构](architecture.md)，用户可见契约见[交互模型](interaction-model.md)，尚未实现的具体方案见[工作提案](working/proposals/README.md)。

它的作用是防止陌生维护者虽然读懂了功能，却用自己默认的工程价值观填补空白。例如，“从零重写”不自动意味着 Clean Architecture、DTO、依赖注入容器、effect interpreter、统一 session class 或能力枚举；这些方案必须像其它抽象一样，用本项目中的具体问题证明自己。

## 优化目标

柚子优先追求的是：用少量透明、可组合、可现场修改的机制，获得很大的功能表达面；系统出错时，人仍能通过聊天、源码、文件和日志理解、介入并恢复。

因此这里的“简单”不是文件少、类型少或代码短，而是：

- 使用者需要同时理解的规则少；
- 数据和控制流可以一路追踪；
- 常见功能不被罕见需求增加固定成本；
- 失败后仍有清晰的观察和恢复入口；
- 新抽象消除的复杂度大于它引入的概念、间接层和迁移成本。

自 2022 年延续至今的旧代码既不是必须原样保存的圣物，也不是只剩需求价值的垃圾。重写首先要辨认哪些形状是历史偶然，哪些小机制已经被长期使用证明。

## 主要判断原则

### 从普通数据和函数开始

OneBot 事件保持普通 dict，能力优先以普通函数、谓词、装饰器和小型数据结构表达。函数可以被命令、`.py`、link、LLM 工具和其它函数直接组合，这是重要的复用方式。

class、DTO、注册表或 manager 不是禁用项，但必须回答：普通数据加几个函数为什么不够？新对象是否隐藏了原始协议字段，迫使所有功能依赖一份框架视图？

### 抽象必须由已经发生的问题挣得

不要因为某个概念重要，就立即把它升级成框架子系统。状态范围很重要，不代表必须建立 ScopeManager；取消语义有缺口，不代表必须先设计通用 Interaction class；副作用需要测试，不代表全系统必须改写成 Effect AST。

优先找出重复出现的压力，尝试最小函数或数据约定；只有它无法覆盖真实用例时，再增加更强的结构。

### 极简内核，复杂能力由组合产生

`cmds` 的价值不只是“插件很多”，而是文件加 `run(body)` 就能获得稳定入口；参数解析、权限提醒、分页、线程和持久化由可替换函数提供。类似地，`Tool` 从函数签名和 docstring 生成 LLM schema，`call_delay` 和 `to_thread` 保持普通函数调用外观。

重写可以修复全局反向依赖和失败隔离，但不应默认用强制基类、生命周期接口和注册元数据取代这些低样板组合方式。

### 直接能力与逃生口是产品能力

`.py`、link、文件、shell 和重启不是开发期后门，而是这个个人系统的现场编程、维护和恢复界面。它们很锋利，但当前 op 本来就是宿主机完全信任域。

可以收束权限遗漏、调用来源和危险工具暴露，却不能只为了架构纯洁性，把所有直接能力藏到无法临时组合的中间层后面。任何隔离方案都要说明管理员如何在系统半坏时观察和修复它。

### 明确状态归属，不强求统一状态系统

每项功能必须回答状态属于用户、群、聊天窗口、交互线、Bot 实例、全局池还是跨进程 continuation。这个问题是行为设计，不只是存储 key 设计。

不同范围可以使用不同机制；统一只有在确实减少认知成本时才有价值。群共享 LLM、用户线 yield 和全局 cave 不需要为了框架整齐而获得相同生命周期。

### 动态能力不能吞掉稳定恢复入口

link、LLM 和现场代码具有很大表达力，也更容易出现宽匹配、异常循环和提示注入。明确命令、取消、权限控制和生命周期入口必须保持更高或独立的优先级，使动态部分损坏后仍能恢复。

这项原则约束的是用户可见控制流，而不是要求所有 handler 同权竞争后再用优先级数字排序。

### 可观察、可编辑、可修复优先于基础设施规格

文件系统长期被选择，不只是因为早期不会数据库，还因为 JSON、文本和目录能直接查看、搜索、备份和修理。chatlog 的实时追加同样把聊天历史变成人能用普通工具观察的产品数据。

未来可以采用数据库或索引，但不能只用“更正规”作为理由。方案必须保留清楚的数据所有者、导出/修复路径和运行内存与磁盘之间的权威关系。

### 一个事实一个写入权威，允许多个有意投影

避免 config、cache、storage 和动态环境分别成为同一事实的可写真相源。但单一权威不等于只能有一种表示：内存 cache、可读 chatlog、规范 storage 和搜索索引可以并存，只要谁负责写入、谁是派生结果、何时同步和冲突时谁获胜足够明确。

### 允许真实的不对称

不同语言 REPL、不同交互命令、群聊与私聊、线性 link 与少量分支本来就有不同约束。不要为了目录、接口或类型形式统一，让所有功能承担最复杂成员的成本。

当某项能力极少使用时，先考虑把它降为可选函数或明确特例，而不是把它提升成整个框架的通用模型。

### 重启是原子切换边界

热重载要同时处理模块引用、动态环境、线程、scheduler、连接和缓存，很容易留下半新半旧状态。当前秒级完整重启是主动选择的 KISS cutover，并通过一次性钩子恢复聊天反馈。

局部文件或配置热同步可以单独讨论，但不应无意间演变成整进程代码热替换体系。

## “从零重写”真正表示什么

从零写新框架，是为了让结构重新从行为和长期经验中长出来，而不是为了把现有功能装进预先选定的标准架构。

推荐顺序是：

1. 先记录当前行为、群友实际入口、状态范围和已知缺陷；
2. 把内容分成“必须保留的用户行为”“值得保留的机制”“历史偶然”“仍待决定”；
3. 明确这次重写希望消除的具体认知成本或失败边界；
4. 从一条真实纵向闭环实现最小框架；
5. 用行为证据判断抽象是否够用，再迁入下一类能力；
6. 对每个不兼容点明确选择保留、迁移或删除，不把顺手变化冒充重构。

“从零”不要求同时移植全部功能，也不表示底层模块可以只凭一句产品口号全部推翻。`run(body)` 插件、原始 dict、link 新节点优先、函数式适配器、文件透明性和完整重启都是值得重新验证的强候选，而不是默认丢弃项。

## 评审新方案时必须回答

在画目标目录或类型层级前，先回答：

1. 它解决了哪个已经观察到的重复问题或失败？
2. 当前普通 dict、函数或显式 composition 为什么不足？
3. 新增了哪些概念、间接层、隐式生命周期和迁移状态？
4. 是否削弱 `.py`、link、命令插件或聊天维护的直接组合能力？
5. 是否把少见需求变成所有功能的固定成本？
6. 状态的写入权威、派生表示和失败恢复是什么？
7. 动态功能损坏时，管理员还能从哪里观察、禁用和修复？
8. 哪些现有行为保持、哪些明确迁移、哪些有意删除？
9. 能否先用一个纵向切片或纯函数边界验证，而不是先搭完整框架？
10. 删除新抽象后，系统会失去什么无法由更小机制提供的能力？

如果这些问题没有答案，整齐的目录图本身不构成架构论证。

## 不要反向教条化

这些原则并不意味着：

- 永远不能使用 class、类型、数据库、async 或依赖反转；
- 所有历史命令语法和 bug 都必须兼容；
- `from main import *`、多重 globals 和不可取消线程值得保留；
- op 信任域内的所有能力都应继续暴露给普通聊天或外部模型；
- 只要代码可以现场修改，就不需要测试和错误边界。

它们要求的是用本项目证据选择工具，并让复杂度有明确支付者。出现冲突时，先陈述行为、收益、代价和不确定性，再由维护者决定；不要悄悄用通用工程惯例替代项目判断。

## 新会话的理解检查

遇到重写、模块重划或框架设计任务时，陌生会话在提出目标架构前应先用自己的话说明：

- 维护者当前主要优化什么；
- 哪些是用户可见行为不变量；
- 哪些现行小机制可能本身就值得保留；
- 哪些只是已知缺陷或历史偶然；
- 本次仍有哪些语义没有决定。

如果总结只剩“QQ 是持续存在的个人计算环境”，或者立即落到 kernel/adapters/platform、统一 DTO、统一 session、capability ontology 等结构，说明它还没有充分理解本项目的设计倾向。

### 推荐的新会话开场

仅把一组长文交给新会话仍然不够，因为无法知道它是采用了文档里的判断标准，还是只提取功能后继续使用自己的默认架构。架构任务可以先发送下面这段理解闸门：

```text
请先阅读 README.md、docs/design-principles.md、docs/interaction-model.md、
docs/architecture.md，以及本任务对应的功能文档。

暂时不要提出目标目录、类、接口或重写方案。先按以下六项回复：
1. 维护者主要在优化什么；
2. 必须保留的用户可见行为；
3. 可能值得保留其设计形态的小机制；
4. 明确属于历史偶然或现行缺陷的部分；
5. 目前仍未决定、需要询问的问题；
6. 你原本会默认采用、但在本项目中不能未经论证采用的架构惯例。

每项都要引用具体文档证据。等我纠正这份理解后，再讨论结构。
```

这不是要求新会话复述标准答案，而是尽早暴露它的默认假设。若它把 `run(body)`、普通 dict、函数式工具和重启边界全部归为可丢弃实现，或者自动把重要概念变成 manager/class/subsystem，就应先纠正理解，不继续在错误前提上细化方案。
