# 演进历史与仍然有效的教训

本文保存旧 README、`first.md`、`second.md` 和 0.4 使用文档中的历史信息。它解释能力从哪里来，不把旧实现误写成当前承诺。

## 起点：为了聊天记录，也为了自己写一个

最直接的推动力是 QQ 自带聊天记录检索不好用。尝试现成 Bot 后，作者仍觉得不够顺手，于是从 OneBot、NoneBot 和 go-cqhttp 的资料开始学习 QQ 客户端与 Bot 进程如何分工：登录端接收 QQ 事件、暴露 API，Bot 端消费 JSON 事件并调用 API。

更长期的动机不是“凑一组群聊命令”，而是借 Bot 思考自然语言与编程语言的关系。QQ 聊天窗口同时容纳自然语言、代码、状态和人的连续互动，很适合成为两者交叉处。由此很早就确定了四条主线：记录聊天、`.py` 现场编程、`.link` 映射/反应、`.reboot` 远程应用修改。

## 最初的通信与命令行设想

早期实验直接连接 go-cqhttp 的正向 WebSocket `ws://localhost:6700`，用 asyncio/websockets 接收 OneBot JSON，并把 API 请求发回同一连接。那时已经出现一个后来一直保留的认识：事件和 API 本质上就是数据，不一定需要先套进庞大的消息 class 层级。

早期还设想过一个类似命令行的中间层：既能模拟输入输出，又能绑定事件和执行 Python。这与今天的 `5701` 事件入口、`!` shell、`.py`、`.post` 路由和 link 共享环境并非同一份实现，但属于同一条设计线。

## 第一次重构：`.py`、重启 continuation 与输入映射

早期 `.py` 只是主循环里检测前缀后 `exec`，第一次重构把命令收进 Command 模块。那一代 `.py` 使用持久化的 `msg_locals.pkl` 保存可序列化变量；消息包装 `Msg` 负责在正确位置收发。当前实现已经改成进程内共享 `loc`，重启默认清空，只有 `###` 代码追加到 `data/pyload.py`，不应再按旧 pickle 模型理解。

`.reboot` 从一开始就不只是退出：旧实现把一次性 `initfunc` 保存下来，下一进程启动、重新获得 Bot 连接后再向原窗口说“重启完成”。当前由 `mods.reboot` / `mods.shutdown` 保存一次性问候状态并完成同一种跨进程 continuation。实现换过，设计意图没有变。

第一代 `.link` 更接近“输入 A 映射成输入 B”，用正则命名组和 `{name}` 替换符把自然语言改写成 `.py` 或其它命令，甚至能用 link 创造新的问答命令。当时还没有成熟权限系统，这使 link 间接触达 `.py` 的风险尤其明显。之后它曾演化成带 `cond`、`action`、`succ`、`fail` 和反向 `while` 的执行图；2026 年 Mods 切换又把实际近乎线性的主链收束成四字段有序列表和源码 capture。“自然语言模式捕获后进入共同可编程环境”始终是核心。

## 0.2、0.3 与 0.4

- 0.2 时代命令是 class，并出现了整数 `level` 权限字段；当前函数插件没有保留统一 level 检查，但这也是未来“整数级别 + 少量正则/函数例外”并非凭空出现的原因。
- 0.3 写到一半停止，甚至没有完整上传；它不是当前架构的直接祖先。
- 0.4 重新以 HTTP 通信为基础编写，随后因长文本等判断改用 WebSocket，又发现问题并不来自 HTTP；WebSocket 封装曾保留，之后主路径再次回到 HTTP。
- 老文档以 go-cqhttp 为客户端；当前设备已改由 NapCat 提供 OneBot HTTP API。旧 `connect_with_ws.py` 已随架构切换退出正式代码树。

这些往返不是单纯摇摆：HTTP 的同步字典接口更贴近当前简单主循环，WebSocket/async 的统一生命周期管理反而会增加整个项目的概念成本。当前局部使用线程承载耗时操作，没有为了吞吐量把全仓改成 async。

## 多年未变的产品约束

- 面向一个 Bot 账号、一个进程实例；没有设计多账号，也没有协调同群多个 Bot。
- 性能从来不是主要目标。旧 README 直说“无 async，有一点点多线程，低性能”；自 2022 年以来的真实聊天规模证明这种取舍可接受，但不等于没有并发和失败语义问题。
- 文件命令、`.py`、link 和全局环境都让源码保持可现场访问；编辑后整进程秒级重启，比维护可靠热重载更符合 KISS。
- 普通显式命令必须比 link 优先，否则一个过宽动态反应就可能切断恢复入口。
- 群聊交互不应统一成一种状态范围：LLM 是全群共同上下文，操作型 yield 通常按同一用户线隔离，回声洞则是全局池。
- op 类似 Minecraft 的 op：简单、完全信任。任何 op 都能通过 `.py`、shell 或文件能力控制 Bot 和宿主机，也能绕过 `.op` 对 master 的表面保护。
- 不使用数据库最初也来自学习阶段的限制：看不见内部内容的系统难以信任和修理，因此选择可直接阅读的 JSON、文本日志和目录结构。后来 storage 逐渐取代旧 config 成为主要状态系统，这个偶然起点也沉淀成“数据应可观察”的设计偏好。

## Minecraft 能力的来路

Minecraft 管理长期依赖本机 `data/pyload.py`：screen 负责启动进程和读取控制台，RCON 适合快速发送有返回值的服务器命令，screen 则能看到某些 RCON 不返回的控制台输出。Bot 重启会失去内存中的 RCON 连接，需要重新连接；也可以在设备启动注入中自动连接。

`.mcf` 直接编辑 datapack 的函数和标签；link 中不同反斜杠前缀分别委托 RCON 或 screen，因此更具体的前缀必须排在更宽的模式前。这里再次体现倒序 link 的实际意义。路径、端口、密码、screen 名等始终是设备配置，不进入受控文档。
