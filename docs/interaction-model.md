# 交互模型与设计哲学

本文记录柚子 Bot 应当保留的交互特征和设计取舍。它描述的是用户可感知的系统，而不是当前模块布局。

## Bot 是一个持续存在的聊天环境

柚子不是一组彼此隔离的无状态 API。聊天记录、窗口状态、用户数据、群数据、计划任务、link 图和通过 `.py` 注入的环境会共同影响后续反应。

这带来两个有意的结果：

1. 用户不必在每句话前重复完整上下文；许多操作可以直接继续上一轮交互。
2. 一次操作的影响范围必须能被理解，否则群聊中的共享状态会产生意外干扰。

“上下文延续”是产品行为，不应在重构时被简单替换成每条消息独立处理。

## 入口有优先级

当前消息处理顺序的核心意图是：明确命令不能被宽泛的自然语言反应覆盖。

按 `mods.bot` 的真实接收路径，顺序是：

1. `None`、心跳和输入状态通知被提前处理，不进入普通反应。
2. 其余事件先成为当前消息并写入聊天日志；`-l/--log-only` 模式在这里停止。
3. 文本消息不被改写。开头的 reply CQ 和紧随其后的 at 由 `msgs.body()` 现算剥离（只去开头的 at，作参数用的保留），只作用于下面各入口的匹配；事件里的 `message` 始终是原文。
4. 若消息是 `^C` 或 `^c`，先取消同一交互线上的 continuation。
5. 如果该交互线仍有等待中的 generator 或 `.py input()` Queue，它会接收整条消息并阻止后续入口。
6. `.` 开头且能匹配文件命令的消息执行命令插件。
7. `!` 开头的消息进入 Linux shell 执行入口。
8. `#!` 开头的消息进入 shell 测试分支：只回报将执行的内容，不实际执行。
9. 前面都没有消费文本消息时，才按顺序检查持久 link 和进程内 capture。
10. notice 事件先处理撤回；其它 notice 才进入 link。

这个顺序保护了管理和恢复能力。即使某个 link 条件过宽，`.reboot`、`.link`、`.py` 等明确命令仍然有机会执行。只有成功匹配文件命令的点前缀才占用命令入口，未知的 `.xxx` 仍可能落入 link。唯一能抢在当前用户阻塞会话前面的聊天控制是 `^C`；普通点命令也会被同一用户尚未结束的 `yield/input` 当作回复吃掉。调整优先级属于用户可见行为变更，不能只当作内部重排。

## 五种反应模式

### 1. 显式命令

以 `.` 开头，默认以文件名作为命令名；模块可在重命名时显式保留既有公开名。它们适合需要稳定语法、帮助文本、权限检查或较复杂交互的功能。

### 2. 自然语言和模式反应

由 `.link` 管理。触发可以是精确短语、正则式捕获、CQ 消息结构、回复关系、通知事件或任意 Python 条件。它们让 Bot 看起来像聊天参与者，而不只是命令行。

### 3. 延续式交互

命令可以 `yield` 一段提示，随后等待同一条交互线中的下一条消息，例如 `.cave add`、`.edit` 和翻页。阻塞期间，同一用户在同一位置发送的任何消息——包括另一个点命令——都会成为 reply。

`^C`/`^c` 是专门的逃生入口：它在检查阻塞前删除该 `(群或私聊, 用户)` 的 catch，使 yield generator 不再继续。取消消息本身仍会走后续普通路由，因此 link 理论上仍可能观察到它；当前约定是不为 `^C` 注册普通反应。

generator 与 `.py input()` 共用 `mods.context` 的 continuation 登记。`^C`/`^c` 会唤醒并取消等待，不留下仍阻塞的输入线程；裸 `^` 不是取消语法。

框架层交互线目前按 `(群号或私聊, 用户)` 区分——群聊那一半是发言者，私聊那一半是**对端**（`target_id`），所以同一条私聊里 Bot 自己的回声与对端的消息落在同一条线上。因此群里的两个人可以分别进行多数命令会话，不会互相抢走下一条输入。

### 4. 中心聊天与同一段上下文

主聊天只有一个中心 agent。群聊、私聊仍各自保留原始聊天记录；群里任何人的消息都可成为同一主体的经历，不为每个窗口创建独立的主模型。

2026-10-22 起，只要不交接，她就一直在同一段上下文里（取舍见[无状态主循环提案](working/proposals/stateless-agent-loop.md) §7.2）。每次被叫醒只往后追加，前面看过、做过的都还在眼前；交接之后这一段归档，下一段从新的笔记重新开始。

1. **一段的开头**（交接后第一次被叫醒）：
   - 系统提示（最前面是笔记 self，注意事项从 `prompts.json` 的 `base` 读取并附有"你的记忆"说明）；
   - 笔记：做法（global）、眼下的事（recent，可在白天阶段性进展或折叠时随时刷新，交接时亦会确认）、最近一篇日记（每篇标题后标出文件相对路径）；
   - 之前交接过的段（`data/notes/years.md` 年鉴索引，最近 8 段）；
   - 一份只列名字的目录：其它最近有消息的窗口（带名字：她起的名 > 群名 > 昵称）、笔记、日记；
   - 当前完整工具状态（放在笔记和第一次出现的相关人笔记之后、第一条窗口画面之前）。
2. **每次唤醒往后追加**：
   - 这一段里第一次出现的窗口和叫她的人的笔记；
   - 叫醒她的窗口画面：开头一行写哪个窗口、为什么给她看、什么时候，下面是 `chatlog/` 的原文格式，每个窗口和日期补一行标题。别人说的话只出现在这种消息（user）里，系统自己说的话（唤醒原因、笔记、交接、提示）都是 system 消息，所以群友冒充"系统"说话也只是群友的话。上次看过的位置之后标出新消息。这一段里第一次出现的窗口，如果以前看过，只带看到位置之后的新消息和前面 3 条旧记录接话；从没看过的窗口才按 `max_events`（默认 80，至少 3 条）补历史。已经出现过的从上次给到的那条之后接着给；新消息超过 60 条时只给最新的 60 条，并写明跳过了多少、怎么往前翻，只有 `follow` 期间（包括说完话自动听）到的不截、全给；
   - 谁叫醒的她、什么时候，或闹钟的理由（末尾附一句是谁在管、改哪里）；
   - 她干活时画面里的窗口又来的消息：每次子请求之前追加进这一段，写明哪个窗口、什么时候到的、其中有没有叫她的。那次请求有了输出才算看过，这次唤醒收尾时不会为它们再叫她一次；请求失败的话它们仍算没看过，会再叫醒她。只有她自己刚发出去的回显不单独插进来。

   每次请求末尾还有待办（笔记 todo）、其它窗口未读数和当前时间，它们只挂在这一次请求上，不留在这一段里。
3. **召回是她自己的事**：这一段之外的东西用工具读。
   - `read_log` 按窗口读聊天记录原文，可按时间往前翻；
   - `search` 按线索（名字、QQ号、话题里的词）一次找遍聊天记录（默认最近 30 天）、所有笔记和日记，以及归档的上下文里她当时想的、说的和调用过的，按出处分组，每条写明在哪个窗口、哪份笔记、哪一段；
   - `read_actions` 读自己做过的事，可按词在完整原文里筛，太长的按 `start` 分页读完；
   - `read_note` 读笔记。

   被叫醒不等于必须开口，沉默是正常的行动。说话像人用手机打字：`type_word` 把话打进那个窗口的输入框（返回框里现在的字；重打一遍就是改，传空串清空），下一步再 `send`；同一次输出里刚打的字不发，所以打字到发送之间到的消息她一定看过，看完再决定发、改还是不发。输入框草稿像真实 QQ 一样保留在各个窗口里（存入 storage，跨唤醒与重启不丢），画面底部会展示当前窗口输入框里的草稿；发出去后才消失。
4. **笔记是普通文件**：`data/notes/` 下的 Markdown，她随时能用 `write_note` 改，维护者也能直接编辑，改写或删除前自动备份到 `.history/`。
   - self 是她对自己的认识，放在系统提示最前面，取代了旧的提示词；白天改不了，只在夜间反思时由她改，维护者随时可改；
   - global 是核心待人直觉与笔记/技能索引（过程记忆），recent 是眼下的事（短期工作台，可在白天阶段性进展或折叠时随时刷新，交接时亦会确认），todo 是待办，awaker 是闹钟规则；她还可以用任意名字或 `分类:名字`（如 `消消乐`、`topic:线代`）随时新建专题笔记，目录自动列出、只留引用在 global；
   - person:<QQ号>（也是与此人私聊的笔记）和 group:<群号> 分"认识"（语义）与"经历"（带日期和出处的情景索引）两段；
   - diary:<日期> 是当天的日记，白天有触动可随时写，每次交接也会改写成到目前为止的这一天，月末、年末各有一篇汇总；
   - `.setname` 的自定义称呼不再进入画面，作为这个人笔记的一部分出现；
   - 旧的 storage 待办第一次读到时搬进 todo 笔记。
5. **交接**：驱动力是"这段上下文要被移除了，确认交接做好"。
   - 什么时候：她调用 `tidy`；交接条件成立（普通 Python 文件 `data/notes/policy/tidy.py`，维护者直接改，她在反思里改，要 Bot 有 op 权限；文件不存在时默认是这一段超过 `#limit` 的整理阈值，未发言时有 2 次唤醒宽限，先在末尾提示她自己挑时机交接）；夜里 `reflect` 规则到点。
   - 怎么做：在同一段末尾加一句交接指令，她对照这一段逐类确认：眼下的事在 recent，关于人和群的在他们的笔记，答应的事在 todo，今天的事在当天日记（global 留给夜里反思统一打理）。已经在了就不重写，所以交接可以安全地多跑几次；交接时不对外说话。
   - 之后：这一段原样归档到 `data/context/archive/`，留作排查记录，并往 `data/notes/years.md` 追加一行年鉴摘要；交接没完成就不归档，下次再来一遍。

**什么时候醒**：除了被 at、叫名字、戳一戳和私聊里的每条消息，她还会被笔记 awaker 里的规则叫醒。规则每行一条：
- `every 10m <理由>`：间隔规则，最短 1 分钟；
- `daily 23:30 <理由>`：每天定点；
- `at 2026-10-23 08:00 <理由>`：到这个时刻；
- `on g123 <理由>`：这个窗口下一条消息来时（`g123:QQ号` 只等这个人，`u号` 是私聊）；
- `wait g123:QQ号 until 2026-10-23 10:30 <理由>`：等这个人的后续——后续来了就由那条消息叫醒她，到点还没来也叫醒她，只叫一次。对方话说了一半、她决定先不接时用它，那半句就不会挂着没人管；死板的延迟唤醒做不到，对方接上了延迟到点还会再叫一遍；
- `when <Python 表达式> -> <理由>`：每分钟用 `.py` 那份共享环境求值，第一次为真时叫醒她，比如等 MC 出新版本；
- `follow g123 until 2026-10-23 22:30 <理由>`、`mute bili until 2026-10-24 08:00 <理由>`：覆盖层，见下一段。

`at`、`on`、`wait`、`when` 是一次性的，响过就从笔记里划掉。她平时用 `wake_me` 写这些行（"10m" 这样的相对时间在写的时候换成时刻），也能用 `write_note` 直接改；维护者用 `#awaker`。`every`、`daily`、`at`、`wait` 的超时和 `when` 由 `chat.awaker` 每分钟检查，`on`／`wait` 的消息由 `capture_chat` 在到达时认领，只认开了聊天的窗口。理由会交给她；理由是 `reflect` 的那条是夜间交接与反思，笔记为空时默认只有 `daily 04:00 reflect`。

**触发器与覆盖层**（2026-10-23 起）：每种窗口有默认触发器——私聊每条都叫醒她；群里是 at、叫名字、戳一戳；B 站这类窗口是投递方说要叫的（回复和 @）。窗口上可以盖一层限时的覆盖层，盖着的时候由它决定叫不叫：
- `follow`：每条消息都叫醒她，只认 QQ 窗口（B 站只收到回复和 @，本来就都叫醒她，不为了 follow 一个评论区去轮询它）；
- `mute`：都不叫；
- `other`：代码用 `awaker.override(目标, 函数, until=…)` 设的，函数看这条决定叫不叫，只在内存里，重启就没了。

覆盖层只管叫不叫：消息照样记成未读，她醒着时照样在画面和"其它窗口还有没看过的消息"里看见；她自己埋的 `on`／`wait` 照样响。目标是一个窗口（`g123`、`u456`、`g123:QQ号` 只管这个人、`bili:BV…`）或一整类（`group`、`private`、`bili`），越具体的越优先，同一目标只留一层。`me` 不能盖；master（`ops` 第一位）的话 mute 压不住，别的管理员可以。她用 `wake_me("follow g123 30m")`、`wake_me("mute bili 2h")` 写（不写多久是 30 分钟，期限不设上限：她看得见未读，随时能揭），`mute g123 off` 揭掉，到期由每分钟检查静静划掉、不叫醒她。盖着覆盖层的窗口在画面头和未读提示里标出状态和到期时间，比如 `mute 到 2026-10-24 08:00`、`follow（只看 30001）到 …`、`mute（整类 bili）到 …`；被它叫醒时，唤醒原因里写"覆盖层 follow 到 …：理由"。

她在群里 `send` 之后的 5 分钟里，这个群自动算 `follow`（标成"说完话自动听"），为的是别人不 @ 她接话时她也看得见；她连着两次 `dismiss` 掉看过它的唤醒就停，再说话重新算。她自己盖的任何一层都比它优先，`follow g123 off` 也能提前揭掉。只在内存里，重启就没了。

被叫醒了看一眼没什么要做的，她调 `dismiss`（或者整轮唤醒一个工具都没调，收尾时也会自动触发）：这一轮结束后，从最近一行"这次唤醒你的是（#序号 · 时刻）"起（或者她点名更早一行的时刻或 #序号 起，中间又叫醒她的几次一起）的画面、插话、她的思考、工具调用和结果都从上下文里清掉，像没被叫醒过。叫醒不攒、不延迟：她想的那段时间里到的插话照样叫醒她，画面从清掉之前接着给，被清掉的消息回到没读，和新的连在一起排在"以下是上次之后的新消息"下面；画面外那个窗口的未读条数不算它们（oplog 的已读不退）。笔记、文件这些做过的事撤不回，行动记录和 llm.log 也不清。从那以后她发过话，或者输入框里有那以后打的、改过的字，就不能清；跟着的窗口 follow 期间攒下、清了会退回去的消息超过 60 条，也不能再清，她得把这批看完留下（兜底是思考），不想跟了就揭掉 follow；最远清到这一段开头，不跨交接。

**潜意识**（2026-10-24 起，默认开，`#subconscious off` 关；2026-10-25 改成提醒；2026-10-27 扩充子序号粒度；2026-10-28 序号化与层级感知）：不再有自动整理。这一段比上次提醒时又长 5 万 token，她下一次请求的末尾会多一条 system 提醒：这一段多长、能收哪几段（带固定序号及耗量较大的具体子步骤 `28.1`、`28.2` 等）、各有多大；提醒只活这一次请求，不进这一段，收掉以后自然不在。收不收、收哪段、摘要怎么写都由她自己调 `compress`：全面采用序号定位，支持按唤醒整轮收 `compress(first=26, last=27, summary=...)`（只收一轮 `last` 留空或填 0；收至最新唤醒之前填 `last="latest"`），也支持参考 billion_context 细粒度按子步骤精确折叠 `compress(first="28.1", last="28.1", summary=...)`，即使当轮失误读了大段长日志也能当场收掉中间调用，只留一条 system 摘要，原文另存成归档段（名字带 `-folded`，用 `read_context` 读回来；画面位置不退）；系统自动识别折叠层级（L1 一级折叠、L2 递归折叠），并在保留工具调用存照的同时自动将入参 `summary` 截短存照，避免大段重复；回执详细告知折叠成功的序号范围、折叠层级、归档段标识、节省 token 与最新上下文占用。当 `recent` 超过 2 小时未更新时，`nudge` 提醒与 `compress` 回执会温和提醒她顺手刷新 `recent`，使白天长会话能靠折叠维持而不必强行交接；同时当前段 `current.json` 落盘时带有 `current.bak.json` 滚动备份与损坏自动恢复保护。已载入上下文的笔记若中途被改动（`write_note` 或磁盘编辑），系统在唤醒时自动检测并以追加方式（`【笔记更新】`）注入最新版，既不打碎历史前缀缓存、也保证早期思考依赖早期笔记版本的因果历史完整。摘要要不看原文也接得上：什么事、和谁、到哪一步、结果怎样，引原话带 mid，答应的和没做的单独写“还欠着”，零碎的“看了几眼群，没我的事”可以合成一句；还在进行中的不收。整轮收时最近一次唤醒和这一段第一次唤醒（连着交接留下的笔记）不收；子步骤收时允许收当前轮中已完成的前序步骤；一次可以收好几段或好几步，分几次调。收起之后她那条下一次请求从收起的位置往后要按原价重读，所以提醒里写着每段之后还有多少、鼓励收到靠后。提醒过一次就把基准推进到现在的长度，再长 5 万才提醒下一次。

**循环**（2026-10-24 起，2026-10-26 改为显式开启）：总开关默认开（`#loop off` 关），但外部唤醒（有人说话、闹钟、白醒）结束时不再自己起空循环；只有她调 `loop("在做什么")` 写下在做什么时才开启一串循环（每次写下的备注记进 `data/context/loop.jsonl`，可用 `loop_note_history` 反查、`clear_loop_note` 清空；备注超过 30 分钟或 5 轮时提醒里标明何时留下的；没写 `note` 且未 `wait` 的循环不续轮），之后每次唤醒结束后隔两秒，她自己的 `me` 窗口里多一条“循环第几轮：在做什么”并叫醒她，一轮接一轮，直到她彻底做完用 `loop(stop=True)` 结束这一串。她连着几轮什么都没做时，间隔翻倍、最长半小时。要等别人回、等东西加载时她用 `wait(秒数)`：这一轮马上结束，过那么久再叫她，循环不关，期间来了消息照样叫醒她。不设时长；没人干预就一直转到夜里 4 点整理时停，维护者叫停她那一轮时也一起停。循环开着时潜意识照常整理。运行态只在内存里，重启就没了；备注历史落在磁盘上。

**后台任务**（2026-10-24）：要跑很久的事（`exec_code` 脚本、手机的 `aim`、`frames`、`host__run_command` 里没跑完的命令）她可以声明结果怎么回来：等着做完（默认），或者先拿一张回执、接着做别的，做完的结果作为一条记录进她的 `me` 窗口，声明 `wake` 时叫醒她、`quiet` 时只记下。手机的后台任务排成一条队依次做；`exec_code` 的后台跑在独立线程，`run_command` 转后台的命令各自一个进程、也不排那条队——慢的或无限等的不能把手机工具堵住。

**手机自动连拍**（2026-10-24）：她用 `frames(auto=True)` 开着时，手机画面变了才截一张，攒够一波拼成一张、标好每张隔了几秒，推进她的 `me` 窗口并叫醒她；画面静下来就交出最后一波、自己停，她也可以随时关。她正忙着时，`me` 在她眼前就在下一步之前插进来，不在就等这次唤醒结束再叫醒她。

不是消息叫醒她时（规则到点、条件成立、别处的代码调 `chat.wake(reason=..., kind=...)`），理由作为一条记录写进她自己的窗口 `me`，像一条消息一样出现在画面里，她用 `read_log("me")` 能翻以前的；记录在磁盘上，重启不丢。她正忙就等这次唤醒收尾时接上；只有夜间反思遇到她正忙会下一分钟再试，错过三小时以上就等下一次。间隔规则第一次见到时从当下起算。

**QQ 以外的窗口**：别的来源（以后的 B 站评论区、手机通知等）登记成一种窗口，标签写 `种类:目标`，记录和 QQ 窗口一样在 chatlog 里，能叫醒她、能翻、能搜；登记时给了发送函数的种类，她也用 `type_word`／`send` 在那里说话。`me` 只能看。

**夜间交接与反思**：`reflect` 规则到点时，她占住中心 agent。
1. 先交接手上这一段，月末、年末再各汇总一篇日记。
2. 然后用新的一段加载 `memory_system` 与 `data/prompts/reflect.md` 反思，不对外说话：用 `read_context` 回看归档上下文里的对话与心声 `【她想】`（开场的常驻笔记、目录与完整工具状态自动折起，当时版本的笔记用 `note_history` 查），顺着聊天记录与行动记录做四件事——①回味今天哪一刻最像自己、哪一刻在拿死规矩自我审查或心虚迎合，对 `self` 与 `global` 优先做减法；②把白天交接没写透的人情温度补进 `person:`／`group:`、日记「心里」或 `data/yuzu/` 随笔；③给常驻记忆做新陈代谢，把特定游戏坐标或实操步骤从 `global` 迁往 `ops_lessons`、`消消乐` 等专题笔记，顺手清理 `todo` 与合并过长的 `years.md`；④评估 `changes` 里的改动是否合身，真遇到卡点或环境故障再修代码或写进 `proposals`（环境坏了不记成自身缺陷，今天顺遂就什么都不改）。反思这一段也会归档。
3. 期间来的召唤在结束后接着处理。

工具模块 `memory_system` 说明记忆如何流转与夜间如何打理自己，提供读归档上下文、看笔记历史版本、改策略、记评估的工具；它开头"你的记忆怎么流转"那一节每次都在系统提示里。
- **策略层**：交接的附加说明（`data/notes/policy/handoff.md`，附在交接指令后面）、什么时候交接（`data/notes/policy/tidy.py`）、她的做法笔记 `global` 和 `self`。旧的潜意识策略文件（`data/notes/policy/subconscious.md`）2026-10-25 起不再读，盘上留着。每次改动必须写原因和预期，记进 `data/notes/policy/changes.md`。

**设置**：主模型、提示词、工具激活与这些预算只从全局 agent 设置读取；`#model` 等命令查看全局状态，修改命令由管理员操作。

### 5. 持久任务和延迟反应

`.later`、`.todo` 和部分 link 会在当前消息结束之后继续存在。它们保留最初的聊天目标，使未来的结果回到原群或原私聊。

## 状态范围不是统一答案

不同功能有意采用不同范围：

| 状态 | 范围 | 原因与取舍 |
|---|---|---|
| 命令等待的下一条输入 | 同一窗口中的同一用户 | 防止群友互相抢操作步骤 |
| 主 LLM 设置、行动记录、笔记与唯一 agent | Bot 全局 | 一个执行主体；模型不因读取哪个窗口而切换身份 |
| LLM 窗口未读与"看到哪里" | 聊天窗口 | `oplog` 登记到达与唤醒；画面展示过的窗口记下看到的时间，并把未读登记标为已读 |
| `.later` / `.todo` 列表 | 群或私聊用户 | 群任务是公共安排，私聊任务是个人安排 |
| 用户名、自定义偏好 | 用户 | 跨聊天位置识别同一个人 |
| 群名和部分游戏数据 | 群 | 维持群体共享世界 |
| `.cave` 内容 | 全局池，附带投稿人和来源群 | 漂流瓶的价值来自跨时空混合，而删除权仍归投稿人或管理员 |
| 线性 link 列表、`.py` 运行环境和工具模块 last-good registry | Bot 实例级 | 它们是在修改 Bot 的共同能力，而不是某个窗口的私有插件 |
| 中心 agent 已激活工具模块 | Bot 全局 | 名单只从全局 agent storage 读取；遗留窗口值不参与运行，清理仍待授权 |
| `.edit` 输入接续 | 用户线 | 避免输入串线；当前编辑缓冲还会按聊天窗口和路径复用，群内可能共享同一文件会话 |

新增有状态功能时，应先明确它属于“人”“聊天窗口”“群”“全局 Bot”还是“一次交互”，不要默认复制现有某个命令的选择。

## 自修改与重启

Bot 可以通过 `.py`、`.file`、`.edit`、`.link`、`!` 等入口修改运行状态、文件或反应配置。热重载需要正确处理模块引用、后台线程、动态环境和持久状态，复杂度高且容易留下半新半旧的进程。

柚子选择更直接的策略：

1. 在聊天中修改代码或配置；
2. 用 `.reboot` 优雅退出；
3. 由外层 `run.py` 在秒级重新启动完整进程；
4. 通过退出保存和启动加载恢复持久状态。

因此重启不是缺少热重载的临时替代，而是用短暂不可用换取单一、完整运行状态的设计。局部例外只有统一的 `mods/tools`：顶层 Python/Markdown 模块必须经显式 `reload_tools` 才替换进程级 last-good，再经 `load_tools` 才进入当前 `Chat`；中心 agent 的激活名单全局存档，重启后仍然生效。两步都按模块隔离，失败不影响 Bot 或旧版本。普通 Module、命令、link 底座和后台资源仍通过完整重启切换。`.shutdown` 则表示有意停止，并在下次启动时恢复相应提示。

## 权限哲学

`.op` 管理人类管理员集合。人类直接发出的代码、shell、文件操作、反应图修改或进程控制命令按消息作者判权；普通成员主要使用聊天、娱乐、回声洞和安全形式的计划任务。模型调用工具属于 Bot 自己的行动，按固定的 `config.bot_permissions.op` 判权，不会因为这一轮读到哪位成员的消息而改变。

这里的边界是“谁可以改变 Bot 或宿主机”，而不是简单按命令复杂度划分。link 的管理入口需要管理员权限，但已注册的 link 会自动响应普通消息；因此每个 link action 自身也构成能力边界。

当前仍只有 op 与非 op，且每个命令或工具自行执行权限检查。模型显式代行某个用户时按该用户判权，但不能借代行取得 Bot 自身没有的 op 权限；完整边界见[运行架构](architecture.md)。整数命令级别配合少量正则或函数校验仍是[未实现部分](working/proposals/permissions.md)，不能当作现有能力。

## 灵活性优先的 link 取舍

link 把条件和动作都当作可执行配置，能即时组合已有函数、消息上下文和模块能力。持久状态是一份四字段有序列表；按顺序检查并由首个匹配节点消费消息。新节点默认进入列表头，也可显式移动，因此“新反应优先”不需要维护图边。

版本控制内的通用捕获由 `@capture` 注册，不写入 `links.json`。它可以定位在某个持久节点前，或默认作为持久列表后的兜底。这样，设备上的可编辑反应与源码内可复用捕获共用一条可观察顺序，但所有权仍然分开。

这种设计让新反应无需发布新版本，但代价是：

- 某节点意外成功会截断后续匹配；顺序本身就是行为。
- 条件和动作共享 `.py` 环境，强大但依赖显式导出和设备脚本名称。
- 配置既是数据也是可执行控制，损坏时影响范围可能超过单个反应。
- `.link catch` 会真实求值条件，只是不执行 action，不是无副作用 dry-run。

维护时首先保护“普通命令优先”和可恢复入口，不应为了整洁把 link 降级成只能返回静态文本的规则表。
