# 交互模型与设计哲学

本文记录柚子 Bot 应当保留的交互特征和设计取舍。它描述的是用户可感知的系统，而不是当前模块布局。

## Bot 是一个持续存在的聊天环境

柚子不是一组彼此隔离的无状态 API。聊天记录、窗口状态、用户数据、群数据、计划任务、link 图和通过 `.py` 注入的环境会共同影响后续反应。

这带来两个有意的结果：

1. 用户不必在每句话前重复完整上下文；许多操作可以直接继续上一轮交互。
2. 一次操作的影响范围必须能被理解，否则群聊中的共享状态会产生意外干扰。

“上下文延续”是产品行为，不应在重构时被简单替换成每条消息独立处理。

## 入口有优先级

当前消息处理顺序的核心意图是：明确命令不能被宽泛的自然语言反应覆盖。

按 `mods.bot` 的真实接收路径，顺序是：

1. `None`、心跳和输入状态通知被提前处理，不进入普通反应。
2. 其余事件先成为当前消息并写入聊天日志；`-l/--log-only` 模式在这里停止。
3. 文本消息不被改写。开头的 reply CQ 和紧随其后的 at 由 `msgs.body()` 现算剥离（只去开头的 at，作参数用的保留），只作用于下面各入口的匹配；事件里的 `message` 始终是原文。
4. 若消息是 `^C` 或 `^c`，先取消同一交互线上的 continuation。
5. 如果该交互线仍有等待中的 generator 或 `.py input()` Queue，它会接收整条消息并阻止后续入口。
6. `.` 开头且能匹配文件命令的消息执行命令插件。
7. `!` 开头的消息进入 Linux shell 执行入口。
8. `#!` 开头的消息进入 shell 测试分支：只回报将执行的内容，不实际执行。
9. 前面都没有消费文本消息时，才按顺序检查持久 link 和进程内 capture。
10. notice 事件先处理撤回；其它 notice 才进入 link。

这个顺序保护了管理和恢复能力。即使某个 link 条件过宽，`.reboot`、`.link`、`.py` 等明确命令仍然有机会执行。只有成功匹配文件命令的点前缀才占用命令入口，未知的 `.xxx` 仍可能落入 link。唯一能抢在当前用户阻塞会话前面的聊天控制是 `^C`；普通点命令也会被同一用户尚未结束的 `yield/input` 当作回复吃掉。调整优先级属于用户可见行为变更，不能只当作内部重排。

## 五种反应模式

### 1. 显式命令

以 `.` 开头，默认以文件名作为命令名；模块可在重命名时显式保留既有公开名。它们适合需要稳定语法、帮助文本、权限检查或较复杂交互的功能。

### 2. 自然语言和模式反应

由 `.link` 管理。触发可以是精确短语、正则式捕获、CQ 消息结构、回复关系、通知事件或任意 Python 条件。它们让 Bot 看起来像聊天参与者，而不只是命令行。

### 3. 延续式交互

命令可以 `yield` 一段提示，随后等待同一条交互线中的下一条消息，例如 `.cave add`、`.edit` 和翻页。阻塞期间，同一用户在同一位置发送的任何消息——包括另一个点命令——都会成为 reply。

`^C`/`^c` 是专门的逃生入口：它在检查阻塞前删除该 `(群或私聊, 用户)` 的 catch，使 yield generator 不再继续。取消消息本身仍会走后续普通路由，因此 link 理论上仍可能观察到它；当前约定是不为 `^C` 注册普通反应。

generator 与 `.py input()` 共用 `mods.context` 的 continuation 登记。`^C`/`^c` 会唤醒并取消等待，不留下仍阻塞的输入线程；裸 `^` 不是取消语法。

框架层交互线目前按 `(群号或私聊, 用户)` 区分——群聊那一半是发言者，私聊那一半是**对端**（`target_id`），所以同一条私聊里 Bot 自己的回声与对端的消息落在同一条线上。因此群里的两个人可以分别进行多数命令会话，不会互相抢走下一条输入。

### 4. 中心聊天与同一段上下文

主聊天只有一个中心 agent。群聊、私聊仍各自保留原始聊天记录；群里任何人的消息都可成为同一主体的经历，不为每个窗口创建独立的主模型。

2026-10-22 起，只要不交接，她就一直在同一段上下文里（取舍见[无状态主循环提案](working/proposals/stateless-agent-loop.md) §7.2）。每次被叫醒只往后追加，前面看过、做过的都还在眼前；交接之后这一段归档，下一段从新的笔记重新开始。

1. **一段的开头**（交接后第一次被叫醒）：
   - 系统提示（最前面是笔记 self，注意事项里有"你的记忆怎么运作"）与当前工具状态；
   - 笔记：做法（global）、上次交接留下的 recent、最近一篇日记；
   - 一份只列名字的目录：其它最近有消息的窗口、笔记、日记。
2. **每次唤醒往后追加**：
   - 这一段里第一次出现的窗口和叫她的人的笔记；
   - 叫醒她的窗口画面：装在系统替她打开的 `incoming` 框里，框头写哪个窗口、为什么给她看、什么时候，下面是 `chatlog/` 的原文格式，每个窗口和日期补一行标题；图片跟在框后面单独一条。别人说的话只出现在框里，所以群友冒充"系统"说话也只是群友的话。上次看过的位置之后标出新消息。这一段里第一次出现的窗口给默认 80 条，已经出现过的从上次给到的那条之后接着给；新消息超过 200 条时只给最新的 200 条，并写明跳过了多少、怎么往前翻；
   - 谁叫醒的她、什么时候，或闹钟的理由；
   - 她干活时画面里的窗口又来的消息：每次子请求之前追加进这一段，写明哪个窗口、什么时候到的、其中有没有叫她的。那次请求有了输出才算看过，这次唤醒收尾时不会为它们再叫她一次；请求失败的话它们仍算没看过，会再叫醒她。只有她自己刚发出去的回显不单独插进来。

   每次请求末尾还有待办（笔记 todo）、其它窗口未读数和当前时间，它们只挂在这一次请求上，不留在这一段里。
3. **召回是她自己的事**：这一段之外的东西用工具读。
   - `read_log` 按窗口读聊天记录原文，可按时间往前翻；
   - `search` 按线索（名字、QQ号、话题里的词）一次找遍聊天记录（默认最近 30 天）、所有笔记和日记，以及归档的上下文里她当时想的、说的和调用过的，按出处分组，每条写明在哪个窗口、哪份笔记、哪一段；
   - `read_actions` 读自己做过的事，可按词在完整原文里筛，太长的按 `start` 分页读完；
   - `read_note` 读笔记。

   被叫醒不等于必须开口，沉默是正常的行动。说话像人用手机打字：`type_word` 把话打进那个窗口的输入框（返回框里现在的字；重打一遍就是改，传空串清空），下一步再 `send`；同一次输出里刚打的字不发，所以打字到发送之间到的消息她一定看过，看完再决定发、改还是不发。输入框跟着这次唤醒走，中途交接也还在，交接后接着做时告诉她一次框里还有什么；唤醒结束时没发的清空。
4. **笔记是普通文件**：`data/notes/` 下的 Markdown，她随时能用 `write_note` 改，维护者也能直接编辑，改写或删除前自动备份到 `.history/`。
   - self 是她对自己的认识，放在系统提示最前面，取代了旧的提示词；白天改不了，只在夜间反思时由她改，维护者随时可改；
   - global 是做法（过程记忆），recent 是上次交接留下的眼下的事，todo 是待办，awaker 是闹钟规则；
   - person:<QQ号>（也是与此人私聊的笔记）和 group:<群号> 分"认识"（语义）与"经历"（带日期和出处的情景索引）两段；
   - diary:<日期> 是当天的日记，每次交接改写成到目前为止的这一天，月末、年末各有一篇汇总；
   - `.setname` 的自定义称呼不再进入画面，作为这个人笔记的一部分出现；
   - 旧的 storage 待办第一次读到时搬进 todo 笔记。
5. **交接**：驱动力是"这段上下文要被移除了，确认交接做好"。
   - 什么时候：她调用 `tidy`；交接条件成立（普通 Python 文件 `data/notes/policy/tidy.py`，维护者直接改，她在反思里改，要 Bot 有 op 权限；文件不存在时默认是这一段超过 `#limit` 的整理阈值）；夜里 `reflect` 规则到点。
   - 怎么做：在同一段末尾加一句交接指令，她对照这一段逐类确认：眼下的事在 recent，关于人和群的在他们的笔记，做法的教训在 global，答应的事在 todo，今天的事在当天日记。已经在了就不重写，所以交接可以安全地多跑几次；交接时不对外说话。
   - 之后：这一段原样归档到 `data/context/archive/`，留作排查记录；交接没完成就不归档，下次再来一遍。

**什么时候醒**：除了被 at、叫名字、戳一戳和私聊里的每条消息，她还会被笔记 awaker 里的规则叫醒。规则每行一条：
- `every 10m <理由>`：间隔规则，最短 1 分钟；
- `daily 23:30 <理由>`：每天定点；
- `at 2026-10-23 08:00 <理由>`：到这个时刻；
- `on g123 <理由>`：这个窗口下一条消息来时（`g123:QQ号` 只等这个人，`u号` 是私聊）；
- `wait g123:QQ号 until 2026-10-23 10:30 <理由>`：等这个人的后续——后续来了就由那条消息叫醒她，到点还没来也叫醒她，只叫一次。对方话说了一半、她决定先不接时用它，那半句就不会挂着没人管；死板的延迟唤醒做不到，对方接上了延迟到点还会再叫一遍；
- `when <Python 表达式> -> <理由>`：每分钟用 `.py` 那份共享环境求值，第一次为真时叫醒她，比如等 MC 出新版本。

`at`、`on`、`wait`、`when` 是一次性的，响过就从笔记里划掉。她平时用 `wake_me` 写这些行（"10m" 这样的相对时间在写的时候换成时刻），也能用 `write_note` 直接改；维护者用 `#awaker`。`every`、`daily`、`at`、`wait` 的超时和 `when` 由 `chat.awaker` 每分钟检查，`on`／`wait` 的消息由 `capture_chat` 在到达时认领，只认开了聊天的窗口。理由会交给她；理由是 `reflect` 的那条是夜间交接与反思，笔记为空时默认只有 `daily 04:00 reflect`。

不是消息叫醒她时（规则到点、条件成立、别处的代码调 `chat.wake(reason=..., kind=...)`），理由作为一条记录写进她自己的窗口 `me`，像一条消息一样出现在画面里，她用 `read_log("me")` 能翻以前的；记录在磁盘上，重启不丢。她正忙就等这次唤醒收尾时接上；只有夜间反思遇到她正忙会下一分钟再试，错过三小时以上就等下一次。间隔规则第一次见到时从当下起算。

**QQ 以外的窗口**：别的来源（以后的 B 站评论区、手机通知等）登记成一种窗口，标签写 `种类:目标`，记录和 QQ 窗口一样在 chatlog 里，能叫醒她、能翻、能搜；登记时给了发送函数的种类，她也用 `type_word`／`send` 在那里说话。`me` 只能看。

**夜间交接与反思**：`reflect` 规则到点时，她占住中心 agent。
1. 先交接手上这一段，月末、年末再各汇总一篇日记。
2. 然后用新的一段反思，像人排查她的问题那样：从症状出发（有人说她忘了、找东西没找到、答错了、交接漏了），用 `read_context` 读当时那一段的原样，顺着聊天记录、行动记录和笔记的历史版本查原因，必要时改一两处，不对外说话。反思这一段也会归档。
3. 期间来的召唤在结束后接着处理。

工具模块 `memory_system` 说明怎么排查、她能改什么，提供读归档上下文、看笔记历史版本、改策略、记评估的工具；它开头"你的记忆怎么运作"那一节每次都在系统提示里。
- **策略层**：交接的附加说明（`data/notes/policy/handoff.md`，附在交接指令后面）、什么时候交接（`data/notes/policy/tidy.py`）、她的做法笔记和 self。每次改动必须写原因和预期，记进 `data/notes/policy/changes.md`。
- **不由她改的**：醒来时带什么、阈值和代码。她写进 `data/notes/policy/proposals.md` 交给维护者。

**设置**：主模型、提示词、工具激活与这些预算只从全局 agent 设置读取；`#model` 等命令查看全局状态，修改命令由管理员操作。
- `#limit` 查看或修改窗口画面默认条数（默认 80）与整理阈值（token，默认 500000，约是模型上下文的一半）；
- `#awaker` 查看或改写闹钟规则；
- `#reflect` 查看上次反思时间，`#reflect now` 立即跑一次夜间交接与反思。

旧窗口聊天设置不再读取；每窗口独立的 `#hint` 仍用于聊天结束时向 QQ 发送状态，配置是 `data/hint/` 下的普通文件（`default.py` 与 `g<群号>.py`／`u<QQ号>.py`，首行 `# on`／`# off`）。`聊天开始`/`聊天结束`是普通聊天内容，不划分上下文边界。

唤醒仍由 `oplog` 的到达与激活登记决定：at、名字开头、私聊里对方发来的消息、`#poke` 和指向 Bot 的戳一戳经 `chat.wake` 标为激活，唤醒唯一中心 agent；普通消息只登记，不单独唤醒。窗口一旦出现在画面里并且这次唤醒有了输出，就记下"看到哪里"，并把该窗口的未读登记标为已读。启动时，对已有本地档案的窗口从 NapCat 连续补回离线消息；补回内容写入按日 sidecar，当前的窗口画面只读普通日志文件，补回的消息暂不出现在画面里。

### 5. 持久任务和延迟反应

`.later`、`.todo` 和部分 link 会在当前消息结束之后继续存在。它们保留最初的聊天目标，使未来的结果回到原群或原私聊。

## 状态范围不是统一答案

不同功能有意采用不同范围：

| 状态 | 范围 | 原因与取舍 |
|---|---|---|
| 命令等待的下一条输入 | 同一窗口中的同一用户 | 防止群友互相抢操作步骤 |
| 主 LLM 设置、行动记录、笔记与唯一 agent | Bot 全局 | 一个执行主体；模型不因读取哪个窗口而切换身份 |
| LLM 窗口未读与"看到哪里" | 聊天窗口 | `oplog` 登记到达与唤醒；画面展示过的窗口记下看到的时间，并把未读登记标为已读 |
| `.later` / `.todo` 列表 | 群或私聊用户 | 群任务是公共安排，私聊任务是个人安排 |
| 用户名、自定义偏好 | 用户 | 跨聊天位置识别同一个人 |
| 群名和部分游戏数据 | 群 | 维持群体共享世界 |
| `.cave` 内容 | 全局池，附带投稿人和来源群 | 漂流瓶的价值来自跨时空混合，而删除权仍归投稿人或管理员 |
| 线性 link 列表、`.py` 运行环境和工具模块 last-good registry | Bot 实例级 | 它们是在修改 Bot 的共同能力，而不是某个窗口的私有插件 |
| 中心 agent 已激活工具模块 | Bot 全局 | 名单只从全局 agent storage 读取；遗留窗口值不参与运行，清理仍待授权 |
| `.edit` 输入接续 | 用户线 | 避免输入串线；当前编辑缓冲还会按聊天窗口和路径复用，群内可能共享同一文件会话 |

新增有状态功能时，应先明确它属于“人”“聊天窗口”“群”“全局 Bot”还是“一次交互”，不要默认复制现有某个命令的选择。

## 自修改与重启

Bot 可以通过 `.py`、`.file`、`.edit`、`.link`、`!` 等入口修改运行状态、文件或反应配置。热重载需要正确处理模块引用、后台线程、动态环境和持久状态，复杂度高且容易留下半新半旧的进程。

柚子选择更直接的策略：

1. 在聊天中修改代码或配置；
2. 用 `.reboot` 优雅退出；
3. 由外层 `run.py` 在秒级重新启动完整进程；
4. 通过退出保存和启动加载恢复持久状态。

因此重启不是缺少热重载的临时替代，而是用短暂不可用换取单一、完整运行状态的设计。局部例外只有统一的 `mods/tools`：顶层 Python/Markdown 模块必须经显式 `reload_tools` 才替换进程级 last-good，再经 `load_tools` 才进入当前 `Chat`；中心 agent 的激活名单全局存档，重启后仍然生效。两步都按模块隔离，失败不影响 Bot 或旧版本。普通 Module、命令、link 底座和后台资源仍通过完整重启切换。`.shutdown` 则表示有意停止，并在下次启动时恢复相应提示。

## 权限哲学

`.op` 管理人类管理员集合。人类直接发出的代码、shell、文件操作、反应图修改或进程控制命令按消息作者判权；普通成员主要使用聊天、娱乐、回声洞和安全形式的计划任务。模型调用工具属于 Bot 自己的行动，按固定的 `config.bot_permissions.op` 判权，不会因为这一轮读到哪位成员的消息而改变。

这里的边界是“谁可以改变 Bot 或宿主机”，而不是简单按命令复杂度划分。link 的管理入口需要管理员权限，但已注册的 link 会自动响应普通消息；因此每个 link action 自身也构成能力边界。

当前仍只有 op 与非 op，且每个命令或工具自行执行权限检查。模型显式代行某个用户时按该用户判权，但不能借代行取得 Bot 自身没有的 op 权限；完整边界见[运行架构](architecture.md)。整数命令级别配合少量正则或函数校验仍是[未实现部分](working/proposals/permissions.md)，不能当作现有能力。

## 灵活性优先的 link 取舍

link 把条件和动作都当作可执行配置，能即时组合已有函数、消息上下文和模块能力。持久状态是一份四字段有序列表；按顺序检查并由首个匹配节点消费消息。新节点默认进入列表头，也可显式移动，因此“新反应优先”不需要维护图边。

版本控制内的通用捕获由 `@capture` 注册，不写入 `links.json`。它可以定位在某个持久节点前，或默认作为持久列表后的兜底。这样，设备上的可编辑反应与源码内可复用捕获共用一条可观察顺序，但所有权仍然分开。

这种设计让新反应无需发布新版本，但代价是：

- 某节点意外成功会截断后续匹配；顺序本身就是行为。
- 条件和动作共享 `.py` 环境，强大但依赖显式导出和设备脚本名称。
- 配置既是数据也是可执行控制，损坏时影响范围可能超过单个反应。
- `.link catch` 会真实求值条件，只是不执行 action，不是无副作用 dry-run。

维护时首先保护“普通命令优先”和可恢复入口，不应为了整洁把 link 降级成只能返回静态文本的规则表。
