# 交互模型与设计哲学

本文记录柚子 Bot 应当保留的交互特征和设计取舍。它描述的是用户可感知的系统，而不是当前模块布局。

## Bot 是一个持续存在的聊天环境

柚子不是一组彼此隔离的无状态 API。聊天记录、窗口状态、用户数据、群数据、计划任务、link 图和通过 `.py` 注入的环境会共同影响后续反应。

这带来两个有意的结果：

1. 用户不必在每句话前重复完整上下文；许多操作可以直接继续上一轮交互。
2. 一次操作的影响范围必须能被理解，否则群聊中的共享状态会产生意外干扰。

“上下文延续”是产品行为，不应在重构时被简单替换成每条消息独立处理。

## 入口有优先级

当前消息处理顺序的核心意图是：明确命令不能被宽泛的自然语言反应覆盖。

按 `mods.bot` 的真实接收路径，顺序是：

1. `None`、心跳和输入状态通知被提前处理，不进入普通反应。
2. 其余事件先成为当前消息并写入聊天日志；`-l/--log-only` 模式在这里停止。
3. 文本消息不被改写。开头的 reply CQ 和紧随其后的 at 由 `msgs.body()` 现算剥离（只去开头的 at，作参数用的保留），只作用于下面各入口的匹配；事件里的 `message` 始终是原文。
4. 若消息是 `^C` 或 `^c`，先取消同一交互线上的 continuation。
5. 如果该交互线仍有等待中的 generator 或 `.py input()` Queue，它会接收整条消息并阻止后续入口。
6. `.` 开头且能匹配文件命令的消息执行命令插件。
7. `!` 开头的消息进入 Linux shell 执行入口。
8. `#!` 开头的消息进入 shell 测试分支：只回报将执行的内容，不实际执行。
9. 前面都没有消费文本消息时，才按顺序检查持久 link 和进程内 capture。
10. notice 事件先处理撤回；其它 notice 才进入 link。

这个顺序保护了管理和恢复能力。即使某个 link 条件过宽，`.reboot`、`.link`、`.py` 等明确命令仍然有机会执行。只有成功匹配文件命令的点前缀才占用命令入口，未知的 `.xxx` 仍可能落入 link。唯一能抢在当前用户阻塞会话前面的聊天控制是 `^C`；普通点命令也会被同一用户尚未结束的 `yield/input` 当作回复吃掉。调整优先级属于用户可见行为变更，不能只当作内部重排。

## 五种反应模式

### 1. 显式命令

以 `.` 开头，默认以文件名作为命令名；模块可在重命名时显式保留既有公开名。它们适合需要稳定语法、帮助文本、权限检查或较复杂交互的功能。

### 2. 自然语言和模式反应

由 `.link` 管理。触发可以是精确短语、正则式捕获、CQ 消息结构、回复关系、通知事件或任意 Python 条件。它们让 Bot 看起来像聊天参与者，而不只是命令行。

### 3. 延续式交互

命令可以 `yield` 一段提示，随后等待同一条交互线中的下一条消息，例如 `.cave add`、`.edit` 和翻页。阻塞期间，同一用户在同一位置发送的任何消息——包括另一个点命令——都会成为 reply。

`^C`/`^c` 是专门的逃生入口：它在检查阻塞前删除该 `(群或私聊, 用户)` 的 catch，使 yield generator 不再继续。取消消息本身仍会走后续普通路由，因此 link 理论上仍可能观察到它；当前约定是不为 `^C` 注册普通反应。

generator 与 `.py input()` 共用 `mods.context` 的 continuation 登记。`^C`/`^c` 会唤醒并取消等待，不留下仍阻塞的输入线程；裸 `^` 不是取消语法。

框架层交互线目前按 `(群号或私聊, 用户)` 区分——群聊那一半是发言者，私聊那一半是**对端**（`target_id`），所以同一条私聊里 Bot 自己的回声与对端的消息落在同一条线上。因此群里的两个人可以分别进行多数命令会话，不会互相抢走下一条输入。

### 4. 中心聊天：每次唤醒先构造，再行动

主聊天只有一个中心 agent。群聊、私聊仍各自保留原始聊天记录；群里任何人的消息都可成为同一主体的经历，不为每个窗口创建独立的主模型。

2026-11-01 起没有一段一直往后接的上下文（设计与裁定见[一次一个目的](working/proposals/one-purpose-stateless-core.md)，当前实现见[LLM 文档](llm.md)）。每次调用只为一个目的：唤醒时先跑一次**构造**，为接下来的**行动**准备上下文；行动做完，这次的上下文原样封存到 `data/chat/views/<ctx>.json`，下次醒来重新准备。一段经历结束后有一次**沉淀**，把值得留下的写进笔记。

1. **构造**（每次唤醒、行动之前）：她自己的一次短运行，原来的旁观助手并在这里。
   - 看到：笔记 `policy/construct` 里的构造说明（不存在时用内置说明）；黑板 `recent` 的全文，其中 `@引用` 行只显示展开前的一句描述；几份折叠索引：笔记目录（名字和首行）、最近几小时她在各窗口做过的事（带日志编号）、最近几次运行的目的、其它窗口的未读与 @；这次唤醒的原因和叫醒她的窗口的新消息（前面带 20 条接话）。
   - 能做：用 `search`、`read_note`、`read_log`、`read_actions` 先确认，用 `fork` 分几路找线索；用 `construct__assemble(goal, refs, note, windows)` 提交一份或几份规格。不能发言、不能写笔记。
   - 规格：一句具体的目的；材料引用（笔记名、日志编号、运行 ctx、`log:窗口@时刻*条数` 的聊天片段、`policy:名字`），坏引用当场退回让她改；写给行动的注意（陌生说法用「」括起来，代码去笔记和日记里查有没有并注在词后，矛盾、情绪、意外）；负责回应的窗口。
   - 一次唤醒有几件互不相干的事，可以交几份；被 @、戳一戳和私聊的那份先跑。没被任何一份认领的被叫醒窗口，系统补一份标明“没有经过构造”的默认规格。
   - 构造关着（`#construct off`）、出错、超时（默认 45 秒）或一份都没交时，按黑板加这次的消息直接行动，并在注意里写明原因。
2. **行动**：
   - 看到：系统提示（最前面是笔记 self，附"你的记忆"说明）；规格展开的材料；准备时写下的注意；输入框里还没发的字；规格负责的窗口的新消息。窗口画面开头一行写哪个窗口、为什么给她看、什么时候，下面是 `chatlog/` 的原文格式；上次看过的位置之后标出新消息，前面带 10 条接话；从没看过的窗口按 `max_events`（默认 80）补历史；新消息超过 60 条时只给最新的 60 条并写明怎么往前翻，`follow` 期间到的不截。别人说的话只出现在 user 消息里，系统说的话（唤醒原因、笔记、注意、提示）都是 system 消息。
   - 她干活时这份规格负责的窗口又来的消息，每次子请求之前追加进来；别的窗口来的消息留给下一次唤醒，由新的构造处理。那次请求有了输出才算看过；请求失败的话它们仍算没看过，会再叫醒她。只有她自己刚发出去的回显不单独插进来。
   - 每次请求末尾还有待办（笔记 todo）、其它窗口未读数、后台命令、当前时间；这次的画面提到她有、但不在眼前的笔记时（按笔记名和 `别名：` 那一行匹配），还有一行指路。它们只挂在这一次请求上。
3. **召回是她自己的事**：眼前没有的东西用工具读，构造时和行动时都可以。
   - `read_log` 按窗口读聊天记录原文，可按时间往前翻；
   - `search` 按线索一次找遍聊天记录（默认最近 30 天）、所有笔记和日记，以及封存的运行里她当时想的、说的和调用过的，按出处分组；
   - `read_actions` 读自己做过的事，可按词筛，太长的按 `start` 分页；
   - `read_note` 读笔记。

   被叫醒不等于必须开口，沉默是正常的行动；没什么要做就什么都不做，这次运行结束眼前就收起。说话像人用手机打字：`type_word` 把话打进那个窗口的输入框（重打一遍就是改，传空串清空），下一步再 `send`；同一次输出里刚打的字不发，所以打字到发送之间到的消息她一定看过。输入框草稿保留在各个窗口里（存入 storage，跨唤醒与重启不丢），每次行动都会看到还没发的字；发出去后才消失。
4. **笔记是普通文件**：`data/notes/` 下的 Markdown，她随时能用 `write_note` 改，维护者也能直接编辑，改写或删除前自动备份到 `.history/`。
   - self 是她对自己的认识，放在系统提示最前面；白天改不了，只在夜间反思时由她改，维护者随时可改；
   - recent 是**黑板**：此刻的心情、手头的事、还挂着的话，加上 `@引用` 行（一行一条，写法同规格的材料引用）记下下次可能用得上的材料。每次构造都从黑板开始，所以她随时刷新它，沉淀也会改写它；
   - global 是核心待人直觉与笔记/技能索引（过程记忆），todo 是待办，awaker 是闹钟规则；她还可以用任意名字或 `分类:名字`（如 `消消乐`、`topic:线代`）新建专题笔记，目录自动列出，在 global 只留引用；`log:` 开头的名字留给聊天片段引用，不能作笔记名；
   - person:<QQ号>（也是与此人私聊的笔记）和 group:<群号> 分"认识"（语义）与"经历"（带日期和出处的情景索引）两段；
   - diary:<日期> 是当天的日记，白天有触动可随时写，沉淀时会改写成到目前为止的这一天，月末、年末各有一篇汇总；
   - `.setname` 的自定义称呼不进入画面，作为这个人笔记的一部分出现。
5. **沉淀**：一段经历结束时，把它留下来。
   - 什么时候：她在某个窗口最后一次行动之后安静 20 分钟，或者那里自上次沉淀后积攒超过 200 条聊天记录，或者夜间反思之前。只在中心执行线空闲时跑；有新的召唤就在两轮工具调用之间让路，之后再重跑。她没被叫醒过的窗口不沉淀。
   - 看到：这段时间那个窗口的聊天原文（一次最多 300 条，更多的分几次）、她在那里每次行动的目的、注意、思考、工具调用和结果（按日志编号取回的就是她当时看到的材料）、黑板、那个窗口的群或人笔记、这段里说过话的人的笔记（最多 5 份）、当天日记和 todo。
   - 做什么：把对人和群的认识与经历、当天日记、黑板（含下次可能用得上的 `@引用`）、答应了还没做的事写好；情绪、玩笑和关系的变化也算。global 留给夜里反思。已经在了就不重写，重跑是安全的。附加说明在 `data/notes/policy/settle.md`（原 `handoff.md`，第一次读到时改名）。
   - 之后：正常结束才推进这个窗口的沉淀位置（storage `agent.settled`），出错隔 10 分钟再试；沉淀的运行进 `data/notes/years.md` 年鉴索引。

**什么时候醒**：除了被 at、叫名字、戳一戳和私聊里的每条消息，她还会被笔记 awaker 里的规则叫醒。长期规则写在 awaker 文件中；wait 通过工具设置到内存。可用写法：
- `every 10m <理由>`：间隔规则，最短 1 分钟；
- `daily 23:30 <理由>`：每天定点；
- `at 2026-10-23 08:00 <理由>`：到这个时刻；
- `on g123 <理由>`：这个窗口下一条消息来时（`g123:QQ号` 只等这个人，`u号` 是私聊）；
- `wait g123:QQ号 until 2026-10-23 10:30 <理由>`：等这个人的后续——后续来了就由那条消息叫醒她，到点还没来也叫醒她，只叫一次。对方话说了一半、她决定先不接时用它，那半句就不会挂着没人管；死板的延迟唤醒做不到，对方接上了延迟到点还会再叫一遍；
- `when <Python 表达式> -> <理由>`：每分钟用 `.py` 那份共享环境求值，第一次为真时叫醒她，比如等 MC 出新版本；
- `follow g123 until 2026-10-23 22:30 <理由>`、`mute bili until 2026-10-24 08:00 <理由>`：覆盖层，见下一段。

`at/on/when` 是文件里的一次性规则，响过就划掉；follow/mute/on 跨重启保留。wait 由 `wake_me` 或 send 写入内存等待表，重启丢弃，不能靠直接写笔记恢复。长期规则每分钟检查，wait 超时与消息认领由 attention 调度。`#awaker` 同时显示文件规则和内存等待。理由会交给她；理由是 `reflect` 的那条是夜间沉淀与反思，笔记为空时默认只有 `daily 04:00 reflect`。

**触发器与覆盖层**（2026-10-23 起）：每种窗口有默认触发器——私聊每条都叫醒她；群里是 at、叫名字、戳一戳；B 站这类窗口是投递方说要叫的（回复和 @）。窗口上可以盖一层限时的覆盖层，盖着的时候由它决定叫不叫：
- `follow`：每条消息都叫醒她，只认 QQ 窗口（B 站只收到回复和 @，本来就都叫醒她，不为了 follow 一个评论区去轮询它）；
- `mute`：都不叫；
- `other`：代码用 `awaker.override(目标, 函数, until=…)` 设的，函数看这条决定叫不叫，只在内存里，重启就没了。

覆盖层只管叫不叫：消息照样记成未读，她醒着时照样在画面和"其它窗口还有没看过的消息"里看见；她自己埋的 `on`／`wait` 照样响。目标是一个窗口（`g123`、`u456`、`g123:QQ号` 只管这个人、`bili:BV…`）或一整类（`group`、`private`、`bili`），越具体的越优先，同一目标只留一层。`me` 不能盖；master（`ops` 第一位）的话 mute 压不住，别的管理员可以。她用 `wake_me("follow g123 30m")`、`wake_me("mute bili 2h")` 写（不写多久是 30 分钟，期限不设上限：她看得见未读，随时能揭），`mute g123 off` 揭掉，到期由 attention 调度静静划掉、不叫醒她。盖着覆盖层的窗口在画面头和未读提示里标出状态和到期时间，比如 `mute 到 2026-10-24 08:00`、`follow（只看 30001）到 …`、`mute（整类 bili）到 …`；被它叫醒时，唤醒原因里写"覆盖层 follow 到 …：理由"。

她在群里说完话，别人不 @ 她接话她也想看见时，用 `send` 的 `wait`（如 `"5m"`，只等某个人加 `who`）：等待期间那个窗口（或那个人）来消息就叫醒她，到点没人接也叫她一次。2026-10-31 起：这次唤醒若是群里某人叫醒她的、她又没写 `who`，默认只等这个人（`wait g群号:QQ号 时长`），路人插话吞不掉这次等待；只认叫醒她的人，不认之后路过的人；自主唤醒（闹钟、B 站等没有人叫她的唤醒）不写 `who` 则等全群，也可以显式写 `who="any"`。CLI 窗口和 B 站窗口里挂的 wait，由 push 进来的回复认领。2026-10-29 以前这件事是 `send` 之后自动 `follow` 5 分钟、连着两次 `dismiss` 就停，现在由她发言时自己定。

被叫醒了看一眼没什么要做的，她什么都不做就结束这一轮。2026-11-01 以前她用 `dismiss` 把这样的唤醒从同一段上下文里清掉；现在每次运行都是独立的，不会叠在一起，`dismiss` 随之删除。叫醒她的要是她挂的 `wait`，那条规则在叫醒时就划掉了；还想接着等，用 `wake_me("wait g123:QQ号 10m", 理由)` 重新挂上。

**运行与封存**：经历原文只追加到 `data/chat/journal/`；每次运行（构造、行动、沉淀、反思、分身、汇总）有自己的编号视图，结束时冻结到 `data/chat/views/<ctx>.json`，能用 `read_context` 原样读。不再有整段压力、折叠或交接；`#reasoning drop` 只影响引用来的旧行动里的思考。

**循环与等待**：她调用 `loop("在做什么")` 开启连续循环，每轮结束后通常隔两秒再叫醒，没动作时退避、最长半小时。`wait(seconds, reason)` 在循环内推迟下一轮，循环外单独排一次唤醒，理由保留。`loop(stop=True)`、维护者取消或夜间反思停止循环。loop/wait 重启丢弃，已发生的理由仍在 me 日志；`loop_note_history` 从 journal 查备注。

**后台任务**（2026-10-24）：要跑很久的事（`exec_code` 脚本、手机的 `aim`、`frames`、`host__run_command` 里没跑完的命令）她可以声明结果怎么回来：等着做完（默认），或者先拿一张回执、接着做别的，做完的结果作为一条记录进她的 `me` 窗口，声明 `wake` 时叫醒她、`quiet` 时只记下。手机的后台任务排成一条队依次做；`exec_code` 的后台跑在独立线程，`run_command` 转后台的命令各自一个进程、也不排那条队——慢的或无限等的不能把手机工具堵住。

**手机自动连拍**（2026-10-24）：她用 `frames(auto=True)` 开着时，手机画面变了才截一张，攒够一波拼成一张、标好每张隔了几秒，推进她的 `me` 窗口并叫醒她；画面静下来就交出最后一波、自己停，她也可以随时关。她正忙着时，`me` 在她眼前就在下一步之前插进来，不在就等这次唤醒结束再叫醒她。

不是消息叫醒她时（规则到点、条件成立、别处的代码调 `chat.wake(reason=..., kind=...)`），理由作为一条记录写进她自己的窗口 `me`，像一条消息一样出现在画面里，她用 `read_log("me")` 能翻以前的；记录在磁盘上，重启不丢。她正忙就等这次唤醒收尾时接上；只有夜间反思遇到她正忙会下一分钟再试，错过三小时以上就等下一次。间隔规则第一次见到时从当下起算。

**QQ 以外的窗口**：别的来源（以后的 B 站评论区、手机通知等）登记成一种窗口，标签写 `种类:目标`，记录和 QQ 窗口一样在 chatlog 里，能叫醒她、能翻、能搜；登记时给了发送函数的种类，她也用 `type_word`／`send` 在那里说话。`me` 只能看。

**夜间沉淀与反思**：`reflect` 规则到点时，她占住中心 agent。
1. 先把各窗口还没沉淀的经历沉淀完，月末、年末再各汇总一篇日记。
2. 然后开一次反思运行，加载 `memory_system` 与 `data/prompts/reflect.md`（不在时用仓库里的 `mods/chat/reflect.md`）：材料里有上次反思以来行动、构造、沉淀的次数和每次沉淀的名字，她用 `read_context` 回看沉淀（里面有那段聊天原文和她的每次行动）和构造（准备了什么、行动里又召回了什么），顺着聊天记录与行动记录做四件事——①回味今天哪一刻最像自己、哪一刻在拿死规矩自我审查或心虚迎合，对 `self` 与 `global` 优先做减法；②把白天没写透的人情温度补进 `person:`／`group:`、日记「心里」或 `data/yuzu/` 随笔；③给常驻记忆做新陈代谢，顺手清理 `todo` 与合并过长的 `years.md`；④评估 `changes` 里的改动是否合身，构造漏带材料就改 `construct`，真遇到环境故障再修代码或写进 `proposals`。反思运行也会封存。
3. 期间来的召唤在结束后接着处理。

工具模块 `memory_system` 说明记忆如何流转与夜间如何打理自己，提供读归档上下文、看笔记历史版本、改策略、记评估的工具；它开头"你的记忆怎么流转"那一节每次都在系统提示里。
- **策略层**：构造说明（`data/notes/policy/construct.md`，每次构造都读；她在反思里改，改动被下一次构造实际使用）、沉淀的附加说明（`data/notes/policy/settle.md`）、她的做法笔记 `global` 和 `self`。每次改动必须写原因和预期，记进 `data/notes/policy/changes.md`；评估一次改动时可以给出改动时刻和证据的日志编号，证据早于改动的会在账本里直接标出。旧的 `policy/tidy.py` 与 `policy/opening` 不再读取。构造说明改得好不好，可以用 `chat.construct.replay(构造的 ctx, 新说明)` 拿过去某次唤醒重跑构造比较（只看规格，不行动）。
- **代码与提案**：她有 op 权限时可直接修改代码与提示词文件（改完记入 `changes` 并重启）；没权限或拿不准的改动写进 `data/notes/policy/proposals.md` 交给维护者，每条写证据、原因、改动方案、代价和验证方法。

**设置**：主模型、提示词、工具激活与这些预算只从全局 agent 设置读取；`#model` 等命令查看全局状态，修改命令由管理员操作。
- `#limit` 查看或修改从没看过的窗口的首屏条数（默认 80）与单次反思、沉淀运行的增长上限（token，默认 500000）；
- `#construct` 查看或修改构造运行：开关、模型、思考等级、超时、构造说明；
- `#awaker` 查看或改写闹钟规则；
- `#reflect` 查看上次反思时间，`#reflect now` 先沉淀再反思，`#reflect keep` 不沉淀直接反思。

旧窗口聊天设置不再读取；每窗口独立的 `#hint` 仍用于聊天结束时向 QQ 发送状态，配置是 `data/hint/` 下的普通文件（`default.py` 与 `g<群号>.py`／`u<QQ号>.py`，首行 `# on`／`# off`）。`聊天开始`/`聊天结束`是普通聊天内容，不划分上下文边界。

唤醒由 attention 队列认领，首次输出确认实际展示记录并消费召唤；请求失败释放认领。窗口展示身份与已确认阅读分开，确认只改 `agent.read`。启动和补回后恢复未确认召唤：普通离线消息只进历史，离线时有人叫她则即使早于已确认时间也能看到、能叫醒，原因写「离线时叫你」。

图片（2026-10-31）：`#image off/lazy/eager` 控制自动看聊天图，`#image discribe on/off`（也可写 `describe`，默认 on）独立控制自动生成文字描述；主模型能看图时也会留下描述。一次运行自己的图在续轮中一直可见；构造带进来的旧材料里的图只给地址和已有描述；`attach_image` 可重新打开，`off` 下也能主动看图。GIF 默认给首帧并标明动图，DeepSeek 保留原始 GIF；主动打开与生成描述时，全部帧按顺序排成每张最多 25 帧的网格，超过就用多张。具体输入与缓存规则见[图片处理说明](llm.md#多媒体与提示词笔记图片语音与音乐)。

CLI 窗口（2026-10-30）：`dsh:main`、`agy:review`、`codex:code` 这类窗口把她 `send` 的整段话作为一轮本机 CLI 任务，立即回执，回答回到同一窗口并以“dsh:main 回复了”叫醒她；需要 Bot 自身有 op。配置与续接见[CLI agent 窗口](cli-agents.md)。

语音（2026-10-23 起）：她可以加载 `tts` 工具把要说的话念成语音（默认音色晓伊），在 QQ 里作为一条语音消息发出；什么时候发语音由她自己决定，合成失败时改发文字。

表情（2026-10-23 起）：她有自己的表情柜子（`meme` 工具）。看到顺眼的图，她一句话收下并记个心情和一句说明，图当场存进 `data/memes/`，同一张只存一份；想发时按心情或关键词挑一张，像别的图片一样经 `type_word`／`send` 发出，以表情包的样子显示。心情是她自己起的词，没有固定的表。

B 站（2026-10-23 起）：柚子有自己的 B 站号，`.bili login` 扫码登录，二维码只发到管理员私聊（管理员自己发，或者她在管理员私聊里经命令工具发起），`.bili` 看状态。她能直接翻 B 站消息中心（回复、@、赞、系统通知、私信），通知一次来太多时会在她自己的 `me` 窗口提醒她去翻。有人在 B 站回复她、@ 她，那条评论出现在窗口 `bili:BV…`（动态等写 `bili:t<类型>-<oid>`）里并叫醒她；她像在 QQ 里一样 `type_word`／`send` 回评论，但只能发文字和 B 站表情（写成 `[doge]` 这样），发不了图片；别人评论里的图片她要用评论工具翻出来再看。刷首页、搜索、读字幕原文和评论区是她的工具，不会自己叫醒她；想定时刷，就写一条 awaker 规则。

### 5. 持久任务和延迟反应

`.later`、`.todo` 和部分 link 会在当前消息结束之后继续存在。它们保留最初的聊天目标，使未来的结果回到原群或原私聊。

## 状态范围不是统一答案

不同功能有意采用不同范围：

| 状态 | 范围 | 原因与取舍 |
|---|---|---|
| 命令等待的下一条输入 | 同一窗口中的同一用户 | 防止群友互相抢操作步骤 |
| 主 LLM 设置、行动记录、笔记与唯一 agent | Bot 全局 | 一个执行主体；模型不因读取哪个窗口而切换身份 |
| LLM 窗口未读与"看到哪里" | 聊天窗口 | `agent.read` 持有阅读确认；画面准备后等模型输出才确认对应记录身份 |
| `.later` / `.todo` 列表 | 群或私聊用户 | 群任务是公共安排，私聊任务是个人安排 |
| 用户名、自定义偏好 | 用户 | 跨聊天位置识别同一个人 |
| 群名和部分游戏数据 | 群 | 维持群体共享世界 |
| `.cave` 内容 | 全局池，附带投稿人和来源群 | 漂流瓶的价值来自跨时空混合，而删除权仍归投稿人或管理员 |
| 线性 link 列表、`.py` 运行环境和工具模块 last-good registry | Bot 实例级 | 它们是在修改 Bot 的共同能力，而不是某个窗口的私有插件 |
| 中心 agent 已激活工具模块 | Bot 全局 | 名单只从全局 agent storage 读取；遗留窗口值不参与运行，清理仍待授权 |
| `.edit` 输入接续 | 用户线 | 避免输入串线；当前编辑缓冲还会按聊天窗口和路径复用，群内可能共享同一文件会话 |

新增有状态功能时，应先明确它属于“人”“聊天窗口”“群”“全局 Bot”还是“一次交互”，不要默认复制现有某个命令的选择。

## 自修改与重启

Bot 可以通过 `.py`、`.file`、`.edit`、`.link`、`!` 等入口修改运行状态、文件或反应配置。热重载需要正确处理模块引用、后台线程、动态环境和持久状态，复杂度高且容易留下半新半旧的进程。

柚子选择更直接的策略：

1. 在聊天中修改代码或配置；
2. 用 `.reboot` 优雅退出；
3. 由外层 `run.py` 在秒级重新启动完整进程；
4. 通过退出保存和启动加载恢复持久状态。

因此重启不是缺少热重载的临时替代，而是用短暂不可用换取单一、完整运行状态的设计。局部例外只有统一的 `mods/tools`：顶层 Python/Markdown 模块必须经显式 `reload_tools` 才替换进程级 last-good，再经 `load_tools` 才进入当前 `Chat`；中心 agent 的激活名单全局存档，重启后仍然生效。两步都按模块隔离，失败不影响 Bot 或旧版本。普通 Module、命令、link 底座和后台资源仍通过完整重启切换。`.shutdown` 则表示有意停止，并在下次启动时恢复相应提示。

## 权限哲学

`.op` 管理人类管理员集合。人类直接发出的代码、shell、文件操作、反应图修改或进程控制命令按消息作者判权；普通成员主要使用聊天、娱乐、回声洞和安全形式的计划任务。模型调用工具属于 Bot 自己的行动，按固定的 `config.bot_permissions.op` 判权，不会因为这一轮读到哪位成员的消息而改变。

这里的边界是“谁可以改变 Bot 或宿主机”，而不是简单按命令复杂度划分。link 的管理入口需要管理员权限，但已注册的 link 会自动响应普通消息；因此每个 link action 自身也构成能力边界。

当前仍只有 op 与非 op，且每个命令或工具自行执行权限检查。模型显式代行某个用户时按该用户判权，但不能借代行取得 Bot 自身没有的 op 权限；完整边界见[运行架构](architecture.md)。整数命令级别配合少量正则或函数校验仍是[未实现部分](working/proposals/permissions.md)，不能当作现有能力。

## 灵活性优先的 link 取舍

link 把条件和动作都当作可执行配置，能即时组合已有函数、消息上下文和模块能力。持久状态是一份四字段有序列表；按顺序检查并由首个匹配节点消费消息。新节点默认进入列表头，也可显式移动，因此“新反应优先”不需要维护图边。

版本控制内的通用捕获由 `@capture` 注册，不写入 `links.json`。它可以定位在某个持久节点前，或默认作为持久列表后的兜底。这样，设备上的可编辑反应与源码内可复用捕获共用一条可观察顺序，但所有权仍然分开。

这种设计让新反应无需发布新版本，但代价是：

- 某节点意外成功会截断后续匹配；顺序本身就是行为。
- 条件和动作共享 `.py` 环境，强大但依赖显式导出和设备脚本名称。
- 配置既是数据也是可执行控制，损坏时影响范围可能超过单个反应。
- `.link catch` 会真实求值条件，只是不执行 action，不是无副作用 dry-run。

维护时首先保护“普通命令优先”和可恢复入口，不应为了整洁把 link 降级成只能返回静态文本的规则表。
